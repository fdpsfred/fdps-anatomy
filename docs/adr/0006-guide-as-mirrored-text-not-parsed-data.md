# 攻略站以原文鏡像保存，不解析成結構化資料

攻略站的內容以原文形式鏡像進版控（每頁一份原始 HTML、一份剝掉標籤的純文字），需要查什麼就對純文字做字串搜尋。不寫解析器，也不產出結構化的攻略資料檔。

## Considered Options

原本的規劃是把 9 個內容頁解析成 JSON，讓攻略資料變成可程式化查詢的表。實作到一半就看得出這條路的成本結構不對：頁面是人手寫的，同一站台三代遊戲的排版各不相同——一代的裝備表根本沒有物品編號、二代的物品編號寫作 `00h` 而外傳寫作 `00`、一代用「第一章之一」而其他兩代用「第1章」、有的區段有編號有的沒有。每發現一種就要長一個分支，而且解析器讀錯時不會報錯，只會安靜地產出錯誤的事實，比沒有結構化資料更危險。

鏡像原文則沒有失真的可能。內容全部在單一 `<pre>` 區塊內，剝掉標籤後就是作者原本的等寬排版，欄位對齊、縮排、章節分段都原樣保留，直接就是可讀可搜尋的文字。

鏡像進版控而不是放 `workspace/`：這份資料是專案長期引用的參考來源，站台哪天改版或消失都不該影響已經建立的結論，且進版控後內容穩定、可 diff。頁面引用的圖片一併鏡像——章節地圖是攻略頁的一半內容，只留文字等於留了一半。三代合計約 13 MB，這個量級進版控沒有問題。

## Consequences

查攻略資料的動作變成搜尋加閱讀上下文，和人翻攻略是同一件事，沒有中間層可以出錯。代價是攻略資料無法被程式直接取用——需要交叉比對時（例如把攻略給的資料檔偏移拿去對實際資源檔）得由人讀出數值再寫進知識庫，而知識庫本來就是這些結論的正確歸屬地。

站台改版時鏡像不會自動更新；重跑抓取後由 diff 顯示改了什麼。抓取失敗、頁面不再含 `<pre>` 區塊都直接中止，且要整批抓完才落地，不會產生半份鏡像。
