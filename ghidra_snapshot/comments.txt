=== 00011460 [PLATE]
Traces the battle movement cost map and returns either a direction path or the nearest reachable unit.

Algorithm:
The global at DAT_00060144 points to a movement map header: word width, word height, then width*height cells of 2 bytes each. Byte 1 of a cell holds the flood-filled step cost, 0xff meaning unreachable. Cell stride is 2 and row stride is width*2; both are computed into locals up front.

mode == 2: scans the unit table (count in DAT_00060150, records fetched by index through FUN_0002d210). Units are filtered by side: when arg4 is zero only units with record byte 6 == 0 are considered, otherwise only units with byte 6 != 0. Units with bit 0 of record byte 5 set are skipped. For each surviving unit the cost cell at (unit.x, unit.y) is read and the minimum is tracked. If no unit was found the function returns -1, otherwise it stores the winning unit's x and y into out_path[0] and out_path[1] and returns the minimum cost.

mode == 0 or 1: starts at (arg4, arg5) and repeatedly steps to the neighbouring cell with the lowest cost, recording one direction code per step into a local buffer: 0 = y-1, 1 = x+1, 2 = y+1, 3 = x-1, 4 = no move. Edge neighbours are skipped at the map borders. If the starting cell is already 0xff the function returns -1 immediately. Mode 0 takes a neighbour only on a strictly lower cost, which makes runs of identical cost keep the current heading. Mode 1 also accepts an equal cost, but only when the previously recorded step used a different direction code, which makes ties alternate direction instead of running straight. The walk stops once the current tile equals (arg1, arg2). The recorded direction codes are then copied into out_path in reverse order and the step count is returned.

Parameters:
arg1 goal_x   - x of the tile at which the walk terminates (unused in mode 2)
arg2 goal_y   - y of the tile at which the walk terminates (unused in mode 2)
arg3 out_path - byte buffer receiving the reversed direction codes, or the found unit's x,y in mode 2
arg4 start_x  - x of the tile the walk starts from; in mode 2 this is the side filter instead
arg5 start_y  - y of the tile the walk starts from (unused in mode 2)
arg6 mode     - 0 straight-preferring trace, 1 turn-preferring trace, 2 nearest-unit query

Returns:
Number of direction codes written in modes 0 and 1, the minimum cost found in mode 2, or -1 when the start tile is unreachable or no unit matched.

Algorithm:

=== 00014550 [PLATE]
Advance a SAF animation playback cursor by one tick.

Algorithm:
The cursor is a 3-dword state block: [0] current frame index, [1] tick counter inside the current frame, [2] pointer to the loaded SAF image. When mode == 1 the call is a reset: both counters are zeroed and 0 is returned without touching the SAF. Otherwise the SAF header is sanity-checked by comparing the magic bytes 'S', 'A' and 'F' at offsets 0, 1 and 2 (note the original code accepts the file if ANY one of the three matches, not all three), and the frame count is taken from the u16 at header offset 0x0C; a zero frame count makes the function return -1. The tick counter is then incremented and the current frame record is located as saf + *(i32 *)(saf + *(i32 *)(saf + 0x0E) + index * 4), with the index bounds-checked against the frame count (an out-of-range index yields a null frame pointer). The frame's hold time is the i16 at frame offset 0x02; while the tick counter stays below it the frame is held. Once the counter reaches the hold time it is cleared and the frame index is incremented. If the index then reaches the frame count the animation has completed one pass: the tick counter is cleared and, when mode == 0, the index wraps to 0 to loop, otherwise it is clamped to the last frame so playback stops on the final frame; the function returns 1 in that case.

Parameters:
cursor - pointer to the 3-dword playback state block described above.
mode - 1 resets the cursor, 0 loops back to the first frame at the end, any other value holds on the last frame.

Returns:
1 when the animation just passed its last frame, 0 while it is still playing or after a reset, -1 when the SAF data is unusable (bad magic or zero frame count).

=== 0002b1b0 [PLATE]
Finds the palette index whose RGB triple is closest to a requested color.

Algorithm: keeps a running best squared distance seeded with 10000000 and a running best index seeded with 0x100. Walks a fixed 256 iterations over the palette, consuming three consecutive bytes per entry (red, green, blue in that order) through an advancing byte cursor. For each entry it forms dr = r - pal[0], dg = g - pal[1], db = b - pal[2] and computes dr*dr + dg*dg + db*db as signed 32-bit arithmetic. If that sum is strictly less than the current best it becomes the new best and the loop counter becomes the new best index. The loop count is hardcoded to 256 and is not derived from any argument, so the palette buffer must hold at least 768 bytes. The strict less-than test makes the first of several equally close entries win. The 0x100 seed can never survive because the maximum possible distance is 3*255*255 = 195075, well below the 10000000 seed, so the function always returns a value in 0..255.

Parameters: r, g, b are the target color components, passed as full 32-bit ints and only compared as such (the palette bytes are zero-extended, the targets are not masked). palette points at the first byte of a 256-entry, 3-bytes-per-entry RGB table.

Returns: the 0..255 index of the closest palette entry.

=== 0002e710 [PLATE]
Renders the scaled (zoomable) battle map overview into an offscreen 320x200 buffer.

Algorithm:
Reads the current map dimensions from the map header pointed to by the global at 0x00069cb0: width = *(int16*)(hdr+7), height = *(int16*)(hdr+9). Converts the requested camera centre into a top-left world position by subtracting step*0x9c horizontally and step*0x60 vertically (0x9c=156 and 0x60=96 are half the 312x192 viewport), so the caller passes the point that should land at the centre of the view.

World coordinates are 1.12-style fixed point with 0xc00 units per map tile and 0x80 units per source pixel, i.e. every tile is 24x24 pixels (0xc00/0x80 = 24). The top-left position is split into tile index (world / 0xc00) and sub-tile remainder (world % 0xc00), with a manual floor correction that adds 0xc00 to the remainder and decrements the tile index when the remainder is negative, so negative camera positions still sample the correct tile.

The destination buffer is first cleared to colour 0 over its full 64000 bytes, then drawing starts at buffer + 0x504 (row 4, column 4) and advances by 0x140 (320) bytes per output row.

For each of 192 output rows the sub-tile Y remainder is converted to a source row offset ((rem >> 7) * 0x18) inside the tile bitmap. Rows whose tile Y is outside [0, height) are skipped, leaving the cleared background. Otherwise the tile bitmap pointer is fetched from the caller-supplied pointer table as table[tileY * 64 + tileX] (the table has a fixed stride of 64 entries per map row) and the row offset is added.

For each of 312 output columns one byte is copied from the tile bitmap at source column (subX >> 7), skipped when tile X is outside [0, width). After each column the sub-tile X remainder advances by step; when it reaches 0xc00 the tile X index advances, the remainder wraps by subtracting 0xc00, and the tile bitmap pointer is re-fetched from the table. The same wrap logic advances tile Y between rows. Tile X and its remainder are restored from the saved row-start values before each new row.

The step parameter is therefore the zoom factor in source-pixel fixed point: 0x80 gives 1:1, larger values zoom out, smaller values zoom in.

Parameters:
  dest       - destination 320x200 8bpp offscreen buffer, cleared to 0 first
  world_x    - camera centre X in 1/0x80-of-a-pixel fixed point (0xc00 per tile)
  world_y    - camera centre Y in the same fixed point
  step       - fixed-point source step per output pixel, i.e. the zoom factor
  tile_table - array of pointers to 24x24 tile bitmaps, indexed [tileY * 64 + tileX]

=== 0002eab0 [PLATE]
Advances the VGA palette colour-cycling animation for the current scene.

Algorithm:
1. Copies about twenty short byte ramps out of read-only tables at 0002b2a0..0002b4e9 onto the stack. The ramps come in R/G/B triples; every byte is a 6-bit VGA DAC component (observed range 0..63). Each ramp is (count + count/... ) bytes long so that a sliding window of `count` entries can start at any phase without wrapping: e.g. a 5-colour cycle stores 9 bytes, a 15-colour cycle stores 29 bytes.
2. Calls fdps_cd_music_repeat_poll (00030c50) as per-frame housekeeping.
3. Gates on the frame tick: if the last-serviced tick at 00069d20 already equals the current tick at 00069d64 the function returns without touching the palette, so the animation advances at most once per tick.
4. Switches on the scene / screen id at 00069cf4 (cases 0, 2, 8, 0x14, 0x15, 0x16, 0x17, 0x1a, 0x1c, 0x1d). Each case picks its own R/G/B ramp triple, its own DAC start index (0xf0, 0xf5, 0xf6 or 0xf8) and its own colour count (5, 7, 9, 10, 11 or 15).
5. Advances the shared phase counter at 00069d24 as (phase + 1) mod (count * 4) — the times-four factor makes the cycle advance one colour every four ticks — then derives the window offset as phase / 4 and calls FUN_0002f240(first_index, r + offset, g + offset, b + offset, count) with cdecl argument order (the caller does ADD ESP,0x14).
6. Records the serviced tick by storing 00069d64 into 00069d20.

Parameters: none. All inputs are globals: 00069cf4 scene id, 00069d20 last serviced tick, 00069d24 cycle phase, 00069d64 current frame tick.

Returns: nothing.

=== 0002f2f0 [PLATE]
Strided rectangular block transfer for framebuffer/surface memory.

Algorithm:
Two modes selected by src_stride. When src_stride is zero the routine runs in fill mode: it treats src_or_fill as a byte value and calls memset(dst, src_or_fill, bytes_per_row) once per row, advancing dst by dst_stride after each row. When src_stride is non-zero it runs in copy mode: it calls memmove(dst, src, bytes_per_row) once per row, advancing src by src_stride and dst by dst_stride after each row. Both modes loop exactly rows times with a signed comparison, so a rows value of zero or less transfers nothing. No clipping, no bounds check and no transparency test is performed; the caller is responsible for the geometry. The row counter is kept in a stack local and the working src/dst cursors are stack copies of the incoming pointers, so the caller's values are not disturbed.

Parameters:
  src_or_fill  - in copy mode the source base pointer; in fill mode the byte value used to fill every row (only the low 8 bits reach memset)
  src_stride   - bytes added to the source cursor per row; zero selects fill mode
  dst          - destination base pointer
  dst_stride   - bytes added to the destination cursor per row
  bytes_per_row- number of bytes transferred per row
  rows         - number of rows to transfer; signed, values <= 0 do nothing

Returns:
  Nothing.

=== 0002fb80 [PLATE]
Mosaic screen transition: copies the source surface to the destination in block-sized rectangles, visiting them in a shuffled order so the image appears in random patches.

Algorithm:
1. Allocates grid_cols*grid_rows entries of 4 bytes (two int16 fields: column, row) via the CRT allocator and fills it with every (col,row) pair of the phase grid.
2. Shuffles the table in place: for every index i it draws two rand() values and forms j = rand()%grid_cols + grid_cols*(rand()%grid_rows), then swaps entry i with entry j. This is a random-swap shuffle, not a Fisher-Yates pass.
3. Computes the block counts: blocks_x = ceil((width/block_w)/grid_cols), blocks_y = ceil((height/block_h)/grid_rows). Each shuffled entry therefore owns a lattice of blocks spaced grid_cols apart.
4. For each shuffled entry (bx,by), walks that lattice. Row index is y = block_h*(j*grid_cols + by); column index is x = bx + i*grid_cols. A block is drawn only when x < width and y < height. Source address is src + y*src_pitch + x*block_w; destination address is dst + y*dst_pitch + (dst_pitch ? x*block_w : 0). Each block is handed to fdps_blit_rect with block_w by block_h.
5. After finishing one shuffled entry it calls the delay/present thunk at 0003d370 with the delay argument, so one entry of the table equals one visible step of the transition.
6. Frees the table before returning.

Note the bound test on the horizontal axis compares a block-column index against the pixel width, while the vertical test compares a pixel row against the pixel height. The horizontal test is therefore far looser than the vertical one; the real bound comes from the blocks_x loop count.

Parameters:
  dst        destination surface base address
  dst_pitch  destination bytes per row; zero suppresses the horizontal destination offset entirely
  src        source surface base address
  src_pitch  source bytes per row
  width      source width in pixels
  height     source height in pixels
  grid_cols  number of phase columns; also the horizontal stride between blocks of one phase
  grid_rows  number of phase rows
  block_w    block width in pixels
  block_h    block height in pixels
  delay      value passed to the per-step delay/present thunk at 0003d370

Returns:
  Nothing.

=== 00030010 [PLATE]
Alpha-blends a single constant palette colour over an 8bpp source rectangle.

Algorithm:
blend_table is a [18][256] array of dwords holding each palette entry pre-scaled by a weight, with the three colour channels packed one per byte (channel n in bits 8n+4..8n+7 before the shift below). Rows 0..8 hold weights 0..8; rows 9..17 (dword offset 0x900 = 9*256) hold the complementary weights. To keep the row index inside 0..8 the function folds alpha: for alpha <= 8 the constant colour reads row alpha and the source pixels read row 9+alpha; for alpha > 8 alpha is replaced by 16-alpha, the constant colour reads row 9+alpha' and the source pixels read row alpha'. Either way the constant colour ends up weighted by the caller's alpha and the source pixel by 16-alpha.
The scaled constant colour is fetched once before the loops. For each pixel the scaled source colour is added to it, the sum is shifted right by 4 (dividing out the /16 of the weights) and masked with 0x000F0F0F, leaving 4 bits per channel at bits 0..3, 8..11 and 16..19. Those are folded into a 12-bit index by (v & 0xFFFF) | (v >> 12), giving channel0 in bits 0..3, channel2 in bits 4..7 and channel1 in bits 8..11. That index selects a palette byte from the 4096-entry inverse-palette table rgb444_lut, which is stored to the destination.
Rows advance by src_stride and dst_stride; no clipping, no transparency test, every pixel in the rectangle is written.

Parameters:
src         - source 8bpp pixels, top-left of the rectangle
src_stride  - bytes to add to src per row
dst         - destination 8bpp pixels, top-left of the rectangle
dst_stride  - bytes to add to dst per row
width       - pixels per row
height      - number of rows
blend_table - base of the [18][256] dword weighted-colour table
rgb444_lut  - base of the 4096-entry packed-RGB to palette-index table
tint_color  - palette index of the constant colour being blended in
alpha       - blend weight of tint_color, 0..16 (0 = source only, 16 = tint only)

Returns:
Nothing.

=== 00043c82 [PLATE]
Watcom C runtime initialiser: calibrate the delay() busy-wait loop.

Algorithm:
  Phase 1 (sync): issue DOS "Get System Time" (INT 21h, AH=2Ch; returns
  CH=hour, CL=minute, DH=second, DL=hundredths), keep the seconds field
  (DH), then re-issue the call until DH changes. This aligns the
  measurement with a whole-second boundary so no partial second is
  counted.
  Phase 2 (count): with the new seconds value latched in BL, spin issuing
  INT 21h AH=2Ch and incrementing a counter until DH changes again. The
  counter therefore holds the number of INT 21h AH=2Ch round trips this
  machine performs in one second.
  The result is stored to the global at 0x00069ea8. delay() at 0x00043cb0
  is its only consumer: it computes
  iterations = (milliseconds * [0x00069ea8] + 500) / 1000, clamps a zero
  result up to 1, and spins that many INT 21h AH=2Ch calls. The stored
  value is thus "loop iterations per 1000 ms" on the host CPU.

  The routine is not reached by a CALL. It is entry 0 of the Watcom
  runtime init table at 0x000638f0 (6-byte records: status byte,
  priority byte, 32-bit routine address); its record reads
  00 20 82 3C 04 00 - status 0 (pending), priority 0x20
  (INIT_PRIORITY_LIBRARY), routine 0x00043C82. The table walker at
  0x0004DFA6 invokes it during startup and then marks the record 2 (done).

Parameters:
  None. EBX and ESI are pushed on entry and popped on exit; every other
  register the body reads (EAX, EDX) is written by INT 21h before being
  used, so no incoming register or stack argument exists.

Returns:
  void. The calibration result is delivered through the global at
  0x00069ea8. Stack is balanced by a plain RET (no purge).

=== 0004dfa6 [PLATE]
Watcom C runtime __InitRtns -- run the link-time initialiser table.

Algorithm:
The linker gathers records of the form

    struct rt_init { unsigned char rtn_type;      /* 2 == already run */
                     unsigned char priority;
                     void (*rtn)( void ); };      /* 6 bytes each */

into a contiguous "XI" table. Here that table spans 0x000638f0
(inclusive) to 0x00063920 (exclusive), i.e. 8 entries; a matching
"YI" rundown table begins at 0x00063920 and is walked by the
termination routine at 0x0004dff1.

Outer loop, repeated until no candidate remains:
  - set the running minimum priority to the caller-supplied bound and
    the selected entry to the table end (the "nothing found" sentinel);
  - scan the whole table forward; an entry is a candidate when its
    rtn_type is not 2 (not yet executed) and its priority is <= the
    running minimum, in which case it becomes the new selection and
    lowers the minimum. Because the test is <= rather than <, a later
    entry with a priority equal to the current minimum displaces an
    earlier one, so entries sharing a priority execute in reverse
    table order;
  - if nothing was selected, return;
  - otherwise reload ES from DS, call the entry's function pointer
    when it is non-NULL, and stamp rtn_type = 2 so the entry is never
    run twice.

The current table holds eight entries, all rtn_type 0, with priorities
0x01 (0x0003d50a), 0x02 (0x00044749) and six at 0x20 (0x00043c82,
0x0004cfc8, 0x0004e040, 0x00043612, 0x00054893, 0x00054f86).

Parameters:
  EAX (only AL is used) -- the priority ceiling. Entries whose
  priority exceeds it are skipped. The startup code at 0x00043310
  passes 0xff, i.e. "run everything".

Returns:
  Nothing. ESI, EDI, EBX, EDX and the ES segment register are saved on
  entry and restored before returning.

=== 0004e692 [PLATE]
Watcom C runtime: stackavail() -- report remaining stack space.

Algorithm:
  Copies ESP into EAX and subtracts the global stack-low limit stored at
  0x00060430, then returns. Because ESP at function entry already points at
  this call's own return address, the reported figure is 4 bytes smaller than
  the space the caller actually has, which is conservative and harmless.
  The same 0x00060430 global is the limit used by the compiler-generated
  stack-overflow probe at 0x0004362d (which tests ESP-size against it) and is
  initialised by the startup code at 0x000434c0, confirming it is __STACKLOW
  rather than a stack base or margin constant.

  All three callers are CRT internals that use the result to choose between an
  on-stack scratch buffer and the heap: 0x0004df4c and 0x000556a9 both compare

  with LF->CRLF translation) calls the stack-overflow handler at 0x0004364b
  when fewer than 0xB0 bytes remain and otherwise picks a 0x200-byte staging
  buffer when at least 0x230 bytes are free, falling back to 0x80 bytes.

Parameters:
  None. EAX is written before any register is read, and no argument register
  or stack slot is consumed.

Returns:
  EAX = bytes of stack remaining below the current stack pointer, as an
  unsigned value. Every caller treats it as unsigned.

=== 00056837 [PLATE]
Keyboard IRQ1 interrupt service routine (protected mode, DOS/4G).

Installed by fdps_install_keyboard_isr at 0005680a; it is never called
directly, only entered through the interrupt vector, and exits with IRETD.

Algorithm:
  1. STI, then save EDX/ECX/EBX/EAX and DS on the interrupt stack, and load
     DS with selector 0x0002 so the handler can reach the program data
     segment regardless of the interrupted context.
  2. IN AL,0x60 reads the raw scancode; it is stored unconditionally in the
     last-scancode byte at 0x00070006.
  3. IN AL,0x61, set bit 7, OUT it back, then clear bit 7 and OUT again --
     the classic XT-style keyboard acknowledge strobe on port 0x61.
  4. Compare the new scancode with the previous one at 0x00070021. If they
     are equal, nothing is queued (this suppresses the auto-repeat stream and
     duplicate reports). Otherwise the new value becomes the previous one.
  5. If the scancode is below 0x80 (a make code, i.e. key press rather than
     the 0x80-or-above break code), store it into the byte ring buffer that
     begins at 0x0007000f, indexed by the write cursor at 0x0007001d, then
     increment the cursor and wrap it to 0 when it reaches 10. The buffer has
     10 entries and the cursor is a pure write index -- the consumer side
     tracks its own read position.
  6. OUT 0x20,0x20 sends the non-specific EOI to the master PIC.
  7. Restore DS and the four saved registers and return with IRETD.

Note that break codes and repeats only update the last-scancode bytes; they
never enter the ring buffer. The original interrupt handler is not chained.

Parameters:
  None. Entered from the interrupt gate, not by a call, so no arguments are
  passed in registers or on the stack. The decompiler's invented param_1 is
  the interrupt frame and is not real.

Returns:
  Nothing. Exits with IRETD; all side effects are in the globals at
  0x00070006 (last scancode), 0x00070021 (previous scancode for the repeat
  filter), 0x0007000f (10-byte scancode ring buffer) and 0x0007001d (ring
  write index).
