# 22.1 — 移除每批回掃，改為全部 emit 完成後的一次性疑慮總掃

**What to build:** 把 rescan 段從 `emit_ticket22.js` 整個拿掉，讓每一批只做 emit → review → gate → commit；等票 22 的 514 支 game function 全部落地之後，再由一支獨立的 workflow 逐條處理 `emit_issues.json` 裡的每一則疑慮。

## 為什麼

票 22 第一批（`t22-01`）的量測。該批 40 支全數落地、0 未完成、0 中斷、無拆檔，共開 196 個 agent、17.4M subagent token、13.5 小時。**其中 rescan 佔 30 個 agent**——相對 40 支落地 function。

`emit_issues.json` 跑完後的狀態：

| | |
| --- | --- |
| 帶疑慮的位址 | 30 |
| 疑慮條目 | 97（已解 51／未解 46） |
| 51 筆已解中的 `same_as` 鏡像 | 21（emitter 與 reviewer 記到同一件事，其中一筆只指向另一筆） |
| **真正的獨立結論** | **30** |

那 30 筆靠什麼解掉：

| 證據來源 | 筆數 |
| --- | --- |
| 鄰居的 verdict 檔——emit 當下確實不存在的證據 | **9** |
| Ghidra 唯讀查詢、出貨資料檔、知識庫頁、**emit 那輪自己就已經建置出來的 `.OBJ`** | **21** |

30 個 rescan agent 裡有 22 個至少解掉一筆、25 個改動了檔案，所以問題不是它在空轉。問題有三個，每一個單獨都不足以拆掉它，合起來足夠。

**一、七成的結論在 emit 當下就答得出來。** `00014550` 要的是 `get_xrefs_to` 掃 12 個 caller；`00010b20` 要的那個 `.OBJ` 就是 emit 那一輪 build 出來的。掃描本身在哪做都一樣貴，省不掉；省得掉的是 **rescan agent 從零重讀這支 function、它的兩份 verdict、它的 assembly**——一整份重新建立的 agent context，每支一份，這一批 30 份。

**二、每批回掃會重複問同一批問題。** 一則疑慮只要鄰居還沒到齊就答不出來，而它每一批都可能因為「某個鄰居動了」被重新挑出來問一次。46 筆未解裡有相當一批卡在票 23（資料 emit）或票 24（實機遊玩），那些在票 22 內永遠答不出來，每批重問是純浪費。

**三、一次一支的形狀看不見共同根因。** 未解的疑慮裡有明顯的族群——`00011da0`、`00023050`、`00014550` 問的都是「這個 index 會不會超出緩衝區」的變體；`0002af60` 與 `00014550` 問的都是同一個 `_inline` 展開問題。一次調查可以同時結掉一整族，但 per-function 的回掃只看得到自己那一支，只能一支一支各自重新推導。

## 這不牴觸 ADR-0007 第四條

第四條的原文是「**工作結束前**要把所有低信心或留有未決問題的判定挑出來重讀一次」。一批不是一項工作。票 22 的工作在 514 支全部落地時才結束，在那個時點做一次總掃，正是條文的字面讀法；現在的每批回掃是 `emit_ticket22.js` 自己採的嚴格讀法，不是 ADR 要求的。

第四條的其餘要求在總掃裡全部保留：允許 agent 讀鄰居的**判定檔**當證據、一個 agent 一個項目、重讀後仍無解就照實留著、提示必須明講「第二次嘗試不是硬掰結論的理由」。

## 總掃能做到每批回掃做不到的事

- **鄰居全部到齊。** 沒有任何一則疑慮會因為「它等的那支還沒 emit」而無解。這一批 9 筆鄰居相依的疑慮之所以解得掉，靠的是運氣——鄰居剛好落在同一批。等在後面的那些沒有這個運氣。
- **每則只看一次。** 不再有「鄰居動了就重新挑出來問」的重複。
- **可以按根因分群。** 總掃有全部疑慮在眼前，能先分群再調查，一次結掉一族。
- **不需要挑選階段。** `rescan-worklist` 那個選單 agent 整個不存在。

## 代價與界線

**一支有問題的 emit 會在 `src/` 裡留到最後。** 這是這個做法唯一真正的代價，要講清楚它有多大：

- reviewer 仍然逐支獨立驗證、build gate 仍然每支跑，這兩道沒有變動。回掃從來不是等價性的主要防線。
- 實測支持這一點：`t22-01` 的 30 筆結論裡，**沒有任何一筆構成合法的等價性 blocking**。唯一標成 BLOCKING 的 `0002af60` 是誤判（見下節）。
- 疑慮不會遺失，它們都在 `emit_issues.json` 裡，總掃會逐條處理。

**留到最後才改的東西會比較難改**——上面可能已經疊了依賴它的程式碼。真實但有界，而且只影響那些真的需要改 code 的疑慮，依實測那是極少數。

**總掃的規模要先有心理準備。** 依 `t22-01` 的比率（40 支產出 97 筆條目、扣掉鏡像約 60 筆獨立疑慮）外推到 514 支，總掃面對的會是**數百則**。這是下一節那條收斂門檻存在的理由：它直接決定總掃的大小。

## 順帶要修的：一條沒人審過的自訂準則

查證「回掃有沒有回頭改過 code」時挖出來的，與拆不拆回掃無關，但必須一起修。

25 個回掃 commit 全部只碰 `emit_issues.json`，沒有一個動到 `src/`／`tests/`——符合設計。但 `0002af60` 那筆標成 BLOCKING 的判定**本身是錯的**：rescan 證明 `src/palette.c` 的 open-coded RGB 打包是 `fdps_pack_rgb` 的編譯器 inline 展開（決定性證據是三個參數槽 dword store／byte read 的寬度不符，加上旗標無 `-oe`，展開只能是 source 用 `_inline` 要求的），然後判定該處應改成呼叫它。

ADR-0001 訂的是功能等價，明講暫存器配置這類 binary 層級差異不要求對齊。open-coded 與 inline 展開在該標準下等價，rescan 自己也寫了「functionally neutral／no test expectation moves／nothing about the game's behaviour is at risk」——它的證詞否定了它的標籤。而且照它說的改會更遠離原版：不加 `_inline` 直接呼叫會產出一條原版沒有的 CALL。現況反而精確對上原版——image 裡沒有東西呼叫 `0002af20`，重建裡也沒有東西呼叫 `fdps_pack_rgb`。emitter 在 `src/palette.c:223` 已經把理由寫成註解，判斷是對的。

**根因**：emitter 在自己的 `needs` 裡訂了「證明是 `_inline` 就該改成呼叫」，下游達成條件後照著執行。一個判定檔裡臨時發明的準則，被當成義務履行，中間沒有任何一關拿它對過 ADR-0001。pipeline 的每一關都在檢查「有沒有照規則做」，沒有一關在檢查「這條規則本身對不對」。

拆掉回掃不會讓這個洞消失，只會把它推遲到總掃。所以守門要加在兩處：**emit／review 不得訂出牴觸 ADR-0001 的條件式義務**，以及**任何 blocking 標記成立前要先分辨它是等價性問題還是原始碼字面還原問題**——後者不是 blocking。

## 收斂門檻：現在更重要，不是更不重要

拆掉回掃之後，一則被推遲的疑慮要等到全部 514 支跑完才有人看。推遲的代價變高了，不是變低。而且總掃的大小直接由 emit 階段推遲了多少決定。

所以這條要一起做：**記疑慮的條件是「答案所需的證據還不存在」，不是「我還沒去查」。** 寫進 `emit_ticket22.js` 的 RULES（emitter 與 reviewer 共用）與各自的 prompt，並明確列出當下就該用掉的證據來源：Ghidra 唯讀查詢、出貨的遊戲檔與資源、知識庫、**以及這一輪 build 已經產出的 `.OBJ`**（最容易被忘記，就在 `workspace/code_emit/out/objs/` 底下）。

與票 21.7 那條「判斷不出用途的變數是一則 `open_issues`」不衝突，但界線要寫明：**證據不存在**才記疑慮，**還沒去查**不算。

同時看 `same_as` 鏡像數：21／51 偏高，emitter 與 reviewer 大量記到同一件事本身就是重複工，值得一併檢討是否該由 reviewer 只註記「同 emitter 第 N 則」而不重寫一遍。

## 現在就要落地的與可以等的

分界是：**會改變後面 471 支怎麼 emit 的結論現在就要落地；個別疑慮的裁決等總掃。**

所以「原版用了 `_inline`」這個結論**現在**就要寫進 `rebuild_info/`——它改變 image 裡每一處 inline 展開的讀法，後面還有 471 支會遇到。`00014550` 自己的 verdict 把同樣的展開讀成「`-od` 不會 inline，所以原始碼寫了兩遍」，那個讀法是錯的，要一併更正。

反過來，`0002af60` 那筆 BLOCKING 標籤的撤銷是個別裁決，留給總掃。

## 總掃的形狀

自己一支 workflow（ADR-0007：每張票寫自己的，不抽共用骨架），落在 `tools/code_emit/` 下。實作時機在票 22 的 514 支全部落地之後，但**設計現在就定下來**，否則它會被忘記。

- **一次一則，不批次**（CLAUDE.md 鐵則）。工作清單只存在於腳本中，每次 agent 呼叫只帶一則。
- **判定寫檔，只回傳摘要**；agent 不寫 `src/`，需要改 code 的裁決記成 finding，由獨立的落地階段處理。
- **先分群再調查。** 開跑第一段把全部未解疑慮按根因分群，之後以群為單位派工——這是總掃相對每批回掃的主要優勢，不做就白拆了。
- **五條錯誤處理全套**，含續跑：總掃的規模保證會中斷。
- **殘留要交接**：卡在票 23／24 的疑慮在總掃結束後仍然無解，要明確列成交接清單，不得混在「已處理」裡。

## 怎麼驗證

**拆除的驗證**看下一批：rescan agent 數為 0、agent 總數與 token 相對 `t22-01` 的降幅、40 支仍然全數落地且 gate 全綠、`emit_issues.json` 仍然照常累積（bookkeeper 那一段沒有被一起拆掉）。

**收斂門檻的驗證**要看同一批記下的疑慮裡，有多少是用「emit 當下就拿得到的證據」寫成的——這個數字應趨近 0。這才是真正的驗收；只看疑慮總數下降會被「emitter 乾脆少記」蒙混，而少記比多記更糟。所以同時要確認**沒有反向失效**：那 9 類鄰居相依的疑慮仍然被記下來。門檻寫太緊會逼 emitter 把答不出來的問題硬收斂成編出來的結論，那比現況嚴重得多。

**總掃的驗證**在票 22 收尾時做，不在這張票。

### `t22-02` 的實測結果

拆除本身通過：5 支全數落地、0 未完成、gate 全綠、**rescan agent 0 個**。23 個 agent 恰好是 recover 1 ＋ worklist 1 ＋ 5×4 ＋ report 1，沒有多餘的階段。

**收斂門檻的驗證沒有結論，因為那 5 支一則疑慮都沒記。** `emit_issues.json` 停在 30 個位址／97 筆，與 `t22-01` 結束時完全相同。

這個結果指向兩個相反的可能，n=5 分不出來：門檻生效了（該收斂的都當場收斂），或者門檻寫太緊、emitter 為了不違規而不記該記的疑慮。後者比拆除前的狀況嚴重。`t22-01` 的比率是每支約 2.4 筆，連續 5 支掛零不是可以直接當成好消息的數字。

同時 `emit_issues.json` 沒有累積，也代表「bookkeeper 那一段沒被一起拆掉」這件事只由 bookkeeper 的自述佐證（5 支都回報讀寫該檔且逐 byte 相同），沒有被真正的寫入路徑驗證過。

**所以這一項留著未勾，要用下一批的實際數字判定**，判準是：疑慮數不該是 0，而是明顯低於 2.4／支且記下來的每一則都真的無解。

### `t22-03` 的實測結果：兩項都收掉

**收斂門檻通過，但不是滿分。** 40 支 12 條，**0.3 條／支**，對照 `t22-01` 的 2.4——低但不是 0，落在判準要的區間裡。逐條看過 `needs`，12 條裡 11 條成立（等未 emit 的鄰居、等 `ENEMYDAT.DAT` 解讀、等章節資料）。不成立的是 `00019f80` 第二則的其中一路：它把「四件 AP 10000 的物品能不能同時裝在一個單位上」記成無解，理由寫的是「沒有 `assets/` 頁面記載可裝備遮罩」——但那份遮罩就是出貨檔 `PROEQU.DAT` 的 216 個 byte，而**出貨的遊戲檔與資源正是門檻明列「當下就該用掉」的證據**。知識庫沒寫過不等於證據不存在，這正是門檻要擋的那種推遲。同一則的另一路（負的基礎值等 `ENEMYDAT.DAT`）成立。

**反向失效沒有驗到，只驗到沒有全面崩壞。** 記下來的那一側乾淨（`00013920` 要等 `fdps_map_actor_behavior_step` 先 emit，鄰居相依那一類確實還在記），但零疑慮的 34 支那一側完全沒取樣，「門檻寫太緊逼 emitter 少記」這個風險仍然沒被量到。票 22.1 自己寫過少記比多記更糟，所以這一項的正確狀態是「未觀察到反向失效」，不是「證明沒有反向失效」。

**`same_as` 定案為「保留查證、只寫增量」。** 這批 12 條分佈在 6 支，其中 5 支是 emitter 與 reviewer 各記一條講同一件事，5 條全部整段重寫、沒有一條填 `same_as`。約束的是描述不是查證——reviewer 仍然自己重推一遍，但 `what` 只留自己這趟多出來的東西。規則的正典在 [`rebuild_info/emit_pipeline.md`](../../../rebuild_info/emit_pipeline.md)，實作落在 `emit_ticket22.js` 的 reviewer prompt、verdict 欄位形狀與 bookkeeper 的欄位轉錄；走到這個結論的過程見 `devlog/2026-08-31-emit-t22-03.md`。
