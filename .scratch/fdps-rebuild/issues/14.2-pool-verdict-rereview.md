# 14.2 — 全 pool 逐 function 覆核

**What to build:** `FDPS.LE` 裡每一個 function 的 pool 歸屬、符號名稱、邊界與 signature、plate comment，都被第二雙眼睛獨立重讀過一次，錯的當場修掉。做完這張票，票 14 的產物從「一輪做出來的結果」變成「覆核過的結果」，票 15 才有可信的工作清單。

工作清單是 Ghidra 內的全部 function，一個不排除。

## 為什麼要有第二輪

票 14 的錯誤率不是零，而且它的錯**全部是在有第二條證據線的地方才被發現的**：

- 票 14.1 拿前作的 `ailv3.lib` 走 FID pipeline，一次就撞出 24 個與票 14 判定不一致的個案，17 個改判 `ail`。
- 混音分派表下的 11 個 function 第一遍判成 `fdps`，與同表的另外 125 個相衝突，是「同表成員必須同 pool」這條旁證揪出來的。
- 命名同樣有錯：`000435a2` 原本掛著 `sprintf`，實際是 `spawnlp`。

三件事都指向同一個結論——第一輪的判定會錯，而發現它需要一條獨立的證據線。**沒有第二條證據線的地方從來沒有被問過**，其中最大的一塊是 `fdps` pool：那 517 個是「扣掉 `crt` 與 `ail` 之後剩下的」，沒有任何函式庫比對證明它們是遊戲自己的程式碼。本票就是那條缺席的證據線。

另一個獨立的理由是**判定發生在移動的地基上**。票 14 一邊把未定義區塊建成 function、一邊判 pool，早期判定所依據的鄰居、caller、資料參照，在後續建出 305 個新 function 之後已經是另一幅圖了。早期的判定沒有機會看到最終的那張圖。

## 覆核的意思是重讀，不是複查標記

agent 先從 assembly、xref、資料參照與函式庫比對結果自己得出結論，**再**與 Ghidra 現況比對；現況只在比對那一步才准看。順序倒過來就只是在替既有判定找理由，那樣跑一千次也只會確認原判。

有函式庫 byte 全等命中的 function 一樣開 agent 重讀。命中是一條很強的證據，但它證明的是「這段 byte 與程式庫的某個 module 相同」，不是「這個 function 的邊界、名稱與註解都對」——`sprintf`/`spawnlp` 那筆錯誤就發生在有命中的區域裡。

## 四個軸

一次 agent 呼叫讀一個 function，四軸一起判，每軸各自給結論、證據與信心：

1. **pool** — `fdps` / `ail` / `crt` / `binary_artifact` 哪一個，依據 [`program_info/code_pools.md`](../../../program_info/code_pools.md) 認可的四類證據。位址範圍不算證據；只被函式指標表指到的 function，pool 由分派者決定。
2. **名稱** — 是否符合 [`rebuild_info/naming.md`](../../../rebuild_info/naming.md)：vendor 用程式庫原名逐字照抄、file-static 用 `L$N_`、判不出 PUBDEF 就不硬湊。特別要抓「名字來自形狀撞號的命中」這一類。
3. **邊界與 signature** — 起訖位址是否正確、有沒有吃掉隔壁、有沒有該併進來的 fall-through 尾巴、calling convention 與參數是否與 assembly 相符。手寫組語那一族的 `__watcall` 是 Ghidra 猜的，要明確標記。
4. **plate comment** — 記錄的證據敘述與實際 assembly 相符，沒有沿用被後續發現推翻的推論。

四軸的判定各自獨立：名字對不代表 pool 對，pool 對不代表邊界對。

## 邊界改動會讓鄰居的判定過期

這是本票專屬的結構，票 14 沒有對應物。改動 function 邊界會改變它與鄰居的 body，鄰居先前那份判定描述的範圍已經不存在——即使鄰居的判定檔還在。

處理方式：落地階段套用邊界修正之後，把該修正涵蓋的位址範圍內的所有 function 判定檔**退休**，讓它們重回工作清單。ADR-0007 第五條的「判定檔要記下涵蓋範圍，續跑時比對現況」就是為這件事寫的，票 14 的區塊縮小已經踩過同一個坑。判定檔因此要記下它涵蓋的位址範圍與 body 雜湊。

同理，pool 改判會連帶讓名稱失效（`fdps_` 前綴與程式庫原名互斥），改判的 function 名稱一律重新判定。

## 執行方式

依 [ADR-0007](../../../docs/adr/0007-workflow-automation-and-agent-context.md) 的五條原則，本票寫自己的 workflow。規模與票 14 同級，1,347 個項目必然塞不進一次 workflow 呼叫，續跑機制是這張票能不能跑完的關鍵，不是保險。

`tools/pool_triage/` 的小工具可以照抄或改寫——`ApplyPoolVerdicts.java`、`ReconcilePoolTags.java`、`DumpFdpsFunctions.java` 都是現成的落地與盤點手段，FID 查詢結果在 `tools/pool_triage/fid/` 可以直接餵給 agent 當證據。**workflow 本身自己寫**，不要拿 `triage_ticket14.js` 改造：它的兩段結構（先建 function 再判 pool）在本票沒有對應物，本票的結構是單段判定加上邊界改動觸發的鄰居退休。

gate 沿用票 14 的基準稽核（孤立程式碼 0、error bookmark 0、未定義 byte 0、無 `unknown` pool），再加一項本票專屬的：改名之後沒有兩個位址搶同一個 vendor 符號。

## 收尾要重算的東西

pool 規模一旦變動，這些數字全部要重新統計而不是手改：

- [`program_info/code_pools.md`](../../../program_info/code_pools.md) 的四個 pool 規模、AIL 三個功能區的成員數、信心分佈。
- 票 14.1 的 FID 命中率與兩邊 function 數的差額解釋——改判會同時改變分子與分母。
