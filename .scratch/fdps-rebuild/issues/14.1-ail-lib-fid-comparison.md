# 14.1 — 用前作的 AIL 靜態庫對 `FDPS.LE` 做 FID 比對

**What to build:** 「FDPS 的 AIL 與 FD2 的 AIL 是不是同一份」有一個以函式庫比對得出的答案，而不是只有 body 逐一比對的結果。

票 14 判出 423 個 `ail` function，但那批判定完全沒有函式庫佐證——Miles 的 `.LIB` 不在手上，Ghidra Function ID 對 AIL 的命中率是 0，判定靠的是連結方向、debug build 的 API 字串與共用執行期狀態。CRT 那 379 個有 196 筆 FID 命中撐著，AIL 這 423 個沒有對應的東西。

前作有：`fd2-anatomy/libs/ailv3/ailv3.lib`（209,920 byte）是從 `FD2.LE` 的位元組合成出來的 OMF 靜態庫，附 `ailv3.h`。把它餵進票 14 已經跑通的 FID pipeline，就能對每個 `ail` function 給出「命中前作 lib 的哪個 module」這一層證據。

**注意這證明的是什麼**：`ailv3.lib` 是從 `FD2.LE` 合成的，不是 Miles 的官方發行版。命中代表「FDPS 的這段 AIL 與 FD2 的那段位元組相同」，不代表「與某個官方 Miles build 相同」。這正好是本票要回答的問題。

## 與 ADR-0004 的關係

[ADR-0004](../../../docs/adr/0004-reuse-fd2-ail-library.md) 已經決定直接沿用前作的 AIL 庫，依據是 428 個 AIL function 的 body 逐一比對：394 個（92.1%）位元組相同，其餘 30 個只有 codegen 層級差異。本票不是重做那件事，是用**另一種方法**獨立覆核它，並收掉 ADR 自己列出的兩處未驗證風險：

1. 4 個 body 完全由重定位欄位構成、無法判定的 thunk
2. mixer dispatch table 的 slot 內容未逐一核對——票 14 剛好把這一區的 136 個 function 全部定案為 `ail`（`0x52c5c`–`0x54823`），現在有材料核對了

兩邊的 function 數也要對得起來：前作 428、本作 423。差額要有解釋，不能只記下數字。

## 執行方式

FID pipeline 已經在 `tools/pool_triage/fid/` 跑通，本票只換輸入。`ailv3.lib` 是 OMF 庫，`wlib -q -x` 拆得開，Easy OMF-386 的 quirky record 一樣要先修（前作合成它時用的就是同一組 record 編碼規則，很可能整批都是 quirky）。

比對是整份 binary 的事實調查，不是逐個 function 下判斷，所以**不需要 workflow**（[ADR-0002](../../../docs/adr/0002-no-batch-processing-per-function.md) 的邊界）。只有在出現「命中與票 14 的判定不一致」的個案時，才逐一開 agent 重讀那幾個 function，一次一個。
