# 21.7 — 區域變數與參數的語意命名接進 workflow

**What to build:** 「emit 出來的 C 裡，每一個區域變數與每一個參數都有說得出意思的名字」這條要求，從一句寫在票 22 裡的期望，變成 emitter 照著做、reviewer 擋得住、知識庫擁有的規則。

票 22 已經把驗收條件寫進去了，但 `tools/code_emit/emit_ticket22.js` 的 RULES、emitter prompt 與 reviewer 檢查表**一個字都沒有提到這件事**，`rebuild_info/naming.md` 也只管符號前綴、不管 function 內部。也就是說這條要求目前沒有任何執行機制。

## 為什麼要單獨一張票

已經落地的兩支（`000160e0`、`000109f0`）人工檢查是合格的：`unit`／`count`／`index`／`dist`，參數 `tile_x`／`max_dist`／`out_indices`／`cmd_disabled`，沒有一個反編譯器預設名。

**這正好是不能靠它的理由。** 那是 emitter 自己的判斷，當時沒有任何規則要求它，也沒有任何檢查會擋。兩支剛好都是短小、控制流清楚的 function，取名本來就容易；真正會出問題的是後面那些幾百行、暫存器被重複利用、Ghidra 給出一串 `iVar1..iVar9` 的 function，而那時候沒有規則就只剩運氣。等到那時候才發現，代價是回頭重改已經 commit 的程式碼，還要重跑 gate。

放在票 22 裡當「順便做」也不行：改的是 workflow 的三個地方加一份知識庫正典，跟 emit 本身是兩種工作，混在同一批裡會讓那一批的 diff 分不清哪些是規則造成的、哪些是那支 function 造成的。

## 規則的內容

正典寫進 `rebuild_info/naming.md`，該檔目前只有符號前綴，要新開一節管 function 內部。內容是票 22 已經定好的那三段，搬過去當結論寫：

- **禁止的是反編譯器的預設名稱**：`iVar1`、`uVar3`、`param_1`、`local_8`、`puVar2`、`in_EAX`、`unaff_*`、`extraout_*` 這一類。改寫成 `iVar1_index` 這種半吊子也不算。
- **名稱要反映角色，不是型別也不是來源暫存器**：`tile_index`、`remaining_mp`、`cursor_row` 是對的，`int_var`、`eax_val` 不是。
- **迴圈索引叫 `i`／`j` 可以**，那是慣例不是預設名。
- **真的判斷不出用途的變數是一則 `open_issues`，不是一個可以留著的名字。** 這一條是規則的出口：它保證 emitter 不會為了通過檢查而編一個好聽但沒有根據的名字，而編名字比留 `iVar1` 更糟——後者至少誠實。

理由與 function 名稱、全域名稱那條鐵則同源，也要寫進正典：`src/` 是之後解析遊戲行為的主要依據（`README.md` 的 `src/` 那一列），一支滿是 `iVar1` 的 function 讀起來與反編譯輸出沒有差別，等於這一步沒有把任何理解沉澱下來。而且名字是理解的證據——說不出一個區域變數是什麼，通常代表那段控制流其實還沒讀懂。

## 要動的四個地方

1. **`emit_ticket22.js` 的 `RULES`**，因為 emitter、reviewer、rescan 三個角色共用它。
2. **emitter prompt 的寫 C 那一段（B 步）**，講清楚取名是工作的一部分而不是修飾，以及判斷不出來時走 `open_issues` 而不是硬編。
3. **reviewer 的檢查表**，加一項：有沒有殘留預設名稱、名稱有沒有反映真正的用途。發現就 block。注意這一項與別項不同——它不是拿 assembly 對照 C，而是拿 C 對照 reviewer 自己讀 assembly 得到的理解，所以證據的形式是「這個變數在 assembly 裡是什麼」而不是引用某一行。
4. **`rebuild_info/naming.md`** 新開一節，並反映到 `rebuild_info/_index.md`。

## 取捨的結論（實作後補）

兩半都做，界線是**機器答得出的問題不要問人**。

**預設名稱下放到建置。** `build_emit.py` 在啟動 DOSBox 之前掃 `src/` 與 `tests/`，命中就中止。放這裡而不是 reviewer 的理由是成本：emitter 自己會跑 `build_emit.py all`，幾秒鐘就知道，不必燒掉一輪 review。findings 寫成 Watcom 自己的錯誤格式（`E9001`）進 `OUT/NAMES.OUT`，由 `diagnostics()` 與兩份連結 transcript 一起讀，所以走既有的通報路徑、`gate.py` 一行都不用改——不新增第二套要跟著維護的機制。

**reviewer 只處理名不副實**，第 13 項，明文寫著只針對它在第 1–4 項本來就得弄清楚的那幾個值，不做全變數掃描。

實測（`00010b20`）第 13 項的證據形狀正是設計時想要的：它在覆述自己讀 assembly 的結論，不是在對變數表發表意見。

## 一個要想清楚的取捨（原始記錄）

「名不副實」比「預設名稱」難擋得多。預設名稱是機械可判的（一個 regex 就抓得到），名不副實只有讀懂那段 assembly 的人才看得出來——也就是只有 reviewer。

所以這一項的成本落在 reviewer 身上，而 reviewer 已經是整條 pipeline 最貴的一段。要決定的是：reviewer 對命名的檢查要做到多深？兩個極端都不對——只掃 regex 等於沒做，逐個變數寫證據會讓 reviewer 的輸出膨脹一倍而且大部分是廢話。傾向的做法是「只對它在其他檢查項裡本來就讀到的變數表示意見」，也就是命名檢查搭在既有檢查上而不是獨立掃一遍，但這要在實作時確認可行。

機械可判的那一半可以更便宜地擋：`build_emit.py` 或 gate 加一條 regex 檢查，`src/` 出現預設名稱就紅。這樣 reviewer 只需要處理難的那一半。要不要做、放在哪一層，一併決定。

## 怎麼驗證

規則沒有執行機制時就先跑過的那兩支，人工檢查已經合格，所以它們**不能**當驗證。驗證要用一支還沒 emit 的、Ghidra 會吐出一串預設名的 function：跑一批，確認 emitter 取的名字說得出意思、reviewer 的判定檔裡有這一項、而且沒有出現硬編的名字。
