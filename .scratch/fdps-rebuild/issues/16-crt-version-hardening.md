# 16 — CRT pool 版本判定補強

**What to build:** 編譯器小版本的結論不再建立在最弱的一環上。目前判定為 Watcom 10.0a，但排除 10.0b 只靠兩個浮點函式符號——因為兩版的 C 函式庫差異模組沒有被這個 binary 連結到。Ghidra 中累積的每一個確認的 CRT function 都是一個新的判別點。

**執行方式：** 逐一比對的部分依 [ADR-0007](../../../docs/adr/0007-workflow-automation-and-agent-context.md) 由 workflow 跑完，每次 agent 呼叫只帶一個 CRT function、把比對結果寫成判定檔、只回傳摘要。收斂版本結論是整體推理，由 workflow 最後一段統合判定檔完成，不是逐項工作。

本票沒有 Ghidra 寫入，gate 換成「每個判定檔都有明確的比對依據，不得只寫結論」。

**Blocked by:** 14

## 結果

- 395 個 `pool_crt` function 逐一比對 11 個發行版、9,309 個 OMF 模組，比對只遮掉模組自己 FIXUPP 宣告的 byte。381 個問得出相容集合，交集是**單一發行版 Watcom C/C++ 10.0a**；只取 392 個高信心判定，交集相同。
- **10.0b 現在排除得掉**，原判定的括號「10.0b 無法排除」被推翻。靠的是 `MATH387S` 兩個在 10.0b 改過的模組：`00055443` 的 `strtod`（443 個可比 byte、362 個不符，10.0b 把框架加大 4 byte）與 `00042ca0` 的 `IF@TAN`（自己只有 5 byte，靠整段 136 byte 的 `trig387` 定位比對定案）。10.0 由 7 個 function 排除，最強的是 `0004c423` 的 `__prtf`（649 個可比 byte、606 個不符）。
- **「函式庫版本＝編譯器版本」量得到一半。** 同語料差分編譯：10.0a 與 10.0b 的 `wcc386` 產出 334/334 完全相同，所以 a/b 之爭在編譯器側永遠無解、但也不花代價（用哪個編都一樣）。10.0 則有 22 個模組不同，把標頭釘死後差異仍在，是碼產生器差異；`FDPS.LE` 遊戲段有 38 處 10.0a 形狀、0 處 10.0 形狀，**編譯器不是 10.0 這件事不靠函式庫比對就成立**。
- 順帶抓到本機 `WATCOM_10.0a\lib386\dos\clib3s.lib` 是殘缺副本（少 `stk386`，393 對 394 模組）。它一度偽裝成「兩份 10.0a 互相矛盾」。已確認沒有污染票 14 的結論，票 14 的 FID 管線改指完整副本，處置進 `pitfalls.md`。
- 舊 `build_flags.md` 把 `0x43657` 記成 `__CHP`，實為 `int386x`（`CLIB3S` `intx386`）；真正的 `__CHP` 在 `0x3d4ec`（`MATH387S` `fchop`），且它連 10.5 之後都排除不掉。已更正。
- 結論頁 [`rebuild_info/build_flags.md`](../../../rebuild_info/build_flags.md) 的工具鏈一節，工具在 [`tools/crt_version/`](../../../tools/crt_version/_index.md)，敘事在 `devlog/2026-08-24-crt-version-hardening.md`。

**執行情形**：分 3 次 workflow 呼叫，共 657 個 agent。第二次的 judge 階段完整跑完，但後段被 API 529 打掉 69 個 agent；因為 converge 失敗，知識庫與 devlog 兩段依規則沒有產出，不存在半套成品。第三次把剩下的 1 個判定、25 個二讀、收斂與知識庫補完，0 錯誤、gate 395/395 通過。中斷暴露的兩個缺口已修回工具：gate 曾禁止「模組由鄰居佈局認出、但 byte 本身通用」這個合法狀態，回掃的工作清單曾只存在於單次執行的記憶中而無法續跑。
