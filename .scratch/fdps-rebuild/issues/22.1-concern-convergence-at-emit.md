# 22.1 — 疑慮的收斂點移到 emit／review，rescan 只留真正的鄰居相依

**What to build:** emit 與 review 在「證據現在就拿得到」的時候必須當場收斂，不准記成疑慮留給 rescan；rescan 的工作清單縮到只剩「答案所需的證據在 emit 當下確實不存在」的那一類。

## 為什麼

票 22 的第一批（`t22-01`）跑完後量的。該批 40 支全數落地，0 未完成、0 中斷、無拆檔，共開 196 個 agent、耗 17.4M subagent token、13.5 小時。其中 **rescan 開了 30 個 agent**——相對 40 支落地 function。

`tools/code_emit/data/emit_issues.json` 的狀態：

| | |
| --- | --- |
| 帶疑慮的位址 | 30 |
| 疑慮條目 | 97（已解 51／未解 46） |
| 51 筆已解中，`same_as` 鏡像 | 21（emitter 與 reviewer 記到同一件事，其中一筆只指向另一筆） |
| **真正的獨立結論** | **30** |

這 30 筆靠什麼解掉：

| 證據來源 | 筆數 |
| --- | --- |
| 鄰居的 verdict 檔——emit 當下確實不存在的證據 | **9** |
| Ghidra 唯讀查詢、出貨資料檔、知識庫頁、**emit 那輪自己就已經建置出來的 `.OBJ`** | **21** |

30 個 rescan agent 裡有 22 個至少解掉一筆、25 個改動了檔案，所以 rescan 不是在空轉。

**rescan 掃的不是無關緊要的東西。** 它解掉的都是真問題，證據也扎實：`00014550` 掃了全部 12 個 caller 的實際 immediate（67 個呼叫點逐一讀，不抽樣）；`00010b20` 用 WDISASM 反組譯自家 `MOVEGRID.OBJ` 與原版逐 byte 比對迴圈頭；`00011da0` 從出貨的 M320 地圖量出 26×56，證明那兩個 byte store 不可能溢位。

問題在**收斂點放錯位置**。30 筆裡有 21 筆，答案所需的證據在 emit 當下全都在手上——`00014550` 要的是 `get_xrefs_to`，`00010b20` 要的那個 `.OBJ` 就是 emit 那一輪 build 出來的。emitter 選擇記一筆疑慮而不是掃完。

代價比表面大。掃描本身在哪做都一樣貴，省不掉；省得掉的是 **rescan agent 必須從零重讀這支 function、它的兩份 verdict、它的 assembly，只為了做一件 emitter 當時已經滿手材料的掃描**——也就是一整份重新建立的 agent context，每支一份，這一批 30 份。

## 不是把 rescan 拿掉

那 9 筆是 ADR-0007 第四條真正要的東西，拿掉就沒有任何機制會回收它們。典型是 `000140e0`：.SAF header 要不要包成 struct、還是全檔用 byte offset 定址，這是一個**全檔一致性**的決定，要等兄弟 reader（`000144e0`、`00014550`、`000142d0`）都出現才知道大家實際上選了什麼。單獨一支 function 永遠答不出來，記下它的那一批也永遠不是能回答它的那一批。

## 兩件要改的事

**1. emit／review 加收斂門檻。**

記疑慮的條件是「答案所需的證據還不存在」，不是「我還沒去查」。要寫進 `emit_ticket22.js` 的 RULES（三個角色共用）與 emitter／reviewer 各自的 prompt，並明確舉出當下就該用掉的證據來源：Ghidra 唯讀查詢、出貨的遊戲檔與資源、知識庫、**以及這一輪 build 已經產出的 `.OBJ`**（最後這項最容易被忘記，它就在 `workspace/code_emit/out/objs/` 底下）。

這一條與票 21.7 那條「判斷不出用途的變數是一則 `open_issues`」不衝突，但界線要寫清楚：**證據不存在**才記疑慮，**還沒去查**不算。

**2. rescan-worklist 過濾掉結構性延後的條目。**

46 筆未解裡有一批卡在票 23（資料 emit）或票 24（實機遊玩）。這是票的切法決定的——票 22 跑在票 23 之前，那些條目在本票內永遠答不出來，跟 pipeline 好壞無關。每批重問它們是純浪費。

`rescanWorklistPrompt` 現在只用「鄰居這批動了沒」當篩選條件，要再加一層：`needs` 指向票 23／24 的條目不進本票的回掃清單，留給那兩張票回收。這也需要 `emit_issues.json` 的條目能機械判別自己卡在誰身上——目前只有自由文字的 `needs`，是否要加一個結構化欄位（例如 `deferred_to`），實作時一併決定。

## 怎麼驗證

不能拿已經跑完的 `t22-01` 當驗證——那一批的疑慮是在舊規則下記的。

驗證要用**改完之後的下一批**，比對兩個數字：

- rescan agent 數 ÷ 落地 function 數。`t22-01` 是 30／40；預期降到 9／40 附近
- 新一批記下的疑慮中，事後被 rescan 用「emit 當下就拿得到的證據」解掉的筆數。**這個數字應該趨近 0**——不是 0 就表示門檻的措辭還沒擋住

第二個數字才是真正的驗收，第一個只是它的副作用。只看第一個會被「emitter 乾脆少記疑慮」蒙混過去，而少記疑慮比多記更糟。

同時要確認**沒有反向失效**：改完之後那 9 類鄰居相依的疑慮仍然被記下來、仍然進回掃清單。門檻寫太緊會讓 emitter 把答不出來的問題也硬收斂成一個編出來的結論，那比現況嚴重得多。
