# 21.6 — Emit workflow 的無人值守與中斷復原

**What to build:** 票 22／23 的 emit workflow 可以一批接一批連續跑完，中途完全不需要人介入；撞到 usage limit 或任何強制中斷時，除了當下飛在半空的那一支 function 之外不損失任何東西，下一次呼叫自己把現場收乾淨再繼續。

批次大小由呼叫者（agent）決定，不由 workflow 自己依預算決定。一批跑完，呼叫者快速檢查狀態與結果是否符合預期、修掉問題、再呼叫下一批——**使用者不介入任何一個環節**。

## 現況與三個缺口

票 21 的 workflow（`tools/code_emit/emit_ticket21.js`）與票 22 沿用它改出來的 `emit_ticket22.js` 都有下面三個問題。前兩個在票 21 一支 function 的規模下不會出現。

**一、workflow 自己在管預算，會提前停。** `minBudgetPerFn`（預設 120k）在每支 function 開跑前檢查剩餘預算，不夠就把剩下的全部記成 `not_started_budget` 並停止。這與「跑完呼叫者指定的數量」直接衝突：呼叫者說要跑 40 支，workflow 可能只跑 12 支就停，而且停的理由是一個呼叫者沒有要求它去管的東西。預算耗盡的正確表現是被外部中斷，不是自己提前收手。

**二、中斷之後沒有人收拾現場，而收拾的責任被推給了人。** 一支 function 失敗時，workflow 會開一個 agent 清掉 `src/`／`tests/` 的工作區殘留並把狀態記成 `failed`。這條路徑要求 session 還活著。撞到 usage limit 時 session 正是不活著的那個東西：workflow 當場死掉，工作區留著半成品，`emit_state.json` 沒有記下任何東西。

後果不是「損失那一支」而已——下一次呼叫的第一支 function 一開跑，reviewer 看到的 diff 裡混著上一支的殘骸，bookkeeper 的 `git add src tests` 會把它一起 commit 進去，而 commit 標題寫的是別人的名字。腳本現在對這件事的處置是印一行 `check git status before the next run`，也就是交給人。

**這一條是本票的核心。** 使用者的要求是「只損失撞到時當下在處理的那個單一 function，需要再重跑一次而已」，現在的實作做不到：它還會污染下一支。

**三、沒有辦法在不看工作區的情況下知道剛才在做哪一支。** 中斷時 `emit_state.json` 對飛在半空的那一支仍寫著 `pending`——這對續跑是對的（它確實還沒做完，該重發），但沒有任何地方記下「上一次是死在這一支」。工作區的殘留是唯一的線索，而殘留正是要被清掉的東西。收尾報告因此無法區分「這一支還沒輪到」與「這一支跑到一半被殺」。

## 要做到的

**開跑前先收拾，而不是失敗時才收拾。** workflow 的第一段（取工作清單那一段之前或之中）要檢查工作區：`src/`／`tests/` 有未 commit 的改動就是上一次中斷的殘骸，丟掉它，把對應的 function 記成 `interrupted` 回工作清單，然後才開始。這是唯一能在「session 已經死過一次」之後還執行得到的時機。

界線要畫清楚：能丟的只有 `src/` 與 `tests/` 底下的未 commit 改動。`workspace/` 不能碰（判定檔是中斷現場的紀錄，下一次要讀），已經 commit 的東西不能碰，其他資料夾的改動不能碰——遇到那種情況要停下來報告，不能自作主張。

**中斷前留下一行足跡。** 每支 function 開跑前把它記成 `in_flight`（帶時間），通過後才推進到 `committed`。這樣續跑時「工作區髒」與「狀態檔說 `in_flight`」互相印證，收尾報告也講得出「上一輪死在哪一支」。注意這不改變續跑規則：`in_flight` 與 `pending` 一樣要重發。

**取消 workflow 自己的預算判斷。** 拿掉 `minBudgetPerFn` 與 `not_started_budget` 這條路徑。workflow 跑完呼叫者給的清單為止；停下來的理由只剩三種：清單跑完、上游失效（ADR-0007 5.2／5.5）、外力中斷。

**票 23 的 workflow 一併適用。** 本票的結論寫進 `rebuild_info/emit_pipeline.md`（emit 的工作狀態與續跑那一段），票 23 自己寫 workflow 時照著做——ADR-0007 說不要抽共用骨架，共用的是原則。

## 怎麼驗證

這三件事都只在「被殺過」之後才看得出來，所以要真的殺一次，不能只讀程式碼：跑一批、在某支 function 飛在半空時強制中斷、確認工作區有殘留與狀態檔有 `in_flight`，再呼叫下一批，確認它自己收乾淨、那一支重新排進清單、而且下一支的 commit 裡沒有任何屬於前一支的東西。

## 驗證與 review 追加的六條

`b4136c4` 裡混進了 `tools/build_gate/gate.py`——bookkeeper 為了讓「tree 必須乾淨」的檢查過關，把 `git add` 清單以外的東西也 add 了進去。那一刻被殺的話，下一輪的 Recover 段會看到界線外的髒路徑而停下來等人。界線因此改成雙向：pipeline 自己也只准把它自己的產出弄髒，界線外的改動當場單獨 commit。

code review 再抓出這些，全部修掉：

- **`git add -N` 的殘留清不掉。** reviewer 為了讓新檔進 diff 會 `git add -N -- src tests`，intent-to-add 的檔在 index 裡，`checkout` 只截成 0 byte、`clean` 跳過它。從 review 到落地的整段時間被殺都會卡住。Recover 與 abandon 兩處都補上 pathspec 的 `git reset --`（已在 scratch repo 實測）。
- **abandon 的成敗只看 commit 不看工作區**，殘留會被下一支 commit 成它的。driver 改成同時檢查 `tree_clean`。
- **Report 段寫的 devlog 從來沒 commit**，而 `devlog/` 在界線外——每批跑完都會卡死下一批。Report 段改成自己 commit。
- **bookkeeper 自己會弄髒 `ghidra_snapshot/` 與 `emit_issues.json`**（第 2、4 步寫，第 5 步才 commit）。界線擴成 pipeline 各段真正會寫的六個路徑；`ghidra_snapshot/` 髒了改成重新匯出而非還原。
- **Split 段的職責就是改 `build_routing.py` 與 `code_layout.md`**，原本那條 RULES 等於禁止它工作。規則改以「是不是你被指派的工作」為準。
- **stray 的 commit 順序反了**：staged 之後再 `git add <stray> && git commit` 會把整支 function commit 在 stray 的標題底下。改成 stage function 之前處理，且 commit 帶 pathspec。
- **`problems` 在成功路徑被丟掉**，界外 commit 的唯一記錄消失。改成也帶上成功那一列。
- reviewer 第 A 步十行內自相矛盾（要 review 知識庫改動／未 commit 的知識庫改動要 block），刪掉前者。
