# 22 — 全 function emit

**What to build:** 遊戲本體的每個 function 都有對應的、經過獨立審查的 C 原始碼。做完這張票，程式邏輯的重建就完成了。

**執行方式：** 沿用票 21 建好的 workflow，不另外設計，規模放大到全部遊戲本體 function。[ADR-0007](../../../docs/adr/0007-workflow-automation-and-agent-context.md) 的四條在這裡是硬需求而非建議——這是全專案規模最大的逐項工作，任何「把完整產出帶回 orchestrator」的寫法都撐不到終點。

每個 function 寫進哪一個 `.c` 由票 21.5 的 routing 規劃決定，本票不在 emit 過程中臨時決定落點。

這張票是最需要「全自動跑完、不中途回來確認」的一張：以每個 function 一次確認計，人工節奏會讓工期完全被回覆延遲支配。批次大小由呼叫的 agent 決定，一批跑完就自己檢查、修正、呼叫下一批；workflow 不自己管預算，中斷之後的現場收拾由票 21.6 負責。

## 資料還沒 emit 之前怎麼驗證

真實的全域資料內容是票 23 的產物，本票跑的時候還不存在。這不構成阻塞，因為編譯、連結、執行三層對資料的需求完全不同：

**編譯只需要宣告。** `wcc386` 要的是 `extern` 宣告與 struct 佈局，票 17 已經全數定案，所以每個 function 都編得過，不需要任何資料內容。

**連結需要定義，用自動生成的零填充 stub。** 本票的 gate 是 build gate，必須連得起來。做法是兩段式連結：先不帶 stub 連一次，收集連結器回報的未定義符號清單；再依票 17 的型別與大小自動生成零填充的 stub 模組，第二次連結通過。stub 是每次建置從「票 17 符號表減去 `src/` 已有真實定義」重新生成的產物，不是手寫檔，不進 `src/`。這樣做同時保住票 23 的設計：**票 23 的權威工作清單就是第一次連結吐出的那份未定義符號清單**，而且它在本票的每一輪建置都被重新產生一次，等於持續驗證。

**執行驗證不做整機實跑。** 零填充的資料跑不了遊戲，本票不勉強。本票的執行驗證只有兩種，都不依賴靜態資料表：純機械計算的 function 由單元測試自行提供輸入，期望值來自攻略公式或 Ghidra emulator；讀取真實遊戲檔的 function，資料來自檔案而非靜態表。整機實跑是票 24 的範圍。

**行為由靜態表決定的 function** 是唯一的例外（查表分支、以表驅動的狀態機等）。處置是測試內自備局部 fixture 表，**不得為了測試提前 emit 該符號的真值**；真的無法在本票確認等價性的，記入等價性疑慮清單，留到票 23／24 回收。

## Function 內部的符號也要有語意名稱

emit 出來的 C 裡面，**每一個區域變數與每一個參數都必須有說得出意思的名字**。Ghidra 反編譯器產生的預設名稱——`iVar1`、`uVar3`、`param_1`、`local_8`、`puVar2`、`in_EAX` 這一類——一個都不准留在 `src/` 裡，改寫成 `iVar1_index` 這種半吊子也不算。

理由與 function 名稱、全域名稱那條鐵則同源：這份原始碼是之後解析遊戲行為的主要依據（見 `README.md` 的 `src/` 那一列），一支滿是 `iVar1` 的 function 讀起來與反編譯輸出沒有差別，等於這一步沒有把任何理解沉澱下來。而且名字是理解的證據——說不出一個區域變數是什麼，通常代表那段控制流其實還沒讀懂。

界線：名稱要反映它在這支 function 裡的角色（`tile_index`、`remaining_mp`、`cursor_row`），不是它的型別（`int_var`）也不是它的來源暫存器。迴圈的索引叫 `i`／`j` 可以，那是慣例不是預設名。真的無法判斷用途的變數，是一則 `open_issues`，不是一個可以留著的名字。

emitter 與 reviewer 兩邊都要遵守：emitter 負責取名，reviewer 把「有沒有殘留的反編譯器預設名稱、名稱有沒有反映真正的用途」列進檢查表並在發現時 block。結論寫進 `rebuild_info/naming.md`——該檔目前只管符號前綴，不管 function 內部。
