# 22.3 — RLE sprite 繪製的 15 支改回原版的手寫組語

**What to build:** 重建版畫 sprite 的那一組——`fdps_blit_dispatch`（`000568db`）與它底下 `00056a0d`–`00057a74` 的 14 支（13 種畫法加 `fdps_rle_skip_row`）——不再是 C，而是從原版轉錄的組合語言原始碼，以 `wasm` 組譯後連進執行檔。

**驗收標準只有兩條：與原版功能相同，而且執行效率與原版組語完全相同。不要求逐 byte 相同。** 票 22 寫好的 C 版不刪，註解掉留在原檔作為閱讀用的參考。

## 為什麼

這 15 支在原版就是遊戲自己手寫的組語，不是 `wcc386` 的產物（辨識特徵與整段手寫模組 `00056799`–`00057c54` 的範圍見 `program_info/code_pools.md`）。票 22 依 ADR-0001 把它們連同暫存器交接一起改寫成一般 C，功能等價；代價是速度：原版一段同色像素是一道 `REP STOSB`／`REP MOVSB`，C 版是逐 byte 迴圈，每像素的指令數多好幾倍。這一組是每畫一個 sprite 都會跑的逐像素熱路徑，票 24 已經因此列了「重建版不能明顯變慢」的實機疑慮（`00056a0d#0`、`00056c5e#1`）。

使用者決定（2026-09-23）不賭實機結果，直接保留原版組語。同一段手寫模組裡的鍵盤 7 支與存檔 2 支（`fdps_compute_save_checksum`、`fdps_xor_crypt_buffer`）不在範圍內，維持 C——它們不在熱路徑上。

## 「執行效率完全相同」的定義

判定單位是**指令**，不是 byte。對每一支，重建版組出來的機械碼必須滿足：

1. **指令序列逐道相同**：同樣的指令、同樣的順序、同樣的運算元，分支落在對應的那一道指令上。**原版的 NOP 也算指令，要照樣寫出來**——條件跳躍沒跳時會順著執行它們，拿掉就改變了執行的指令數。
2. **每道指令的長度與原版相同**，所以函式內的程式碼佈局、每個分支的距離、每道指令的執行週期都與原版一致。
3. byte 只允許在兩種地方與原版不同：
   - **同一道指令的另一種等長編碼**。WASM 10.0a 對暫存器對暫存器的 `mov`／`add`／`sub`／`xor`／`and`／`or`／`cmp` 選另一個方向位元（`or bx,bx`：原版 `66 0B DB`、WASM `66 09 DB`），`cmp ax,0` 選 imm8 形式（原版 `66 3D 00 00`、WASM `66 83 F8 00`）。這些與原版長度相同、CPU 執行的動作與週期相同，**照 WASM 的預設編碼寫一般指令即可，不要為了對齊 byte 改用 `DB`**。
   - **重定位欄位**：原版的絕對位址在重建版一律是符號，由連結器填值。

違反 1 或 2 的就是不合格，不論它「功能上是不是一樣」。

## 開工前就知道的事

以下是先前一次嘗試（以「逐 byte 相同」為標準，已整批撤回）量到的事實，開工時要重新確認，但不必從頭摸索：

- **原版這段不是 WASM 10.0a 組出來的。** 除了上面的等長編碼差異，原版每個「往前跳、目標在短跳距離內」的分支都是短跳加 NOP 填充：條件跳躍 2 byte + 4 個 NOP，`JMP` 2 byte + 3 個 NOP；目標太遠才用長形式；往回跳沒有填充。這是單趟組譯器的特徵。所以轉錄時前向短跳要明寫 `short`，後面照原版逐行寫 `nop`，其餘分支不指定長短讓 WASM 自己選。
- **不要寫 `jcc near ptr`**：WASM 10.0a 的前向 `jcc near ptr` 位移多算 1，會跳到目標的下一個 byte。`jmp near ptr` 是對的，但沒有必要用。
- **WASM 的標籤是整個模組共用的**，同一個 `.asm` 裡的每支 function 要用各自的標籤前綴，否則 `E071: Symbol already defined`。
- **NT 版 `WDISASM.EXE` 讀長路徑的物件檔會 access violation**，要在物件檔所在目錄以短檔名呼叫。
- **原版 15 支用 capstone 可以完整解碼**，沒有夾雜資料；所有 NOP 都是前向短跳後的填充，沒有任何分支的目標落在 NOP 上。
- **Ghidra 快照對這一段記的 function 大小偏小**（例：`fdps_blit_dispatch` 記成 `0x11d`，入口到 `RET` 實際是 `0x132`）。比對時函式範圍要取「本支入口到下一支入口」，最後一支到 object 1 的結尾；`tools/build_flags/fn_match.py` 用記錄的大小切，對這一段會切錯。這是 Ghidra 端的問題，本票要查清楚原因並修正。

## 要做的

1. **逐支轉錄成 `wasm` 原始碼。** 一次一支、用 workflow 跑，每次 agent 呼叫只帶一支（CLAUDE.md 鐵則、ADR-0002、ADR-0007）。組語的寫法（segment、model、`PUBLIC`／`EXTRN`）以現有的 `src/ailflags.asm` 為準，建置流程已經會組譯 `src/*.asm`。
   - **絕對位址一律換成符號。** 原版的 `[0x00070022]` 這類運算元是原版連結器排出來的位置，照抄等於指到重建版那個位置上碰巧放著的東西（`rebuild_info/pitfalls.md` 已有這一條）。分派者寫、畫法讀的 `data_fdps_graphics_rle_blit_*` 等全域留在 C 的定義裡，組語以 `EXTRN` 引用；呼叫目標同理用符號。
   - **對外介面維持原樣。** C 端 46 個呼叫點看到的仍是 `blit.h` 那個 7 個參數、呼叫端清堆疊的 `fdps_blit_dispatch`，符號名稱與 Ghidra 逐字相同（`naming.md`）。分派者保存與還原的暫存器照原版。
2. **比對工具**：逐支檢查「執行效率完全相同」的三條定義。兩邊都反組譯成指令，重定位欄位遮掉後逐道比對指令文字、長度與分支目標（以落在第幾道指令表示，所以位移差 1 byte 的分支會被抓到）；另外驗證原版每個重定位欄位在重建版也是重定位、指向 Ghidra 在原目標處的符號與同一個偏移，重建版不能多出原版沒有的重定位；原始碼裡不能有落在原版映像位址範圍內的數字。工具要有自我測試，證明每一種不合格都抓得到。
3. **檔案配置**：組語分五個 8.3 檔，對應現有 C 檔的分組——`rledisp.asm`（分派者）、`rlebase.asm`（`rle.c`）、`rlepal.asm`（`rlecolor.c`）、`rleturn.asm`（`rlerot.c`）、`rlemix.asm`（`rleblend.c`）。不能叫 `rle.asm`，因為建置會把它和 `rle.c` 都輸出成 `RLE.OBJ`。
4. **C 版註解掉、留在原檔。** `/* */` 不能巢狀，而這幾支 C 裡滿是區塊註解，所以用 `#if 0` 包起來，並在檔頭寫明「這是參考用的 C 譯本，實際連進去的是哪個 `.asm`」。這不是測試 hook，與 ADR-0003 不衝突。`rle.h`、`rlecolor.h`、`rlerot.h`、`rleblend.h` 裡 13 種畫法的 C 原型不再是真的介面（它們只能從分派者的 frame 裡被呼叫），一併移進參考區，只留 `fdps_blit_dispatch` 的宣告。`rlerot.c` 與 `rleblend.c` 裡的資料定義要留著，組語會讀它們。
5. **新增經過分派者的測試，C 版的測試保留。** `tests/rle.c`、`rlecolor.c`、`rlerot.c`、`rleblend.c` 目前直接用 C 簽章呼叫各畫法（共 159 處），畫法變成組語之後這種呼叫不存在。
   - 新增一套呼叫 `fdps_blit_dispatch` 並指定模式的測試，涵蓋現有測試驗到的每一種情況，對組語版生效。測試檔以組語檔命名（`tests/rledisp.c` 等），分派者現有的測試從 `tests/blit.c` 搬過去。
   - 現有直接呼叫 C 版畫法的測試**不刪**，與 C 版原始碼一樣以 `#if 0` 保留，檔頭寫明它們測的是參考用的 C 譯本。目的是保留日後改回 C 版的彈性：改回去時這些測試要能直接重新啟用。建置腳本不能登記 `#if 0` 裡的測試進入點。
   - 「一個測試檔鏡像一個 `src/` 子檔」在這裡怎麼對應，要在 `rebuild_info/emit_pipeline.md` 寫明。
   - **改回 C 版的步驟寫進知識庫**（`rebuild_info/code_layout.md`）：要移除哪幾個 `.asm`、要打開哪些 `#if 0`（原始碼、C 原型、C 版測試）、要跑哪些檢查。步驟要實際走過一次確認可行——切回 C 版建置並跑完兩套測試全綠，再切回組語版——而不是只寫在紙上。

7. **知識庫與 Ghidra 跟著改。**
