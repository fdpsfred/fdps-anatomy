# 25.17 — 全知識庫逐條驗證與 README

**What to build:** 知識庫的每一條結論（含本票新寫的）都對照實際的程式碼、Ghidra 狀態、資源檔驗證過，事實漂移全部修正；README 完整說明專案成果、如何建置、知識庫如何閱讀。

**執行方式：** 依 ADR-0007 由 workflow 跑完。每次 agent 呼叫只帶**一份知識庫文件**，agent 把逐條驗證結果寫成檔案、只回傳「幾條通過、幾條有問題」的摘要。修正是獨立的轉錄階段——驗證的 agent 不改文件，避免「自己驗自己改」把錯誤合理化掉。粒度取一份文件而非一條事實，因為一條事實的對錯往往要看它在文件裡的上下文；但一個 agent 仍只處理一份文件，不得拿到文件清單自行分配。

## 做法

前作參照：`fd2-anatomy` 的知識庫翻新 batch 7（commit `ad85325b`–`2bfa777e`）是逐檔逐條驗證、再做跨 `_index.md` 一致性收尾，但由主 session 逐一親核，沒有留下工具；本票沿用兩段的形狀，工具自己寫在 `tools/kb_verify/`（見該資料夾的 `_index.md`）。

1. **逐文件驗證**（`verify_ticket25_17.js`）：一段一個 agent，判定寫成檔、只回摘要；每個問題是一筆帶精確字串替換的發現；有修正、有外部修正、信心不是 high 或判斷不了的發現都交第二位 agent 確認、修改或駁回。
2. **轉錄**：同一支 workflow 的最後一段，由不做判斷的 agent 跑 `kbverify.py apply`（只落地第二位 agent 確認或修改的修正，其餘逐項列出拒收理由）與全部閘門。需要改 `src/` 註解、Ghidra 或產生器的（`outside`）由票的 session 逐項處理。
3. **跨文件一致性**（`consist_ticket25_17.js`）：`kbconsist.py` 以確定性方法產生候選——第一段每筆事實修正的錨點（位址、`fdps_` 符號、檔名）在其他文件與同頁其他地方出現的行、字元 4-gram 大量重疊的段落、驗證者回報的矛盾、驗證者提出的踩雷點候選、下方收尾項目 10 的分類重判（一個條目一項：C16c、C16d、C16e、C10、`30:0x13`、`30:0x14`、S19）——一項一個 agent，同樣回掃後才落地並跑閘門。
4. **收尾**：`kbverify.py lint`（全知識庫：禁引 `workspace/`／`legacy/`、流水帳字眼、連結、引用位址對快照、未知符號）與 `indexes`（`_index.md` 一致性）歸零、README 重寫、待開發者決定的問題整理成一份交給主 session。
