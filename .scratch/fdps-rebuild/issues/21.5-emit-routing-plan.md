# 21.5 — Emit routing 規劃

**What to build:** 每個要 emit 的 function 與資料符號都事先指派好目標 `.c`／`.h` 檔，且每個檔的預估行數受控。做完這張票，票 22 與 23 開跑時不必再決定「這個東西寫進哪裡」。

前作 FD2 有這一步（`tools/code_emit/data/routing.md` 與 `routing.json`），本專案缺，補上。理由是 emit 是序列的：檔案落點如果邊做邊決定，後面必然要回頭重組已經通過 review 並 commit 的檔案。控制單檔行數的目的是 model 的讀寫效率——一個一千行以上的 `.c` 每次修改都要整檔進 context。

**這不是逐項判定工作。** 子系統歸屬要看整體 call graph 與資料存取關係才定得出來，把它切成「一個 function 一個 agent」會得到互相矛盾的分組。本票整體規劃，不受 [ADR-0002](../../../docs/adr/0002-no-batch-processing-per-function.md) 的逐一鐵則約束——性質與票 17 的 struct 佈局那一段相同（該鐵則管的是「身分、calling convention 與 emit」的判定，不管檔案編排）。

**輸入：**

- 票 15 的命名判定檔與 plate comment（`tools/logic_naming/`）——function 的語意就是分組依據
- 票 12 的 call graph（`tools/call_graph/` 的 `graph.json`、共用 helper 排名、叢集結構）
- 票 17 的全域符號判定與 struct 佈局（`tools/global_data/`）——資料符號的分組依據是誰取用它
- 票 14.2 覆核後的 pool 判定——`pool_crt` 與 `pool_ail` 不在本票的規劃範圍，它們是連結進來的既有程式庫

**行數預估的來源是 Ghidra decompiled code 的行數**，沿用前作的做法。這是估計值不是保證值，票 22 實際 emit 後會偏離；偏離的處置寫在下面。

**輸出：** `tools/code_emit/data/routing.json`（機器讀）與 `routing.md`（判定依據與逐檔說明），結論收進 `rebuild_info/` 的一份新正典檔。
