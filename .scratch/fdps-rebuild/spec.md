# FDPS 逆向工程與重建

Status: ready-for-agent

## Problem Statement

「炎龍騎士團外傳」(FDPS) 是一款 1997 年的繁體中文 DOS 遊戲。它的執行檔 `FDPS.LE` 是一個 362,469 byte 的 32-bit DOS/4G LE 模組，沒有 import table、沒有符號、執行檔內連一個中文字串都沒有。除了能在模擬器裡玩之外，這款遊戲的內部運作方式——戰鬥公式怎麼算、資源檔怎麼組織、章節事件怎麼分派——完全是黑箱。

前作 FD2 已經完成同樣的逆向工程，但兩代的遊戲引擎是重寫的：兩個執行檔在遊戲邏輯區的共同 byte 是 **0**。前作的 `program_info/` 與 `src/` 一行都不能沿用。可以沿用的只有方法論、工具鏈知識、以及少數與遊戲邏輯無關的共用資產（Miles AIL 音效庫、存檔編解碼、sprite RLE 解碼器）。

## Solution

從 `FDPS.LE` 的機械碼還原出完整的 C 原始碼，用 Watcom C/C++ 10.0a 重新編譯出**功能等價**的執行檔，能在 DOS 環境下直接取代原始執行檔遊玩。同時建立一套涵蓋程式碼、資源檔、遊戲資料三個視角的知識庫，讓這款遊戲的每個面向都變成可查證的事實。

「功能等價」的定義見 ADR-0001：外顯行為與功能一致，不要求 binary byte 相同。

過程分七個階段，前後有明確的依賴關係，但不是嚴格的瀑布——知識庫、Ghidra 狀態、程式碼三者從頭到尾持續互相修正並保持同步。

## User Stories

### Phase 0：攻略與資源基準真值

1. 作為專案維護者，我想要把 FDPS 攻略站的 9 個內容頁鏡像進專案，這樣我在 Ghidra 裡看到一塊數值表時，能立刻查到它對應遊戲中的哪個概念。
2. 作為專案維護者，我想要攻略抓取 pipeline 以遊戲代號參數化，這樣同一套程式也能跑前作與一代的攻略站。
3. 作為專案維護者，我想要拿前作攻略站與前作知識庫的已知正確答案抽查鏡像，這樣我能確認鏡像沒有失真。
4. 作為專案維護者，我想要鏡像的純文字版保留原本的等寬排版與空行分段，這樣搜到一行之後讀上下文就能看懂整張表。
5. 作為專案維護者，我想要把攻略站給出的資料檔偏移與 record 結構（物品 23 byte、法術 7 byte、人物出場屬性 24 byte、升級 11 byte、法術習得 12 byte、職業 10 byte）確認到底指向哪一個檔案，這樣它們才能當成基準真值使用。
6. 作為專案維護者，我想要把 8 個 `.VFS` 容器裡全部 1,190 個 entry dump 出來，這樣後續每個資源檔都有具體的檔案可以分析。
7. 作為專案維護者，我想要 `MISC.VFS` 內的巢狀 VFS 能被遞迴解出，這樣不會漏掉包在裡面的資源。
8. 作為專案維護者，我想要逆向出 `SAF` 多 frame 動畫容器的格式，這樣佔資源大宗的 522 個動畫檔才能被解讀。
9. 作為專案維護者，我想要驗證前作的 RLE 4-op sprite 解碼器能正確解出 `.CEL` 的像素，這樣我能確認圖檔編碼確實可沿用。
10. 作為專案維護者，我想要把光碟兩片映像的內容清單（檔名、大小、SHA-256）記進知識庫，這樣光碟上有什麼變成可查證的事實。
11. 作為專案維護者，我想要釐清光碟上的外部程式與 `.Aud` / `.Vid` 檔在遊戲中扮演什麼角色，這樣才能界定 CD 音源子系統是不是逆向範圍的一部分。
12. 作為專案維護者，我想要在 Phase 0 結束時把累積的遊戲資料建成可查詢的 knowledge skill，這樣後續階段查數值不用每次翻原始檔。

### Phase A：Ghidra 全 binary 解析

13. 作為專案維護者，我想要查清楚重新自動分析後 function 數從 811 掉到 719 的那 92 個差額去了哪裡，這樣我能確認沒有真正的程式碼被漏掉。
14. 作為專案維護者，我想要確認這個 binary 的 calling convention 到底是不是 stack-based，這樣所有 function 簽章才有正確的基礎。
15. 作為專案維護者，我想要每個 function 的 calling convention 都是逐一讀過 assembly 後判定的，這樣不會有任何一個是靠規則套上去而錯誤的。
16. 作為專案維護者，我想要建出完整的 call graph，這樣我能看出叢集結構、知道從哪裡切分平行工作。
17. 作為專案維護者，我想要先人工走過從 entry point 到主迴圈的骨幹路徑，這樣後續處理個別 function 時有共同的整體圖像。
18. 作為專案維護者，我想要每個 function 都被判定歸屬到四個 pool 之一，這樣我能區分哪些是遊戲本體、哪些是 runtime 或 vendor 程式碼。
19. 作為專案維護者，我想要 pool 判定是逐一進行而非用位址範圍圈定，因為 pool 成員在位址上互相交錯。
19.1. 作為專案維護者，我想要每個 function 的 pool、名稱、邊界與註解都被第二雙眼睛逐一重讀過，這樣第一輪那些只在有旁證的地方才被抓到的錯誤，在沒有旁證的地方也能被抓到。
20. 作為專案維護者，我想要每個 function 都有語意正確的名稱與 plate comment，這樣知識庫與程式碼能共用同一套詞彙。
21. 作為專案維護者，我想要 CRT pool 的辨識結果能累積成編譯器版本的判別證據，這樣 Watcom 10.0a 的判定能持續被加強或推翻。
22. 作為專案維護者，我想要補強 10.0a 與 10.0b 之間的區分（目前只靠兩個浮點符號），這樣編譯器版本的結論不會建立在最弱的一環上。
23. 作為專案維護者，我想要 12 個既有的 error bookmark 全部被修復並手動移除，這樣「零 error bookmark」能成為可信的完成訊號。
24. 作為專案維護者，我想要處理掉 orphan code、jump table 與 fall-through，這樣沒有任何程式碼區域是未被辨識的。
25. 作為專案維護者，我想要在階段結束時達成「0 個 `FUN_*` 殘留名 + 0 個 error bookmark」，這樣 Phase A 有客觀的完成判定。
26. 作為專案維護者，我想要 global data 符號也被賦予語意名稱，這樣後續 data emit 有正確的起點。
27. 作為專案維護者，我想要 struct 佈局被定義出來，這樣 decompiled C 能讀懂而不是滿是位移運算。

### Phase B：最小可編譯骨架

28. 作為專案維護者，我想要驗證 Watcom 10.0a 加 wlink 能產出在 DOSBox-X 裡跑得起來的 DOS/4G 執行檔，這樣工具鏈風險在投入大量 emit 工作之前就被排除。
29. 作為專案維護者，我想要一個能在 DOSBox-X 內自動完成編譯與連結的建置腳本，這樣建置不需要人工介入。
30. 作為專案維護者，我想要建置腳本在啟動時自動掛載光碟，這樣測試環境與實際遊玩環境一致。
31. 作為專案維護者，我想要建置腳本在光碟映像不存在時明確報錯，而不是讓遊戲跑起來才丟出找不到 CD-ROM 的訊息。
32. 作為專案維護者，我想要建置流程有可靠的結束偵測而不是固定等待，這樣自動化不會因為時間抓不準而失敗。
33. 作為專案維護者，我想要確認前作抽出的 AIL 靜態庫能實際連結成功，這樣 ADR-0004 的假設得到驗證；若失敗則改用前作的抽取 pipeline 重抽。
34. 作為專案維護者，我想要一個自我回歸的 build gate，這樣任何改動如果意外改變了編譯結果我會立刻知道。

### Phase C：function emit

35. 作為專案維護者，我想要每個 function 的 emit 都是一次處理一個、由結構性機制強制，這樣不會退化成批次處理。
36. 作為專案維護者，我想要 emit 時同時參考 plate comment、disassembly 與 decompiled C 三源，這樣不會單獨採信 decompiler 的輸出。
37. 作為專案維護者，我想要每個 emit 完的 function 都經過獨立的 reviewer 驗證，且 reviewer 不信任 emitter 也不信任 decompiled C。
38. 作為專案維護者，我想要 reviewer 能看到 emitter 這一輪的精確改動，這樣審查範圍明確不會越界。
39. 作為專案維護者，我想要每個 function 完成後獨立 commit，這樣進度可中斷、可續跑、可回溯。
40. 作為專案維護者，我想要工作進度以逐 function 的狀態記錄追蹤，這樣重跑時會跳過已完成的部分。
41. 作為專案維護者，我想要 emit 出來的符號名與 Ghidra 中的名稱完全一致，這樣程式碼與 Ghidra 能互相對照。
42. 作為專案維護者，我想要 emit 的程式碼是 C89 且檔名符合 8.3 限制，這樣能被當年的工具鏈編譯。
43. 作為專案維護者，我想要每個 function 在 emit 時就對照前作記錄的八類實機 bug 檢查一遍，這樣隱性契約問題盡量在當下被擋掉而不是留到最後。
44. 作為專案維護者，我想要絕不接受半成品（改名、空殼、`_impl` 之類）也不為了讓測試通過而扭曲程式碼。
45. 作為專案維護者，我想要 emit 過程中發現的 Ghidra 描述錯誤當場修正並同步知識庫，這樣三者不會漂移。
46. 作為專案維護者，我想要無法當下確認的等價性疑慮被明確記錄下來，這樣它們不會被遺忘。

### Phase D：data emit

47. 作為專案維護者，我想要以連結器回報的未定義符號清單作為權威工作清單，這樣不會遺漏任何需要的資料符號。
48. 作為專案維護者，我想要全域資料的真實 byte 被還原成 C 的初始值，這樣重建版的資料與原版一致。
49. 作為專案維護者，我想要資料符號的判定同樣逐一進行，不用批次規則套用。
50. 作為專案維護者，我想要資料表的內容能與 Phase 0 建立的攻略基準真值交叉比對，這樣我有獨立的正確性依據。

### Phase E：連結與實機驗證

51. 作為專案維護者，我想要重建的程式碼能完整連結成可執行檔，這樣專案的核心目標達成。
52. 作為玩家，我想要重建的執行檔能直接取代原始執行檔遊玩，這樣我玩到的是原汁原味的遊戲內容。
53. 作為專案維護者，我想要在 DOSBox-X 中實際遊玩驗證完整流程，這樣功能等價得到最終確認。
54. 作為專案維護者，我想要實機遊玩發現的偏差能被定位到具體的 function，這樣修正有明確的著手點。

### 貫穿全程的基礎建設

55. 作為專案維護者，我想要 Ghidra 的分析成果定期匯出成純文字進版控，這樣「Ghidra 改了什麼」變成可 diff 的東西。
56. 作為專案維護者，我想要每次 commit 時程式碼、知識庫、Ghidra 快照、devlog 四者同時落地，這樣三者同步是可驗證的而不是口頭承諾。
57. 作為專案維護者，我想要知識庫只寫結論、不寫分析過程，這樣它保持可讀且不會變成流水帳。
58. 作為專案維護者，我想要另外有一個地方記錄完整的開發過程與失敗的嘗試，這樣三個月後回來能重建當時的判斷。
59. 作為專案維護者，我想要 devlog 特別記錄走過的死路，因為成功的路徑會沉澱進程式碼與知識庫，失敗的路徑是唯一會遺失的資訊。
60. 作為專案維護者，我想要知識庫的每次大量產出之後都排一輪對照基準真值的逐條驗證，這樣不會累積事實漂移。
61. 作為專案維護者，我想要所有工作過程中產生的待辦項目在工作結束前都被解決，只有真的無法處理的才進入未解決問題清單。
62. 作為未來的讀者，我想要知道每個重要決定的理由，這樣我不會「好心優化掉」一個刻意的設計。

## Implementation Decisions

### 整體

- 開工前先查前作 `fd2-anatomy` 有沒有現成成果，能沿用就沿用，只有確認沒有或不適用才自己造。做法與理由見 `CLAUDE.md`。
- 等價目標是功能等價，不是 byte-exact（ADR-0001）。
- 逐項判斷的工作（function 身分、calling convention、code emit、data 符號判定）一律一次處理一個，禁止批次或抽樣（ADR-0002）。
- 這些逐項工作一律由全自動 workflow 從頭跑完，每張票自己寫適合自己的 workflow，不抽共用骨架（ADR-0007）。
- 平行化在 Phase A 用腳本層的並行結構達成（每個並行單位仍只處理一個 function）；Phase C 改為序列，因為該階段的 reviewer 依賴版本控制的暫存狀態檢視改動，要求一次只有一個 function 在飛。
- Ghidra 的寫入競爭不需要驗證：判定階段的 agent 一律不寫 Ghidra，落地是單一序列的轉錄階段，競爭情境不會發生。

### 不需重新求證的既有結論

已定案的事實以知識庫為正典，spec 不複製一份：工具鏈版本與預設 calling convention 見 `rebuild_info/build_flags.md`，pool 規模與 Miles AIL 版本見 `program_info/code_pools.md`，CD 音源的重建邊界見 `program_info/cd_audio.md`，資源檔格式見 `resource_info/` 各檔。AIL 靜態庫沿用前作的理由見 ADR-0004。

兩件從前作繼承、知識庫尚無正典擁有者的事實：

- 存檔的加解密、checksum、slot 佈局、角色結構與前作同構，已用前作演算法對實際存檔驗證通過。
- 遊戲文字與字型都在外部檔案，執行檔內不含任何中文字串——不能靠中文字串定位遊戲邏輯。

### 需要建立的模組

- **攻略鏡像**：以遊戲代號參數化，把內容頁與其圖片抓成原文鏡像進版控，並提供字串搜尋入口。需處理 UTF-8 BOM、剝標籤時不位移等寬排版。不解析成結構化資料（ADR-0006）。
- **資源檔解析**：VFS 容器（含巢狀）、CEL 圖檔、SAF 動畫容器、調色盤與其他 VFS 內格式。
- **建置流程**：在 DOSBox-X 內驅動 Watcom 編譯與連結，自動掛載光碟，具備前置檢查與可靠的結束偵測。
- **Build gate**：SHA-256 比對與 LE fixup 感知的比對兩支工具（用法見 Testing Decisions 的 Seam 2）。
- **Ghidra 狀態匯出**：function 簽章、calling convention、pool 標記、plate comment、struct 與 enum 定義、label、global 命名。
- **Workflow 驅動腳本**：Phase A 的身分判定與 Phase C 的 emit/review/記帳迴圈。

### 可沿用前作的資產

方法論層面：知識庫四視角結構與索引規範、命名慣例、calling convention 判定規則、Easy OMF-386 格式陷阱、工具鏈陷阱、八類實機 bug 的檢查清單、編譯器版本判定方法論。

程式層面：LE fixup 感知的比對工具、SHA-256 gate、OMF record 編碼器、RLE sprite 解碼器、存檔編解碼、LE 檔抽取工具、建置腳本架構、AIL 靜態庫與其 ABI 契約。

## Testing Decisions

好的測試只驗證外部行為，不驗證實作細節。對這個專案而言，「外部行為」指的是 function 在給定輸入下的回傳值與記憶體寫入，以及解析器對已知檔案的解析結果——不是它內部怎麼算的。

### Seam 1：獨立的測試執行檔（最高的自動化 seam）

測試碼放在與生產程式碼分離的 translation unit，連結生產程式碼但不修改它（ADR-0003）。

涵蓋範圍是純機械計算的 function：傷害與命中公式、亂數產生器、RLE 解壓縮、checksum、存檔加解密、資料表索引運算、位元打包。涵蓋政策是風險導向——數值計算、複雜控制流分支、狀態轉移必須測；純繪圖副作用可延後。

期望值的來源優先序：攻略站提供的公式與數值 > Ghidra emulator 對純計算 function 取得的 ground truth > 手動從 assembly 推導。禁止用臆測值當期望值。

會讀取真實遊戲檔的測試必須讀真檔，禁止捏造結構假檔。

前作的測試組織方式（測試檔鏡像原始碼子檔、集中式測試註冊、建置接線自動產生、真實遊戲檔暫存到測試工作目錄）可直接沿用。

### Seam 2：Build gate

每次改動後重建，與本專案前一版的建置結果比對（ADR-0001）。純改名之類不改變行為的改動用 fixup 感知的比對，其餘用雜湊比對。要求零錯誤、零新增警告、全部測試通過。

### Seam 3：對前作驗證

資源檔解析器先跑前作的資源檔，比對前作知識庫已記錄的正確答案。這是免費的正確性檢查——parser 如果在有標準答案的資料上就錯了，在 FDPS 資料上的輸出也不可信。攻略鏡像同樣先跑前作站台，拿前作知識庫抽查，確認鏡像沒有失真。

### Seam 4：人工實機遊玩

整合行為的驗證由開發者在 DOSBox-X 中實際遊玩完成，安排在所有程式碼完成之後（ADR-0003）。

## Out of Scope

- **決定論 golden 測試系統**：不建虛擬時鐘、輸入注入、畫面與狀態檢查點對拍那一整套設施（ADR-0003）。
- **byte-identical 的重建**（ADR-0001）。
- **從 `FDPS.LE` 重抽 AIL vendor library**：除非直接沿用前作的庫實際連結失敗（ADR-0004）。
- **遊戲內容的修改或增強**：這個專案的產出在遊戲體驗上沒有任何新東西，玩到的是原本的遊戲。
- **中文文字與字型檔的處理**：遊戲文字在外部檔案，屬於資源檔解析範圍，不涉及翻譯或改寫。
- **前作 FD2 專案的任何修改**：它是唯讀的參考資料。
- **公開發佈的實作**：發佈是最後階段的事，前作的發佈流程到時候再沿用。目前維持單一本地版本庫，不加遠端。
- **光碟映像進版控**：體積不允許；只有內容清單進知識庫。

## Further Notes

### 規模參考

前作 FD2 專案的數字可作為估算基礎：2,338 個 commit、約 11 週、binary 內 1,342 個 function（其中 651 個需要 emit 成 C）、重建原始碼 64 個檔案 51,115 行、實機階段修掉 8 類 bug。FDPS 的 binary 稍大（362,469 vs 346,650 byte），function 數與各 pool 的規模見 `program_info/code_pools.md`。

### 已知的最大不確定性

1. **編譯器小版本**。10.0a 與 10.0b 尚無法區分，現有證據與缺口見 `rebuild_info/build_flags.md`。
2. **前作 AIL 靜態庫的覆蓋率**。ADR-0004 原列的兩處已由票 14.1 的函式庫比對收掉；剩下的不確定性是有 12 個 `ail` function 前作的庫裡沒有，連結階段要另外補（`program_info/code_pools.md`）。

### 流程層面的已知風險

- 並行工作若切分不當會產生協調落地債務——前作的教訓是共用輔助程式碼的叢集必須整包放在同一個分區。
- 知識庫會漂移。大量產出之後必須排一輪對照基準真值的逐條驗證，不能相信寫過就是對的。
- Windows 繁中環境下所有 JSON 與文字檔的讀寫都要顯式指定 UTF-8 編碼，否則會產生亂碼。
- 反組譯工具對含連字號的路徑會誤判成選項，需要把中繼檔複製到不含連字號的目錄。
