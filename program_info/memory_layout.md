# 記憶體佈局

**驗證對象**：`FDPS.LE` 的整個位址空間（`0x10000`–`0x70053`）與 LE 容器的 object table。位址空間的分段、權限、初始化邊界，以及「哪些區域是程式碼、哪些是資料」的結論以此檔為唯一正典。

## LE object table

執行檔是 DOS/4G 的 LE 模組，page size `0x1000`。載入後的三個 object 是位址空間的權威定義——權限與初始化邊界都以這張表為準，不以 Ghidra 匯入後的區塊屬性為準。

| object | 載入位址 | virtual size | flags | file-backed page 數 | 權限 |
| --- | --- | --- | --- | --- | --- |
| 1 | `0x10000` | `0x47c60` | `0x2045` | 72（`0x48000`） | `R-X` |
| 2 | `0x60000` | `0xc3c0` | `0x2043` | 4（`0x4000`） | `RW-` |
| 3 | `0x70000` | `0x54` | `0x2043` | 1（`0x1000`） | `RW-` |

三個 object 都帶 `BIG32`（`0x2000`）與 `PRELOAD`（`0x40`）。**object 1 不可寫**：程式碼與唯讀資料同在這個 object，跳躍表、具名 const 物件與區域陣列的初值影像都落在這裡；字串字面值與浮點常數則在 object 2。object 2 與 3 可寫但不可執行。

## object 2 的內部分段

object 2 就是 DGROUP，段序是 `CONST`、`CONST2`、`_DATA`、`_BSS`、`STACK`，堆疊固定在最後：

| 範圍 | 段 | 內容 |
| --- | --- | --- |
| `0x60000`–`0x6392f` | `CONST` + `CONST2` + `_DATA` | 初始化資料，14,640 byte |
| `0x63930`–`0x6a3bb` | `_BSS` | 27,276 byte，啟動時由 CRT 明確歸零 |
| `0x6a3bc`–`0x6a3bf` | — | 4 byte 對齊填充 |
| `0x6a3c0`–`0x6c3bf` | `STACK` | 8,192 byte |

`0x63930` 與 `0x6a3bc` 這兩個邊界不是推測的：CRT 啟動碼 `0x434cc` 把 `_end`（`0x6a3bc`）與 `_edata`（`0x63930`）當立即值載入，相減之後歸零這一段。

`STACK` 段不是純堆疊。初始 ESP 是 `0x6c3c0`（LE header），堆疊由上往下長；同一段的下緣則由 CRT 啟動時放命令列與環境變數的複本（`0x6a3c0` 起），近端堆積接在其後往上長，`0x60430` 存的界線值就是給堆疊檢查用的。

## 檔案內容與載入時補零的分界

object 的 page 數只涵蓋檔案裡實際存在的部分，virtual size 超出的尾巴由載入器補零。三個 object 裡只有 object 2 有這個尾巴，分界點是 `0x64000`：

- `0x60000`–`0x63fff`：檔案帶進來的 4 個 page。注意 `0x63930` 之後已經是 `_BSS`，這段在檔案裡是實際存在的零
- `0x64000`–`0x6c3bf`：33,728 byte 檔案裡不存在，包含 `_BSS` 的尾巴與整個 `STACK` 段

object 1 與 object 3 的 page 數都覆蓋了整個 virtual size，沒有這個尾巴。

## 位址空間各區的內容

| 範圍 | 內容 |
| --- | --- |
| `0x10000` 起 | 遊戲邏輯程式碼，夾雜遊戲自己的唯讀常數表與區域陣列初值影像 |
| `0x3c000` 之後 | 以 Watcom CRT、Miles AIL 音效庫、80x87 浮點模擬器為主，夾雜這些程式庫的唯讀常數表 |
| `0x60000`–`0x6392f` | 初始化資料：函式指標表、字串字面值、浮點常數 |
| `0x63930`–`0x6a3bb` | BSS：遊戲狀態、旗標、音效庫的執行期結構 |
| `0x6a3c0`–`0x6c3bf` | 堆疊、環境變數複本與近端堆積 |
| `0x70000`–`0x70053` | 低階輸入常式的狀態區。224 條指令取用它，全部落在 `0x56799`–`0x57c52`（含鍵盤中斷處理常式 `0x56837`）。它自成一個 object，代表它來自某個不屬於 DGROUP 也不屬於 CGROUP 的段 |

遊戲邏輯與程式庫的分界寫成「`0x3c000` 之後」是概略值——兩者在位址上並非乾淨切開，精確的歸屬由 pool 判定決定。

進入點是 `0x43298`，它是一個跳到 `0x43310` 的 thunk。

## 函式指標表

`.object2` 裡有四張章節／事件處理函式的指標表，全部以 `CALL dword ptr [reg + 表位址]` 的形式間接呼叫，程式碼裡沒有任何直接 `CALL` 指向表中的函式：

| 表位址 | entry 數 | 呼叫端 |
| --- | --- | --- |
| `0x60074` | 30 | `0x2a85e`、`0x31505` |
| `0x601c4` | 50 | `0x188d8`、`0x1dcae`、`0x2e140` |
| `0x6028c` | 30 | `0x12a48`、`0x12aff`、`0x12beb`、`0x1584e`、`0x1fb50` |
| `0x60304` | 30 | `0x293a1` |

80x87 模擬器在 `0x4e8e8` 起有連續 176 個 slot，但它不是一張表而是四段，各有自己的分派者與分派形式：`0x4e8e8`（24 項，`CALL`，`0x4ec86`）、`0x4e948`（24 項，`CALL`，`0x4ef6f`）、`0x4e9a8`（64 項，`JMP`，`0x4ecba`）、`0x4eaa8`（64 項，`JMP`，`0x4ed67`）。後兩段的 slot 多半指向大函式 `0x4ec3c` 內部的標籤而非任何 entry point。

## 未被辨識為程式碼的區域

`.object1` 內尚未反組譯的 byte 共 43,143，分成三類：

| 類別 | 範圍數 | byte 數 | 內容 |
| --- | --- | --- | --- |
| 對齊填充 | 205 | 745 | 函式之間的補位，由 `8d 80 00 00 00 00`／`8d 54 22 00`／`90`／`cc` 這類多 byte NOP 組成 |
| 被參照的資料 | 16 | 2,746 | 有 reference 指向的常數表與跳躍表資料。這些落在程式碼 object 裡是 flat 記憶體模型的正常結果，不是誤判，見 [`rebuild_info/build_flags.md`](../rebuild_info/build_flags.md) |
| 無參照 | 485 | 39,652 | 沒有任何 reference 的區塊 |

無參照的 39,652 byte 裡，7,096 byte 在遊戲邏輯區（`< 0x3c000`），其餘在程式庫區。抽樣檢視顯示這些區塊多數是完整的函式（`8d ..` 填充之後接 `53 56 57 55 89 e5 81 ec` 這組 Watcom prologue），少數是數值表；它們是連結器帶進來但呼叫圖走不到的程式碼。把它們逐一判定並建成 function 屬於後續的 orphan code 工作，不在基準盤點的範圍。

## 基準狀態的判定條件

`tools/ghidra_baseline/AuditGhidraBaseline.java` 逐項複查上述事實，並輸出兩個門檻值：

- **孤立程式碼 = 0**：沒有任何指令落在所有 function body 之外
- **error bookmark = 0**：沒有反組譯損壞

兩者目前都是 0。
