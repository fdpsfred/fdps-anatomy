# 2026-08-14 Ghidra 基準盤點與修復（票 10）

票上寫了兩件待釐清的事：重新自動分析後 function 數從 811 掉到 719、那 92 個差額去哪了；以及 12 個既有的錯誤標記。實際盤下去發現這兩件事只是同一個根因的兩個症狀，而且真正的差額比 92 大得多。

## 錯誤標記其實是 10 個，而且位址有規律

先數了一遍：`Bad Instruction` 類的 error bookmark 是 10 個不是 12（票上的數字是舊的）。列出來之後位址一眼就有規律——`217af`、`377ac`、`3a7ac`、`3b7aa`、`497ae`、`4f7ae`、`507ac`、`507c2`、`537ab`、`537b3`，衝突指令全部落在 `??7b0`。頁內偏移固定 `0x7b0`，跨了八個不同的 4KB 頁。

查符號表，那些位址上坐著 `LE_PAGE_22`、`LE_PAGE_44`、`LE_PAGE_47`……：Ghidra 的 LE loader 為每個 page 建了一個標記，而且**標記的位址是錯的**。`LE_PAGE_0` 會落在 `0xb7b0`，比 `.object1` 的起點 `0x10000` 還小——loader 拿檔案偏移當載入位址在放標記，於是 78 個標記平均散落在頁內偏移 `0x7b0` 的位置上。其中 34 個剛好落在某條指令的中間、37 個湊巧與指令對齊、5 個落在未反組譯區、1 個落在資料上。

真正咬人的是這些位址被反組譯了。反組譯從 `0x7b0` 這個錯誤的起點開始，往後解出一串垃圾指令，正確的指令流稍後流過來就撞上——這就是那 10 個 error bookmark。沒有撞上的位置（周圍本來就沒反組譯）連 bookmark 都不會有，但垃圾指令一樣在那裡：`3c7b0`、`3f7b0`、`417b0`、`447b0`、`4b7b0` 就是這種。合計 13 處損壞。

找過是什麼機制在那些位址下反組譯的：外部進入點只有 `_entry` 一個，`CodeMap` 這個 AddressSetPropertyMap 是 null，所以不是「標記為程式碼」的持久化屬性在作祟。結論是匯入當下一次性造成的，修完不會復發——後面重跑 auto-analysis 驗證確實沒有再出現。

修復逐處做：讀出原始 byte 手動對出正確的指令邊界（例如 `537ab` 那處實際上是 `cmp edx,-8000h` / `jl` / `xchg ah,al` / `xchg dl,dh` 的 16-bit 樣本 byte swap 迴圈），清掉錯開的指令，再從正確的起點重新反組譯。最後把 78 個 `LE_PAGE_*` 標記全部刪掉——它們的位址沒有任何分析價值，而且其中一個還把 `0x307b0` 的 function 名字搶去叫 `LE_PAGE_37`。

## 92 這個數字本身是錯的方向

差額的調查沒有從「哪 92 個不見了」下手——811 那個狀態已經不存在，沒得比對。改成問「現在有多少程式碼落在所有 function body 之外」，答案是 **190 個孤立區塊、31,503 byte**，遠超過 92 個 function 的量。

逐區塊讀下去，成因很單一：這些程式碼只被**函式指標表**指到，沒有任何直接 `CALL`。`.object2` 有四張表（`0x60074`／`0x601c4`／`0x6028c`／`0x60304`，共 140 個 entry），全部以 `CALL dword ptr [reg + 表位址]` 呼叫；`0x4e8e8` 的 176 個 entry 是 80x87 模擬器的 handler 表；`0x5289c` 起一整排是音效庫的取樣格式轉換常式。Ghidra 的自動分析會為直接 `CALL` 的目標建 function，但不會為指標表的目標建——所以同一個 binary 重跑一次分析，function 數本來就會比曾經建過 function 的狀態少。「92」只是某一次重跑掉了多少，不是一個有意義的量。

程式碼一個 byte 都沒少：對照 commit 裡的舊快照，719 個 function 的位址在最終狀態裡一個不缺。

## 讀了 180 個區塊才動手

判定「這個位址是不是 function 進入點」屬於 ADR-0002 管的範圍，不能靠規則批次套。做法是把 180 個孤立區塊的完整反組譯（含每條指令的 incoming reference）匯出成一個 10,306 行的檔案，逐區塊讀過去。

讀完之後的分類：

- 章節／事件處理函式：Watcom 的 `53 56 57 55 89 e5` prologue、`5d 5f 5e 5b c3` epilogue，指標表 entry 一個蘿蔔一個坑——是 function
- switch 的 case 區塊：沒有 prologue，結尾是 `JMP` 回共用尾巴——不是 function，要靠修 function body 收進去
- 80x87 模擬器的 opcode handler：由 `JMP [表]` 分派、結尾 `JMP` 回模擬器核心——不是 function

有幾個區塊裡藏了不只一個 function（相鄰的兩個 function 中間沒有空隙就會被併成同一個區塊），例如 `378a0`／`378f0`、`38e60`／`38fd0`、`39840`／`398c0`；也有區塊的起點比真正的進入點晚一個 byte——`20e91` 是 `push esi`，前一個 byte `20e90` 的 `push ebx` 沒被反組譯，而 epilogue 有 `pop ebx`。這種錯位靠掃描規則抓不出來，只能讀。

## 分不清的地方：RET 不代表是 function

寫了個分類器輔助，判斷每個候選區塊的流程是不是以 `RET` 結束。第一版把 x87 模擬器的 handler 全判成 function，追下去才發現 Ghidra 把 `JMP 0x4ec3c` 的 flow type 標成 `CALL_TERMINATOR`（尾呼叫），`isTerminal()` 對它回 true。分類器看到的「有 RET」其實是「有尾呼叫」。

第二版改成把流程限制在候選區塊自己的範圍內，跳出範圍就記成 exit，這樣才把 19 個 tail-jump 的 case 區塊與 4 個 `JMP [ebp+0x76]` 間接尾跳的 handler 分出來。

即使如此仍有三個漏網的：`2faa0`、`475da`、`478b2` 是 case 區塊，但它們是 fall-through 進共用尾巴而不是 `JMP`，分類器看不出差別，被誤建成 function。發現的方式是回頭把每張跳躍表的 entry 逐一對照「這個位址現在是不是 function」——是就代表判錯了。刪掉這三個之後，再檢查一次「進入點只有 JMP 型 reference」的 function，剩下 4 個都是合理的 thunk 目標。

同一輪還揪出兩個名字就是證據的誤判：Ghidra 早先自己建的 `caseD_0` / `caseD_40`，以及一個叫 `default` 的 function——後者坐在 `0x2fb38`，正是那八個 case 匯流的共用結尾。名字裡帶 `caseD` / `default` 的 function 幾乎一定是判錯的。

## 資料被當成程式碼的那一處

`0x50d82` 有 65 byte 被反組譯成 `DEC ESI` / `SBB DH,AH` / `LDS EBP,...` 這種完全不成句的東西。找到唯一的參照是 `0x50f9a` 的 `LEA EDX,[0x50d82]` 配 `MOV EBX,0x8`——是把表位址與長度傳給一個常式。清掉重新當成 10 byte 的 `float10` 定義，出來的值是 `0.0443895157`、`-0.0648319351`、`0.0767936869`、…、`-0.3333333333`、`1.0`：反正切的多項式係數表，9 個不是 8 個（`EBX=8` 是別的意思）。這是票上「誤判的資料被正確排除」的唯一實例。

一個小坑：`createData` 建 9 元素的 `Float10` array 一直回報 `Conflicting instruction exists at 00050ddc`，位址正好是陣列結尾的下一個 byte。沒去追是不是邊界計算的差一，改成逐個建 9 筆 `float10` 就過了。

## 權限錯了，而且錯得有後果

順手查記憶體區塊屬性，三個 block 全是 `r--`——**程式碼區沒有執行權限**。去 LE header 把 object table 解出來對答案：object 1 flags `0x2045` = `R-X`、object 2 與 3 是 `0x2043` = `RW-`。Ghidra 的 loader 把三個都設成唯讀了。修正之後 `.object1` 是 `r-x`、另外兩個是 `rw-`。

同一張表還順便回答了票上「資料段與未初始化段的精確分界」：object 的 page 數只涵蓋檔案裡真的存在的部分。object 2 的 virtual size 是 `0xc3c0` 但只有 4 個 page，所以 `0x60000`–`0x63fff` 是檔案內容、`0x64000`–`0x6c3bf` 是 BSS。實際讀過那 33,728 個 byte 確認全是 0，`0x63f00`–`0x63fff` 也全是 0（所以不能靠「開始出現連續零」去猜分界，只能看 page 數）。這條進了 pitfalls：照 Ghidra 顯示的零值 emit 成初始化陣列會多塞 33KB 進映像檔。

沒有把 `.object2` 拆成兩個 block。拆了會讓分界在快照裡更顯眼，但把 BSS 段改成 uninitialized 會丟掉現有的 byte 值、也可能動到已定義的資料，代價大於收益，改成寫進知識庫。

## 收尾

修完之後孤立程式碼從 190 個區塊降到 7 個，剩下的都是「函式進入點本身沒被反組譯」造成的。往回找進入點：`2f6d0`、`2f410`、`3c6f9`、`3c7aa`、`47490`、`474b0`、`47500`、`47520`、`47540`、`47560`、`47580`、`475b0`、`47650`、`476e0`、`47740`、`47884`、`49790` 共 17 個，全部是前一個 function 的 `ret` 之後接 `8d 80 00 00 00 00` 這類對齊填充，再接 prologue。建完之後 `0x2f6d0` 的 body 是 `[2f6d0,2f6dd][2f700,2fb76]`——跳躍表夾在函式自己的程式碼中間，body 因此是不連續的兩段。

跳躍表的 case 區塊靠替分派指令補 `COMPUTED_JUMP` reference、再重算 function body 收進去。這裡踩了一次位址錯誤：`475c3` 是指令中間，reference 加上去不會報錯但 body 重算不吃，改成 `475c4` 才對。

最後兩個區塊 `4ed70`／`4edac` 是模擬器的捨入模式續行區塊，位址被 `lea edx,[...]` + `mov DS:[ebp+0x76],edx` 存起來、由別處的 `JMP DS:[EBP+0x76]` 跳進來。這種「位址被取走的續行區塊」建成 function 與留成孤立各有道理，選了建成 function，理由是「孤立程式碼 = 0」是個能自動複查的門檻，而模擬器內部的模型後續還要重新整理。

終局：719 → 1,042 個 function，孤立程式碼 0 byte，error bookmark 0 個，全部 function 仍是 `__watcall` / `ANALYSIS` 的預設值（calling convention 的逐一判定是票 15）。

沒有做完的是無參照的 39,652 byte——抽樣看下來多數是完整的函式，但呼叫圖走不到。spec 的 story 24 就是這件事，留在那裡做，這裡只把清單與分類寫進知識庫。
