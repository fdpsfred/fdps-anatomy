# 2026-08-30 emit t22-02：票 22 的第二批五支

票 22 是遊戲自身 function 的 emit。這批 t22-02 排了 5 支，5 支全部落地，沒有跳過、沒有中途停、沒有拆檔、沒有任何一支跑到第二輪。開跑時待處理 471 支。

流程跟 t22-01 一樣：每支走 emitter（三來源，產出 C 與測試）→ 獨立 reviewer（從 assembly 與 working tree 的 diff 看）→ fix loop → 對 `src/` 與 `tests/` 跑 build gate → 自己一個 commit。序列跑，因為 reviewer 認定「這一輪改了什麼」的依據就是 working tree 本身。順序 callee 先於 caller，讓 function 對著真的 callee 測而不是對著產生出來的 stub 測；建置連結兩次，讓票 23 還沒 emit 的資料以零填補頂上而不遮住任何東西。

五支是 `fdps_build_scene_layer_draw_order` @ 0002c220、`fdps_unit_select_status_icon` @ 0002ccd0、`fdps_get_unit_record` @ 0002d210、`fdps_unit_is_retired` @ 000109b0、`fdps_move_path_trace` @ 00011460。callee-before-caller 在這批看得特別清楚：0002d210 是純 accessor，000109b0 只是它加一次遮罩，00011460 則同時呼叫 0002d210 三次——後兩支因此都是對真的 accessor 測，不是對 stub 測。

`recovered` 是空的，上一輪不是被砍掉的，這批沒有丟棄任何人的半成品。gate 沒有擋下任何一支。emit 階段一筆等價性疑慮都沒記（`concerns_logged` 0），兩份 verdict 的 `open_issues` 五支全空，所以 `emit_issues.json` 這批一個 key 都沒新增，維持 30 筆。

沒有 fix round 不代表沒有代價。這批的成本全部落在**把已核可的 `ghidra_fixes` 套進 Ghidra 的那個階段**，下面三節都是那裡的事。

## 修正指示裡的出現次數兩次都不對

0002c220 的 review 寫「replace the four occurrences of DAT_00069cdc and the three of DAT_00069cfe」。實際 plate 裡 `DAT_00069cdc` 出現 5 次（Algorithm 段 4 次＋Pool 行 1 次）、`DAT_00069cfe` 出現 4 次（Algorithm 段 2 次＋Pool 行 1 次＋Rebuild note 1 次）。0002ccd0 也一樣：emitter 說 `FUN_0002cda0` 出現四處，reviewer 自己數是三處（unit_index 說明、cycle 說明、Returns 段），實際是三處。

兩次的處理方式相同，也是對的：**把數字讀成敘述而不是待驗證的斷言，照指示句子裡的「全部」執行，不去調整決定來遷就數字。** 0002c220 那輪把兩個符號的所有出現處都換掉（因為 what 欄自己寫了 "body text and the Pool line both"），0002ccd0 那輪把三處都換掉並記為一次套用。

值得寫下來是因為這件事會誘發一個很花時間的錯誤反應：發現數字對不上，於是懷疑指示、去比對是不是自己看的 plate 版本不同、或者只改到數字所說的那幾處而留下一處沒改。`ghidra_fixes` 的 `what` 欄是自然語言，計數是寫的人順手數的，不是契約。契約是那句「換掉這個符號」。

## 一則「替換這段文字」的修正差點留下一句斷句

00011460 的 review 要求把 mode 2 的側別子句改寫（因為原本的措辭把過濾方向寫反了：實際上 `start_x == 0` 保留 side 非零的單位）。指示是把 A 段文字換成 B 段文字，但 B 段在句子中間結束，而原文在 A 段之後還接著 "and whose record byte +0x05 bit 0 is clear"。直接替換的結果是那條尾巴改為黏在新插入的 side byte 子句上，語意會變成「side byte 那個 byte 的 bit 0 要是 0」——跟原意（單位的 +0x05 bit 0 要是 0）不同。

處理是在插入文字尾端補一個 " -- " 讓尾巴仍然接回 "keeps only units whose ..."，只動標點、兩段文字一個字都沒改。這是**只給替換片段、不給周邊上下文的修正指示，在套用時會自己長出來的風險**：片段本身正確，接縫不正確。下一批遇到 `kind: "plate"` 而 `what` 是「把 X 換成 Y」時，套用前要把 Y 前後各一句一起讀過。

同一支還留下一處沒有人負責的不一致：prototype 被改成 `uchar mode`（reviewer 的第三筆修正，理由是那個參數只以 byte 被零延伸讀取，`XOR EAX,EAX` / `MOV AL,[EBP+0x28]`），但 plate 自己的 "Signature:" 行仍寫 `int mode`，而沒有任何一筆修正要求動它。套用的 agent 選擇標記而不是自行決定，這是對的——但意思是 database 的 prototype 與同一支的 plate 現在對這個參數的說法不同，需要有人補一刀。它沒有進 `emit_issues.json`（兩份 verdict 的 open_issues 都是空的），只在這批的 run report 裡。

## 這批解出來、下一批不知道會很貴的三件事

**00011460 的接受門檻是「起點格」的成本，不是當前格的。** `[EBP-0x28]` 全函式只被寫一次（00011600），而 00011631 在每一步的開頭都拿它重新種 `[EBP-0x20]`。也就是說每一步的候選鄰居要比**起點**便宜才會被接受，不是比腳下這格便宜。照直覺寫成「從當前格重新種」的話，走到某些格之後所有鄰居都不合格，do-while 的唯一出口是「抵達目標」，於是迴圈永遠不結束。reviewer 為此寫了一個會分辨兩種寫法的測試（東向成本 5,2,3：第二步站在 2 上、唯一候選是 3，比腳下貴、比起點便宜，原版會走，當前格版本走不動）。這件事已經以 Rebuild note 的形式進了 plate。

**00011460 的 mode 2 對同一個 index 呼叫 `fdps_get_unit_record` 兩次。** 第一次的回傳拿去讀 side 與座標，第二次（0001151b）的回傳只用來讀 flags byte。合併成一次會刪掉原版真的做了的一次呼叫，改呼叫 `fdps_unit_is_retired` 則會多一次——兩種「整理」都會偏離。emit 照原樣保留兩次呼叫。

**0002d210 回傳的指標活不過 `fdps_relocate_unit_array`。** 那支會重配陣列、memset 舊區塊再 free 掉，所以 battle turn 迴圈裡的呼叫端必須重新呼叫這個 accessor，不能把上一次的結果留著用。這個 lifetime 事實這批寫進了 0002d210 的 plate。同一段修正還換掉了 plate 裡「16 static callers / 228 references」這個數字——`get_function_callers` 回一整頁 100 筆而且還卡在它自己的查詢上限，也就是原本的數字至少短了六倍，而且讀起來像是做過完整普查。**MCP 查詢的上限會偽裝成事實**，寫進 plate 的計數如果來自一次查詢，要寫清楚那是不是達到上限。

## 一個沒有人該去追的體積差

0002c220 的 reviewer 自己用 `WDISASM.EXE` 反組譯了建出來的 `MAPDRAW.OBJ`（沒有採信 emitter 的說法），指令逐條對得上，但重建版比原版短 12 byte。算出來的組成是：原版在三個 increment block 的開頭各有一條 dead `MOV EAX,[EBP-...]`（3 byte × 3），而且正因為那三條在，0002c316 那條回跳的距離變成 0x84、短跳編碼放不下，多花 3 byte 變成近跳。同樣的 dead-load-before-INC 也出現在 caller 0002bf8d 與 00022800，所以那是**原版建置的性質，不是原始碼寫法的差異**。0002d210 也有類似的東西：重建版多一對 spill（`sub esp,8` 與兩組存取），原版只有一對。兩者都是 frame 配置與暫存器配置，ADR-0001 明確劃在標準之外。追這種差額去改 C 的寫法是在追原版的措辭，不是在追等價。
