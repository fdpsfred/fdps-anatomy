# 票 25.9 的驗證工具：workflow 寫好了，但這個 session 跑不起來

票 25.9 要把刪減調查的 53 條發現逐條獨立驗證。依 CLAUDE.md 與 ADR-0007，這是逐項判定的工作，必須由 Workflow 工具一條一個 agent 跑完。這次接手的 agent 是被派來平行處理 25.9 的子 agent，開工前先照規矩確認工具：`ToolSearch "select:Workflow"` 查無此工具，deferred 工具清單裡也沒有。派工指示明講「沒有 Workflow 工具就不要改用批次處理繞過，停下來回報」，所以這一段只做了不需要判斷的部分——把 workflow 與它的記帳工具寫好、測好——判定本身一條都沒有做。

曾經想過的替代路線是自己用 Agent 工具一條一條派出去。它表面上也是「一次呼叫一條」，但清單就放在派工者的 context 裡、由派工者逐一分派，正是 CLAUDE.md 說的「結構性強制」要排除的形狀，而且 ADR-0007 要的錯誤處理（整輪全滅停止、續跑）也會變成靠派工者自律。放棄。

## 形狀從哪裡來

先查前作。`fd2-anatomy/tools/` 裡名字沾得上邊的只有 `kb_overhaul`（章節表產生器）與 `rsrc_unresolved`（資源死碼的一次性驗證腳本），都不是逐條判定的 workflow，沒有可沿用的東西。本專案裡形狀最接近的是票 16 的 `tools/crt_version/`：固定清單、判定寫檔、`pending.py` 從判定檔推導待辦、`rescan_list.py` 從判定檔推導回掃清單。照這個形狀寫，但把它的四支小腳本收成一支 `cutverify.py` 的五個子命令，因為這張票的清單只有 53 條，不值得拆那麼細。

## 幾個當下做的決定

**主張不複製進腳本，從票檔讀。** 一開始打算把 53 條主張原文貼進 workflow 腳本，讓腳本自足；但主張裡滿是反引號，塞進 JS template literal 要逐一跳脫，而且兩份文字早晚會分岔。改成 `cutverify.py` 直接切票檔的「發現清單」一節，只看結構（粗體編號開頭的頂層條目、`###` 節名裡的「轉錄到 25.x」），內文完全不解讀。記憶裡「不要對人寫的內容做 parser」的規則管的是解讀語意的規則式解析，這裡只切 Markdown 條目的邊界，不算。workflow 腳本自己仍保有 ID 清單，Plan 段比對兩邊，不一致就停——清單「只存在於 workflow 腳本中」這條沒有被打破，腳本只是沒有自帶主張全文。

副作用是判定要綁住它判的是哪一版措辭：判定檔記主張文字的 SHA-1，清單措辭一改就 stale。這對應 ADR-0007 5.7「判定檔要記下它涵蓋的範圍」——票 14 吃過「範圍變了但開頭位址沒變、舊判定永遠被跳過」的虧。

**「否定性結論」自成一類。** 票面列的分類是五類（殘留內容、空殼、被封住的內容、前作遺留、排除），但清單有五條（C13、C15、U10、B6、S13）是「某物不存在」的主張，沒有痕跡可以分類。硬塞進「排除」會讓 25.10 分不出「這是真的痕跡但不算刪減」和「這裡什麼都沒有」。另設 `negative`。

**gate 擋的是「只憑調查產出下判定」。** 票面最擔心的是 agent 把調查腳本的輸出直接當結論。gate 因此要求至少一條一手證據，且格式要帶得回原處：`src` 要 `檔名:行號`、`ghidra` 要位址、`data` 要 `檔名@偏移`。「SHOP25.DAT」這種只有檔名的寫法會因為檔名本身有數字而騙過「含數字」的檢查，所以 data 改成要求 `@`。

**判定檔的文字欄位用繁體中文。** 以往各票的判定檔是英文，因為它們要轉錄進 Ghidra 的 plate comment。這張票的下游是知識庫，英文判定到了 25.10–25.14 還要再翻一次，專有名詞會在翻譯中走樣。列舉值與欄位名仍是英文。

## 沒驗到的地方

這台機器沒有 node，也沒有任何 JS 解析器，workflow 腳本無法在這裡做語法檢查，只能人工逐段讀過。第一次真正啟動 Workflow 時若有語法錯誤，會在啟動當下報出來，不會跑到一半才壞。`cutverify.py` 有 14 個單元測試，包含對真實票檔切出 53 條、各子票條數 16／10／8／6／13 的檢查。
