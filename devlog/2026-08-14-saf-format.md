# SAF 動畫格式逆向（票 06）

522 個檔、佔資源總量一大半的 `.SAF`，前作完全沒有對應物，票上寫的是「從零逆向，必要時對照 Ghidra」。實際走下來順序是反過來的：先從檔案本身把結構猜出來，再拿 Ghidra 去驗，而且驗的時候幾乎每一項都對上了。

## 從最小的檔開始

第一步是找最小的檔案下手。`MISC.VFS` 裡有一批 66 byte 的 `EE05.SAF`、`ME03.SAF`，還有 990 byte 的 `POSEFF.SAF`。66 byte 的那個幾乎全是 0，正好把「哪些欄位有值」襯出來：

```
0000  53 41 46 06 00 34 00 18 00 18 00 00 01 00 34 00
```

`SAF` 之後照 `.CEL` 的慣例往下讀，`0x03` 的 `u16` 是 6、`0x05` 的 `u16` 是 52、`0x07` 與 `0x09` 是 24 和 24。`.CEL` 的 `0x05` 也是「偏移表的位置」而且恆等於 header 大小，所以這裡 52 是 header 大小這件事幾乎是白送的。

麻煩的是 `0x0B` 之後那 40 個 byte。一開始我把它讀成連續的 `u32`，結果 `POSEFF.SAF` 的 `0x16` 位置怎麼切都不對——`07 00 1b 01 00 00` 當成 `u32` 是 `0x011b0007`，是個沒有意義的數。改成 `u16` 之後 7 和 283 兩個數都合理，才發現對齊點在 `0x0C` 而不是 `0x0E`，欄位是 `u16` 加兩個 `u32` 的 10 byte 一組。40 除以 10 剛好四組，`POSEFF` 的四組起點是 52、283、353、990，而 990 就是檔案大小——四個 section 首尾相接、最後一個收在檔尾。

拿這個假設掃 525 個檔，全過。這是整件事的轉捩點：從這裡開始不再是猜，而是每個假設都能用 525 個檔當測試集。

## 四個 section 分別是什麼

section 內部的形狀（`count` 個 `u32` 偏移加緊接的項目）一眼就看出來，難的是每個 section 裝什麼。

- section 2 最好認：`BACK00.SAF` 有 70 項、20 KB，直接拿 `cel_decode` 的 4-op RLE 解碼器套 24×24 去跑，229,238 個 tile 一次全過，一個都沒錯。這種通過率不可能是巧合。
- section 1 的第一個項目是 `0e 00 05 00` 後面接 `0000 0001 0002 ...` 一路到 `0045`——14 乘 5 等於 70，正好是 section 2 的項目數。tilemap 的假設（`4 + 2 × 欄 × 列`）掃全部 7,967 項也是全過。
- section 3 卡了一下。開頭 `01 08 11 2b`，`0x2b11` 是 11025，看到這個數就知道是音訊了；`01` 和 `08` 是聲道與位元數，後面 `u32` 是長度，資料本身在 0x7f/0x80 附近震盪，是無號 8-bit PCM。608 段全部對上。
- section 0 是最後解的。10 byte 的固定頭加 `k` 個 13 byte，8,335 項全過。但欄位語意光看檔案猜不出來：`0xFFFF`、1、2、3 這些值可以是任何東西。

## 這時才進 Ghidra

從 `EasyAni.Saf` 這個字串往上追是條死路——它落在 `FUN_0001ef40`，那是個把 SAF 當黑箱用的呼叫端，反編譯出來一堆 `extraout_ECX`，看不出它讀了檔案的什麼。

改成從結構本身找：section 的表偏移在 `0x0E`、`0x18`、`0x22`、`0x2C`，要取用項目就一定得做 `saf + *(u32 *)(saf + 這幾個偏移之一)`。用 `search_instructions` 掃 `+ 0x2a]`（section 3 的項目數）只有一個結果，`FUN_000142d0`；掃 `+ 0x22]` 也只有一個，`FUN_00013ed0`。這條路一次就到位，七個函式全部找齊：

| 位址 | 是什麼 |
| --- | --- |
| `0x144e0` | 畫格數 |
| `0x140e0` | 取第 i 格 |
| `0x14550` | 推進一個 tick |
| `0x14140` | 畫一格 |
| `0x13fd0` | 畫一個 layer |
| `0x13ed0` | 畫一個格子 |
| `0x142d0` | 播一段音效 |

`0x142d0` 把 section 3 的欄位一個一個餵給 AIL：型別、`item + 8` 的資料位址、`[item+4]` 的長度、`[item+2]` 的取樣率。猜的全對。`0x13fd0` 讀 `[saf+7]` 和 `[saf+9]` 當每格的步進，外層跑列、內層跑欄，跟 tilemap 的假設一模一樣。`0x13ed0` 把 tile 的串流交給 `0x568db`——就是 `.CEL` 那個繪製器，所以像素編碼相同不是形似，是同一段程式。

section 0 的欄位語意也在這裡收斂：`0x14140` 用 `MOVSX` 讀 frame 的第一個 `u16` 當音效編號（所以 `0xFFFF` 是 −1「不發音」而不是某種旗標），`0x14550` 拿 `+2` 跟 tick 計數比，是停留時間。`+4` 和 `+5` 這兩個 byte 播放器完全不看，是翻到 `0x196d0`（攻擊演出）才看出用途：它先數過全部畫格有幾格 `+5` 非 0，再把目標血條分攤在這些格上扣掉，同時播命中音——這是「命中標記」。

## 一個意外的發現

`0x144e0` 的 magic 檢查編出來是這樣：

```
if (p[0] == 'S') goto ok;
if (p[1] == 'A') goto ok;
if (p[2] == 'F') goto ok;
return 0;
```

三個條件是 OR。原始碼多半是想寫 `&&` 卻寫成了 `||`。實際效果是只要三個 byte 裡有任何一個對上就放行，等於沒有檢查。`0x14550` 裡有一份一模一樣的複製。這種東西重建時很容易「順手修好」，然後行為就跟原版不同了，所以寫進知識庫。

## 決定不做的事

- **動畫 GIF**。「可視的連續畫格」用 filmstrip PNG（一格一張 320×200，排成格狀）就滿足了，寫個 LZW 編碼器換一點點可看性不划算。
- **`dump` 全量跑**。算圖是逐像素的純 Python，全部 525 個檔要跑很久，而且產物大得沒道理。所以拆成 `verify`（全量、不算圖、二十秒）和 `dump`（抽樣、算圖）兩個命令。
- **在 Ghidra 裡把這七個函式命名**。這是票 10 的範圍，這次一個 byte 都沒動 Ghidra，快照自然沒有 diff。
- **證明四個 section 大小欄位「全程式都沒人讀」**。掃 `+ 0x12]` 和 `+ 0x26]` 兩個偏移確認沒有落在這七個函式裡，但 `+ 0x30]` 這種偏移在 `EBP` 相對定址的區域雜訊太大，掃不乾淨。最後的說法收斂成「這七個函式不讀」，而不是更強的全程式宣告——這七個是唯一能走到 section 表的入口，這個範圍已經夠。

## 複審抓到的自打嘴巴

「掃不乾淨所以把說法收斂成七個函式」這個決定寫在上面，結果知識庫初稿還是寫成了「程式一律不讀」。更糟的是同一份文件前面才剛寫「`0x196d0` 讀 frame 的 `0x05`、`0x18d60` 讀 `0x04`」——這兩個函式都不在那七個裡面，等於自己打自己。複審一眼就看出來。

根因是「只有七個函式能走到 section 表」和「只有七個函式碰 `.SAF`」兩句話長得太像，寫的時候滑過去了。改法是把前提直接寫在句子裡（只能靠 `saf + *(u32 *)(saf + 0x0E/0x18/0x22/0x2C)` 走到，全程式只有七個地方做這個動作），再補一段說明另外兩個呼叫端是怎麼拿到 frame 位址的。

同一輪複審還抓到 tilemap 的格子編號型別寫錯：`0x13fd0` 是用 `short *` 取值、`0x13ed0` 用 `-1 < index` 擋下界，所以那是 `i16` 不是 `u16`。而 layer 的 tilemap 編號是零延伸的，真的是 `u16`。兩個看起來一樣的「索引」型別不同，現在的檔案裡最多才 3,487 個 tile，兩種讀法沒有差別，但這種東西照抄進 C 就會變成 bug。解析器跟著改成 `i16` 加 `0 <= tile < count` 的下界檢查，525 個檔重跑一次全過。

## 驗證

`BACK00.SAF` 算出來是一張正確的戰鬥背景石台，`ACT000.SAF` 十四格是完整的揮劍加火焰軌跡，`EXPLO.SAF` 是爆炸的擴散與消散，`GAMEOVER.SAF` 三十二格是「GAME OVER」由小放大的演出。四個都一眼就對。

`ICON0000.SAF` 一度看起來不對：`FDE.PAL` 算出來是幾道死白的細線，換 `FIGHT.PAL` 只是從白變成淡紅，一樣看不出是什麼。本來以為是調色盤挑錯，去數了一下它用到的索引才知道不是——整個檔只用 11 個索引，除了 128 之外全部擠在 209–215，而這段在兩個調色盤裡都是一條完整的漸層（`FIGHT.PAL` 是粉紅到紅、`FDE.PAL` 是藍）。也就是說這個特效本來就是幾道淡色細線加幾顆火花，不是解碼錯也不是調色盤錯。

這個彎路的教訓是：算出來「看起來很淡」不構成證據，要嘛去數索引，要嘛找一個顏色飽滿的檔來看。`ACT000` 和 `GAMEOVER` 那種滿版的才是有效的驗證對象。
