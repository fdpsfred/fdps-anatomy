# 2026-08-15 call graph 建立

票 12 的第一段。目標是把呼叫圖建出來讓叢集結構可見，供後續的骨幹走查與分區使用。

## 先估工作量

動手前先用 `run_script_inline` 打了幾支一次性腳本量規模，因為票 12 的驗收條件裡「骨幹路徑逐一走過」是逐 function 判定，代價完全取決於骨幹有多長。

第一支只收直接 `CALL` 邊，結果是 3,156 條邊、325 個沒有 caller 的 root，而且**從 entry point `0x43298` 只走得到 1 個 function**。這個數字明顯不對。查了 `0x43298` 的反組譯才發現它是 `JMP 0x43310` 的 thunk——Ghidra 不會為 `JMP` 建 call 邊，所以 BFS 在第一步就斷了。加上 `JUMP` 型參照重跑，可達數變成 647、最大深度 14。

接著把票 10 記在 `memory_layout.md` 的四張章節指標表與 80x87 表的位址硬寫進腳本補間接邊，可達數推到 855，剩 187 個走不到。這時候才確定：呼叫圖本身很便宜，貴的是骨幹走查，而且指標表的處理是可達性能不能收斂的關鍵。

## 指標表偵測踩到的兩個坑

正式腳本 `BuildCallGraph.java` 一開始用最直覺的判準掃表：連續的 dword、每個都**等於某個 function 的 entry point**。掃出 21 段，但兩處明顯錯：

**第一個坑是 80x87 模擬器表在第 49 項被截斷。** 文件記載 176 項，腳本只認到 49。把 slot 值逐一印出來才看懂——第 49 項之後的值指向的是 `0x4ec3c` 這個大 function **內部**的標籤，不是任何 entry point。模擬器是一大坨程式碼，Ghidra 把它切成幾個 function，opcode handler 大多是中段標籤。判準改成「指進某個 function 的 body」之後就完整了。

**第二個坑是三張章節表被併成一段。** `0x601c4`、`0x6028c`、`0x60304` 在記憶體裡連續，run-based 偵測看到的是一段 110 個 slot 的連續指標。想過用「切在下一張表的基底」來拆，但擔心 80x87 表那種「同一張表被兩個偏移取用」的情形會被切壞。實際印出來看，`0x4e8e8` 那段的四個被參照基底是 `0x4e8e8`／`0x4e948`／`0x4e9a8`／`0x4eaa8`，切出來剛好 24+24+64+64=176，一格不差；章節表切出來是 50+30+30，與文件完全一致。所以「view 從自己的基底延伸到下一個基底」這個規則對兩種情形都對，而且各 view 恰好把 run 切完，不會有 slot 沒人認領——這點很重要，否則被漏掉的 slot 目標會假裝成孤島。

## jump table 與 pointer table 的分類換過兩次判準

第一版判準是「所有目標都回到分派者自己 → jump table」。結果 `0x5000c` 被判成 pointer table，但文件明明記它是跳躍表。查下去發現它的目標分散在 `0x4ec3c` 與 `0x4f770` 兩個 function——模擬器裡 Ghidra 的 function 邊界本來就是硬切的，一張 switch 表的 label 跨過邊界很正常。

第二版改成「有沒有 slot 剛好落在 entry point 上」。`0x5000c` 還是判成 pointer，因為 `0x4f770` 真的被 Ghidra 建成了 function，表裡就有它的 entry point。

最後放棄從目標形狀反推，直接記**分派指令是 `CALL` 還是 `JMP`**——這才是文件分類的真正依據，也是唯一不需要推測的事實。目標形狀改成另一欄 `exact` 純粹當佐證。換完之後 6 張文件記載的跳躍表全部判成 `JMP`、4 張章節表全部判成 `CALL`，與文件零偏差。

順帶多找出 6 張文件沒記的跳躍表（`0x31328`、`0x35948`、`0x35b84`、`0x35dac`、`0x360b8`、`0x362f8`），全在遊戲邏輯區。

## 沒有分派者的 17 段

`0x5289c`–`0x52bf4` 有 17 段連續指標、118 個 slot，指向 `0x52c79`–`0x544c0` 的 118 個 function。用 `get_xrefs_to` 查基底，**一個 cross-reference 都沒有**。基底是執行期算出來的，靜態上歸不到任何呼叫端，所以這 118 個 function 全部進了不可達集合，也是 150 個孤島裡佔比最大的一塊。

一度想放寬條件、把「任何指令參照」都算成分派者好把它們接上，但那只會製造假邊——沒有參照就是沒有參照。改成在報告裡整段列出來，交給後面讀那個區域的人解。這是刻意不解決而不是漏掉。

## 收尾

`analyze_graph.py` 第一版的孤島表只印前 40 個，尾巴寫「其餘省略」還指向一個不存在的檔案。這正好踩到「不可默默截斷」，補了 `islands.json` 把 150 個分量含單點全部寫出來。

最終數字：1,042 個 function、3,167 條直接邊、411 條表分派邊、從 entry point 可達 790、不可達 252、150 個孤島、75 個 fan-in ≥ 8 的共用 helper、5 個遞迴環。

BFS 分層看下來骨幹非常清楚：`0x43298`（thunk）→ `0x43310`（538 byte，CRT 啟動）→ `0x4df4c` → `0x29220`。`0x29220` 有 468 byte、47 個 callee，而且是 30 項表 `0x60304` 的分派者；depth 4 的 48 個 function 裡有 30 個是清一色 56 byte、4 個 callee 的處理常式，正好對應那張表。骨幹走查從這裡接著做。

## 一個環境雜訊

Ghidra 每次跑腳本都會吐一長串舊 `McpInline_*.java` 的編譯錯誤。把 `~/ghidra_scripts` 底下的殘留檔刪掉之後訊息仍在——Ghidra 的 OSGi bundle 快取記著舊狀態。不影響執行結果，沒有再花時間處理。
