# VFS 容器解析與全量 dump（票 04）

## 起點：只有一句摘要

spec 說 `.VFS` 格式「已完整逆出，8 個檔案全部驗證通過」，`CONTEXT.md` 說「header 帶 `VFS` magic 與 26-byte 定長 entry（含 8.3 檔名）」。除此之外沒有任何欄位層級的記載——沒有偏移表、沒有每個欄位是什麼型別。所以實際上要從頭再逆一次，只是知道答案長什麼樣子，省掉了亂猜的時間。

先 hexdump `BACKGRND.VFS` 的前 256 byte。第一筆名稱 `BACK00.SAF` 落在 `0x23`，往後 13 byte 是 NUL 補齊的名稱欄位，接著 `EF 50 00 00` 出現兩次，再一個 0 byte，再 `89 06 00 00`。13 + 4 + 4 + 1 + 4 = 26，和「26-byte 定長 entry」對上。第二筆的第三個欄位是 `0x5778`，減掉第一筆的 `0x689` 恰好是 `0x50EF`，也就是第一筆的大小——所以那是成員偏移，而且成員之間沒有間隙。

header 就順著推：第一筆成員的偏移 `0x689` = 1673，`(1673 - 35) / 26 = 63`，而 `0x07` 處正好是 `3F 00 00 00`。`0x05` 處的 `23 00` = 35 就是 entry table 的偏移。剩下 `0x0B` 起的 24 byte 是 `Dynasty Information Co.,`。

寫個 probe 腳本套到 8 個容器上，全部通過，entry 總數 1,190，和票上的數字一致。

## 不滿意純靠猜的欄位語意

推到這裡有三個欄位講不清楚：`0x03` 的 `01 00`、entry 裡重複一次的大小、entry 裡那個恆為 0 的 byte。全部容器都是同一個值，光看資料永遠分不出「這是版本號」還是「這是壓縮旗標，只是沒用到」。

所以去翻 `FDPS.LE`。`search_strings("VFS")` 撈到 `Can't open the source VFS_file: %s\n`，xref 指向 `0x39bd0`；那個函式裡 `IMUL EAX, [EBP-0x18], 0x1a` 後取 `+0x1e` 與 `+0x27`，差 9，和「size 在 name+13、offset 在 name+22」對得上。順著它讀的那個 handle 指標往上找到 `0x39ab0`，那是真正的答案：

```
fopen(name, "rb")
fseek(f, 7); fread(&count, 4, 1)      <- entry 筆數在 0x07，u32
fseek(f, 5); fread(&table_off, 2, 1)  <- table 偏移在 0x05，u16
malloc(count * 26 + 17)
memset(handle, 0, 17)
handle->count = count; strncpy(handle + 4, name, strlen(name))
fseek(f, (int16)table_off); fread(handle + 0x11, count * 26, 1)
```

結論比預期有意思：**magic 從來沒有被讀過**。版本欄位、簽章、重複的大小、保留 byte 也都沒有。程式對容器不做任何格式驗證，餵一個非 VFS 檔進去不會被擋。

再看成員查找 `0x39990`，第一行是 `XOR EAX,EAX; MOV AL, byte ptr [EDX]`——筆數是以 8-bit 讀進來的。這是個真的限制：容器超過 255 個成員，第 256 筆以後永遠找不到。實際最多的 `FIELD.VFS` 223 筆，離上限不遠。同樣地開啟時的 `MOVSX EAX, word ptr` 表示 table 偏移是帶號 16-bit，上限 0x7FFF。這兩條寫進了解析器的檢查。

## 工具

`tools/vfs_dump/vfs_dump.py`，三個子命令 `list` / `dump` / `report`。

驗證那一段是刻意寫嚴的。容器沒有 checksum，程式自己也不驗 magic，「解得出東西」完全不代表解對了——偏移少算一個 byte，一樣會產出 1,190 個大小正確的檔案，只是每一個都錯位一個 byte，而且沒有任何訊號會告訴你。唯一擋得住這種錯誤的是要求成員首尾相接並精確填滿整個容器，所以那四條自洽性檢查（首筆偏移 = 35 + 26×筆數、每筆接在前一筆結尾、末筆結束於檔尾、重複的大小欄位相等）是這個工具的正確性依據本身，不是額外的保險。

錯誤路徑用真實容器改一個 byte 來測，測了七種：截斷、版本、簽章、重複大小、保留 byte、筆數溢位、名稱中間插 NUL。七種都報出正確的容器、entry 序號與欄位名。

## 踩到的兩件事

**`dump` 的統計數字一開始是錯的。** 遞迴解巢狀容器時用 `containers[-1]` 取「剛才那個容器」的紀錄，但遞迴已經在後面追加了內層容器，所以 `MISC.VFS` 印成 9 筆（`BASEWAV.VFS` 的筆數）。改成讓 `extract()` 回傳自己的紀錄。這個 bug 的討厭之處是它只影響印出來的數字，manifest 本身一直是對的，掃過去很容易當成沒事。

**`report` 的輸出重導向到檔案就變亂碼。** zh-TW Windows 的 stdout 預設 codec 是 cp950，直接印到 console 看起來正常，一 `>` 到檔案就毀了。`sys.stdout.reconfigure(encoding="utf-8")` 解決。`CLAUDE.md` 早就寫了這一條，還是踩了一次。

## 結果

8 個容器 1,190 個成員，加上 `MISC.VFS` 內 `BASEANI.VFS`（3 個 SAF）與 `BASEWAV.VFS`（9 個 WAV）的 12 個，共 1,202 個檔案解到 `workspace/vfs_dump/`。全部 1,202 個檔案的 SHA-256 與 manifest 對回原容器切片，零不符。

副檔名分布：最外層 SAF 522、DAT 299、CEL 97、MPL 68、TXT 66、DTL 64、COD 63、PAL 5、WAV 3、VFS 2、FON 1。SAF 522 這個數字和 spec 記的一致——順帶確認了 spec 的 522 指的是最外層，不含巢狀那 3 個。

最後補一道與容器算術無關的旁證，因為前面所有檢查都只證明「解析器和容器的自述一致」，萬一 header 佈局整體位移，自洽性檢查一樣會過。查 12 個 `.WAV` 的 RIFF 長度欄位，全部加 8 等於解出的檔案長度；`.PAL` 一律 768 byte；`.CEL` 全部 `CEL\x01` 開頭、`.SAF` 全部 `SAF\x06` 開頭。這才真的釘死了偏移沒錯位。

沒有動 Ghidra 的任何狀態，全程只讀，所以這次沒有快照 diff。

## 複審抓到一個我寫錯的結論

知識庫初稿寫了「成員名稱的比對不分大小寫」。理由是我看到查找迴圈裡有 `0x435f3` 這個把字串弄成大寫的呼叫，就直接推論成 case-insensitive 比對。複審要求把三個 helper 都攤開來看，結果是：

- `0x435bc` 是純 `memcpy`，把 entry 名稱原樣抄出來，沒有任何 case folding
- `0x435f3` 是 `strupr`，而且是**就地**改寫——它只作用在傳入的查找字串上
- `0x42fe0` 是逐 byte 的 `strcmp`

所以正規化是單向的：查詢方被轉大寫，entry 方原樣比對。entry 名稱只要不是全大寫就永遠查不到。這個差別對重建是有實質後果的——照原本那句話寫成 `stricmp(entry, query)`，遇到非大寫 entry 名稱時行為就與原版不同，那正是 ADR-0001 說的「差異會實際影響功能」的情形。

實測 1,202 個成員名稱全部是大寫、全部嚴格 8.3，所以原版永遠踩不到這個差異，也就是說單看資料永遠驗不出這一條。教訓很直接：**看到一個看起來在做正規化的呼叫，不要推論它作用在哪一邊，把它攤開。**

複審另外抓到四個工具層面的問題，都修了：名稱檢查擋了 `/` 和 `\` 卻放行 `:`，而 `Path("out/dir") / "C:EVIL.DAT"` 在 Windows 上會直接丟掉左邊變成 `C:EVIL.DAT`（順帶連 `NUL`、`COM1` 這種裝置名也會默默把內容寫進黑洞），改成只收嚴格 8.3 加擋裝置名；`.d` 後綴不撞名的理由原本只對滿長的名稱成立，改用 8.3 只有一個點來說明；`list` 對不存在的檔案會噴 traceback 而不是走 `error:` 那條路；輸出目錄不清舊檔，而光碟版的 `FIELD.VFS` 與 `ICONANI.VFS` 和硬碟版內容不同，重跑會留下 manifest 沒有記載的殘檔。最後一項用「只刪這個容器目錄下不屬於本次成員集合的東西」處理，範圍限縮在工具自己建的目錄內。
