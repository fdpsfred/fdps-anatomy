# 刪減內容的初次調查與票 25 的重組

開發者問：玩家社群說原版執行檔和資料檔裡留了很多被刪減的內容、有 slot 沒內容，能不能從我們手上的東西找出這類痕跡並整理列出。

## 第一個方向被開發者打斷

一開始我照舊習慣去讀 `program_info/architecture.md` 的「呼叫圖走不到的部分」、`memory_layout.md` 的函式指標表，準備從原版映像的可達性分析切入。開發者中途打斷：不要從原版執行檔分析，我們已經有完整的 Ghidra 專案和還原後的 C code，從那裡找。這個轉向是對的——`src/` 的註解裡已經寫著大量「沒有寫入端」「沒有出貨地圖選用」「unreachable with the shipped table」之類的結論，是 emit 時逐支讀 assembly 留下來的，比重新跑可達性分析準得多。

## 四路平行調查

派了四個背景 agent，各負責一個領域：程式碼（死碼、死旗標、除錯路徑）、章節與地圖（分派表 slot、地圖、事件文字、CD 音軌）、數值表（物品、法術、人物、職業、敵人）、圖像動畫音效（VFS 孤兒成員、SAF、CEL、WAV）。都是只讀，不動 Ghidra 與 `src/`。

意外：四個 agent 都寫不出報告檔——子代理被環境禁止寫報告檔，報告只能以訊息回傳。它們的腳本與中間產物還是寫進了 scratchpad。後來把四個 scratchpad 資料夾複製到 `workspace/cut_content/investigation/`，報告全文由主 session 照錄到同目錄的 `reports/`，否則 session 一丟就沒了。以後派子代理時不要要求它寫報告檔，直接要它回傳全文。

## 報告之間的矛盾與抽查

- 章節 agent 說「0xFF 以外的各章波次都找得到部署者」，程式碼 agent 說第 18 章 wave 1／2 與第 28 章 wave 4 永不出場。回頭讀 `src/chevt3.h` 與 `src/chevt6.c`，emit 時的註解本來就寫著這兩件事，程式碼 agent 對。章節 agent 的普查漏了「呼叫端會傳哪些波次值」這一層，只看了資料裡有沒有非 0xFF 的波次。
- opcode `0x61` 兩份報告說法不同（「unit 3」對「名冊第 3 格法蓮娜 990 經驗」），其實是同一件事；而 `src/icon.c` 把它命名成 `SCRIPT_OP_DEBUG_LEVEL_UNIT_3` 是誤導——`WINGA26.DAT` 正式用它。
- 親自抽查成立的：第 26 章前的城鎮暗號表只有 24 列（`src/village.c`，章節索引 25 有村莊，查表越界）；酒館抽獎先發獎後寫獎項變數（`src/vilbar.c` 註解已寫明，也已在 `pitfalls.md`）；解出的肖像 PNG 裡四種敵兵與肖像 52 的角色確實存在；存檔 slot 畫面只循環 3 個（`src/save.h`）。

## 「舊版資料」的推論被開發者問倒

章節 agent 把光碟 `PACK.VFS` 裡的東西稱為「舊版」，我在彙整時照用了。開發者問：你說的舊版資料是哪些檔、為什麼認為是舊版？另外問光碟上根本沒看到 `FDE.EXE`。

查下去：`FDE.EXE` 是 `PACK.VFS` 容器的成員，不在光碟根目錄。逐成員雜湊比對後，能確定的只有「這是另一個版本的完整遊戲目錄，看起來像開發機工作目錄的快照」（`DEBUG.SAV`、執行期才產生的混色快取、單機的 `DIG.INI`、格式不同的 `DISK.NO`、另外包裝的 `DATA.VFS`）。比正式版早還是晚沒有證據，只有傾向較早的間接跡象（地圖 31／32 各有專用腳本，正式版合併後地圖 31 成了孤兒）。「舊版」是 agent 的推論，我沒驗證就轉述了。這一類因此沒有進詞彙表，整個 `PACK.VFS` 延到票 26，並在票裡寫明版本先後未定。

## 釐清需求（grilling）

開發者要求把全部發現整理成完整的知識庫內容：圖存 PNG、音效與音樂存 WAV、文字全文照錄、程式痕跡逐條列。拍板的決定：

- 分類直接用四個詞：殘留內容、空殼、被封住的內容、前作遺留，**不要上位總稱**（我原本提的「捨棄內容」被否決）。已寫進 `CONTEXT.md` 的新節「刪減與未用」；同時修正 Slot 詞條（檔案 4 個、畫面只選得到 3 個）。
- 新頂層資料夾 `cut_content/`；現有正典檔只加連結。
- PNG 與短音效進版控，CD 音軌 WAV 由工具重生、不進版控。
- 文字解碼：我原本打算沿用前作的字對照表（上次 agent 用它只解出 1792 個字模中的 1354 個）。開發者指出前作是拿倚天 ET3 字型檔做像素比對、反查 Big5 index，要照同一方法補全。讀了 `fd2-anatomy/tools/glyph/` 與 `resource_info/chinese_glyph_encoding.md`：前作其實也有 100 字是人工校正的。開發者決定不完全吻合的字做成網頁讓他填，不由 agent 猜。
- 每條發現在寫進知識庫前要再獨立驗證一次（workflow，一條一個 agent）。

## 票的重組

拆票時發現開發者當天早上擴寫的票 25（知識庫翻新）與這次的工作有三處重疊：`glyph_table.md`、「未使用頁」、「未使用資源」。開發者決定把兩者合併。票 25 改成總票加 17 張子票（25.1–25.17），原票 25 的 A–F 段內容全部拆進子票保留；`PACK.VFS` 另開票 26、狀態「延到下一次」。原票 25 整組被票 24（實機遊玩）擋著，合併後只讓最後的全知識庫逐條驗證（25.17）等票 24，理由是遊玩修正會改 `src/`、驗證要在最終狀態上做；補內容的票不必等。之後開發者說已親自測試過重建版前兩章、基本沒問題，25.17 也不必等票 24，整組因此沒有外部前置。

四份報告的 60 條主張濃縮成票 25.9 的發現清單，每條帶編號、分類建議與證據出處，作為驗證 workflow 的工作清單。

調查中順帶發現的既有錯誤收進票 25.15，本段沒有修：`architecture.md` 說走不到的 36 支 function 多半由章節分派表指到（實際上沒有一支在表裡）、`src/main.c` 說 `FMer*.tmp` 沒人讀回（實際有四處）、`icon.c` 的除錯命名、`items.md` 三個物品名照攻略站寫而與遊戲內文字不同、`characters.md` 的「樣板列」其實是索爾的資料。
