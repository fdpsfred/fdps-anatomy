# 票 08 的 code review 修正

對票 08（commit `fd571b0`）跑 code review，拿到 8 條發現。三條在知識庫、五條在 `tools/cd_scope/inventory_discs.py`。逐條驗證後全部成立，這裡記錄驗證過程與幾個原本沒預期到的收穫。

## 音軌表的加一寫了兩次

`program_info/cd_audio.md` 原本在章節音軌對照表上方寫「表中的值加 1 才是 MSCDEX 音軌編號」，但表格裡填的已經是加過 1 的數字。直接讀 `0x304a0` 的 60 個 byte 對照：開頭是 `13 06 13 06`，而表格第一列寫的是 14 / 7。

這種錯誤自己看不出來，因為兩種讀法各自都自洽——除非回去讀原始 byte。照原文重建的話每章都會多加一次，章節 0 會去要音軌 15 而不是 14。修法是把話講死：表列的是換算後的編號，原始 byte 要加 1，加法在 `0x30cc0` 呼叫 `0x3c85b` 之前完成。

## 拿編號跟條數比

同一份文件的自洽性檢查寫成「章節 0–17 用到最大音軌 19，光碟 1 有 21 條（編號 2–22）」。19 < 21 看起來成立，但這兩個數字根本不是同一個維度：要比的是編號上限 22。這次的資料剛好兩種比法都通過，所以錯誤不會顯現，可是規則本身是壞的——編號從 2 起跳，條數永遠比編號上限小 1，資料稍微變一下就會誤判。改成比對編號範圍。

## PACK.VFS 的差異不只 PASS.DAT

`resource_info/disc_images.md` 原本斷言兩片的 `PACK.VFS` 差異僅在 `PASS.DAT`。但同一份文件的大小表就寫著 82,658,897 與 82,658,243，差 654 byte，而 `PASS.DAT` 兩片都是 3 byte。這兩件事不可能同時成立。

當時的 workspace 只剩 JSON，複製出來的檔案已刪，所以改成直接從 `.bin` 映像解 ISO9660 找到 `PACK.VFS` 的 extent，再讀它的 header。

解 entry 佈局花了點工夫，中間走過幾條死路。先是把 stride 數成 27、又數成 25，因為手動對 hex dump 的行內偏移數錯了兩次；也一度把 header 的 `0x18` 當成 entry 大小（實際上是 entry 數量 24，`0x05` 的 `0x23` 才是 table 起點）。真正卡住的是 offset 欄位：試著讀成 `+21` 起算 4 byte 時，第一個 entry 得到 659、第二個得到一個天文數字，兩者對不起來。最後定在 `name[13] + size[4] + size[4] + pad[1] + offset[4]` 共 26 byte，第一個 entry 的 offset 正好是 659 = `0x23` + 24 × 26，也就是 header 加 table 的長度——這個巧合就是佈局正確的判準。

驗證方式是兩個獨立的等式：24 個成員的大小差總和恰好等於容器總大小差 654，且最後一個成員的 offset + size 恰好等於檔案大小。兩條都成立才敢用。

比完大小後得到三個不同的成員，本來要就這樣寫進知識庫。停下來的理由是：大小相同不等於內容相同。補做 SHA-256 之後多抓到兩個——`FDE.EXE`（372,789）與 `FDE.SAV`（22,987）兩片大小一模一樣但內容不同。實際答案是 5 個成員不同：`PASS.DAT`、`FDE.EXE`、`FDE.SAV`、`FIELD.VFS`、`ICONANI.VFS`。**只比大小會漏掉四成的差異**，這是這次最值得記的一條。

順手也發現原文「24 個 entry——安裝會用到的全部遊戲檔案」講得不對。容器裡有 `FDE.EXE`、`FDE.SAV`、`F30.SAV`、`DEBUG.SAV`、`DATA.VFS`、`FMER*.TMP`、`MER*.TMP` 這些光碟資料軌上根本不存在的成員，同時又沒有 `INSTALL.BAT`、`SETSOUND.EXE` 和大部分 `.DIG`。改成直接列出 24 個名稱，不再用概括的說法。

`PASS.DAT` 的內容 `1\r\n` / `2\r\n` 另外從映像讀出來確認過，原文這部分是對的。

## 腳本的靜默失敗

五條腳本問題裡最要緊的是 `copy e:\*.* f:\` 不遞迴、而且結果從來沒被檢查過。`subprocess.run(check=True)` 只確認 DOSBox-X 這個行程結束了，但 DOSBox-X 不管 `IMGMOUNT` 成功與否都回傳 0——掛載失敗的結果是一個空目錄、一份格式漂亮的 JSON，和一張憑空少掉檔案的知識庫表格，全程沒有任何錯誤訊息。

review 建議拿複製出來的 byte 總量對照資料軌的 sector 數。沒採用，因為那只能抓到「差很多」的情況，抓不到少一兩個檔案。改成直接從映像解 ISO9660 根目錄當作權威清單，逐檔比對名稱與大小——解析程式碼在查 `PACK.VFS` 時已經寫過一次，等於免費。`copy` 與 `report` 都會跑這道檢查。

拿它回頭驗票 08 已經產出的兩份 JSON，ISO 目錄解出的 32 / 9 個檔案與大小跟舊 JSON 完全相同。所以當時的複製確實沒漏檔，知識庫的清單是可信的——這道檢查是補上保險，不是修正既有數據。

其餘四條都是「錯了也不會報錯，只會算出錯的數字」這一類：`RAW_SECTOR = 2352` 寫死而解析出來的 `mode` 只拿去濾 `AUDIO`；`startswith("INDEX 01")` 會漏掉 `INDEX 1` 的寫法，漏掉的軌會被前一軌的長度吸收；`FILE` 指令完全沒解析，multi-FILE 的 cue 會把各檔案的區域偏移當成同一條時間軸。這三個一律改成不支援就直接中止，不猜。最後是 `conf.unlink()` 沒有 `finally` 保護，和 `main()` 沒檢查 `sys.argv` 長度會噴 `IndexError` 而不是印用法。

改完實跑一次 disc 1 的完整 `copy` 流程，確認 DOSBox-X 內建的 `XCOPY` 可用、驗證路徑會通，接著跑 `report` 產生新 JSON 與票 08 的舊 JSON 逐位元組比對，結果相同——改動只增加保護，不動輸出。三種壞 cue（multi-FILE、`MODE1/2048`、`INDEX 1`）也各測過一次：前兩種中止，第三種現在解析得到，改之前會被靜默漏掉。

disc 2 沒有重跑完整複製。走的是同一條程式路徑，而它的 ISO 目錄清單已經拿去跟舊 JSON 對過並且相同，多花十幾分鐘複製 282 MB 換不到新資訊。
