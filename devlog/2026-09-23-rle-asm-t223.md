# 票 22.3：RLE 繪製的 15 支改回原版組語

## 起點與先前那條撤回的路

票 22 把 `fdps_blit_dispatch` 與它底下的 14 支 RLE routine 連同暫存器交接一起改寫成一般 C，依 ADR-0001 功能等價，代價是速度：原版一段同色像素是一道 `REP STOSB`／`REP MOVSB`，C 版在 `-od` 下是經 EBP 區域變數的逐 byte 迴圈。票 24 因此列了「重建版不能明顯變慢」的實機疑慮（`00056a0d#0`、`00056c5e#1`）。使用者決定不賭實機結果，直接保留原版組語。

這張票第一次做的時候，標準定成「組出來的 byte 與原版逐 byte 相同」。那條路撤回了，而且那次的 commit、工具、workflow、測試都已經從 git 歷史與 workspace 抹除，這一次是照改寫後的票從頭做，沒有沿用任何舊實作。撤回的理由記在這裡，因為它是唯一會遺失的資訊：

- **原版這段不是 WASM 10.0a 組出來的。** reg,reg 指令的方向位元不同（`or bx,bx` 原版 `66 0B DB`、WASM `66 09 DB`），`cmp ax,0` 原版用累加器形式、WASM 用 imm8 形式，前向分支原版是「預留長形式、縮短後補 NOP」的單趟組譯器形狀。要 byte 相同，每一道這種指令都只能用 `DB` 手寫編碼。
- **換到的只有 byte。** 等長編碼的另一種寫法，CPU 執行的動作與週期都相同；功能與執行效率一點都沒有多得到，原始碼卻變成一堆 `DB`，失去作為組語原始碼的可讀性。

所以這次的標準是「指令序列逐道相同、每道指令長度相同」，byte 只允許在等長編碼與重定位欄位不同，並且明文禁止為了對齊 byte 寫 `DB`。

## 先把 WASM 的行為量清楚

開工前先在 DOSBox-X 裡用 DOS 版 WASM 組探針，逐條確認票上「開工前就知道的事」：

- 前向 `jcc short` / `jmp short` 加明寫的 `nop`，位移正確。
- **不指定長短的前向分支，WASM 是多趟組譯、直接排最短形式**。這裡第一次踩到陷阱的輪廓：原版以「保留長形式時的距離」決定要不要縮短，WASM 以「自己縮短後的距離」決定，所以位移 D 落在 124–127 的原版前向長 `jcc`，WASM 會自作主張組成短跳。掃原版 15 支，這種邊界分支有四個：`0x57801`、`0x57984` 兩個 `jb`（D=127），`0x56e89`、`0x5718a` 兩個 `jmp`（D=126）。探針裡 D=126 的 `jmp` WASM 保留了長形式，當時就據此判斷「JMP 不必處理」——這個判斷後來被推翻（見下面落地那段）。
- **`jcc near ptr` 的 +1 錯誤不是每次都發生。** 票上寫「前向 `jcc near ptr` 位移多算 1」，探針做了前向 16 種距離、後向 14 種距離：前向 D ≤ 126 錯、≥ 127 對；後向跳過 ≤ 123 byte 錯、≥ 124 對。原版那兩個需要強制長形式的 `jb` 正好 D=127，落在組得對的那一側，所以 `jb near ptr` 在這裡可用，而比對工具以「落在第幾道指令」比對分支，錯了也不可能通過。
- 外部資料用 `extrn x:word` 直接引用，WASM 產生的 fixup 以目標決定 frame（wcc386 用 `FLAT` group）。怕 LE 裡解出來的位址不同，實際連結一支 C 主程式跑在 DOS/4GW 下印位址，兩種 frame 都得到同一個位址，因此不需要 `.model flat`。
- C 呼叫端的契約：先懷疑 `-4s` 下 `parm caller []` 的呼叫端會不會假設 ECX／EDX 保留（分派者會破壞它們）。編一支會跨呼叫保留很多值的探針看產生的碼——`-od` 下所有值都放在 EBP frame，不在暫存器裡跨過呼叫；`-4s` 的 callee-saved 正好是分派者保存的 EBX／ESI／EDI／EBP。

## 比對工具

`tools/rle_asm/asm_match.py`。原版側直接讀 `FDPS.LE`（objects、page、fixup 連同目標），名稱取 Ghidra 快照；重建側讀 WASM 的 OMF 物件檔，不必連結就能單支比。考慮過改讀連結後的 `EMITTEST.EXE`（`lefixup.py` 現成可用），但最後一支 routine 的結尾在連結後的映像裡要從 map 猜，物件檔的 SEGDEF 長度直接就有，而且轉錄時可以單獨組一支來比。OMF 記錄的讀法參考前作 FD2 的 `extract_obj_bytes.py`（CLAUDE.md 記著「別自己寫 OMF parser」的教訓，那次撞的是函式庫的 quirky 記錄；WASM 的輸出很規矩，而且這裡的讀法只認得到它實際產生的記錄型態，遇到別的就拒絕）。

比對時先把兩邊的重定位欄位抹零再用 capstone 解碼，逐道比長度、助記符、運算元文字；分支一律換成「第幾道指令」或符號名再比。自我測試 24 項，第一次跑全過，反而不放心，把幾個「應該失敗」的案例的失敗訊息逐一印出來，確認是被正確原因抓到（例如少一個 NOP 那案是 `jne #7 | jne #6` 加長度錯位，而不是誤中）。

`listing` 子命令印原版 routine 給轉錄者看：每道指令的長度、分支落點的指令序號、重定位欄位直接換成符號名，並標出「縮短後就進得了短跳範圍」的前向長跳。第一版有兩個錯：函式外的後向跳躍沒做有號處理，印成 `0x100056a0d`；重定位欄位只遮成 `[0]`。兩個都在拿 `mirrored_vertical` 手動試跑整條管線時看出來。那次試跑寫在 scratchpad，跑通就刪，正式轉錄全部交給 workflow。

## Workflow

`tools/rle_asm/rle_ticket223.js`：轉錄（一支一個 agent，片段只寫進 workspace，自己在 DOSBox 裡反覆組譯比對到通過）→ 回掃 → 落地（`land.py` 機械式接成五個檔，接著整份 build gate，過了才 commit）→ 測試移植（一支一個 agent，序列，各自 commit）→ 舊案例覆蓋檢查與最終 gate。進度一律從檔案判斷：判定檔記著它背書的片段雜湊，片段在蓋章後改過就不算完成。

準備過程的兩個坑：

- 我這端的 `Start-Sleep` 被 harness 擋掉，推測 agent 也一樣，原本提示裡「背景跑 gate、用短 sleep 輪詢」的寫法會卡住，開跑前改成「背景執行、等完成通知」。
- 全套單元測試跑超過 16 分鐘（建置約 6 分鐘）。測試移植要逐支序列跑、每支可能建好幾次，所以替 `build_emit.py` 加了 `--only`：照樣全部編譯連結（避免讓編不過的檔溜過），只呼叫指定測試檔的 runner，結果檔記下有過濾；正式 gate 永遠跑全套。
- C 端的切換（`#if 0` 包 C 譯本、原型與舊測試，分派者測試搬到 `tests/rledisp.c`）我先手做在工作樹裡、不 commit，讓落地 commit 同時帶上組語與 C 端切換，避免任何一個 commit 把 routine 定義兩次或一次都沒有。副作用是開跑後我改的知識庫檔會讓落地 agent 的「工作樹只准有這些髒檔」檢查失敗——發現時立刻先把文件 commit 掉。

一次跑完，68 個 agent、0 錯誤，約 110 分鐘。

### 轉錄與回掃

15 支轉錄全部通過。`fdps_rle_blit_translucent_color_range` 的轉錄者留下一則真的新發現：`0x57bcb` 的 `jmp short tcr_end_row`（D=127）WASM 組成了 5 byte 的 `E9`，沒有任何警告；它改寫成 `jmp short $+129` 才組出 `EB 7F`。回掃 agent 確認位置計數器的寫法不受接檔影響，但「WASM 為什麼在這裡不照 short 組」它無法從證據判斷，照實留成未決。

我接手量：單純的 D=127（中間全是 NOP）四種變形都組得對，於是拿轉錄片段本身把 `$+129` 換回標籤重現成功，再二分。中間有前向短 `jcc`、有外部記憶體運算元、有後向長 `jcc`、有另一個前向短 `jmp`，逐一做成探針都不重現。回頭看 listing，發現這個短跳之前有一個前向長 `jb`（`0x57ae4`）跳進它與它目標之間，另一個前向長 `jmp`（`0x57b57`）跳到同一個目標。分開做兩個探針：跳到同一目標的那種不重現，**跳進兩者之間的那種重現**。同樣條件下再量 `jcc short` 的 D=127（也被組成 6 byte）、D=126、125（都正常）。結論與 `$+N` 的寫法寫進 `build_flags.md` 與 `pitfalls.md`。

### 落地

第一次落地被自己的閘擋下：接成 `rleturn.asm` 之後，`asm_match.py check --fresh` 報 `fdps_rle_blit_rotated_scaled` #30（`0x5718a`，D=126 的 `jmp`）長度 5 對 2。這支片段單獨組時 WASM 保留長形式，接在 `fdps_rle_blit_rotated` 後面組時卻被縮短——正是我開工前「D=126 的 JMP 不必處理」那個判斷被推翻的地方。落地修正 agent 把它改成 `jmp near ptr`（`jmp near ptr` 的位移一律正確）、重新蓋章，第二次落地通過。事後我把 `0x56e89`（同樣 D=126、目前碰巧保持長形式）也照規則改成 `jmp near ptr`，更正 `build_flags.md` 的說法為「WASM 對這種 JMP 的選擇隨前後文而變」。

落地的整份 gate：`code_emit.run` 23,286 個檢查 0 失敗，`rle_asm.check` 15 支全過。

### 測試移植

14 支（13 種畫法加 `fdps_rle_skip_row`）逐支把 C 譯本的直接呼叫測試改寫成經 `fdps_blit_dispatch` 的測試，四個舊測試檔的 146 個案例全部對應到新檔的 146 個案例（`coverage` 確認每個舊 `RUN_TEST` 都有人認領，沒有留下 uncovered；`fdps_rle_skip_row` 另外把兩個間接經過它的縮放案例指回縮放那支已移植的案例）。加上分派者自己的 17 個，經分派者的測試共 163 個。沒有任何一支發現組語與 C 譯本的主張不同。`fdps_rle_skip_row` 沒有自己的 mode，它的 10 個直接呼叫案例改成「mode 4、兩列來源畫兩列目的地」，讓縮放畫法在第一列畫完後呼叫一次 skip_row，再從第二列畫出的位置判斷 skip_row 把游標停在哪裡；原本 `remaining_rows` 設成 0x1234 的那個案例做不到（分派者會覆寫它，而且來源高度 0x1234 會讓畫法走 0x1234 列），改成斷言兩次 skip_row 之後寬度與高度的全域不變，記在該支的 findings。

最終 gate：23,948 個檢查 0 失敗，所有套件通過。

## 收尾

- Ghidra：這 15 支的 function body 補上 39 處流程到不了的 `NOP` 填充（前向短 `JMP` 後的 3 byte，原本被定義成 `byte[3]` 資料），大小改成入口到下一支入口；稽核孤立程式碼、error bookmark、未定義 byte 皆 0。plate comment 各加一句重建形式，另外三支（`fdps_rle_skip_row`、`fdps_rle_blit_rotated_scaled`、`fdps_rle_blit_mirrored_horizontal`）改寫了「重建把暫存器契約換成 C 參數」的句子。
- `code_pools.md` 那一節重寫：手寫組語模組是 `00056799`–`00057c5f` 共 24 支（鍵盤 7、存檔 2、RLE 15），原本漏了鍵盤、RLE 的數量寫成 13、模組結尾寫成 `00057c54`（最後一支的 `RET` 在 `0x57c5f`，object 1 的最後一個 byte）。
- 票 24 的 RLE 那一列改成只需確認畫面；兩則速度疑慮在 `emit_issues.json` 結案。
- 改回 C 版的演練：`switch_impl.py c` → `build_emit.py all --only` 那 9 個 RLE 測試檔（C 版直接呼叫與經分派者兩套）→ 零錯誤零警告、1,375 個檢查全過 → `switch_impl.py asm` → 完整 gate。停放的 `.asm` 帶著切換前還沒 commit 的兩處修改一起回來，沒有遺失。

## 審查

收尾前做了兩軸審查（標準面、規格面，各一個唯讀 agent）。採納並修正的：

- `wf_state.py` 為了讀 `#if 0` 而 import `tools/code_emit/build_emit.py`，違反「腳本自足、只准共用 `build_min.py`」——改成自帶一份。
- `code_layout.md` 引用了 `workspace/` 路徑，還有一句「這條路實際走過一次」的事件紀錄——前者改指工具頁，後者改寫成結論，事件留在本篇。
- `emit_issues.json` 裡那兩則疑慮的 review 鏡像（`same_as` 指回去的那兩筆）仍是 handoff，資料自相矛盾——一併結案。`sweep.py handoff` 跳過鏡像，所以原本的檢查看不出來。
- Ghidra 那 39 處 `NOP` 的行尾註解是早先的票替 `byte[3]` 資料寫的，都說它們是「對齊用填充」，正好與新寫的踩雷條目相反——統一改成「分支縮短後留下的填充、流程到不了、屬於 body、照原樣轉錄」。
- `rleturn.asm` 對 `0x56e89` 的註解說「WASM 的選擇隨前後文而變」，但這一處實測兩種情況都保持長形式——改成「強制長形式，因為 WASM 在這個距離的選擇取決於周圍的程式碼」，與知識庫的一般規則一致。
- `ROSTER` 各處用位置索引取欄位，改成具名欄位。

保留不改的：`pitfalls.md` 裡「Ghidra 記錄的大小偏小」那條被評為邊緣——保留，因為拿記錄的大小切原版 byte 正是重建比對時照直覺會做錯的事（`fn_match.py` 就是這樣切的）。
