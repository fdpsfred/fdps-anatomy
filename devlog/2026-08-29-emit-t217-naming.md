## 二、票 21.7 的命名第一次被當成一個獨立檢查項

這是這批唯一「新流程」的部分，也是唯一值得對 workflow 本身下結論的部分。reviewer 的 checklist 第 13 項就是命名：它逐一去問「這個名字說的事，assembly 支不支持」。

- `grid_width` / `grid_height` 是 `+0` 與 `+2` 兩個 header word 的 MOVSX load。哪個是寬哪個是高不是猜的——plate 與 `fdps_field_load_chapter_resources` 的配置式 `4 + width*height*2` 交叉確認，C 讀 `+0` 進 `grid_width`，對得上。
- `cell_index` 是 `[EBP-0x8]`，JG 的比較對象、迴圈計數器。它是 index 不是 byte offset，名字說的就是這件事。
- `cell` 是 `[EBP-0x4]`，被 `ADD 2` 前進的游標，一次一個 `struct fdps_move_grid_cell`——名字說 cell，而型別讓那個 stride 為真。

對照組是 Ghidra decompiler 印出來的東西：`sVar1` / `sVar2` / `local_18` / `local_14`。四個名字沒有一個告訴你它是寬、是高、是索引還是游標。21.7 要買的就是這個差，這批證明 reviewer 有能力用 assembly 去驗證這個差是不是誠實的（而不是編出好聽的名字）。到目前為止成本是零：沒有因為命名多跑任何一個 fix round。

## 三、decompiler 在這支的兩個地方不能照抄

第一個要記進坑書式記憶的：**單一 CMP/JG 被 decompiler 展開成兩個 predicate。** 00010b65 只有一條 `CMP EAX,[EBP-0x8]` 加 `JG`，Ghidra 印出來卻是

```
(int)sVar1 * (int)sVar2 - local_18 != 0 && local_18 <= (int)sVar1 * (int)sVar2
```

那個 `!= 0` 的合取項是重建出來的假象。照它寫會多一個條件、多一段程式碼，而且 emit 出來的 C 會長得跟原版不像。emitter 與 reviewer 各自獨立地否決了 decompiler、照 assembly 寫成一個有號的 `<`。這是 emit 流程「以 assembly 為準、decompiler 為輔」這條原則第一次在一個**非 CALL 的地方**被觸發——之前遇到的都是 post-CALL 回傳值被誤判，這次是純粹的迴圈條件重建。

第二個：00010b6c 的 `MOV EAX,[EBP-0x8]` 接 `INC [EBP-0x8]`，那個 MOV 是 Watcom post-increment 的 codegen 產物，EAX 在它之後到 00010b74 才被重新載入，沒有值跨出這個 block。兩邊都讀成 dead load，沒有去替它編一個語意。

順帶一提這支的主要危險是 contract C：兩個 header word 都是 MOVSX、bound 用 JG，全部有號。如果照直覺當成 unsigned 讀，`0xffff` 的寬度會讓乘積變成 262140 而不是 -4，接著往 block 外面走二十幾萬格。測試 `grid_header_words_are_signed` 就是釘這件事的。

## 四、rescan：contract D 用硬碟上已經有的 .OBJ 收掉，沒有重 build 任何東西

回掃段挑 `00010b20` 重看，`changed: true`、`resolved: 1`、`still_open: 1`。

被收掉的是 concern 1：原版在迴圈頭每一輪重算 `width*height`（00010b5e 的 `MOV EAX,[EBP-0x10]` / `IMUL EAX,[EBP-0xc]`），emit 出來的 C 照著這麼寫了，但**沒有人知道 wcc386 會不會把這個 loop-invariant 乘積提出迴圈**。如果會提，重建的迴圈每格會少幾條指令，是 contract D 等級的差異。emitter 標了這個 issue，reviewer 自己看過 assembly 之後同意並附議，所以 `emit_issues.json` 裡同一件事有 emit 與 review 兩筆。

答案是**不會提**，兩條證據互相印證：

1. `rebuild_info/build_flags.md` 把旗標組釘死在 `wcc386 -bt=dos4g -mf -4s -fpi -s -ot -od`，`-od` 把最佳化整個關掉，根本沒有 loop-invariant motion 這個 pass 在跑。
2. issue 要求的直接檢查——而且不必重 build 任何東西。這輪 emit 自己產生的 `workspace/code_emit/out/objs/MOVEGRID.OBJ` 已經躺在硬碟上，而且裡面只有 `fdps_map_grid_reset` 這一支。LEDATA payload 從檔案 offset `0x0192` 開始，迴圈頭在 payload `+0x3f`：`8b 45 f8 / 0f af 45 f4 / 3b 45 f0 / 7f 07 / eb 18`，也就是 `MOV EAX,[EBP-0x8]` / `IMUL EAX,[EBP-0xc]` / `CMP EAX,[EBP-0x10]` / `JG body` / `JMP epilogue`——跟 00010b5e-00010b6a 一模一樣的四條指令，IMUL 在頭裡面，每一輪都重跑。

這裡有一個**方法上的收穫值得下次照抄**：要驗 contract D 級的 codegen 形狀，不需要建整個 EXE，也不需要跑 gate。emit 那一輪為了 build 已經產出 per-function 的 `.OBJ`，那個檔就是答案，read-only 打開來讀就好。這比重建整條 pipeline 便宜一到兩個數量級。

**踩到的坑**：`.OBJ` 是 Easy OMF-386，拿通用的 OMF record walk 去走它會什麼都找不到——這正是票 14 那個已知的坑（前作的結論是「用 `wlib` 別自己寫 parser」）。這次的處置是不寫 parser：直接 hexdump，從 payload offset 手算位置把 code byte 讀出來對照。花的時間比寫 parser 少，而且不會再撞一次那個 quirky record。**如果下次又需要看某支 function 的 .OBJ 形狀，答案是 hexdump 加手算 offset，不是再寫一次 parser。**

同一輪 byte 對照還多撈到兩處殘留差異。它們沒有被丟掉、也沒有被當成缺陷，寫在 issue 的 `residual` 欄位裡讓下一個讀的人不用重推一遍：

- **frame slot 分配相反。** 原版把 width 放 `[EBP-0x10]`、index 放 `[EBP-0x8]`；重建的放法剛好對調。這純粹是宣告順序造成的，沒有別的意思。
- **原版多一條 dead load。** 00010b6c 是 `MOV EAX,[EBP-0x8]` / `INC [EBP-0x8]`，重建只 emit 了 `INC`，每格少一條 load。EAX 在原版那裡是 dead 的（00010b74 用之前就重載了），沒有值、也沒有 flag 跨過這個差。

兩項都是 codegen 形狀不是行為，按 ADR-0001（功能等價不是 byte-exact）都不是功能差異，**都不構成去動那份 C 的理由**。這句要明寫，因為看到 byte 不同的直覺反應是去改程式碼，而在這個專案裡那是錯的。

rescan 全程對 Ghidra 唯讀（只有一次 `disassemble_function(00010b20)` 拿來跟 object 對照），`ghidra_fixes` 空，唯一動到的檔是 `tools/code_emit/data/emit_issues.json`。
