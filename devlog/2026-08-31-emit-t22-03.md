# emit t22-03：票 22 的第三批四十支

這批跑的是票 22 的 emit，一次四十支，序列跑完沒有中斷。流程和前兩批一樣：emitter 讀三份來源（plate、disassembly、decompiled C）寫出 C 與測試 → 獨立的 reviewer 從 assembly 與工作樹 diff 兩邊自己重推一次 → 有 blocking issue 就進 fix round → src/ 與 tests/ 整包過 build gate → 這支自己一個 commit。序列而非並行的理由沒變：reviewer 判斷「本輪改了什麼」的依據就是工作樹本身，兩支同時在跑的話那個依據就髒了。順序是 callee 先於 caller，讓每支函式是對著真的 callee 測而不是對著生出來的 stub 測；build 連結兩次，票 23 還沒 emit 的資料就用零填補上，這樣缺什麼會被看見而不是被藏起來。

結果：40 支全部落地，0 支跳過，0 支未完成，0 支沒被走到，沒有續跑、沒有中途被砍、沒有檔案需要分割。統計裡的 `recovered` 是空的，所以上一輪不是被殺掉的，這輪開工時工作樹沒有殘骸要丟。累計 88 支 committed，開工時剩 466。

以下記的是這批出過的問題，不是四十支的流水帳。

## 七次 fix round，沒有一次是程式碼

`000132b0`、`0001f510`、`0001c520`、`00027070`、`00027840`、`000285c0`、`00019f80` 這七支各進了一輪 fix。回頭把七份 emit verdict 的 round 2 全部讀過一遍，**七次的 blocking issue 全部是註解或 verdict 文字，沒有任何一次動到指令、簽章、測試斷言或期望值**。這件事本身值得記，因為它說明現在這條 pipeline 的失效模式已經不在「C 寫錯」，而在「C 旁邊那段話寫錯」。

失效的形狀又可以再分成三種，三種都會重複發生：

**一、把 plate 裡的陳年 `FUN_` 標籤解錯人。** `00027070` 是最乾淨的例子。plate 上寫的是「`FUN_00027c20` 測 portrait id > 8 給同樣的 +30」，emitter 去解這個標籤，解成了 `fdps_unit_award_exp_and_level_up`，寫進 `src/unitstat.c` 的註解。reviewer 抓到，emitter 自己重查：`000280cf` 落在 `fdps_battle_spell_command`（entry `00027c20`）體內，而 `fdps_unit_award_exp_and_level_up` 是 `0001dd30` 另一支 486 條指令的函式，根本沒延伸到那裡。位址、比較的界線、`0x1e` 都是對的，只有函式名字掛錯人。這條路的教訓不是「要小心」，是**解 plate 上的 `FUN_` 標籤時要用位址去問資料庫這個位址屬於誰，而不是憑印象配名字**——因為 `FUN_00027c20` 這種寫法看起來很像 entry，實際上 plate 作者當初寫的時候指的可能是「在這支裡面」。

**二、把 plate 上未經查證的斷言原樣搬進 C。** `000285c0` 的 banner 寫著這支「每個動畫動作都會跑」，而且引 `assets/tables/spells.md` 說有 cost 為 0 的記錄。fix round 裡兩半都被推翻：`get_function_callers` 打 `0001a4c0` 只回 `fdps_battle_spell_command` 與 `fdps_map_actor_cast_chosen_spell` 兩支，都是施法指令，沒有普通攻擊的路徑進得來；`assets/spells.md` 四十筆記錄 MP 欄最小值是 4，沒有 0，而它引的那個 `assets/tables/spells.md` 是 7-byte 記錄佈局、根本一個數值都沒有，從來就不支持那句話。emitter 自己的判讀是：「這句話出自 plate，我 round 1 沒查就搬過來，這就是缺陷。」

**三、把自己從一行指令推出來的數字當成量過的。** `00027840` 的 header 寫「image 裡每個 caller 都給它至少 0x40 bytes 的堆疊陣列」，那是從 `LEA` 的位移推的，而 `LEA` 給的是陣列起點不是大小。實際反組譯 `000276f0` 與 `00013420` 兩個 frame 逐條算完，兩個 buffer 是 0x28 和 0x14——一個剛好 40 個 id、一個只有 20 個，所以那句話兩個方向都錯。同一段還說「三個 call site 這樣用」然後只列了兩個，自我矛盾。

`000132b0` 和 `00019f80` 則是同一類的第四種變形：把因果寫反。`000132b0` 的區塊註解說 signed short 的寫法「會給 8，原版給 0x12」，實際上 `000133dc` 讀 `word ptr [EAX+0x40]` 之後 `AND EAX,0xffff`，`0xffff` 比出來是 65535、`JLE` 不成立、原版落到 `000133ea` 給 8，方向整個反過來。這種錯 build gate 永遠抓不到，因為程式碼是對的。

`00019f80` 的 fix 則是把一個沒有依據的詞從程式碼裡拔掉：常數叫 `LAST_PERMANENT_ROSTER_PORTRAIT_ID`、`GUEST_LEVEL_PENALTY`，測試名字叫 `a_guest_attacker_divides_by_thirty_more`。去查 `assets/characters.md` 才發現 00-0B 是十二個玩家角色、各有自己的 FRIAPRDA.DAT 列，0B 蘭斯洛特（聖騎士，AP 220 / DP 140 / DX 60）在裡面，所以 10 不是隊伍名冊的邊界、也沒有誰是「客座」。改成 `XP_PENALTY_PORTRAIT_ID_THRESHOLD` 與 `XP_ATTACKER_LEVEL_PENALTY`，值 10、嚴格大於、`0x1e` 一個都沒動。**測試的名字也是 `src/` 的閱讀材料，錯的詞在那裡一樣會誤導人。**

## Ghidra plate 的陳年標籤是這批最大的固定成本

39 次 plate 修正落地，40 支裡有 29 支至少帶一次，只有 11 支的兩份 verdict 都交白卷。絕大多數是同一件事：plate 寫成的時候旁邊那支還叫 `FUN_xxxxxxxx`，現在它有名字了，plate 沒跟上。

問題是逐函式的修法只會修到眼前那一處。`000274e0` 這支把事情攤開了：reviewer 指的那個不存在的名字 `fdps_collect_defeated_unit_events`，**在整份快照裡出現 7 次**，而資料庫裡根本沒有這個函式（`000274e0` 的實名是 `fdps_collect_death_script_events`）。這輪只改掉 reviewer 明確點名的兩處，第三處（`000274e0` plate 的 Parameters 段 script_count 那行）照規則被留下來了——落地者只轉錄、不自己延伸判斷，這條規則我認為仍然是對的，但代價就是這個名字現在還活在快照裡，用名字搜是搜不到來源的。

再往外量一層：`ghidra_snapshot/comments.txt` 裡還有 **487 個不同的 `FUN_` 佔位名**被 plate 引用著。照現在這個速度（每支平均一次 plate 修正）這些會被 emit 一路慢慢磨掉，但磨的順序是 emit 的順序，不是壞得最嚴重的順序。這件事沒有在這輪解決，記在這裡是因為它不是一次意外而是一個穩定的稅。

## 「兩處」其實只有一處

有四支的 verdict 把修正寫成「replace both occurrences / 兩個地方」，而 plate 實際上只有一處：`0001f510`（Rebuild note 是用位址 `0001f7d0` 指同一個 sibling，沒有寫名字）、`0001fc00`、`00025fe0`（另一處是刻意對比的 `fdps_get_class_record`，是不同的函式、拼法本來就對）、`000285c0`。`000274e0` 是反過來，說兩處實際三處。

五次數錯，方向兩邊都有。這說明 verdict 裡的 occurrence 計數不可信，落地者的做法（照字面把「錯的拼法」全部換掉，然後回報計數對不上）是唯一安全的做法：照計數去換會換到不該換的，照字面換而不回報則會讓錯的計數留在記錄裡。

## 一場假警報：emit_issues.json 沒有壞

`00013920` 的落地者回報 `tools/code_emit/data/emit_issues.json` 裡 `00018ba0` 那筆有 mojibake，原文應該是繁體中文卻讀成亂碼，並且判定「這是本輪之前就有的損壞」。

**這是誤報，檔案是好的。** 事後直接驗：整份 JSON 用 UTF-8 讀進來，`U+FFFD` 出現 0 次；`00018ba0` 那筆讀成亂碼的那四個字，碼位是 `0x5c1a 0x672a 0x89e3 0x8b80`，就是「尚未解讀」。壞的是 CP950 的 console 管線，不是磁碟上的位元組。

同一個坑這批踩到至少三次，另外兩次（`00025fe0`、`00019f80`）的落地者自己就辨出來了，做法是不要用 print 驗——`00019f80` 的做法是把寫進去的四個字串和從 verdict 解析出來的字串做字串相等比較、數 `U+FFFD` 的個數、看指定那段的碼位，`00025fe0` 是逐欄位比對後說明「第一次 readback 印出亂碼，那是 console 不是檔案」。

結論很簡單，但因為每輪換一個 agent，每輪都會有人重新踩：**要驗 UTF-8 內容有沒有壞，不能把它印到 console 看，要在程式內比對位元組或碼位。**（`MEMORY.md` 已經有「PowerShell 不能碰 UTF-8 檔」，那條講的是讀寫；這裡多一層是「印出來看」也不算數。）

## `_watcom_.dmp`：為了讓工作樹乾淨，把垃圾 commit 進版控了

`00012550` 那輪，review 階段用 WDISASM 反組譯 `UNIT.OBJ`，Watcom 的 DOS 工具在 repo 根目錄掉了一個 82 byte 的 `_watcom_.dmp`，內容只有一行 `WDISASM.EXE` 的路徑。它不是任何 function 的 emit 成果，沒過 review、沒過 gate。

落地者的處置是把它單獨 commit（`84a1c38`），理由寫得很清楚：留著不 commit 的話，下一輪的 recovery 階段會看到 pipeline 路徑之外的髒檔案而停下來等人。在當下的規則底下這是唯一走得通的一步——但結果是 repo 裡現在多了一個永久追蹤的 crash dump。**正解是 `.gitignore`，不是 commit**；那是規則層的判斷，不是落地者這個角色能自己做的，所以他明講了「這件事要留給人決定」。現在 `.gitignore` 裡沒有它，`_watcom_.dmp` 還在版控裡。

順帶一提，這也是這條 pipeline 的一個真實邊界：它對「工作樹必須乾淨」的要求是硬的，而工具鏈會在它管不到的地方掉檔案。這種衝突只會再發生。

## pitfalls.md 的懸空引用

`00027070` 與 `00025fe0` 兩輪的 reviewer 各抓到一次同樣形狀的東西：`src/` 的 header 引 `rebuild_info/pitfalls.md` 當作某個事實的出處，而 `pitfalls.md` 裡沒有那一條。

- `src/unitstat.h` 有三處寫「rand() is never seeded by the game (rebuild_info/pitfalls.md)」。事實本身是對的（`ghidra_snapshot/functions.txt` 裡 `srand` 在 `00042d1a` 標成 orphan_block，沒有任何 caller），只是 `pitfalls.md` 沒有這條——現在 grep `srand` / `seed` 一個都不中。
- `src/table.h` 引 pitfalls 當作「裝備掃描沒有 0xFF sentinel」的出處，同樣沒有這條。

對照組是 `0001f7d0` 那輪：emitter 發現「固定字彙浮動指示第 1 格的 x 偏移是位置不是字距」這件事之後，**先單獨開了一個 commit（`26fb1ef`）把它寫進 `pitfalls.md`**，才去做自己的落地。規範（`rebuild_info/_index.md`：發現當下就要記）是有的，做法也有人做對過，但這批四十支裡執行得不一致，兩次只留了引用沒留條目。留下的引用比不留更糟，因為它讓下一個讀的人以為那條已經寫過了。

順帶：`0001f7d0` 這支現在 `git log --grep "@ 0001f7d0"` 會回兩筆，因為 pitfalls 那筆的內文也提到同一個位址；落地的是比較新的 `4ff6e61`。

## 12 條 concern 幾乎是同一件事

這批記了 12 條 equivalence concern（統計的 `concern_mismatches` 是空的，verdict 與檔案對得上），分佈在 6 支函式、每支 emit 與 review 各一條。把它們排在一起看，**六組裡有五組是同一類：原版讀到自己資料結構外面去，答案由「旁邊剛好是什麼」決定，而重建的「旁邊」是連結器排的，不是原版的。**

- `0001c520` / `00019f80`：兩張地形修正表，`00060040` 起六個 int（ap）與 `00060058` 起六個 int（def），中間剛好 24 bytes。shipped map 資料會用 terrain class 6 去索引，所以 `ap_table[6]` 在原版就是 def 表的第一格（常數 0），而 `def_table[6]` 是 `00060070` 那個 dword，它的第一個 byte 是 `data_fdps_village_mode_flag`——一個 `fdps_run_village_phase` 會寫 1 進去的活著的全域。也就是說 def 表越界讀到什麼，靜態讀 image 是讀不出來的。全部 68 個 `M<map><layer>.MPL` 地形層跑完的直方圖是 0: 27398、1: 161、2: 1018、5: 7028、6: 3222，class 6 出現在十六張地圖的 layer 0，這條路是活的。
- `00025fe0`：PROEQU.DAT 只有 216 bytes、36 筆、涵蓋 class code `0x00..0x23`，而 class code 一路到 `0x27`。`0x24..0x27` 的六個 byte 比較落在檔案後面，讀到的是 allocator 留下的東西。
- `0001f510`：指示佇列的游標沒有任何界限。掃 operand `0x00064378` 全 image 回 24 條指令，四條無條件 +4、兩條歸零（`0001f4ff` 播完之後、`000262ac` 在 `fdps_apply_item_effect_to_targets` 的 prologue），沒有任何一條拿它和 200 格比。一批排超過 50 個彈出字就會衝出三個陣列的尾巴；原版三個陣列是連續的（`0x64120` / `0x641e8` / `0x642b0`，間隔 200），重建則是撞上連結器擺在後面的任何東西。
- `000232b0`：最近格搜尋一格都不接受的時候，`[EBP-0x58]` / `[EBP-0x54]` 只在 accept 分支（`0002342e`）被寫過，loop 出口直接落到記錄寫入，所以單位被放在堆疊殘留值上。emit 出來的 C 忠實地讓兩個 local 不初始化，而且**刻意沒有**拿 anchor 去填它——填了會改變所有殘留值剛好是合法格子的地圖上的落點。

意思是票 23 不只要決定「這些全域裝什麼」，還要決定「它們彼此排在哪」。這一批把五個具體的相鄰性契約推到了它面前。第六組 `00013920` 是另一類：單位記錄 `+0x34` 那個 byte 是打包的，`AND AL,0xf` 是 AI 模式的低 nibble、`AND AL,0x40` 與 `AND AL,0x80` 各是一個旗標，而這支的 `AND AL,0x1` 讓治療分數加倍——所以 bit 0 是模式 nibble 的最低位而不是獨立旗標，「AI 對奇數號模式的治療加倍」就是 assembly 講得完的全部，常數只好中性地叫 `AI_BEHAVIOR_MODE_BIT_0`。
