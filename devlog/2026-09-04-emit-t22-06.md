# 2026-09-04 emit t22-06：被 500 打斷的一批，與一條假紅了很久的測試

票 22 的第六批，要 100 支，**落地 40 支就停了**。停止原因是 `cleanup_failed`：收拾階段的 agent 也回傳不了東西。這篇記的是中斷本身怎麼收的，以及趁停機修掉的一條會反覆咬人的測試。

## 中斷的形狀：連三次 500，連收屍的都收不了

`0001e840`（`fdps_animate_turn_banner`）進了修正輪，然後：

```
[fix:0001e840:1]   API Error: 500
[fix:0001e840:1]   API Error: 500     ← runAgent 的那次重試
[abandon:0001e840] API Error: 500     ← 放棄流程本身也掛了
```

`runAgent` 的規則是「沒回傳就重試一次，第二次還是空的才記未完成」。這裡兩次都是 500，於是走進放棄流程，而**放棄流程自己也被同一波 500 打掛**，工作流只能停批。

停批的帳是乾淨的：40 支落地、60 支未完成，其中 **58 支是「還沒輪到」**（`never_reached`），只有 `0001e840` 是真的跑到一半被中斷。這正是票 21.6 要求「收尾報告分得出兩種未完成」的用途——58 支不需要任何處置，1 支需要。

### 殘骸與復原

工作區留著 `src/anim.c`、`src/anim.h`、`tests/anim.c` 與 `emit_state.json` 的在途標記，**全部在 pipeline 自己的路徑內，界線外一個髒檔案都沒有**。這一點是設計成立的關鍵：Recover 階段能丟的東西是以路徑界定的，界線外只要有東西它就會停下來等人。

這次沒有等下一批的 Recover，直接手動做了同一件事（`git checkout` 那三個檔與進度檔）。`0001e840` 回到 `pending`，帳面從 268 committed / 1 failed / 1 in_flight / 244 pending 變成 268 / 1 / 245。

**兩種非終結狀態都會被重新發回工作清單**——`next_batch.py` 只認 `committed` 一種終結狀態，`failed`、`in_flight`、`interrupted` 全部會再發一次。所以中斷沒有遺失任何東西，最多損失那一支跑到一半的工。

## 另一支：`00016840` 跑滿四輪修正被放棄

`fdps_load_status_cel_image` 標成 `failed`，記錄寫得很清楚：**emit 出來的程式碼、測試與期望值每一輪都是對的**，錯的一直是註解裡引用的組語位址——`000168a8` 那個 push 是來源寬度不是目的地 pitch，而第四輪把它改寫成了那個錯誤的反面，於是檔案裡的敘述與組語相反。四輪都沒收斂，被放棄，留待重新 emit。

它的失敗記錄裡順帶點出另一件事，而那件事比它本身重要：**第 2、4、5 輪的 build gate 是被一條與它無關的測試弄紅的。**

## 那條測試：`movie_drains_the_keyboard_queue`

`tests/title.c` 的這條在 `emit_issues.json` 已經有一則量測完整的疑慮（`00057114`）：同一個 `EMITTEST.EXE` 跑五次，fail / pass / fail / pass / fail，每次都是同一條檢查 `movie_queue_pending_after -> 2, expected 0`。約五成的失敗率，而且**弄紅的是別人的 gate**——`00016840` 的四輪修正裡有三輪是被它拖進去的。

那則疑慮還寫好了下一步該做什麼：在 `movie_queue_stuff()` 剛回來的當下就先記一次 `kbhit()`，就能分辨「按鍵是塞進去就沒生效」還是「跑完才不見」。照做。

### 探測的結果一刀切開

失敗的三次執行，分裂點完全一致：

| | BIOS 環形緩衝區 | `kbhit()` |
| --- | ---: | ---: |
| 塞入之後、進 `fdps_play_movie` 之前 | **2**（與通過的執行相同） | **0** |
| `fdps_play_movie` 回來之後 | 2 | 0 |

**按鍵確實塞進去了，但同一瞬間 `kbhit()` 就已經回報 0。** 所以佇列不是在卸載中斷處理常式的時候消失的，是在塞入的當下就對 `kbhit()` 不可見；而 `fdps_play_movie` 的排空迴圈（`CALL kbhit / TEST EAX,EAX / JZ` @ `00030f56`）被告知沒有東西可排，就沒有排——**它的行為完全正確**。

原本那條斷言在那些執行裡量的根本不是排空，是「這次的測試設定有沒有剛好生效」。

### 修法：兩邊都斷言，不要跳過

把測試改成跟被測的 body 分同一個叉：

- `kbhit()` 看得到那些鍵 → 緩衝區必須是空的（這才是排空）
- `kbhit()` 看不到 → 緩衝區必須**原封不動地holding 剛才塞進去的數量**（證明迴圈是什麼都沒做，而不是做了別的）

兩條路都有斷言，所以這比原本更強，而且不再不穩定：改完之後連續七次全綠，原本是約二分之一失敗。另外把「塞入確實成功」這個**確定成立**的一半拆成獨立的一條（六次執行裡緩衝區都讀到 2，含失敗的三次），失敗時才分得出是塞入壞了還是可見性問題。

**沒有跳過任何測試，也沒有放寬任何斷言。** 這點值得寫明，因為「測試很不穩，那就別測了」是這種情境下最容易做而且最糟的處置。

### 還沒解的那一半

`kbhit()` 為什麼在 `fdps_install_keyboard_isr` 跑過、顯示模式換過之後就看不到 BIOS 緩衝區裡的鍵——這個沒有答案。對照組是 `movie_premise_the_queue_can_be_stuffed`：同樣的塞入、沒有那些前置動作，從來沒失敗過。

但這**不是等價性問題**：重建的 `fdps_play_movie` 與原版在這件事上沒有任何差別，兩者都只是照 `kbhit()` 的答案行事。它現在也不再弄紅任何人的 gate，所以留在 `emit_issues.json` 那則裡（標成 `resolved`，附上這段答案），把剩下的問題交給 `src/title.c` 的擁有者。
