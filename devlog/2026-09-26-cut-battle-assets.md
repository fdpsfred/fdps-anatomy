# 票 25.13 刪減與未用：戰鬥資源（第一段：轉錄、素材、workflow）

## 做了什麼

25.9 交給本票的六條發現（B1–B6）已經驗證過，本段不重判，照判定彙整轉錄進新的主題檔 `cut_content/battle_assets.md`：B2、B3、B5 照原結論，B1、B4、B6 照 `corrected_claim`。B1 的 ATTR 檔數改成 69；B4 的「聲音改由 EarQu.wav 另播」改寫成「動畫全程無聲，法術聽得到的聲音在動畫之後」；B6 把 `EB05`／`EL05`／`EE05` 的例外寫明。

票要求每一條寫出程式的選檔邏輯與實際算出的取用集合。判定彙整裡的集合（ATTR `+3` 值缺哪些、各肖像拿得到哪些法術、陣營 0 的法術聯集）直接照抄；寫頁面時另外用一支暫存腳本對原版遊戲檔重算了一遍 ATTR 的值域、63 張背景的重複組，以及 11 段施法動畫、`EB05`／`EL05`／`EMG19`／`EMG33`／`MAG11` 的格數與音效段指向。這是整體事實的統計，不是逐項判定，結果與 25.9 的數字全部一致。順手多掃了全部 525 個 SAF：沒有畫格指到的音效只有 `EMG19`、`EMG33` 各一段，這句寫進了 B4。

腳本第一次跑就失敗：`cut_content.read_vfs_member` 在函式裡才把 `tools/vfs_dump` 加進 `sys.path`，暫存腳本在呼叫它之前就 `from vfs_dump import parse_container`，拿到 `ModuleNotFoundError`。自己補上路徑就好，不是工具的問題。

## 素材

產生器寫成 `tools/cut_content/battle_assets_media.py`，登記在 `cut_content.GENERATORS["battle_assets"]`。25.11 同時在 `cut_content.py` 登記了自己的產生器，用的是「函式裡才 import 模組」的包法；本票一開始寫成模組層級的 `from battle_assets_media import generate`，編輯時發現檔案已被 25.11 改過，就改成跟它一樣的寫法，避免兩種登記方式並存。commit 時用「HEAD 版本加上本票這幾行」組內容放進暫存區，不夾帶 25.11 那段。

幾個取捨：

- **不裁切**。25.11 的產生器把動畫裁到整段動畫共同的最小框；本票保留整個 320×200 畫面。戰鬥背景只蓋上面大約 130 列，下方是戰鬥介面的位置，裁掉就看不出它在畫面上的位置；特效段（`EB05`／`EL05`）的閃電也是從畫面頂端劈到目標位置，位置本身有意義。
- **永遠不載入的動畫，帶的音效全部輸出**。票面寫「SAF 內嵌但不響的音效存 WAV」；檔案本身不會被載入，它帶的音效當然也不會響，所以 B2 的 22 段、B3 的 2 段一起輸出。會播的動畫（B4）只輸出不響的那幾段。
- **`Bonus.wav` 原樣複製**，不經 SAF 解碼。它是容器裡本來就完整的 RIFF（`fmt`、`data` 128,000 byte，後面另有 `LIST`、`cue ` chunk），重新包一次反而會丟掉那些 chunk。
- **空殼（B5）沒有素材**：一個沒有圖層的畫格，畫出來是全透明的 320×200，沒有看的價值。

`check` 要求每個素材檔都被主題檔引用，而 B2、B3 逐格輸出共 299 張 PNG。每段動畫在頁面上放一張總覽圖，下面一行把逐格與音效列成連結。這一段連結是用一支暫存腳本從產生出來的檔名展開的（頁面裡先放 `<!--MEDIA:B2-->` 這種佔位），展開後頁面就是普通的手寫 Markdown，之後不再依賴那支腳本。

產生器的測試先寫：命名規則（全小寫、去副檔名、段號、格號兩位數、每個可能的名字都要過 `MEDIA_NAME`）是純函式測試；有原版遊戲檔時另跑一次完整產生，檢查只寫出規格裡的檔、每格一張、取樣率照 SAF、會響的段不輸出、WAV 成員原樣。完整產生約 35 秒，`verify-media battle_assets` 逐 byte 相同。

總量：347 個檔、3,654,372 byte（PNG 318 個 3,225,676 byte，WAV 29 個 428,696 byte），全部進版控。本票沒有 CD 音軌。

`cut_content.py check` 在工作目錄上跑會報 23 個問題，全部是 25.14 還沒寫進 `story.md` 的 `media/story/` 素材；本票自己的部分另外在「HEAD 加本票改動」組出的暫存樹上跑，結果乾淨。

## 新痕跡的 workflow

25.9 交給本票 11 條新痕跡（`T13-01`…`T13-11`），有重複（`T13-07` 與 B3/B5、`T13-08` 與 B3、`T13-01`／`T13-02` 與 B1 的判定原文都在講同一件事）。照 25.10 的腳本寫了 `tools/cut_traces/traces_ticket25_13.js`，`cuttrace.py` 不動。改的地方：編號、`--ticket 25.13`、主題頁換成 `battle_assets.md` 並說明它收什麼、分類說明補上 CONTEXT.md 剛加的兩條規則（遊戲自己模組的未用成員歸殘留內容；FDPS 改寫過的前作程式歸殘留內容，原封不動的才是前作遺留）、`absorbed` 可以指向任何主題檔的條目（`T13-03` 看起來會被 25.11 的排除項 U09 吸收）。

踩到一個 `cuttrace.py` 的缺口：`ROUTES` 沒有 `25.10`，所以 25.13 的判定沒辦法把一條程式痕跡轉給 `code.md`。依指示不改 `cuttrace.py`；腳本裡請 agent 遇到這種情況以 `kb_fix` 交出、`route_note` 以「code.md:」開頭，落地時由本票自己轉給 `code.md`。11 條裡看起來最可能碰到的是 `T13-06`（NPC 攻擊敵人時經驗值記給被攻擊的敵人），但它比較像 bug 的機制，會走 `known_bugs`。

本機沒有 JS 引擎，腳本靠逐段對照 25.10 的版本與 `git diff --no-index` 自查；另外確認沒有 CR、反引號成對，並實際跑過腳本裡會用到的 `pending`、`check --json`、`rescan` 三個指令。

## 審查後的修正

第一段 commit 之後跑了兩軸審查（規範、票面），各由一個獨立的 agent 做。改掉的：

- **workflow 的停止理由過濾退化了。** 其他幾支 cut_traces 腳本已經改成只保留英數與少數標點，本票抄的是更早的版本，只把雙引號換成單引號；agent 的備註若帶 `$` 或反引號，送進 `--stopped "..."` 時會被 shell 展開。改回與其他幾支一致的寫法。判定形狀裡的 route 列舉也拿掉 `25.13`（轉給自己沒有意義）。
- **B7 重寫了 bug 的成因。** `_index.md` 規定被封住的內容只寫封住的是什麼，成因連到 `known_bugs.md`；初稿把判獎讀的堆疊槽、兩個位址與 `fdps_transition_zoom` 存下的 EDI 全寫了一遍，也與 `pitfalls.md` 那一列重複。改成一句結論，加上連到 `known_bugs.md` 第 18 條的連結（該檔屬 25.5，工作目錄已有、尚未 commit；`code.md` 的 C1 也是這樣連的）。
- **B5 多了一句判定裡沒有的設計動機**（「所以不需要收尾的法術也要放一個檔」）。改成獨立的選檔邏輯段，動機照實寫「判斷不出來」。
- 開頭說明裡的 `units.md` 已經在 HEAD，改成連結；`items.md`、`story.md` 仍是純文字。
- **產生器的檔案清單寫了兩次。** `planned_names()`（給測試用）與 `generate()` 各自依項目種類分派，兩邊的 else 分支甚至代表不同種類，遲早會漂移。改成單一的 `plan()`，回傳（檔名、寫出函式）的清單，兩者都由它衍生。總覽圖直接用 `saf_decode.write_filmstrip`、不經 `write_png` 輔助函式，這件事寫進了工具索引。重生結果不變，`verify-media` 仍逐 byte 相同。

沒改的：審查指出產生器的調色盤載入與逐格轉 RGBA 和 25.11 的 `units_media.py` 形狀重複。兩支是各票自己的產生器，抽共用函式要動 25.11 的檔案，先不動。
