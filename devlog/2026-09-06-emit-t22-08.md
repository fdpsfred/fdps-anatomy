## WDISASM 有一個靜默錯的用法

`00024490` 的 reviewer 留下的，值得單獨拉出來：**`WDISASM -l=<path> -a` 是錯的，而且不會告訴你。** `-a` 在這裡不是合法選項，工具 exit 5，但**照樣寫出一份 listing**，而那份 listing 會漏掉 function——第一次讀 `SAVE.OBJ` 時 `fdps_load_game_screen` 整支不在裡面，即使 PUBDEF 明明就在 object 的 bytes 裡。正確用法是在 object 自己的目錄下跑 `WDISASM -l <file.obj>`。

這是會浪費一天的那種坑：沒有錯誤訊息、輸出看起來完整，你要先知道某支 function 該在裡面才會發現它不在。往後任何人想用「把自己編出來的 OBJ 反組譯回來跟原版比」這招驗證等價性，都會踩到。

### 拆檔真正花時間的不是搬 function，是常數住在誰旁邊

純文字搬移會編不過，因為這個檔的 `#define` 從來不是集中在檔頭，而是「誰先需要就寫在誰旁邊」。三處要處理，而且**每一處的處理方式都是回頭讀組語重推，不是把定義抄過去**：

- `SCENE_PAGE_*` / `SCREEN_WINDOW_*` 定義在等待迴圈那一段，可是關窗也在用。等待迴圈搬去 `statunit.c` 之後，`statwin.c` 要自己留一份——留的時候是照**關窗自己的** push 位址重新推（`000168fa`，以及 `00016932..00016958`），不是把等待迴圈那份抄過去。抄過去大概率會得到一樣的數字，但「大概率一樣」不是這個專案接受的東西。
- `BLIT_MODE_OPAQUE` 定義在載入底圖那一段，真正用它的是等待迴圈的陰影 blit。`statunit.c` 自己定義一份，引用 `00017229` 的 `PUSH 0x0`（從 `000170c0` 的反組譯確認）。
- `tests/statunit.c` 要補 `<stdio.h>`，因為跟著面板 fixture 一起過來的 `FACE.CEL` 探測用到它。

每個檔各自定義共用的 VGA／幾何常數，本來就是 `src/` 的既有慣例（`anim.c`、`blit.c`、`btlend.c`、`chapter.c` 各自定義自己的 `VGA_SCREEN_BASE`）。所以複製定義不是妥協、是規則；要小心的是**複製出來的每一份都要各自從組語推一次**。

一句話版本：拆一個超標的檔，難的部分不是 function 的邊界在哪，是散在 function 之間的 `#define` 各自屬於誰。

拆檔期間 Ghidra 只讀不寫（兩次 `disassemble_function`），所以沒有重匯出快照。

## 然後又是同一個原因收工

結局跟 t22-07 一字不差：**手上這份工作清單是拆檔前排的，路由已經變了，清單過期。** 剩下 98 支狀態記成 `not_started_routing_changed`，一支都沒開工。

差別在時機。t22-07 跑到第 65 支才撞上，這批**排了 100 支、跑了 2 支就沒了**。連續兩批死在同一件事上，值得寫下來的是形狀而不是次數：

**清單在批次開始前一次排好，而 emit 本身會改變路由。** 只要有任何一個檔在批次中途超標，後面的清單就作廢——而超標是 emit *成功*的副產品，不是失敗。批次排得越長，被作廢的期望值越大；更糟的是 callee-先於-caller 這個排序把大 function 全推到後段，而後段正好也是最容易把檔案撐爆的地方。兩者是同一個成因的兩面。

這個 workflow 目前沒有「拆檔後就地重排剩下的清單」的能力，也還沒有人決定要不要加。損失是規劃階段的浪費，不是產出的損失（下一批照新路由重排就能繼續），但這批的比例是 98 比 2，不能當成雜訊看待。

## 一件確認了但還沒有人擁有的事

`fdps_load_game_screen` 有一個確定的洩漏：`malloc(0x59cb)` 在 `0002451b`，整支 function 到 epilogue 為止沒有任何 `free`。這是原版的行為，測試把它**正面**釘住了（確認那條路徑跑完剛好多一塊 used heap block，cancel 那條剛好 0），所以重建版不會不小心把它補掉。

但這正是典型的「照直覺寫就會與原版不同」：任何人之後回頭讀那段 C，都會想在 `fclose` 後面補一行 `free(save_image)`。`rebuild_info/pitfalls.md` 目前沒有這一條。
