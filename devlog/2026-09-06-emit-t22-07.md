## 三面牆

這批的 gate 沒有抓到任何一支 function 的等價性缺陷。它抓到的全是環境問題，而且每一面牆第一次現身時，症狀都落在跟當下這支 function 毫無關係的檔案裡——這是最花時間的部分。

### 一、32 MB 的 guest 已經沒有餘裕了

emit `0001cdc0` 時，新測試檔加了一個 64,000 byte 的 static frame buffer，整支測試程式就死在 `tests/anim.c` 的 banner case，DOSBox-X 吐 `E_Exit: Illegal descriptor type 0 for int 8`。改的是 gauge，死的是 anim，第一時間完全指錯方向。

真正的鏈條是：`tests/anim.c` 每個 banner case 都把整份 27.4 MB 的 `MISC.VFS` 一次 `malloc` 進來，32 MB 的 guest 底下整支 `EMITTEST.EXE` 只剩約 1 MB 餘裕。BSS 一變大，`fdps_animate_turn_banner` 那個不檢查回傳值的 `malloc` 就拿到 NULL 並照樣寫下去，蓋掉 DOS/4GW 的 IDT。門檻低到荒謬：把一個 7,000 byte 的 static 陣列加進任何一個測試檔，**不必被執行到**，就足以重現。也就是說接下來任何一支新 function 落地都會撞到這道牆。

死路：直接把 `memsize` 調到 64 不行。DOS 版 `wcc386` 在 64 MB 之下每個 unit 都以 `A PAGE FAULT HAS OCCURRED DUE TO INSUFFICIENT MEMORY` 收場，建置階段就先垮，連跑測試都輪不到。

最後的解（`d12b9d3`）是把兩個 guest 分開：`build_min.py` 的 `write_conf` 多一個預設 32 的 `memsize` 參數，`build_emit.py` 只在「執行」那一段傳 64，工具鏈那段維持 32。實測 32 MB 重現故障、64 MB 下 12,878 個檢查全過。

### 二、測試 case 把載入器會 free 的全域指向自己的 static

emit `00016130` 時整套測試在 rsrc/village 段爆 `_HEAPBADNODE` 並卡死。肇因在 `tests/menu.c`：ring case 把 `data_fdps_map_unit_array_ptr` 與 `data_fdps_cel_sprite_cache_ptr` 指向測試檔裡的 static 就離開，稍後 `fdps_field_load_chapter_resources` 依「計數不為零」把那些 static free 掉。這件事在既有連結佈局下剛好無害，新 function 一落地、佈局一動就翻臉。寫進了 `emit_pipeline.md`（`76fb445`）。

跟第一面牆是同一種形狀：測試檔留下的髒狀態要等下一個人來撞。

### 三、那條會飄的測試換了一個 case 繼續飄

`tests/title.c` 的 keyboard queue 那組。`00016840` 的第 2、4、5 輪 gate 都栽在 `movie_drains_the_keyboard_queue`，而且不是從原始碼可重現的：同一顆 1,309,901 byte 的 `EMITTEST.EXE` 反覆執行，第 2 到第 5 輪之間大約 8 次乾淨對上 7 次只掛這一項。上一批已經為此開了 `7d538db`。

這批新增的事實是它挪窩了。`0002dcf0` 第 2 輪的 gate 掛在 `movie_premise_the_queue_can_be_stuffed` 的 check 2（`kbhit` 回 0，但 BIOS ring 剛剛才被塞進兩個鍵），不是每一次歸檔都指名的那個 case。這正好推翻 `tests/title.c` 的註解與 `emit_issues` 裡 `00057114` 那則答案共同倚賴的一句話——「premise case 沒有前提要成立，從來沒失敗過」。

那一輪的處理方式值得抄：不是斷言，是量。從頭重建（`build_emit.py all`）到 `EMITTEST.EXE` 1,601,325 byte、sha256 `a52efae3…`，跟失敗那次的 gate 回報同尺寸同 13567 檢查數；然後同一顆 image 再跑三次 `build_emit.py run` 加一次 `gate.py check --target emittest`，五次連過、13567 檢查全過，事後再 hash 一次確認 image 從頭到尾沒變。一份原始碼同時給得出兩種結果，肇因就在程式文字之外。

這件事到現在還沒有人擁有，`src/title.c` / `tests/title.c` 的 emit 者是最後該收它的人。

## 需要修正輪的十支：幾乎沒有一支是程式錯

65 支裡 55 支一輪過，10 支進了修正輪，其中只有 `00020c60` 走到兩輪。值得記的是這些 blocking issue 幾乎全是**散文錯**——註解、標頭說明、plate 把事實講反或講寬——而不是程式錯。emitter 的 C 幾乎每次都是對的，錯的是它對自己寫的東西的說法。

- `00020c60` `fdps_show_chapter_title_card`，這批唯一的兩輪，而且第二輪的錯是第一輪修正自己造出來的。第一輪的註解說三十支章節進入 handler 會先設 `data_fdps_chapter_current_chapter_id`；改寫成「呼叫時全域已經帶著章節」之後，順手斷言列出的那五個寫入點是全部。第三輪才發現那是拿 `get_xrefs_to` 預設的第一頁 100 筆就下的結論。用兩條路重算：分頁取全 133 筆 ref、34 筆是 WRITE（第二頁 33 筆裡有 29 筆，`fdps_chapter_01_end` 到 `fdps_chapter_29_end` 各一）；再用 `search_instructions` 掃 `[0x00069cf4]` 得 56 筆 match，寫入形式全是 MOV，沒有 INC/ADD/AND 形式，所以 34 是完整數而不只是 MOV 數。教訓一句話：**xref 有分頁，「這是全部」這句話沒有分頁過就不要寫。**
- `00015860` `fdps_render_ring_menu_frame` 的 blocking 是常數說明。`0x3d860a8a` 距離最接近 2π/96 的 float 差八個 ulp（mantissa 欄 395914 對 395922），不是原本寫的一個；而且歸因整個錯了——換成 `0x3d860a92`，半徑 `0x18` 上的角度只高出 π/2 約 4.4e-8，`sin` 回 1-1.1e-15，24 倍是 23.999999999999975，截斷後還是 23。那個 23 來自 `sin` 不會超過 1 加上 `__CHP` 的截斷，跟常數挑哪一顆無關；會改變它的是改成四捨五入，不是改常數。
- `000170c0`、`00029660`、`0002cda0`、`0001e840`、`00020820`、`00016840` 是同一類。舉三個具體的：`0001e840` 原本寫「回來時畫面上不留 banner 的痕跡」是假的——最後一格表項是 -60、招牌欄 -40，五個 24 像素格裡有三個通得過 `fdps_draw_tilemap_cell` 的 `x > 0`，收尾 blit 把 scratch 的 24..335 欄搬回螢幕 4..315，所以螢幕 4..59 欄回來時帶著招牌的像素（對照出貨的 `Turn.saf` 是 660 byte），只有數字是真的沒了。`00020820` 把六段高度的走訪順序寫顛倒——counter 只遞減，先到 120 最後才到 190，而 190/170/150/135 是它最後才碰到的列。`00029660` 把唯一的呼叫點寫成 `000293a1`，那其實是經 `0x60304` 表的間接派送，真正的呼叫點在 `00029316`。
- `000119e0` `fdps_battle_move_unit_toward` 是唯一一支 blocking 落在測試而不是文字的。既有的十個 case 分不出 retarget 區塊與選擇迴圈的 fallback，因為在那十個 case 裡兩者的答案剛好一致。補的新 case 用的手法值得變成常態：把 retarget 對外的唯一效果（`dest_x = chosen_x; dest_y = chosen_y;` 的寫回）暫時換成自我賦值、重建、確認掛掉的**恰好是**新 case 那三個 assertion，才算證明它有鑑別力，而不是寫了就算。

另外一件對不上的事：emitter 自己數的輪次跟 workflow 觀察到的不一致（`00020c60` 自記三輪、workflow 記 2；`0002cda0` 自記 0，當時人在第 2 輪）。落地一律照 workflow 的數字寫，但兩邊會有落差這件事本身要知道，看 `emit_state.json` 的 `rounds` 時別當成 emitter 的自述。

拆檔連帶讓 routing 自己冒出一個結果：`data_fdps_ui_save_slot_occupied_flags` 現在由 `savepnl.c` 寫、`save.c` 讀，`build_routing.py` 就把它 route 到 `gamedata.c`，extern 從 `save.h` 搬到 `gamedata.h`，並照那個 header 裡每個陣列的慣例直接寫字面 3（`SAVE_SLOT_COUNT` 留在 `save.h`，`savepnl.c` include 它給自己的 slot 迴圈用）。`data_fdps_ui_saveload_is_load_mode` 三個引用者都在 `save.c`，留在原地。

## 35 筆 concern 進了 emit_issues

`0002dcf0` 與 `00028610` 各貢獻 6 筆，`00016300` 1 筆，其餘成對（emitter 一筆、reviewer 獨立確認一筆帶 `same_as`）。值得單獨點名的：

- `0002dcf0`：terrain class 為 6 時會索引到兩張六格表的下一格，而且這支 function 就是讀者、沒有任何前置條件擋它。原版裡 AP 表的 index 6 落在 `0x60058`（防禦表自己的第一格），防禦表的 index 6 落在 `0x60070`（第一個 byte 是 `data_fdps_village_mode_flag`），而十六張出貨地圖的 layer 0 真的帶 class-6 的格子。C 的形狀沒問題——OBJ 產出的定址形式跟原版一模一樣——差別只在 linker 把三個 object 放哪，所以這是純粹的票 23 佈局問題。
- `0002dcf0` 另一筆：`data_fdps_ui_terrain_hud_panel_offset`（`0x6016c`）在出貨映像裡是 `0x19`，全程式沒有任何地方初始化它（八個 reference 全在這支 function 內，六讀兩寫）。現在連結成零填的 stub，等於章節載入後的第一批面板會畫在第 0 欄，直到游標第一次走到低角落為止。票 23 必須給它帶初始值的定義，不能只給 tentative definition。
- `0001ff60` `fdps_draw_text`：-6 那個數字分支用裸的減 `'0'` 把字元換成 glyph index（`AND EAX,0xff` / `SUB EAX,0x30` @ `0002020b`），沒有範圍檢查。負值會讓 `sprintf` 產生 `'-'` 並把 index -3 送進 `fdps_draw_glyph`，讀到字型 sheet **前面**六個 byte；原版那六個 byte 是配置器留下的東西，重建的堆積佈局不同，畫出來的東西就不同，甚至可能落在沒有對映的頁上。reviewer 多找到一個 emitter 沒點名的來源：`fdps_shop_buy_loop` 有兩個會讓那個 slot 變負的算術寫入，`00033d83` 的 `SUB` 與 `00033e98` 的 `NEG`，後者緊接在一個 `fdps_draw_text` 呼叫之後。
- `00016300`：race name 區塊在 `0x97` 與 `0xa1` 之間只有十格，所以 race byte ≥ 10 的單位記錄會在該畫種族名的地方畫出職業名，`0xff` 會跑出區塊 0x96 格。`assets/` 與 `program_info/` 都沒有寫 race code 的值域。
