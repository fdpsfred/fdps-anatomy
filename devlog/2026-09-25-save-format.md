# 票 25.4：FDE.SAV 存檔格式

## 起點

票要的是一份照著就能寫出存檔讀寫工具的格式文件，外加每個欄位標出讀寫它的 function、用實際存檔驗證檢查碼。

先照規矩查前作。`fd2-anatomy/resource_info/save_format.md` 與 `program_info/save.md` 有完整的 FD2.SAV 佈局，`tools/fd2_play/gen_scenario.py` 與 `tools/program_analysis/realfile_groundtruth/dump_real.py` 各有一份 Python 的解密與檢查碼。FD2.SAV 也是 22,987 byte、同一組 `0x312b`／`0xa28`／`0x59c7`，密鑰常數也是 `0xa5`／`0x9014`／ROL 3——引擎是同一個。所以文件的骨架（整體佈局表、live-state 表、slot 表、加密一節）照抄前作的形狀，內容逐欄回到 FDPS 自己的 `src/` 與 Ghidra 取。工具沒有直接 import 前作（跨 repo），加解密十行照前作的寫法重寫。

## 與前作不同的地方

逐欄對下去，FDPS 與 FD2 在下面幾處不一樣，照抄前作的表會錯：

- 戰鬥狀態標頭 `+0x07`／`+0x08`：FD2 存游標的畫面座標，FDPS 恆寫 0（`00015257`、`0001525b` 的立即值 0），讀檔端也不讀。
- 標頭 `+0x0e`：FD2 是遊戲速度，FDPS 是戰鬥動畫開關（`0x60010`）。
- slot `+0xa07`：同上，FD2 的速度旗標在 FDPS 是戰鬥動畫開關；而且 slot 裡的順序是「地形面板、動畫」，標頭裡是「動畫、地形面板」，兩邊相反。
- FD2 的 slot 沒有存檔戳記。FDPS 在 roster 複本的最後 `0x14` byte 蓋上抽獎旗標與月日時分，這是 FD2 文件完全沒有的東西。

## 讀了哪些 assembly

`src/` 的註解已經把大部分偏移連到指令位址，但本票的前提是「寫過不等於寫對」，所以關鍵的幾段回 Ghidra 直接讀：

- `0x60118`（`"FDE.SAV"`）的 xref：六支 function。`fdps_draw_save_slot_panel` 不開檔，一開始把它算進「引用字串的七支」是錯的，文件改成六支加一支。
- `000568b7` 的 8 個 caller、`00056898` 的 4 個 caller，全部落在那六支裡。
- `fdps_save_game_screen` 的 `000242e4`–`000243ee`：戳記的五次寫入是對「推到 `+0xa00` 的指標」寫 `-0x4`..`-0x14`；`_dos_getdate` 的結構在 `[EBP-0x24]`，`-0x23` 是月、`-0x24` 是日，對上 `struct fdps_save_slot` 的 `save_month` 在 `+0x9fc`、`save_day` 在 `+0x9f8`。
- `fdps_load_game_screen` 的 `00024571`–`00024609`：讀回的順序與寬度，抽獎旗標前面那道 `CMP byte ptr [0x60070],0x0`。
- `fdps_battle_system_submenu` 的 `0001512a`–`000152a1`：四個 slot 章節 byte 的 `0xff`、五個區塊的 `memmove`、標頭十八個 byte。
- `fdps_title_screen` 的 `0002a35e`–`0002a398`：檢查碼相符而且 `+0x30c5` 不是 `0xff`，才同時清掉兩個選單項目的反灰。

最後一段讀出一個原版行為：存讀檔畫面在沒有檔案時造的是整份 `0xff`，所以只在章節之間存過 slot、沒在戰鬥中存過檔的人，下次開機標題選單的讀檔項目是反灰的。這不是格式本身的事，但「修好」它會改變行為，寫進了 pitfalls；機制本身是否該記進 `program_info/known_bugs.md` 交給 25.5 判斷。

## 找實際存檔

`fdps_game_files/FDE.SAV` 就在遊戲目錄裡（22,987 byte，修改時間 8 月 14 日 12:12）。另外在 25.9 的工作目錄看到它從兩片光碟 `PACK.VFS` 解出的 `FDE.SAV`、`F30.SAV`、`DEBUG.SAV` 共六份。知識庫不能引用 `workspace/`，所以驗證表只寫存檔本身的出處，不寫路徑。

七份全部通過：解密後重算的檢查碼等於 `+0x59c7` 存的值，再封裝一次與原檔逐 byte 相同。遊戲目錄那份的欄位也互相印證：slot 0 的戳記 8/14 12:12 等於檔案修改時間；live-state 的地圖腳本區塊前 703 byte 等於 `MAP00.DAT`（703 byte）；slot 1–3 章節 byte 是 `0xff`、其餘是 `b7 b6`、`2b 2b` 這類非 `0xff` 的雜訊——正是「檔案由戰鬥存檔從無到有建立，只寫了四個章節 byte」的樣子，而不是存讀檔畫面那種整份 `0xff`。

## 死路與沒寫進文件的觀察

- **`PACK.VFS` 的存檔拿來驗語意**：一開始想把六份 PACK 存檔也當成欄位語意的佐證，結果光碟 1 `FDE.SAV` 的 slot 1 在抽獎旗標的位置是 `0x81969999`，`DEBUG.SAV` 三個 slot 都是 `0x16b80587`，而且與前面 roster 第 31 筆的內容是連續的——看起來那一版的寫入端沒有在這裡存旗標，或存的是別的東西。那是票 26（另一版遊戲）的題目，文件裡只保留「檢查碼與加密相同」這個可驗證的結論，語意部分明說不在範圍內。
- **`+0x30d5`–`+0x312a` 的 86 byte**：七份存檔這一段逐 byte 相同（`bb bb … b9 b8 …`），連 PACK 那三組不同來源的存檔都一樣。可能是同一條「第一次建檔」的系譜一路帶下來，也可能是 DOS 下同一個堆積狀態重現的殘值；沒有程式讀它，所以沒有追下去，文件只寫「沒有任何程式寫入或讀取」。
- **地圖腳本區塊的長度**：最初以為 `0x8a3` 就是 `MAP%02d.DAT` 的大小，量了 63 個成員才知道 157–2,211 byte 不等，`0x8a3` 是上限（固定部分 `0x83` 加 80 筆部署記錄）。存檔端不管成員多大都搬 `0x8a3`，小的成員會把堆積上的鄰居一起搬進檔案。

## 為什麼沒有寫 workflow

CLAUDE.md 規定逐一判定 function 或 data 的工作要用 workflow。本票沒有要替任何 function 判定身分、calling convention 或 emit，也沒有要替 Ghidra 的資料符號下判斷；「欄位由誰讀寫」是七支已經 emit、已經 review 過的 function 裡的事實，查法是 xref 加上逐段讀 assembly，屬於整體事實的調查。所以文件與工具直接寫，沒有另開 workflow。

## 審閱抓到的

交一個獨立的 agent 只讀審閱文件、工具與 pitfalls 的新列，對照 `src/` 與 Ghidra。沒有偏移錯，抓到的是措辭把事實說大了：「三個會寫檔的路徑」其實是兩條寫檔路徑加一個只讀的版面組裝；讀檔時地圖單位陣列是配置 `0x1e00` 但只搬回單位數 × `0x50`，原文讀起來像整塊搬；「所有 u8 欄位零延伸」漏了四個開關是 byte 對 byte 原樣搬；單位陣列超過單位數的尾巴不是「建檔時的內容」，而是任何一次單位較多的戰鬥存檔留下的。工具這邊，`dump` 原本對章節 byte 是 `0xff` 的 slot 照樣解出分、時、金錢，印出 `save_minute: 3065493175` 這種殘值，與文件「不該解讀」的結論自相矛盾，改成只印標記，並加了一個測試。

## 工具

`tools/save_format/fde_sav.py`：`dump`／`verify`／`decrypt`／`seal` 四個子命令，14 個單元測試。測試的預期值不從實作推：密鑰流前三 byte `cc 00 a1` 是對 `000568c9`／`000568ce` 手算的，欄位偏移取自組語，另有兩項實檔驗證。
