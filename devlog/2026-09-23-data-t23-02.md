# 票 23 資料 emit 批次 t23-02

t23-01 用 `limit 12` 試跑證明管線走得通之後，t23-02 是票 23 的第二輪，也是最後一輪：不設上限，把剩下的 220 個全域一次判完、一次落地。跑完後連結時仍然 undefined 的全域是 0。

## 死路：gate 紅過一次，錯在把 dump 往後數錯一個 dword

這一輪唯一的失敗是落地後的第一次 gate 紅燈（`repairs` 1），而且是 `data_emit.check`（把每個落地的全域跟 `FDPS.LE` 逐 byte 比對）那一關紅，不是編譯或單元測試。

出錯的是 `data_fdps_audio_cd_repeat_tick_counter`（00060170）。第一份 verdict 把它判成有初值 25 的物件，寫成 `int data_fdps_audio_cd_repeat_tick_counter = 25;`。判定的根據是一段從 00060160 開始的 `read_memory` dump 裡看到 `0x19`——但那個 `0x19` 在 0006016c，是前面四個 byte 的 `data_fdps_ui_terrain_hud_panel_offset`（一個 short，`0002dda4` 那條 `MOV word ptr [0x0006016c],0x19` 在執行期也把同一個值寫回去）。00060170 的 image dword 其實是 0，正確的形式是不給初值的 tentative definition。錯的不是判讀邏輯，是用眼睛在一行十六進位裡數位移。

修正回合照 workflow 的規矩只改 verdict、不碰 `src/`（落地是從 verdict 重新 apply 的），重判成 `zero`，順手把誤判的來龍去脈寫進該符號的 evidence，免得日後有人翻到舊結論又走回去。重新 apply、重新 gate 就綠了，所以這批最後還是一次 commit（8c1dfe7）。

這件事有兩個值得記的地方：

1. **抓到它的只有跟原版的逐 byte 比對。** judge 自己填的 `confidence` 是 high；回掃階段只挑信心 low 或留了 `open_questions` 的 verdict 回頭再看（`land.py rescan-list` 的條件），而這 220 份 verdict 全部是 high、`open_questions` 全空，所以回掃這一輪一份都沒排到（`rescanned` 0）。信心欄位是自評，不是關卡；真正的關卡是 gate 裡那個比對。
2. **「全部一起落地、只跑一次 gate」這個設計這次賺到了。** 一個錯的 verdict 只花一輪修正，不必把 27 個檔拆成 27 次 gate（那會是 27 次 DOSBox-X 建置）。它的代價是 gate 紅的時候要從一堆檔案的訊息裡認出是哪個符號，這次 `check_data` 直接指名符號與位址，所以代價沒有真的付出去。後備路徑（gate 修不綠就退回一檔一檔重跑）跟 t23-01 一樣沒有被走到，到現在仍然沒有實戰驗證過。

其餘失敗欄位全空：判定失敗 0（220 份 verdict 第一次 `land.py validate` 就全過，沒有觸發重判）、落地失敗 0、落地被拒 0、workflow 沒有中途停下、`notes` 與未完成清單都是空的。

## `recovered` 與 `not_reached` 這次都是 0，但不是同一件事

- **上一輪被中斷、這一輪撿回來的（`recovered`）：0。** t23-01 是正常跑完收尾的，開跑時 working tree 乾淨、`workspace/data_emit/in_flight.json` 這個落地中標記不存在，恢復階段沒有殘局可撿。是「本來就沒有東西」，不是「撿失敗」。
- **這一輪根本沒輪到的（`not_reached`）：0。** t23-01 的 `not_reached` 有 12 個名字，那是因為那次刻意把上限設成 12，清單還剩 208 個沒被列出來。這一輪沒設上限，worklist 一路取到空為止，清單被抽乾，沒有餘量剩下。

數字剛好都是 0，一個的意思是「沒有殘局」，另一個是「沒有餘量」，合併起來看就會失真。

## 唯一的改路由：`data_fdps_indicator_queue_count`

戰鬥傷害數字的佇列有三個 200 byte 陣列（x 偏移、單位索引、字形 id）加一個游標。四個產生者都用 `MOV byte ptr [EDX+...]` 寫進陣列、再無條件 `ADD [0x64378],4`，**整支程式沒有任何一處把游標跟 200 比較**。字形陣列從 0x642b0 起算 200 byte 剛好到 0x64378，也就是說原版「寫到第 200..203 格」時打到的是游標自己。要重現這個行為，游標必須緊接在字形陣列後面。

原本的路由把游標分給 `gamedata.c`，三個陣列卻在 `indicat.c`——分在兩個 `.c` 就不可能保證連續配置。workflow 的 reroute 階段因此把它改由 `indicat.c` 擁有（commit 0b9438d），`extern` 跟 `tools/code_emit` 的 routing 一起搬。同樣的理由，這四個符號都不能寫成 tentative definition，而是明寫 `= { 0 }` / `= 0`，讓它們落進 `_DATA` 並依原始碼順序相鄰。

`data_fdps_audio_sample_handle_table` 是另一種形狀的同類問題：`fdps_audio_sample_is_playing` 不檢查索引，呼叫端會傳進 `-1`，原版因此讀到表前面那個 dword（0x69d2c，沒有人寫的零 BSS）。重建必須自己擁有那個 dword，verdict 用 `zero_guard_before` 在表前面放一個 `static void *audio_sample_slot_below_table = 0;` 頂上去。
