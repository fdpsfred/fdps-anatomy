# 2026-09-22 票 22 收尾：疑慮總掃與它挖出來的旗標問題

## 總掃 workflow 怎麼長出來的

開工前三項確認都過了：Ghidra MCP 回 `FDPS.LE`、工作區乾淨、`next_batch.py --stats` 514 committed。起點 build gate PASS，量到一次 1012 秒——比印象中的「十幾分鐘」還長一點，所以 gate agent 的 prompt 不能叫它前台跑（單一指令上限 10 分鐘），改成背景起跑、寫 rc 檔、前台每次最多等 9 分鐘輪詢。

前作 `fd2-anatomy/tools/code_emit` 只有 `emit_issues.json` 本身，沒有總掃，這支從頭寫。

設計上最早定下的是「workflow 自己沒有檔案系統」這件事的後果：判斷「做完了沒」必須看檔案，而 workflow 讀不到檔案，所以所有機械性的正確性都塞進 `sweep.py`——鏡像解析、分群驗證、判定檔驗證、轉錄。workflow 只看 `sweep.py plan` 印出來的東西，agent 的自報只當提示。

`same_as` 的兩種格式實測下來：145 筆裡 110 筆是 `emit#N`，35 筆是引一段對方 `what` 的原文。原文那 35 筆用「前綴比對，找唯一命中」全部解得開；`emit#N` 那邊有 3 筆寫成 `emit#1 -- the geometry record's shape ...` 這種後面接說明的形式，regex 改成只吃開頭。唯一解不開的是 `000567f0#3`：它寫 `emit#2`，但那個位址只有兩筆 emit（#0、#1）。看內容應該是指 #0（講的是真正的中斷向量），但那是猜，所以讓它自己成為一則獨立疑慮、由 `items` 報出來，沒有替它選。

一個差點踩到的坑：`items` 一開始每次都重建。可是落地會把 `status` 從 `open` 改成 `resolved`，續跑時重建出來的清單就不再把那些列為未決，`clusters.json` 會整份驗證失敗。改成第一次寫完就凍結，`--force` 才重建。

另一個是 `final_finding` 原本「rescan 檔存在就用它」，一份寫壞的 rescan 會讓 `apply` 當場拒絕，而第一輪那份合格的判定就這樣被卡住。改成 rescan 合格才用，不合格時 `plan` 報 `needs_rescan`，workflow 把它列進未完成清單但照第一輪落地。

沒有 node 可以做語法檢查。從 PyPI 下載 esprima 原始碼到暫存目錄，把 `export` 拿掉、整支包進一個 async function 再 parse——過了。

## 150 個直接推送：死掉的假說與真正的答案

`open_issues.md` 裡的線索是「它們常常成對出現在相鄰槽位，像 8-byte 值拆成兩個 dword」。派一個 agent 把 150 個全部分類，結果假說完全不成立：沒有一處推的是 `double`、struct 或 varargs，所謂 17 對其實是 17 次呼叫一個兩引數的 function。

真正的共同點是：**150 個全部落在 inline 展開的副本裡**，107 個是展開出來的參數槽、43 個是展開本體的區域變數，來自 11 支被展開的 function。同一句 C 在 out-of-line 副本裡走 EAX 中轉，在展開副本裡直接推。規則是「程式設計師宣告的變數經 EAX，編譯器為展開配的槽直接推」——這正是除錯資訊產生器的樣子。

這讓 `-d2` 解釋得了全部 2,587 處，於是請它做編譯實驗：

- 它原本設計的探針用 `_inline`，**在 10.0a 編不過**：`_inline`、`__inline`、`inline` 全部 E1009。知識庫「原始碼用 `_inline` 要求了展開」這條結論是錯的——那是票 22.1 從 `0002af60` 推出來的，推論的前提（`-od` 之下不會自動展開，所以一定是原始碼要求的）本身就錯在 `-od`。
- 展開來自 `-oe`。`-oe -d2` 完全重現原版的形狀；`-od`、`-d2`、`-d1` 都不展開；`-oe -od` 展開但全部直接推。
- `debug_info_off == 0` 分辨不了 `-od` 與 `-d2`：wlink 從來不填那個欄位，帶 `DEBUG ALL` 時是在檔尾附一段 `0x8386` 尾碼的除錯資訊，原版沒有這段尾碼，所以只說明連結時沒帶 `DEBUG`。
- 用 7 個真實 `src/` 檔、42 支 function 逐 byte 對照原版（遮掉 LE 重定位與 `E8` 目標）：`-od` 6 支完全相同，`-oe -d2` 17 支，前者對上的後者全部也對上。
- 預設 `-oe` 展開不到 saf 與 unit-gauge 那幾處；`-oe=24`～`26` 全部重現，27 以上開始多展開原版沒展開的。兩種位置在任何門檻下都不展開：`&&`／`||` 右側（解釋了 `000107be` 那個孤立的 CALL）、含兩個以上呼叫的運算式（`0002b034` 的 `get_rgb_*`）。

問使用者重建版要不要跟著改，回答是完全對齊，而且「既然檔案都要分組了，CD 模組也一起對齊」。這是一張新票的工作量——`-oe` 只在 translation unit 內展開，`src/` 的分檔與原版的 unit 邊界不同，照搬旗標會跨檔展開原版沒展開的呼叫——開成票 22.2，CD「明文放棄 probe」的決定由它取代。

## 改知識庫之前的獨立重現

**獨立重現。** 探索用的腳本全在 `workspace/`，知識庫不能引用，所以另派一個 agent 把它們重寫進 `tools/build_flags/`（`oe_probes.py`、`fn_match.py`、`fn_variants.py`、`oe_threshold.py`），原始 byte 改成直接從 `FDPS.LE` 讀、用 `tools/build_gate/lefixup.py` 遮重定位，而不是靠 Ghidra 的 dump。數字全部重現：三個關鍵字 E1009、探針 21/21、42 支 6／17／17、門檻 24–26、CD `-os` 4 支而 `-os -d2` 0 支、`verify_flags.py` 15/15。

這次多問了一個原本沒人問的：`-ot` 放在 `-d2` 後面行不行。舊文件說 `-ot -od` 的順序不能換，換成 `-d2` 之後是否還成立沒人量過。答案是一樣不能換，而且後果更大：`-ot` 擺到後面會把最佳化器重新打開，42 支掉到 0 支、15 項特徵只剩 9 項。

也有一條被部分推翻：探索時說「一個運算式裡有兩個呼叫就都不展開」，實際是左邊的展開、右邊的保持呼叫。所以 `0002b034` 那三個連在一起的 `fdps_get_rgb_*` 為什麼全部是真的 `CALL`，現有規則解釋不了，寫進 `build_flags.md` 當未定的事，留給票 22.2 做全映像對照時再看。

中間撞到一個小坑：重現的 agent 被告知「gate 印出 `[result]` 才開 DOSBox」，而 gate 的 log 在跑完之前一直是 0 byte（Python 的輸出被緩衝到最後才寫），它的 30 分鐘監看在 gate 跑完前就逾時交回，什麼都沒跑。之後改成直接通知它開跑。

## 鍵盤佇列測試為什麼時紅時綠

總掃剩下的唯一一則 open 是 `tests/title.c` 的 premise case：同一支執行檔六次失敗一次。總掃的 agent 已經排除了 ISR、AIL、mode 13h（那個 case 連它們都沒裝），推到「DOSBox-X 的 INT 21h AH=0Bh 路徑」為止，下一步是寫探針。

派出去的 agent 做了一支最小的 DOS/4GW 探針：手塞環形緩衝區，然後記下 INT 16h AH=01h、INT 21h AH=0Bh、`0x41a`／`0x41c`／`0x480`／`0x482` 與 ungetch byte。結果是：塞之前沒有任何一次空查詢，第一次查詢每次都看得到；塞之前同一個 tick 內有過一次空查詢，之後要再查 4 千到 20 萬次才看得到——換算下來永遠恰好是等到 `0x46c` 前進一次。同一支探針編成不經 extender 的 real-mode `.EXE`，每次第一次就看到。所以「記住沒有鍵」發生在 DOS/4GW 的保護模式路徑上，不是 DOSBox-X 的 BIOS 或 DOS。

之前猜的三個嫌疑（遊戲的 INT 9 處理常式、mode 13h、AIL）全部不是原因；它們最多改變空查詢落在同一個 tick 的機率。premise case 自己收尾的那次 `kbhit` 就是一次空查詢，剛好排在 `run_movie` 塞鍵之前。

修法只動測試：塞完之後不查鍵盤地等 `0x46c` 變一次（有上限），然後無條件斷言。拿掉了原本 drain case 的兩分支權宜寫法。刻意在塞之前強制一次空查詢，舊版 premise 5/5 失敗、新版 10/10 通過；`build_emit.py all` 連跑 6 次全過，正式 gate 也 PASS。那個 agent 被要求把結果寫進 `workspace/kbd_probe/findings.md`，工具拒絕它寫那個檔。探針原本也只在 `workspace/` 裡，收尾時把 DOS/4GW 那支搬進 `tools/kbd_probe/`（輸出改寫到 `workspace/kbd_probe/`），重跑 3 次照樣重現；real-mode 對照那一支是臨時拼的批次檔，沒有搬。
