# 遊戲資料查詢 skill（票 09）

## 資料集要從哪裡長出來

票的第四條寫「建置流程可重複執行，資料更新後能重新產生」，這句話直接決定了資料不能用抄的。第一版的想法是把 `assets/` 四張表的名稱人手轉錄進建置腳本、數值從 `MISC.VFS` 現解——名稱本來就是攻略站來的，ADR-0006 又說攻略原文不解析，寫成腳本裡的字面常數看起來很自然，`crosscheck.py` 就是這樣做的。

寫到一半停下來了。`crosscheck.py` 的常數是**期望值**，它存在的目的就是跟資料檔對打；名稱不是期望值，它沒有東西可以對打，抄進第三個地方只會多一個會漂移的副本。而名稱其實已經有擁有者了——`assets/items.md` 的全表、`assets/spells.md` 的全表、`chapters/_index.md` 的章節總表，那些表就是攻略站名稱在本專案的轉錄結果。

所以改成讀知識庫的 markdown 表。這跟「不對人寫的內容做 parser」不衝突：那條規矩防的是攻略站那種手寫 HTML，而 `assets/` 的表是本專案自己產生的、欄位固定的表格。真正讓這個決定站得住的是接下來那件事——既然已經把整列讀進來了，順手就能拿那一列的數值欄位去對同編號的 record。

## 3181 個比對，一次就全過

`build.py` 現在對每一列做的事是：從編號欄取 code，去解出來的 record 裡找同一筆，然後逐欄位比。物品比類型／AP／HIT／DP／EV／距離／附加屬性／價格，使用效果表再比 K1／數量／距離／範圍／對象／選取模式，並且反過來確認**不在**使用效果表裡的物品 `use_effect` 都是 0；法術比六欄，其中「AP × 1.60」要還原成 -160、「直線 7」要還原成 `0x17`；職業比八個地形消耗、暴擊、以及 100 減魔抗的換算；人物比出場屬性 13 欄、成長 5 組範圍加習得索引、法術習得那格的「Lv16 → `01`」也拆出來對。

第一次跑就 3181 個全過。這個數字本身沒什麼了不起，重要的是它擋掉的東西：知識庫的數值如果哪天被改壞、或者表格改版讓解析錯位一列把名稱掛到隔壁的 record 上，建置會直接中止而不是產出一份看起來正常的資料集。事後把 `assets/spells.md` 裡業火的 MP 從 7 改成 8 試了一次，確實中止，訊息是 `spell 00 mp: knowledge base says 8, data file has 7`。

附加屬性的對照表也是從這個比對長出來的，沒有手寫：`中毒 10%` 這種格子拆成標籤與百分比，標籤按 record 的 `hit_effect` 值分組，同一個值出現兩種標籤就中止。四個代碼各自只有一種標籤，`01 麻痺`／`02 雙擊`／`03 暴擊`／`04 中毒` 就這樣被資料自己證明出來。

## 蘭迪斯／劍聖的 HP 960

把三張人物表合起來的時候，直覺寫法是「索引 `0F` 的出場屬性就是 `FRIAPRDA.DAT` 第 `0F` 筆」。跑出來 `0F 蘭迪斯／劍聖` 的職業是 `03`、LV 10、HP 960、MP 480、AP 300。

沒有一個數字是離譜的。劍聖是轉職型態，HP 960 對後期單位很合理，職業 `03` 是英雄——同一條升級線上的更後面一階，看起來甚至像是有意義的。差一點就這樣送出去了。

起疑是因為列表裡 `10 法蓮娜／法師`、`11 費塔加／法師`、`12 裘娜／聖戰士` 的那幾欄一模一樣。把 60 筆按解出來的欄位分組，再退回去按 24 個原始 byte 分組，結果是：`0C`–`22` 之中有 20 筆是同一列樣板（`00030AC003E00106000000006278FFFFFFFF2C016400A000`）、`24`–`31` 共用另一列、`32`–`3A` 是 `00`–`08` 的逐 byte 複本、`15` 與 `1F` 又是一對。真正各自獨立的只有 `00`–`0B` 十二筆，也正是 `assets/characters.md` 出場屬性表列的那十二筆。

`FRILEVUP.DAT` 沒有這個問題，它的 `0F`–`23` 每一筆都是該轉職型態自己的成長範圍，攻略站也列到 `21`。兩張表都是 60 筆、都用肖像編號索引，只有一張的後半是實的——這正是會踩進去的原因。

處理方式是資料集只給知識庫出場屬性表列出的那十二個索引，其餘索引的出場欄位一律 `null`，另有 `appearance_documented` 標記。那些 byte 不是空的，但把它們掛在索引上就是在製造看起來合理的假事實，而這個資料集的用途恰恰是拿來回答「這個數字是什麼」。

結論分兩處落地：完整的分組表寫進 `assets/characters.md`，「照直覺索引整張表會拿到合理的假資料」寫進 `rebuild_info/pitfalls.md`。

## 查詢介面上的三個小坑

**範圍語法**。一開始寫成 `ap=300-400`，開放區間是 `ap=300-` 與 `ap=-400`。後者跟負數撞在一起——法術的威力欄位為負時是攻擊力加乘率，`power=-160` 是完全合理的查詢，但它會被讀成「上限 160」。改成 `..` 就沒有歧義了。

**`--json` 的位置**。放在主 parser 上時 `query.py show item 4A --json` 會失敗，放在主 parser 而從子命令後面給又會被子命令的預設值蓋掉。最後用一個共用的 parent parser 掛到每個子命令上。

**`find` 看不見巢狀清單**。人物的 `initial_items`、`initial_spells`、`learn` 是 dict 的清單，第一版的 `find` 只認純數字與整數清單，於是 `find 0x33 --table character` 查不到珊的光之杖——而「這個代碼出現在哪」正是這個指令存在的理由。複審抓到的，現在會把 dict 裡的 `code`／`spell` 拆出來比。

**`power` 與 `damage` 兩個欄位**。原本除了 `power` 還輸出一個「威力為正時的傷害值」，結果 `find 150` 每筆法術都報兩次。既然 `where spell power=500..1000` 對負數天然無感，那個衍生欄位沒有存在必要，砍掉。

## 複審打掉的一個假宣稱

`build.py` 的註解本來寫「這份歧異清單的完整性由 `crosscheck.py` 保證」。複審指出這句對人物法術是假的：`crosscheck.py` 的 `GUIDE_APPEARANCE` 只比 LV／AP／DP／DX／HP／MP，根本沒碰法術遮罩，所以清單裡那三筆 `initial_spells` 歧異沒有任何東西在守；而 `build.py` 自己那側的檢查是拿 `assets/characters.md`（本來就抄 dump）去對 dump，結構上不可能發現攻略站的說法。

兩個選擇：把宣稱改弱，或者把宣稱做成真的。選了後者——攻略站 `spell` 頁的第一張表就是「人物職業等級擁有的法術」，等級欄寫 `--` 的那些就是出場即有的法術，12 個索引全部可以人手轉錄。加進 `crosscheck.py` 之後比對欄位從 1435 變 1447，跑出 5 筆不一致。

其中兩筆是原本清單裡沒有的：

- `02` 費塔加的遮罩是 `00`、`08`、`09`，攻略站只給他冰爆術。`09` 絕殺冰封是他 Lv15 的習得而攻略站列他 15 級出場，說得通；`00` 業火不在攻略站給費塔加的任何一列裡。
- `09` 蓋亞的遮罩是空的、攻略站列他有轟神砲。這筆知識庫本來就解釋過（來自 `A4` 強化套件），只是沒有進歧異清單。

這正好證明了複審的顧慮不是理論問題——沒有守的欄位真的漏了兩筆。

`ACCEPTED` 與 `DISCREPANCIES` 是兩份手維護的清單這件事沒有結構性解法（一份在 `workspace/` 的 pipeline 上、一份要 self-contained 地隨 skill 出貨），最後做的是：兩邊互相寫明「加一筆就要加另一邊」，並且讓 `build.py` 把每一筆歧異的**資料檔那一側**回頭對 record 驗證——清單過期會被擋下，只有「漏加一筆」還是靠人。

## 沒做的事

物品的類型代碼（`TY`）、使用效果代碼（`K1`）、使用對象代碼目前都只輸出原始值。`assets/items.md` 描述的是「某件物品做什麼」，不是「某個 `K1` 值是什麼」，兩者不能直接互換——`A4` 強化套件的 `K1` 是 `21`，而它同時給 AP+30／DP+30／MV+1 與習得轟神砲，把 `21` 標成其中任何一個都是窄化。要建對照表得從 `FDPS.LE` 的使用效果分派處讀出來，那是後面的票的事。查詢工具寫錯的代價比查不到高。
