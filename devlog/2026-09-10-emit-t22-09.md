## 三件真的差點出事的

### 一、`00012e50` 整套測試 hang，原因是別的測試檔留下的旗標

`fdps_map_actor_move_and_attack` 落地的第一次全跑直接卡死。卡死的原因不在這支 function 裡面，而是**它從 stub 變成真程式碼這件事本身**。

`tests/mapai.c` 的 `tba_` 那組 case 是透過 `fdps_map_actor_take_best_action` 打進來的，而那個 fixture 是在這個 callee 還是「回傳 0 的 stub」的年代寫的：沒有安排 timer interrupt，沒有 cursor kit、沒有 gauge sheet、沒有動畫容器。callee 一旦真的開始畫東西，第一個 frame 就再也不會回來。

定位過程本身值得記：在 DOSBox-X 裡用暫時的 probe case 二分，先把測試套件裁到兩個檔讓一次跑只要九十秒；個別 callee 全部跑得完，手抄一份整個 body 也跑得完，**只有真的那個 call 會 hang**——這才把觸發點指向 `tests/aiact.c` 而不是 `tests/mapai.c`。真兇是自己那個動畫旗標 case 把 `data_fdps_ui_battle_animation_enabled` 留在 1，於是 mapai 的 dispatch 走了全螢幕那條臂，clip 名字要用 portrait id 組出來，最後停在 `fdps_wait_any_key` 等一個 fixture 沒有的成員。

兩處都改在 `tests/`：`aa_unstage` 把旗標放回 0 並寫上理由，`tba` fixture 改成自己指名那個旗標而不是繼承，並且把真的那條臂需要的東西全部立起來。

形狀是這樣的：**測試檔之間透過全域狀態耦合，而引爆時機是某個 stub 變成真程式碼的那一刻**。這在 callee-先於-caller 的排序下會一再發生，而且症狀是 hang 不是 fail，沒有任何一行輸出指向兇手。

### 二、`00014ea0` 的合成 CEL 把 heap 打壞

`fdps_battle_system_submenu` 第一次 build 編得乾乾淨淨，跑起來在 `fdps_menu_animate_open` 裡面把 heap 弄壞然後 fault。用一個暫時的 case 在一趟選單的各段之間夾 `_heapchk` 才定到位置。

原因在測試自己捏的 `.CEL`，不在 emit 出來的 C：`fdps_render_ring_menu_frame` 是**自己帶 25×22 的尺寸**進去的，不去讀 sheet header；而一整排 24 pixel 的 skip run 永遠湊不出剛好 25 的 row width，於是 RLE decoder 就一路讀出陣列外面（`rle.h` 沒有任何東西界住它）。fixture 改成 25×22 就好了。

值得記的是這條的一般化：**合成 fixture 的尺寸要對到呼叫端寫死的尺寸，不是對到 sheet header**，而且 RLE decoder 不會抱怨，它會安靜地越界。

## `0001dd30` 的重複 commit 事件

`fdps_unit_award_exp_and_level_up` 那一支被 commit 了兩次。第一次 `git commit -F <訊息檔>` 跑早了一步——**訊息檔還沒寫出來**，而 stderr 被 `Out-Null` 吃掉，所以沒看到發生什麼事。commit 還是建立了（`6ef92e9`），內容正是該有的五個檔一個不多，但主旨是**別支 function 的**：`emit: fdps_combat_play_spell_on_targets @ 0001a4c0`。那個主旨屬於同一天早上 10:17 落地的 `a8cdc5c`。

機制沒有釘死：`commit.template` 沒設定，`.git/hooks` 只有 `.sample` 檔，所以要嘛是 git 退回去用了 `.git/COMMIT_EDITMSG` 的舊內容，要嘛是有另一個行程 commit 了共用的 index。修法是確認 HEAD 的 tree 就是自己那 1140 行五個檔、`emit_state.json` 沒有別的 function 掛在 in_flight、`0001a4c0` 早就記成 committed、repo 沒有 remote，然後就地 `--amend` 換訊息。內容沒動、沒有丟掉任何 parent object。副作用是那個 commit 的 author date 停在第一次嘗試的 15:45:23。

同一份回報裡有一條懷疑值得澄清，因為後來查了是**誤判**：那位 agent 說啟動時拿到的「Recent commits」區塊（`069759b`、`96d5626`、`1c2f24c`…）在 history 裡找不到，因此懷疑「這個 repo 同時被不只一個 workflow 在推」。實際上 `git merge-base --is-ancestor 069759b HEAD` 是真的，`069759b` 就在 HEAD 的祖先鏈上，距離 HEAD 185 個 commit。**那個區塊只是舊的快照**——這批每一個 agent 拿到的都是同一份過期快照。`6ef92e9` 確實不在 HEAD 上，那是 `--amend` 之後被丟下的舊 object，符合預期。

教訓兩條：把 `git commit` 的 stderr 丟進 `Out-Null` 會讓這種事完全無聲；啟動時給的 commit 快照不能當成 repo 現況的證據。

## Ghidra：套 plate 修正的三個反覆出現的坑

這批動 Ghidra 的比例很高，絕大多數是把 plate 裡過期的 `FUN_` / `DAT_` 換成現名。三個反覆出現的操作細節：

1. **`set_plate_comment` 是整份覆寫。** 同一個位址上有多筆 fix（emitter 一筆、reviewer 兩筆之類）就必須合成一次寫入，分三次寫後面會把前面蓋掉。`000262a0`（3 筆）、`0002b4f0`（3 筆）、`00010010`（emitter 2 + reviewer 4）、`00035aa0`（2 筆）都是這樣處理的。
2. **fix 裡寫的「N 處」幾乎都會偏，而且是照抄套用、不要為了湊數改寫。** 這批至少六次：`00030cc0` 說四個過期名字實際只有三個（`FUN_000205b0` 根本不在 plate 裡）、`00023e20` 說兩處只有一處、`000352c0` 說兩處只有一處、`000120d0` 說三處只有兩處、`00039770` 說「兩個 hold 都寫了 retrace-paced」實際只有一個 hold 那句有這個詞、`00031bc0` 的 fix 只點名兩處但 plate 裡有三處。**一律照 fix 的字面套，剩下的留著並回報**——把沒被點名的那一處也順手改掉是在替決策者做決定。
3. **`set_plate_comment` 回三條 advisory warning（缺 Algorithm / Parameters / Returns）是工具的通用模板檢查，不是失敗。** 這個專案的 plate 格式本來就沒有那三節。這批至少五支回報了同樣的警告，每一支都正確地沒有為了消警告去加東西。

還有一件機制上的事：`0001d990` 的 emit fix 掛的是 `kind: "prototype"`，但 `000601c4` 是**資料**不是 function——`set_function_prototype` 對不上。做法是建一個 function-signature 型別 `void_int_fn`（回傳 void、一個參數 `int unit_index`，照既有的 `void_fn` 慣例命名）再 `apply_data_type` 成 `void_int_fn *[50]` 蓋掉原本的 `void_fn *[50]`。決策本身（50 格、指向 `void(int)`）一個字沒改，改的只是達成手段。那次第一個 `apply_data_type` 呼叫被**權限分類器**擋掉一次，原封不動重試就過了——那不是 Ghidra 連不上。

`000288f0` 有一筆 Ghidra fix 被**刻意不套**，記在這裡免得後面的人以為是漏掉：把 `data_fdps_teleport_destination_tile_y` 改名成 `data_fdps_battle_teleport_dest_tile_y`。那筆決策自己的最後一句就是「如果那四個地方沒辦法一起動，名字就維持現狀」——它要求 Ghidra、`routing.json` 的 globals 表、`src/gamedata.h` 的 extern 與 `src/spell.c` 的兩個使用點一步到位，而落地那一段本來就不改原始碼。

## 雜項

- **編碼**：這批每一次落地都是把 commit 訊息寫成 UTF-8 檔再 `git commit -F`，而不是走 PowerShell 字串或 console pipe。反覆出現的假警報是「把 JSON 回讀印到主控台看到亂碼」——那是 CP950 的主控台，檔案本身沒事，多支都用 python 以 UTF-8 解碼或用 `git cat-file` 看 raw byte 確認過。另一個假警報是 `Measure-Object -Line` 的行數比實際少（它會吃掉空行），`000378f0` 記 714 對 832、`00012c10` 記 731 對 806、`000374e0` 記 566 對 651——**要行數就數 newline**。
- **git 的 CRLF 正規化警告**在新檔上是這個 repo 在 Windows 上的常態，不是問題。
- **commit trailer 在批次中途變了**：session 的 attribution 設定要求每個 commit 除了 `Co-Authored-By` 之外再帶一行 `Claude-Session`，所以這批後半的 commit 比前半多一行。多支 agent 各自把這件事當成偏離回報了一次。
