# 票 25.8 前半：章節頁的產生器、閘門與 workflow

這一段只做確定性的部分：從資料產生每章的機械事實與頁面區塊、閘門、落地腳本、`_index.md` 的組裝，以及逐章撰寫的 workflow 腳本。30 章的敘述與判定由 workflow 逐章派 agent 做，本段沒有寫任何一章。

## 先看前作

`fd2-anatomy/chapters/` 的章節頁節次（劇情、加入、敵人、寶物、商店、特殊機制、處理流程、事件、對話）直接拿來當涵蓋面。前作的產生器 `tools/kb_overhaul/gen_ch_encounters.py` 解的是 `FDFIELD.DAT`，`gen_ch_shops.py` 讀寫死在 EXE 裡的商店表，FDPS 的部署、寶物、事件都在 `MAPnn.DAT`、商店在 `SHOPnn.DAT`、還多了過場腳本與 66 個文字區塊，程式一行都用不上，只沿用了「部署按單位與等級彙總」的呈現。前作的 `_index.md`（handler 總表、跨章機制鏈、章號與資源對照）沿用為新 `_index.md` 的骨架。

## 頁面怎麼切

一開始想讓 agent 直接寫整頁，產生器只給它資料。問題是票的要求「對話與腳本一律由解碼器產生，不手打」——agent 抄進頁面就是手打，而且沒有辦法事後驗證它沒抄錯。改成頁面是「敘述 + 標記之間的產生區塊」，落地時才填，落地後的頁面可以隨時重產比對（閘門的 `stale`）。

接著碰到：有些區塊的內容取決於判斷。「波次 4 會不會出場」要讀章節事件的程式才知道，資料本身只說有這幾筆記錄；「條目 0x0f 由誰顯示」有時是執行期算出來的編號。把這些判斷交給 agent 寫進 meta，區塊從 meta 讀——但這樣落地後重產時需要 meta，而 meta 在 `workspace/`。決定把 meta 的判定子集落地到 `tools/chapter_docs/judgements/`，跟字模校對那份開發者答案同一種處理：無法重生的人工（agent）輸入跟著讀它的工具進版控。

## 文字讀取端的掃描，兩次誤判

第一版直接拿 `global_text` 的掃描函式找 `fdps_draw_text(data_fdps_current_chapter_text_ptr, …)`，沒有章號的函式一律算在每一章頭上。結果第 3 章的 `0x10`–`0x15` 多了一個讀取端 `fdps_icon_script_prompt_three_way_choice`——那是過場直譯器裡三選一提問的程式，條目是寫死的六個，但它只在某一支腳本裡執行，算到每一章頭上就是錯的。腳本的追蹤本來就給了三選一的條目，所以改成：過場直譯器與死亡腳本這兩類「條目來自資料」的程式碼位置一律不算，改讀腳本追蹤與 `MAPnn.DAT`。

第二個漏洞是 `0x01`（章名）找不到讀取端。存讀檔畫面畫章名時用的是它自己載入的 `chapter_text`，不是 `data_fdps_current_chapter_text_ptr`；`global_text` 的常數裡本來就列了這兩個指標，掃描時兩個都要帶。

最後把「沒有章號的函式屬於哪幾章」寫成一張明確的表（`GENERIC_READERS`），表外的檔案讀章節區塊就直接報錯，不猜。

## 村莊的文字屬於下一章

讀 `src/rsrc.c` 時注意到村莊載入的是 `SHOP` + 章節索引，文字區塊卻是 `fdetxt` + 章節索引 + 1。村莊在一章勝利、章節索引已經改成下一章之後才跑，所以第 n 章之前的村莊用的是 `SHOP(n−1)` 與第 n 章自己的區塊的 `0x04`–`0x08`。第 1 章區塊裡的「道具店／武器店／酒店」三條，正是因為索引 0 沒有村莊而永遠不會顯示。依此把「村莊」一節放在第 n 章頁，而不是第 n−1 章。

## 過場腳本的呈現

`cutscene_script.render_markdown` 的標頭會印呼叫端的 `src/檔:行`。別的子票正在同時改 `src/`，行號一動，落地頁的「重產比對」就會失敗，而那不是章節內容變了。改成自己組標頭，呼叫端寫成函式名加位址。

腳本步驟裡的文字：本章區塊的條目只標編號（全文在「對話」一節，避免同一頁出現兩次），切到額外場景之後的條目直接列出文字，否則像第 10 章開場整段都在 `FDETXT38`／`39`，只讀章節頁會看不到。額外場景文字的正典仍是 `assets/text/scene_text.md`，頁面上寫明。

## 閘門的一個陷阱

沿用 `game_mechanics` 的 `NARRATIVE` 規則擋「後來發現、起初」之類的流水帳字眼。它會掃到產生區塊裡的遊戲對白——目前 30 章剛好沒有命中，但只要有一句台詞含「起初」，那一章就永遠過不了閘門，agent 也改不了對白。改成只掃產生區塊以外的行，並加了測試。

## 沒做的事

- 戰場標註圖（寶箱、埋藏、事件格、起始格）30 張共約 3.5 MB，只畫到 `workspace/` 給 agent 看，沒有放進 `chapters/`：票沒要求，放進版控是另一個決定。
- 本機沒有 JS 引擎。workflow 腳本用 scratchpad 裡裝的 `esprima`（Python 版）包成 async function 解析過一次語法，確認對已知錯誤的片段會報錯；邏輯只能靠讀。

## 審查之後的修正

工具寫完、commit 之後跑了兩路審查（規範與票的要求各一個 agent），抓到的實際問題：

- workflow 的重試回合若因「工具停止回應」而停下，還沒有草稿的章會從未完成清單裡消失（當時寫成 `if (!halted)` 才記帳）。改成無論如何都記。回掃後重新落地的章沒算進 `landed`，run record 會少算。準備階段失敗時直接 `return`，沒有 run record。三處都修了；腳本段（落地、索引、踩雷點判定）也補上「沒回應就重試一次」。
- 章與章之間的連結會被擋住：第一輪（第 1–6 章）落地時第 7 章以後還不存在，閘門把連到後面章的連結判成壞連結，而回掃只重開低信心的章，這些連結永遠回不來。改成草稿與逐輪落地時「連到還沒寫的章」只警告，最後加一道對全部落地頁的嚴格閘門（`--landed-all`）。
- 永遠不部署的波次裡的掉落，寶物表照列、事件表也照列，違反「拿不到的只寫一行」。改成從兩張表拿掉，另寫一行連到 `cut_content/`。
- 判定裡的條目編號若寫成整數 `15`，舊碼用 `int(str(x), 16)` 會讀成 `0x15`。改成整數照值、字串一定要 `0x` 開頭。
- 閘門把 `check_mechanics` 的引用、符號、連結、流水帳檢查整段抄了一份。改成直接呼叫它的 `check_text`，只濾掉不適用於章節頁的兩條（驗證對象、每節都要引用）。
- 閘門另外補兩條：處理流程要引用本章地圖資料呼叫的每支事件處理（不只進入／行動後／勝利三支），加入與離隊要連到 `assets/characters.md`。`_index.md` 的跨章機制鏈每個小節都要引用 function。

沒有照改的：CD 音軌編號仍只連到 `program_info/cd_audio.md`，不在 `_index.md` 重抄（一個事實一個擁有者）；敵兵數值同理只連 `assets/enemies.md`。
