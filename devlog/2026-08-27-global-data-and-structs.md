# 票 17：全域資料命名與 struct 佈局

跑了三天多，1,040 個 anchor、64 個 struct 候選。結論進了 [`program_info/data_structures.md`](../program_info/data_structures.md)，工具與已知的坑進了 [`tools/global_data/_index.md`](../tools/global_data/_index.md)。這篇記怎麼走到那裡，重點放在死路。

## 一開始就得決定「一個項目是什麼」

票面上寫「每次 agent 呼叫只帶一個全域符號」。問題是**全域符號這個東西，在判定之前並不存在**。Ghidra 有的是 `DAT_00069cd8` 這種標籤，而那只是「有指令參照這個位址」的意思；程式碼參照陣列與結構的中間是家常便飯。

先數了一下規模：`.object2`／`.object3` 有 1,062 個被參照的位址，`.object1` 夾在程式碼之間的唯讀資料另有 303 個。如果每個都當成一個變數去命名，會得到一千多個互相矛盾的「變數」，其中大半是別人的欄位。

最後的做法是把匯出的單位叫 **anchor**，明確定義成「參照落在哪裡」這個事實，然後把「這是不是一個變數」當成判定的**第一個問題**。判定檔因此有 `classification` 與 `belongs_to` 兩個欄位，落地腳本遇到 `interior` 就完全不改名。事後看，373 個 anchor（36%）判定結果是 interior——如果沒有這一步，那就是 373 個憑空捏造的符號。

這個設計也帶出兩種本票獨有的爭議：撞名（兩份判定搶同一個符號）與**邊界**（一份判定的型別大到蓋過另一份宣稱自己是變數的位址）。兩種都由落地腳本原樣回報、交給仲裁 agent 讀證據決定，腳本自己不作主。

## 先 smoke test，四個 anchor 就抓到兩個設計缺陷

跑正式的一千多個之前先送四個進去。結果是 gate 失敗，而且失敗得很有價值：

1. `code *[30]` 這個型別 Ghidra 解析不了——函式指標表在這個 binary 裡有四張，全用這個寫法會全部留在無型別狀態。改成 `func_ptr` 加一個 `void (void)` 的 placeholder。
2. 稽核照 pool 要求前綴，但 `binary_artifact_` 橫跨 pool：wcc386 把 auto 陣列的初值影像擺在宣告它的函式旁邊的唯讀資料裡，碰得到那些 byte 的只有遊戲程式碼，可它仍然是編譯器產物。稽核規則與判定規則由建構本身就會撞。

兩個都是「跑完一千個之後才發現」會非常貴的問題。

## 命名規則我自己搞錯了一次

`naming.md` 原本沒有 struct 型別的規則。我補的時候沒有去延伸既有那條「程式庫的東西就叫程式庫的名字」，而是另外發明了一套 `fdps_`／`ail_`／`crt_` 的平行前綴，理由寫成「Ghidra 型別管理員會撞名」。

那個理由連自己都站不住：它直接違反同一份檔案第一條鐵則「Ghidra 名稱與 C 名稱逐字相同」——重建後的 `.c` 是從 `<time.h>`、`<stdio.h>` 拿到 `tm` 與 `FILE` 的。前作 FD2 全庫也只有 `crt_equivalent_` 這個複合前綴，沒有任何裸 `crt_`。

使用者指出來的時候已經產出 21 個 `crt_tm`、`crt_file` 這種候選名，所幸還沒有任何 struct 落地。真正的教訓不是「改回來」，是**命名規則要寫進 gate 而不是只寫進 prompt**——這條之所以溜過去，就是因為 `AuditGlobals.java` 當時沒有機械檢查。加上檢查之後，它立刻抓到兩個因為別的 bug 而溜進型別管理員的 `crt_` 空殼。

## 死路一：落地腳本會靜默摧毀先前套用的 struct

這是整票最嚴重的 bug，而且是轉錄 agent 診斷出來的，不是我。

`applyWhere` 對每個 apply 目標做 `clearListing(a, a+len-1)` 然後 `createData(a, dt)`。三份佈局搶 `0x613c8`–`0x61441` 這段時，最後寫的 `long_double_80` 把前面已經建好的 122-byte `L$N_emu387_state` **整個抹掉**——Ghidra 清掉一個 Data 的任一 byte 就會清掉整個 Data——而腳本的 `globals_typed` 照樣把它算成成功，因為那次寫入當下確實成功了。

轉錄 agent 的回報值得引用，因為它做對了 ADR-0007 第 5.3 條要求的事：它拒絕「照簡報上寫的補救方式」去刪掉那四個孤立標籤，理由是「struct 根本不擁有那些 byte，它自己被摧毀了；刪標籤會讓稽核變綠而記錄仍然不在資料庫裡」。它把問題原樣送上來，沒有自作主張把錯誤埋掉。

修法是寫入前先算衝突：所有 global target 先做範圍比對，兩份佈局重疊就兩邊都不套用、回報給仲裁。順序不該替判定作主。

## 死路二：仲裁明明跑了卻沒有效果

修好偵測之後，衝突正確地被回報、仲裁 agent 也跑了，但下一輪衝突還在。

原因是 workflow 每輪只用**該輪的 struct 名單**呼叫落地腳本。而會撞的兩份佈局，通常正好隔了好幾輪寫成——所以跨輪衝突永遠不會在 run 裡浮現，只有我手動跑 `all` 才看得到。改成每輪都套用全部（重套已在資料庫裡的佈局零成本）之後，衝突當輪被抓到、當輪被仲裁掉。

這個 bug 的形狀值得記：偵測、回報、仲裁三個環節都是對的，錯的是**送去偵測的範圍**。三個環節分開看都沒問題，合起來沒用。

## 死路三：extra_anchors 檔案自己清空

回掃段發現六個「被判定指認為擁有者、但沒有任何指令參照其基底」的位址——編譯器把基底折進位移，每個使用點都直接打到欄位上，所以參照掃描看不到它們。`tzname` 就是一個。

補救是讓 `build_worklist.py` 把這些位址寫進 `extra_anchors.txt`，`DumpGlobalState.java` 讀進來。但我寫成「只寫目前不是 anchor 的」——於是擁有者一被納入，下一次 build_worklist 看到它已經是 anchor 就不寫了，下一次 dump 又把它丟掉。六個裡有三個正在這樣來回擺盪，而每次量測都顯示「todo = 0」，看起來完全正常。

## 兩個誤報停機

ADR-0007 第 5.5 條要的「Ghidra 沒回應就停」，我第一版寫成「任一 agent 回報就停」。判定 agent 被明確告知不需要碰 Ghidra，所以單一 agent 回報「Ghidra 掛了」遠比較可能是它自己跑去做了不該做的呼叫——實測就是這樣，那一輪的轉錄 agent 前後都和 Ghidra 談得好好的。

改成「過半才停」之後又踩一次：rescan 批次只有 4 個 agent，2 個誤報就達到 50%，一個乾淨的 run 被停掉。最後是「至少 3 個且過半」。轉錄段維持單一回報就停，因為它沒有 Ghidra 真的做不了事。

## 其他值得記的

**自我參照 struct。** `__stream_link` 的 `next` 指向自己這個型別，欄位放進去時該型別必須已經在型別管理員裡。落地改成 `declare` / `fill` / `applyWhere` 三趟。

**跨 struct 相依不是錯誤。** `fdps_save_slot` 裝著 `fdps_unit_record[31]`，兩者無論誰先判都會指名還不存在的對方。當成 gate 失敗會讓這對永遠解不開，所以加了第三種結果分類 `DEFERRED`——既不是錯也不是完成，等對方落地就自己好。

**反編譯器顯示名。** agent 很自然地把反編譯器印出來的變數名寫進 `apply_to`，但 `puVar1`、`iVar3` 是純顯示暫存，資料庫裡沒有那個東西。`local_30`、`auStack_50` 倒是把堆疊位移編在名字裡，可以機械解出——這一招把失敗的變數套用救回一大半。

**變數儲存衝突。** 把 4-byte local 改成 28-byte struct 會撞到反編譯器替同一塊記憶體虛構的鄰居槽。那些鄰居不是發現，是還不知道那是一個物件時的猜測，清掉再套即可。

## 最後的收斂很漂亮

`L$N_emu387_state` 落地擁有那 122 bytes 之後，`build_worklist.py` 的退休機制把裡面五個原本自稱是變數的 anchor 判定叫回來重判——struct 階段改變了事實，anchor 階段就得跟上。重判結果全是 interior，落地時舊名字被撤掉，稽核歸零。

沒有預先設計這個互動，它是「判定寫檔 + 每輪重新量測」這兩條規則自己長出來的。

## 數字

1,040 個 anchor 全部判定，稽核 0 violation。64 個 struct 候選全部收斂：45 份佈局、29 個 alias 折疊、1 個結論為「執行檔裡不存在」（章節記錄——章節資料整章從資源檔讀，沒有任何程式碼以固定 stride 索引章節結構）。365 個欄位、60 個全域、207 個區域變數套上型別。

agent 回報的 JSON 歸檔在 [`runs/`](runs/)。

停機四次：一次 session 結束、一次週用量上限、兩次上述的誤報。四次都沒有資料遺失，判定都在檔案裡，落地用「全部重跑一次」補齊——ADR-0007 第 5.7 條說的就是這件事。
