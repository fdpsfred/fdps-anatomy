# 2026-08-30 emit t22-01：票 22 的第一批四十支

票 22 是遊戲自身 function 的 emit。這批 t22-01 排了 40 支，40 支全部落地，一支都沒有跳過、沒有中途停、沒有拆檔。開跑時待處理 511 支，跑完剩 471。

流程照票 22 的規定：每支 function 走 emitter（三來源：plate、disassembly、decompiled C，產出 C 與測試）→ 獨立 reviewer（從 assembly 與 working tree 的 diff 看，不看 emitter 的敘述）→ fix loop → 對 `src/` 與 `tests/` 跑 build gate → 自己一個 commit。序列跑，因為 reviewer 認定「這一輪改了什麼」的依據就是 working tree 本身，並行會讓它看到別支的檔。順序是 callee 先於 caller，這樣一支 function 是對著真的 callee 測，不是對著產生出來的 stub 測。建置連結兩次，讓票 23 還沒 emit 的資料能以零填補頂上而不遮住任何東西。

四十支的逐支流水帳沒有價值——那些都在 commit 裡。以下只記出事的地方、代價、以及下一批不重踩才划算的東西。

## 唯一一次 fix round：00018b40

40 支裡只有一支跑了第二輪：`fdps_get_item_record` @ 00018b40。它本身是十七條指令的單一 basic block，`IMUL EAX,[EBP+0x14],0x17` 加表基底，沒什麼可錯的。錯的是註解。

emitter 第一輪在 `src/table.c` 寫了一段說呼叫端會把 item id zero-extend 成 byte 才傳進來，並引 `fdps_unit_can_equip_item` @ 00025fe0 的 `AND EAX,0xff` 當證據。reviewer 去讀 assembly，發現那個 `AND EAX,0xff` 在 00026001，它餵的是 00026007 那條 `CALL 0x00018ba0`——`fdps_get_class_equip_record`，不是這支。真正抵達 00018b40 的是 00026012 的 `MOV EAX,dword ptr [EBP+0x18]` / `PUSH EAX`，原封不動的第二參數，沒有遮罩。整段歸因錯了一支 function。

值得記的是 reviewer 為什麼抓得到：它的規定是從 assembly 讀，不是從 emitter 的說法讀。如果 review 是「檢查 emitter 說的對不對」，這則會過關——因為那個 `AND` 確實存在、確實在同一支 caller 裡、確實離 CALL 只有六個 byte。第二輪的修正把話收窄成「這條路徑不遮罩」，並且把兩個真的 zero-extend 的 `fdps_unit_equip_slot` 呼叫點（000260b9、0002611b）點名出來。這支的 `ghidra_applied` 是 6，也是全批最高，全部是同一段 plate 的三處措辭更正被 emitter 與 reviewer 各記一次。

gate 沒有擋下任何一支的落地。沒有任何 function 因為超出行數預算而需要拆檔。`recovered` 是空的——上一輪不是被砍掉的，這批沒有丟棄任何人的半成品。

## 工具面的死路，這批撞了七種

這些全部不是 FDPS 的事實，是操作環境的事實，但每一條都害某個 agent 多花了一輪。

**`set_function_prototype` 不吃 C 的 `struct` 關鍵字。** 00018ab0 與 00018b10 各撞一次，錯誤訊息是 `Can't resolve return type: struct fdps_enemy_data *`。Ghidra 的 type manager 用裸名，寫成 `fdps_enemy_data *` 就過。兩個 agent 都正確地判斷這是拼法遷就工具、不是決策改變，但都各繞了一次。

**plate comment 只能整段覆寫。** 於是 emitter 與 reviewer 對同一段 plate 提的多筆 `ghidra_fixes` 必須合併成一次 `set_plate_comment`，否則後寫的會蓋掉先寫的。00010c30 兩份 verdict 提的是同一個決定（reviewer 的是 emitter 的加上指令序列與「全 image 無 caller」一句），套一次就好，所以那支的 `ghidra_applied` 記 1 而不是 2；00018bd0 是三筆合成一次寫入。

**HTML escaping 洩進 Ghidra。** 00022410 那輪第一次寫 plate 時，`i <= 0x40` 被寫成 `i &lt;= 0x40`。當場發現、當場再寫一次蓋掉，快照 diff 因此仍然只有預期的兩段 plate。這是文字在 verdict JSON→agent→MCP 之間傳遞會出的事故，值得知道它會發生。

**`set_plate_comment` 會回 advisory warning。** 「missing Algorithm / Parameters / Returns section」出現了好幾次，那是 server 的通用樣板檢查，不是失敗。至少三個 agent 明確寫下「沒有為了消掉這個警告去編造段落」——這個克制是對的，但代表警告本身在誤導人。

**PowerShell 的 `Measure-Object -Line` 行數是錯的。** 00010b90 報 180 對 206、00022480 報 104 對 121、0001fed0 報 56 對 63、00022e30 報 63 對 69、00023950 報 383 對 447、0002ba00 報 69 對 79、0002ae90 也對不上。七支以上都撞到，最後一律改成數換行 byte，並用 git 的 diffstat 交叉驗證。不要再用它量行數。

**主控台 cp950 讓好幾個 agent 以為檔案壞了。** `emit_issues.json` 裡的繁體中文透過 PowerShell pipe 印出來是亂碼，00018b10、00018ba0、00018bd0 那幾輪都停下來查過。檔案是好的——用 python 以顯式 UTF-8 讀回、或直接看 codepoint（U+5C1A U+672A U+89E3 U+8B80）就知道。commit message 同理：一律寫進 UTF-8 檔案再 `git commit -F`，不要當成 console 參數傳，也不要從 pipe 讀回來驗。

**`ghidra_gate_clean: false` 語意是壞的。** 這批有超過十支的回報要花一整段解釋「false 代表這輪沒動 Ghidra、所以 gate 沒跑，不是 gate 沒過」。回報 schema 把「沒跑」和「沒過」壓成同一個值，逼每個 agent 用自然語言去補救。下一版該拆成三態。

## 回掃：30 支，48 筆結案、43 筆維持 open

回掃段的原始設計假設是「等鄰居的 verdict 出現，再回頭把疑慮結掉」。跑完之後這個假設只對了一半。

**真正結掉疑慮的主力不是鄰居的 verdict，是量測出貨資料與全域 xref 掃描。** 幾個代表：

- 00011da0 問「有沒有章節的 grid 單邊超過 255」。鄰居沒答案，改成追 header 的來源（`get_xrefs_to 00060144` 只有一個 WRITE，在 00022bb3），再把 FIELD1.VFS 裡 68 個 .MPL 全量過一遍——64 個是 layer 0，涵蓋第 00-29 與 31-64 章，最大 33x56、面積 1456。byte 存不可能截斷，結案。
- 00010de0 問 `move_cost[terrain]` 會不會越界。掃 69 個 ATTR 檔的 26,344 列，地形型別只存在 0、1、2、5、6，從來沒有 7 以上；再確認 68 個 .MPL 的每個 tile id 都落在對應 ATTR 的列數內。結案。
- 000109f0 問單 byte 存 unit index 會不會截斷。把 `0x00060150` 的每一個 writer 掃過（不是抽樣），再量 63 個 MAP*.DAT：最大玩家 12、部署 80、和最大 92。結案，順帶記下 `fdps_load_savegame` 用一個 byte 讀 count 卻固定配 96 筆的形狀，那是 save.c 自己的事。
- 00023050 問 30 槽快取會不會滿。同樣是量出貨資料，最壞情況 23 < 30，結案。

**反過來，純粹等鄰居 verdict 的那批幾乎全部落空。** 00018b10、00018b40、00018b70、00018bd0 四支 `changed=false`，一筆都沒動，原因一模一樣：它們要的 caller（deploy_unit、build_map_unit_array、shop_buy_loop、AI 用法術路徑…）一支都還沒 emit，`verdicts/` 底下連檔案都沒有。000119b0 也是，四個 caller 全缺。

這件事直接影響排程：**accessor 太早 emit，它的疑慮就只能一直掛著。** 這批把 table.c 九支 accessor 一次做完，換來的是十幾筆註定要等到 caller 進來才能動的 open issue。下一批如果還是照位址排序推進，同樣的事會再發生一次。

## 兩個回掃翻出來、值得單獨記的東西

**0002af60 翻出一個已經 commit 的 blocking finding。** 0002affc-0002b02d 那段打包 RGB 的碼，原本被當成 inline 寫死的算式。回掃拿它跟 00014550 裡兩處已知的展開（`fdps_saf_frame_count`、`fdps_saf_get_frame`）比對，形狀對上了：callee 的整個 frame 被在 caller 裡重建一遍——參數槽、內部暫存、回傳槽都在——body 逐指令重播、只做統一的槽位替換。決定性的細節是那三個槽用 full dword 存（`MOV dword ptr [EBP-0x68],EAX`）卻只以 byte 讀（`MOV AL,byte ptr [EBP-0x68]`）：那是被 promote 的引數送進 `unsigned char` 形參，跟 out-of-line 的 `fdps_pack_rgb` 在 [EBP+0x14]/[EBP+0x18]/[EBP+0x1c] 做的事一樣。byte 型別的區域變數會產生 byte 存；macro 根本不會配參數槽與回傳槽。旗標組沒有 `-oe`，所以展開只能是原始碼裡寫了 `_inline`。結論是 `src/palette.c` 欠一次重新 emit，把那段還原成對 `fdps_pack_rgb` 的呼叫；這也順便解釋了為什麼 image 裡沒有任何東西 call 0002af20。

順帶被推翻的是 00014550 自己的 emit verdict——它當時把那兩處展開讀成「原始碼裡的文字複製」，因為手上沒有參數槽對應這條線索。它的 emitted C 兩種讀法都不受影響，所以沒去動它的 verdict。但這是一個實例：**已核可的 verdict 也可能是錯的，後來的鄰居會推翻它。**

**00010c30 有半件事被判定為永遠不可解。** 四處鄰居標記在原始碼裡到底怎麼拼，可以用 wcc386 10.0a 的實驗決定綁定結構（兩層綁定 vs 兩個 int 的聚合——宣告不同，`-od` 會給每個宣告的物件自己的槽），但**分不出 macro 與四份手抄**：preprocess 之後兩者是同一串 token，任何對 FDPS.LE 的讀取、任何重建比對都不可能區分。這半件事被明確記成不可解，而不是留著假裝後面某張票會收掉。回掃過程順帶排除了兩個候選：不是 00010da0 的 body 綁一次參數（它的 frame 是 `SUB ESP,0x4`，一個 dword），也不是 00010de0 的慣用法（同一個 translation unit、同一組旗標，也展開四次，但四處寫同一組槽，而 00010c30 每處都給新的一組五 dword）。照 CLAUDE.md 查過前作，fd2-anatomy 沒有 movement grid 的材料。

## 一條這批發明、然後被複用三次的路

`contract D`（時序／節奏）原本的規定是要嘛實機 playtest，要嘛沒辦法。00022f40 那輪走了第三條：拿 `WATCOM_10.0a/BINNT/WDISASM.EXE` 反組譯已經建好的 OBJ，跟 Ghidra 的 disassembly 逐指令對照，把 frame 槽與分支目標正規化之後比。原版 82 指令 / 263 byte 對重建 77 / 256，差異全部是「原版 `MOV EAX,<slot>` / `PUSH EAX`、重建 `PUSH <slot>`」四處加上一條 dead MOV，7 byte 的差額算得剛好對上——算得剛好對上，才是「其他地方沒有藏東西」的證據。

00022410 沿用同一招結掉它的 fade 節奏疑慮（42/110 對 41/109，差異只有一處 push 形狀），0001fed0 用它證明兩個 cell size 全域確實每輪都重讀（`-od` 關掉最佳化，沒有 loop-invariant motion）。這條路不能量真實牆鐘時間，但能定結構與順序，對「步數是不是十六」「retrace 是不是在 upload 之前」這類問題已經夠。

那個到處出現的 `MOV EAX,<slot>` / `PUSH EAX` 對 `PUSH <slot>` 差異被記成 codegen 保真度的線索（歸 `rebuild_info/build_flags.md`），不是缺陷——ADR-0001 要的是功能等價。

## 掉在路上、要有人接的東西

- **0x00063fe4 的 DATA plate 是錯的。** 它寫「未使用的槽存 0，是任何道具都不帶的型別」。兩半都錯：檔案是用 0xff 右側填補，而 0x00 是 251 筆 ITEM.DAT 中 25 筆真的帶的道具型別。這跟 00018ba0 自己的 plate 互相矛盾。回掃階段對 Ghidra 唯讀，所以只記進 `rescan_evidence` 沒套用——**需要後面某輪去改**，否則它就是 00018ba0 的 rebuild note 正在警告重建者的那個陷阱。
- **00015470 `fdps_battle_unit_turn` 的 plate 與票 17 的 layout 相反。** 它的 Details 寫「field 0x20 是移動力、field 0x08 是職業代碼」，實際是 0x20 是 clazz、0x08 是 char_id。這是 00018c30 回掃時順手看到的，不屬於它，沒有寫進任何 verdict，也沒碰 Ghidra。歸 00015470 自己 emit 的那輪修。
- **工作樹不是空的。** `.scratch/fdps-rebuild/issues/22.1-concern-convergence-at-emit.md` 這個未追蹤檔在 000109f0 那輪回掃時出現，該輪 agent 說不是它建的、也照 pathspec 沒有 commit 它。它在 `.scratch/` 底下（進版控的路徑），但落在這條 pipeline 擁有的六條路徑之外，所以 recovery 段會把它當殘骸還是當工作是不確定的。這篇 devlog 落地後，工作樹上只剩它一個。要人決定它該進版控還是該刪。
- 票 23 是現在最大的塞子。掛在它身上的 open issue 至少包含：`data_fdps_ui_palette_cycle_phase` 必須 emit 成帶初始值 15 的資料而不是零填補 bss、`data_fdps_timer_tick_counter` 的定義必須也是 `volatile`（否則 `src/gamedata.h` 那個帶 qualifier 的宣告永遠遇不到定義，而且是靜默的）、`data_fdps_map_unit_array_ptr` 與 `data_fdps_roster_array_ptr` 的宣告型別要一起決定、以及 MAGICDAT.DAT / PROEQU.DAT / ENEMYDAT.DAT 的內容還沒解讀所以沒有測試能斷言真實 record。
