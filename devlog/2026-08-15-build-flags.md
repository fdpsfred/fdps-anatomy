# 2026-08-15 建置旗標組與預設 calling convention（票 11）

從機械碼猜旗標是猜不準的，所以整趟的做法是差分：手上有 Watcom 9.5～10.6 共十三套安裝，直接編一份探針原始碼，看哪組旗標產生的形狀跟原版一樣。真正花時間的是兩個「原版做得到、任何旗標都做不到」的形狀，其中一個最後推翻了我前半段的結論。

## 先把容器解開

`parse_le_header.py` 一寫完就有幾件事直接掉出來：模組名叫 `fde` 不是 `fdps`、初始 ESP 剛好等於 object 2 的尾端 `0x6c3c0`、`debug_info_off` 是 0。ESP 落在 object 尾端表示堆疊被算進 DGROUP 的 virtual size 裡，那堆疊大小就等於 object 2 的尾端減掉 `_BSS` 的結束位址——問題變成「`_BSS` 到哪裡結束」。

答案在 CRT 啟動碼裡。`0x434cc` 是 `mov ecx,0x6a3bc` / `mov edi,0x63930` / `sub ecx,edi` 再 `rep stosd`，對照 10.0a 的 `CSTRTX3S.OBJ` 反組譯，這兩個立即值就是 `_end` 與 `_edata`。`0x6a3bc` 對齊到 16 是 `0x6a3c0`，`0x6c3c0 - 0x6a3c0 = 0x2000`，8K。後來用 `option stack=8k` 實際連一次，map 印出 `STACK ... 0002:0000a200 00002000`、`_BSS` 結束在 `0xa1f8`、對齊到 `0xa200`——完全同一個關係，推導成立。順手也量了 wlink 不寫 `option stack` 的預設值，是 4K，所以那行是原版明寫的。

這也順帶修掉知識庫一個不夠精確的說法：原本寫「`0x64000`–`0x6c3bf` 是 BSS」。`0x64000` 是「檔案內容到此為止」的邊界沒錯，但 BSS 本身是 `0x63930`–`0x6a3bb`，上面那 8K 是堆疊段，而且 CRT 啟動時還會把環境變數複本放在它的下緣。

## 被 CS: 前綴騙了一次

第一版判斷記憶體模型時，我看到 `JMP dword ptr CS:[EAX + 0x2f6e0]` 就下了 `-ms`（small model）的結論——理由是「flat model 下 DS 與 CS 同基底，不需要 CS: 前綴」。這個推理是錯的：實測 `-mf` 產生的 switch 分派同樣帶 `cs:`，這個前綴在兩種模型下都會出現，完全不是模型訊號。

推翻它的是另一件事。object 1 裡夾著 45 段有 reference 指向的資料，最大一段 990 byte，全部被 `rep movsd` 讀出來複製到堆疊上。我照 `-ms` 編了各種變化——`-zc`（文件寫「把字面值放進程式碼段」）、`-zdf`、`-zt0`、區域陣列初值、`static const`、C++ 編譯器、九個版本全掃一遍——這些資料一律落在 DGROUP，沒有任何一組旗標能把它們搬進 `_TEXT`。`-zc` 更誇張，加不加的反組譯輸出 byte 相同，等於在 32-bit 下完全沒作用。

卡住之後改去看原版怎麼複製的：`0x14abc` 是 `lea edi,[ebp-0x48]` / `mov esi,0x146e0` / 四條 `movsd`，**前面沒有 `mov ax,ss` / `mov es,ax`**。而我的 `-ms` 探針每次複製前都會重載 ES。這條線索指向 flat，回頭用 `-mf` 編 `localinit.c`，const 物件與區域陣列初值影像立刻全部出現在 `_TEXT`，ES 重載也消失了。

還有一個附帶的好處：`-mf` 把「具名 const 物件」放 `_TEXT`，但「字串字面值與浮點常數」仍留在 DGROUP 的 `CONST`。原版正是這個組合——`"Fight.vfs"` 在 `0x6001c`（object 2），常數表在 `0x146d2`（object 1）。這兩件事在 `-ms` 下會一起搬到 DGROUP，所以它們同時成立本身就是 flat 的指紋。

## 呼叫慣例：三個獨立來源指同一個答案

統計面很快：遊戲段 2,937 個呼叫點有 2,464 個後面跟著 `ADD ESP,n`，全段 `RET imm` 是 0，序幕一律是 `53 56 57 55 89 e5`，引數從 `[ebp+0x14]` 開始——堆疊慣例。

連結層是獨立的第二個來源。`0x435f3` 那段轉大寫迴圈有 31 個 byte 沒有任何重定位，拿去搜每個版本的 `LIB386`，只命中 10.0／10.0a／10.0b 的 **`CLIB3S.LIB`**；`__CHP` 那 22 個 byte 也一樣。`3S` 就是堆疊慣例的變體，跟反組譯統計無關地確認了同一件事。

CPU 等級花了點功夫才分開。`-3s`／`-4s`／`-5s` 在 `-od` 下大部分完全相同，差別只有兩處：`-3s` 用 `LEAVE` 收尾，`-4s`／`-5s` 改成 `mov esp,ebp` / `pop ebp`；`-5s` 又會把每個 `movsx eax,word ptr X` 換成 `mov eax,dword ptr X-2` + `sar eax,0x10`。原版遊戲段 `LEAVE` 是 0、`MOV ESP,EBP` 有 333 個、`MOVSX` word 有 208 個、`SAR reg,0x10` 是 0——`-4s`，兩邊都夾死。

`-s` 與 `-od` 是同一個實驗掉出來的。第一次編探針時我用預設值，結果每個 function 開頭都是 `push <框架大小>` / `call __CHK`，而原版 400 多個有框架的遊戲 function 一個都沒有——`-s`。至於 `-od`，是因為預設會把引數留在暫存器、把 switch 表放到函式之前；原版每個區域變數都寫回堆疊再讀出、switch 表夾在序幕後面用 `jmp short` 跳過，而且函式 body 因此變成不連續的兩段（`0x2f6d0` 的 `[2f6d0,2f6dd][2f700,2fb76]` 就是這麼來的，票 10 當時只當成現象記著）。

## 浮點：`-fpi` 而不是前作的 `-fpi87`

映像檔裡有 80x87 模擬器，`0x4ec3c` 起的 byte 命中 `EMU387.LIB`。前作 FD2 的記錄是 `-fpi87` 加上在 `.lnk` 裡明列 `EMU387.LIB`，我本來打算照抄。實際連了三個版本才發現不能抄：`-fpi87` 那版就算 `.lnk` 裡列了 `emu387.lib`，產出的 EXE 裡**沒有**模擬器；`-fpi` 那版有。原因是 wlink 只抽出解得掉未定義符號的 lib 成員，而 `-fpi` 與 `-fpi87` 編出來的 obj 唯一差別就是前者多一條 `EXTRN __init_387_emulator`——差一個外部參照，決定整個模擬器進不進得來。

順帶把 `-fp2`／`-fp3`／`-fp5`／`-fpr` 也編了一輪，在 `-od` 下四者產生完全相同的機械碼，這個旗標本 binary 判不出來，如實記著。

## 版本：三條線交叉

`DOS4GW.EXE` 的 SHA-256 與 10.0a／10.0b 的完全相同（9.5c 大小相同但雜湊不同）。`FDPS.EXE` 的 MZ stub 是 10,832 byte，一開始拿 `BINB\WSTUB.EXE`（10,822 byte）直接比，10,207 個 byte 不同，看起來完全不像——後來才想到 wlink 會改寫 MZ header 並補齊對齊，正確的比法是真的連一次再比。連出來的 stub 與 `FDPS.EXE` 的前 10,832 byte **零差異**。加上 CRT 的 byte 比對，三條線都落在 10.0a／10.0b。

工具面兩個坑：NT 版的 `WLINK.EXE` 在這台機器上會無回應，連 `stdin` 關掉都沒用，得殺掉程序；連結一律改走 DOSBox-X 裡的 DOS 版。`WDISASM` 則會把開頭是 `-` 的引數當選項，而 repo 路徑含 `-`——這條前作 playbook 已經寫過，照做（切工作目錄、傳相對檔名）就沒事。

## 沒解掉的一件事

`0x2f753` 是遊戲段唯一一張 switch 表的索引縮放，原版是 `lea eax,[eax*4+0]`（7 byte），而 9.5～10.6 的 `wcc386` 與 `wpp386` 在我試過的所有旗標組合下都產 `shl eax,2`（3 byte）。試過的方向：五種 CPU 等級、三種最佳化層級、`-d1`／`-d2`、`-ze`／`-za`／`-oi`／`-or`、兩種記憶體模型、C 與 C++ 兩支編譯器、九個版本，以及七種不同寫法的 switch（unsigned、short、case 從 1 開始、局部變數、有函式呼叫、12 個 case）。全部是 `shl`。

兩者語意完全相同、也沒有任何旗標能選擇，所以它不影響任何一項旗標判定。剩下的 11 項特徵加上重新檢查過的共 12 項全部重現（`verify_flags.py`）。這一處就當成已知殘留寫進知識庫，不硬編一個解釋。
