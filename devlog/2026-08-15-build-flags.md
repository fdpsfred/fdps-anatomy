# 2026-08-15 建置旗標組與預設 calling convention（票 11）

從機械碼猜旗標是猜不準的，所以整趟的做法是差分：手上有 Watcom 9.5～10.6 共十二套安裝，直接編一份探針原始碼，看哪組旗標產生的形狀跟原版一樣。真正花時間的是一個「原版做得到、任何版本都做不到」的形狀——它讓我一度誤判編譯器不是手上任何一版，最後查出來只是漏了一個旗標，而且是我的 regex 沒抓到。

## 先把容器解開

`parse_le_header.py` 一寫完就有幾件事直接掉出來：模組名叫 `fde` 不是 `fdps`、初始 ESP 剛好等於 object 2 的尾端 `0x6c3c0`、`debug_info_off` 是 0。ESP 落在 object 尾端表示堆疊被算進 DGROUP 的 virtual size 裡，那堆疊大小就等於 object 2 的尾端減掉 `_BSS` 的結束位址——問題變成「`_BSS` 到哪裡結束」。

答案在 CRT 啟動碼裡。`0x434cc` 是 `mov ecx,0x6a3bc` / `mov edi,0x63930` / `sub ecx,edi` 再 `rep stosd`，對照 10.0a 的 `CSTRTX3S.OBJ` 反組譯，這兩個立即值就是 `_end` 與 `_edata`。`0x6a3bc` 對齊到 16 是 `0x6a3c0`，`0x6c3c0 - 0x6a3c0 = 0x2000`，8K。後來用 `option stack=8k` 實際連一次，map 印出 `STACK ... 0002:0000a200 00002000`、`_BSS` 結束在 `0xa1f8`、對齊到 `0xa200`——完全同一個關係，推導成立。順手也量了 wlink 不寫 `option stack` 的預設值，是 4K，所以那行是原版明寫的。

這也順帶修掉知識庫一個不夠精確的說法：原本寫「`0x64000`–`0x6c3bf` 是 BSS」。`0x64000` 是「檔案內容到此為止」的邊界沒錯，但 BSS 本身是 `0x63930`–`0x6a3bb`，上面那 8K 是堆疊段，而且 CRT 啟動時還會把環境變數複本放在它的下緣。

## 被 CS: 前綴騙了一次

第一版判斷記憶體模型時，我看到 `JMP dword ptr CS:[EAX + 0x2f6e0]` 就下了 `-ms`（small model）的結論——理由是「flat model 下 DS 與 CS 同基底，不需要 CS: 前綴」。這個推理是錯的：實測 `-mf` 產生的 switch 分派同樣帶 `cs:`，這個前綴在兩種模型下都會出現，完全不是模型訊號。

推翻它的是另一件事。object 1 裡夾著 45 段有 reference 指向的資料，最大一段 990 byte，全部被 `rep movsd` 讀出來複製到堆疊上。我照 `-ms` 編了各種變化——`-zc`（文件寫「把字面值放進程式碼段」）、`-zdf`、`-zt0`、區域陣列初值、`static const`、C++ 編譯器、九個版本全掃一遍——這些資料一律落在 DGROUP，沒有任何一組旗標能把它們搬進 `_TEXT`。`-zc` 更誇張，加不加的反組譯輸出 byte 相同，等於在 32-bit 下完全沒作用。

卡住之後改去看原版怎麼複製的：`0x14abc` 是 `lea edi,[ebp-0x48]` / `mov esi,0x146e0` / 四條 `movsd`，**前面沒有 `mov ax,ss` / `mov es,ax`**。而我的 `-ms` 探針每次複製前都會重載 ES。這條線索指向 flat，回頭用 `-mf` 編 `localinit.c`，const 物件與區域陣列初值影像立刻全部出現在 `_TEXT`，ES 重載也消失了。

還有一個附帶的好處：`-mf` 把「具名 const 物件」放 `_TEXT`，但「字串字面值與浮點常數」仍留在 DGROUP 的 `CONST`。原版正是這個組合——`"Fight.vfs"` 在 `0x6001c`（object 2），常數表在 `0x146d2`（object 1）。這兩件事在 `-ms` 下會一起搬到 DGROUP，所以它們同時成立本身就是 flat 的指紋。

## 呼叫慣例：三個獨立來源指同一個答案

統計面很快：遊戲段 2,937 個呼叫點有 2,464 個後面跟著 `ADD ESP,n`，全段 `RET imm` 是 0，序幕一律是 `53 56 57 55 89 e5`，引數從 `[ebp+0x14]` 開始——堆疊慣例。

連結層是獨立的第二個來源。`0x435f3` 那段轉大寫迴圈有 31 個 byte 沒有任何重定位，拿去搜每個版本的 `LIB386`，只命中 10.0／10.0a／10.0b 的 **`CLIB3S.LIB`**；`__CHP` 那 22 個 byte 也一樣。`3S` 就是堆疊慣例的變體，跟反組譯統計無關地確認了同一件事。

CPU 等級花了點功夫才分開。`-3s`／`-4s`／`-5s` 在 `-od` 下大部分完全相同，差別只有兩處：`-3s` 用 `LEAVE` 收尾，`-4s`／`-5s` 改成 `mov esp,ebp` / `pop ebp`；`-5s` 又會把每個 `movsx eax,word ptr X` 換成 `mov eax,dword ptr X-2` + `sar eax,0x10`。原版遊戲段 `LEAVE` 是 0、`MOV ESP,EBP` 有 333 個、`MOVSX` word 有 208 個、`SAR reg,0x10` 是 0——`-4s`，兩邊都夾死。

`-s` 與 `-od` 是同一個實驗掉出來的。第一次編探針時我用預設值，結果每個 function 開頭都是 `push <框架大小>` / `call __CHK`，而原版 400 多個有框架的遊戲 function 一個都沒有——`-s`。至於 `-od`，是因為預設會把引數留在暫存器、把 switch 表放到函式之前；原版每個區域變數都寫回堆疊再讀出、switch 表夾在序幕後面用 `jmp short` 跳過，而且函式 body 因此變成不連續的兩段（`0x2f6d0` 的 `[2f6d0,2f6dd][2f700,2fb76]` 就是這麼來的，票 10 當時只當成現象記著）。

## 浮點：`-fpi` 而不是前作的 `-fpi87`

映像檔裡有 80x87 模擬器，`0x4ec3c` 起的 byte 命中 `EMU387.LIB`。前作 FD2 的記錄是 `-fpi87` 加上在 `.lnk` 裡明列 `EMU387.LIB`，我本來打算照抄。實際連了三個版本才發現不能抄：`-fpi87` 那版就算 `.lnk` 裡列了 `emu387.lib`，產出的 EXE 裡**沒有**模擬器；`-fpi` 那版有。原因是 wlink 只抽出解得掉未定義符號的 lib 成員，而 `-fpi` 與 `-fpi87` 編出來的 obj 唯一差別就是前者多一條 `EXTRN __init_387_emulator`——差一個外部參照，決定整個模擬器進不進得來。

順帶把 `-fp2`／`-fp3`／`-fp5`／`-fpr` 也編了一輪，在 `-od` 下四者產生完全相同的機械碼，這個旗標本 binary 判不出來，如實記著。

## 版本：三條線交叉

`DOS4GW.EXE` 的 SHA-256 與 10.0a／10.0b 的完全相同（9.5c 大小相同但雜湊不同）。`FDPS.EXE` 的 MZ stub 是 10,832 byte，一開始拿 `BINB\WSTUB.EXE`（10,822 byte）直接比，10,207 個 byte 不同，看起來完全不像——後來才想到 wlink 會改寫 MZ header 並補齊對齊，正確的比法是真的連一次再比。連出來的 stub 與 `FDPS.EXE` 的前 10,832 byte **零差異**。加上 CRT 的 byte 比對，三條線都落在 10.0a／10.0b。

工具面兩個坑：NT 版的 `WLINK.EXE` 在這台機器上會無回應，連 `stdin` 關掉都沒用，得殺掉程序；連結一律改走 DOSBox-X 裡的 DOS 版。`WDISASM` 則會把開頭是 `-` 的引數當選項，而 repo 路徑含 `-`——這條前作 playbook 已經寫過，照做（切工作目錄、傳相對檔名）就沒事。

## 沒解掉的一件事

`0x2f753` 是遊戲段唯一一張 switch 表的索引縮放，原版是 `lea eax,[eax*4+0]`（7 byte），而 9.5～10.6 的 `wcc386` 與 `wpp386` 在我試過的所有旗標組合下都產 `shl eax,2`（3 byte）。試過的方向：五種 CPU 等級、三種最佳化層級、`-d1`／`-d2`、`-ze`／`-za`／`-oi`／`-or`、兩種記憶體模型、C 與 C++ 兩支編譯器、九個版本，以及七種不同寫法的 switch（unsigned、short、case 從 1 開始、局部變數、有函式呼叫、12 個 case）。全部是 `shl`。

兩者語意完全相同、也沒有任何旗標能選擇，所以它不影響任何一項旗標判定。剩下的 11 項特徵加上重新檢查過的共 12 項全部重現（`verify_flags.py`）。這一處就當成已知殘留寫進知識庫，不硬編一個解釋。

（這一節與下面「手寫組語」那節的判斷後來都被推翻，見最後一節。）

## 複查抓到的四件事

寫完之後跑了一輪 code review，抓到的東西都是「單一觀察被當成兩個結論的證據」這一類：

**`fde` 這個名字證明不了兩件事。** 我原本寫成兩條：「連結時 `name FDE.EXE`」與「第一個 obj 是 `fde.obj`」，兩條都拿 LE 的 resident name 當證據。實測（`link_defaults.py`）發現沒有 `name` 指令時 wlink 會拿第一個 `.obj` 的名字當輸出檔名，而 resident name 又取自輸出檔名——所以這一個觀察分不出是哪一條路。改成一條，把兩種可能都寫出來。

**17 與 18 是兩個不同的量。** `-s` 那一欄寫「17 個 `__CHK` 呼叫端」，cc 統計那一節寫「18 個序幕是 `push imm` / `call __CHK`」，看起來自相矛盾。查下去是第 18 個（`0x51f6b`）呼叫的是 `0x451a8` 不是 `__CHK`，兩個數字都對，錯的是把後者也寫成 `call __CHK`。

**object 3 的取用範圍我抄錯了。** 知識庫原本寫 `0x56799`–`0x57a74`，我寫成 `0x56799`–`0x57c52`。重新量：對 `0x70000`–`0x70053` 的參照有 7,058 筆，但其中 6,834 筆是 LE loader 的 fixup 產物，濾掉之後真正的指令參照是 224 筆，範圍確實到 `0x57c52`——`0x57a74` 是最後一個 function 的進入點，不是最後一個取用點。順帶記住：這個 binary 上任何「數 reference」的量測都要先濾掉 loader fixup，不然會差兩個數量級。

**BSS 邊界改了，pitfalls 沒跟著改。** 同一個 commit 裡把 BSS 起點從 `0x64000` 修成 `0x63930`，但 pitfalls 那條規則還寫著「`0x64000` 以後」——照舊規則做的人會把 `0x63930`–`0x63fff` 那 1,744 byte 當成初始化資料 emit，正好是那條規則想防的錯。

工具面還有兩個坑：DOS 版 `wlink` 開不了超過 8.3 的 `.lnk` 檔名（`fpi87_16k.lnk` 靜靜失敗，只在 `build.out` 裡留一行 `cannot open`）；以及連結產物的「新舊」不能只靠「跑之前先刪掉」保證——Windows 上偶爾有掃描程序抓住剛寫出的 EXE 讓 `os.remove` 失敗。改成比對 mtime，但第一版又立刻踩到 DOSBox 寫出的時間戳只有 2 秒精度且向下取整，把剛產生的檔判成 stale，要留寬容值。

## 「會不會是手寫組語」這個問題把結論翻掉一半

收尾之後被問了一句：`0x2f753` 那個 `lea` 會不會當初就是手寫組語？

要證偽很簡單——量它是不是孤例。答案是遊戲段 **304 處** `lea reg,[reg*N + 0]`、程式庫段另有 41 處，而同一段的 `shl reg,2` 只有 37 處、清一色出現在 `SHL EDX,2` / `SBB EAX,EDX` 這種除法常數展開裡。也就是說：**原版把位址縮放一律編成 `lea`，把算術縮放編成 `shl`**，涇渭分明。304 處分散在整個遊戲段、所在函式從序幕到收尾都是編譯器產物——手寫組語當場排除。

但這個答案比原本的問題嚴重得多。我原本以為那是 switch 分派的單一特例，實際上是全域的 codegen 慣例，而我測過的每一個 Watcom 都反過來用 `shl`。回頭補測：

- 四種來源寫法（指標索引、全域陣列索引、函式指標表呼叫、指標運算後索引）——10.0a 全部 `shl`
- 索引變數改成全域／`unsigned`／`short`／`char`／`long`——全部 `shl`
- 補上先前漏掉的 10.5／10.5a／10.6（這三套只有 DOS 版執行檔，`version_sweep.py` 只掃有 BINNT 的安裝，所以整組被跳過了）——在 DOSBox-X 裡編，還是全部 `shl`

十一個版本、四種寫法、五種索引型別，沒有一個能產出 `lea`。

於是（錯誤地）把結論拆成兩半：**連結器、CRT、數學庫、模擬器、extender 是 10.0a／10.0b（byte 級證據）**，但**編譯器不是手上任何一版**，猜是 11.0 或早期 OpenWatcom，還寫進了 `open_issues.md`。這個推論下一節就被推翻——真正的原因是漏了一個旗標。

教訓有兩個。一是**「只掃有 BINNT 的安裝」這個偷懶讓三個版本整組沒被測到**，而且掃描表印出來的是「每個版本都一樣」，看起來反而像是結論很穩。二是**單一異常先量它的出現次數**——我當初看到一處就歸類成「已知殘留」，如果早點數一遍，這半天的版本結論不會先寫錯再改。（但即使數了，只要 regex 是錯的，結論還是錯的，見最後一節。）

## 全部改回 DOSBox：方法論的修正

使用者指出所有編譯器版本測試都要在 DOSBox-X 裡跑 DOS 版執行檔，不要在 Windows 下跑任何東西。這是對的——判定依據要建立在與原版相同的執行環境上，而不是「理論上 codegen 應該一樣」的 NT 版。我前半段圖快，`probe_matrix.py` / `version_sweep.py` / `verify_flags.py` 都在用 `BINNT` 底下的 `wcc386`，連結那半段才走 DOSBox（而且只是因為 NT 版 `wlink` 會卡住）。

全部改掉之後重跑，結論一項都沒變：十二個安裝、五種形狀、三十四種旗標組合，DOS 版產出的機械碼與 NT 版一致。這個「一致」本身值得記一筆，省得以後有人再驗一次；但它不能反過來當成「所以用 NT 版也行」的理由。

改的過程中要處理三件事：

- **DOS 版編譯器散在不同目錄**：9.5 系列在 `BIN`、10.0 家族在 `BINB`、10.5 之後在 `BINW`，`wdisasm` 又不一定跟 `wcc386` 同一個目錄。批次檔把三個都放進 `PATH` 最省事。
- **8.3 檔名**：`probe_switch.c`／`localinit.c` 得改名成 `probesw.c`／`locinit.c`，旗標矩陣的標籤從 `5s_s_od_fpi` 這種改成 `v01`…`v34` 再附對照表。
- **一次 DOSBox 跑完一批**：每個變體開一次模擬器太慢，改成一個批次檔跑完整批（矩陣 34 個變體、版本掃描每版 5 個探針）。

順帶抓到一個自己的 bug：`const 落在哪個段` 這個判定原本寫成 `_TEXT SEGMENT(?:.|\n)*?const_table` 這種跨行 regex。每份反組譯都以 `_TEXT SEGMENT` 開頭，所以不管 `const_table` 實際在哪一段都會命中——`-mf` 那條結論的兩根支柱之一，驗證方式是假的。改成逐行走 `SEGMENT`／`ENDS` 區塊之後重驗，`-mf` 進 `_TEXT`、`-ms` 進 `CONST2`，結論本身是對的，但先前那個 PASS 不算數。同一個修正也讓 `-d2` 看起來與 `-od` 有差異的假象消失（那也是 regex 誤判）。

## `-ot -od`：一個順序有意義的旗標對

使用者指出 `0x3fa49` 的版權字串 `WATCOM C/C++32 Run-Time system ... 1988-1994` 已經把工具鏈釘在 10 系列，不可能是 11.0，所以差別一定出在還沒試過的旗標或原始碼裡的設定語法。方向對了。

把 `-o` 底下每個子選項、以及所有還沒掃過的 `-z`／`-s`／`-b`／`-e` 旗標各加一個到定案旗標上編 `scale.c`，掃出來的結果是**全部 `shl`**，只有 `-ot` 那一列印出 `-`。第一反應是「這個變體編壞了」，去翻它的反組譯才發現：`-ot` 產出的是 `lea eax,+0H[eax*4]`——**它就是原版那條**，是我的 regex 少寫了 `\+0H` 才漏掉。`wdisasm` 對「只有索引、沒有基底暫存器」的定址一律寫成 `+0H[eax*4]`，因為 x86 這種編碼一定要補 4 byte 位移。

`-ot` 本身會把最佳化器打開，區域變數不再來回堆疊，這又跟原版對不上。於是排列組合：

| 寫法 | 框架 | 區域變數 | 縮放 |
| --- | --- | --- | --- |
| `-od` | 未最佳化 | 來回堆疊 | `shl` |
| `-ot` | 未最佳化 | 留在暫存器 | `lea` |
| `-od -ot` | 未最佳化 | 留在暫存器 | `lea` |
| **`-ot -od`** | **未最佳化** | **來回堆疊** | **`lea`** |

`wcc386` 由左而右處理選項：`-ot` 先設定「以速度為優先」的偏好，`-od` 再關掉最佳化器而**不清掉那個偏好**。只有這個順序三項全中。

補上 `-ot` 之後 `0x2f6d0` 那個 switch 從序幕到分派逐指令對得上，連跳躍表前那 2 byte 填充都是 `8b c0`（`mov eax,eax`），與探針產出的一模一樣。閘從 13 項變 15 項全過，`open_issues.md` 那條「編譯器版本未定」直接撤掉。

兩個教訓。一是**工具的輸出格式要先確認再寫 regex**——「所有版本都做不到」這個結論從頭到尾只是 `\+0H` 這五個字元。二是**掃描表裡的 `-` 比 `shl` 更值得看**：整整一輪掃描裡唯一的異常就在那一格，我卻差點當成雜訊跳過。
