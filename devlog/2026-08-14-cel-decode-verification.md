# CEL 圖檔解碼驗證（票 05）

票 05 的目標是拿前作的 RLE 4-op sprite 解碼器去解 FDPS 的 `.CEL`，實證「前作資產可沿用」這個假設。實際做起來，前作解碼器只花了十分鐘就對上，剩下的時間全在追一個沒預期到的檔案。

## 先從資料看，再回頭找程式

第一步是把 97 個從 VFS 解出來的 `.CEL` 全部讀檔頭，看有沒有一致的欄位。`43 45 4c 01 00 0f 00` 開頭一眼就看得懂：magic、版本 1、然後是 15，跟 `VFS` 的 header 一樣是「表在哪裡」。接著三個 u16 是寬、高、筆數，第四個 u16 是 2。97 個檔的版本全是 1、表位置全是 15、第四個欄位 96 個是 2、只有 `M310.CEL` 是 1。

偏移表用 `count + 1` 個 u32 讀，末項等於檔案大小，單調不減——97 個全過。但第一項本來預期等於「表尾」，有 8 個檔對不上，中間多出 16 到 2,488 byte 不等。把那段拿去當指令流解，解出來是半截半截的圖磚，不是任何欄位。判定成編碼工具留下的殘料，驗證條件從「第一個 sprite 緊接表尾」放寬成「第一個 sprite 不落在表內」。

到這裡才去 Ghidra 對答案。從 `Village.cel` 這個字串往回找到 `0x31210`，看到它把載進來的 blob 丟給 `0x2dba0`；`0x2dba0` 的 assembly 短得很好讀：`MOVSX` 讀 `+0x7` 與 `+0x9`，然後 `cel + *(int *)(cel + index * 4 + 0xf)` 取串流。**偏移表的位置是寫死的 `0x0F`，`0x05` 那個欄位程式根本不讀**——跟 VFS 那邊「欄位存了但程式寫死」的習慣一模一樣。

`0x0B` 的筆數本來以為也沒人讀，搜 `word ptr [.. + 0xb]` 找到 `0x2e640`：它拿筆數乘 `0x240`（576 = 24 × 24）配記憶體，把整批圖磚展開成連續緩衝。所以筆數是真的被讀的。`0x0D` 搜 `word ptr [.. + 0xd]` 一個都沒有。

## 4-op RLE 不用猜

`0x2dba0` 呼叫的 `0x568db` 是個 13 路分派，mode 0 的本體在 `0x56a0d`，`SHL CL,1` 兩次判高 2 bit、`SHR CL,2` 後 `INC CL` 取長度——就是前作 `fd2_rle_blit_sprite` 的同一套。`0x40` 那個 op 的 `INC EDI` 再 `STOSB` 也對得上前作「寫每一對的後面那個」。

比前作多學到一件事：這個繪製器是**逐列**的，`BX` 每列從寬度扣到剛好 0 才換列。一個 op 超出列尾的話 `BX` 會繞回成極大值，繪製器就寫穿記憶體。這代表編碼端一定讓每列剛好填滿——於是「每列剛好、每個串流剛好用完」可以當成硬條件驗證，比前作那種攤平成一維游標的解法嚴格得多。第一版解碼器就是照這個寫的。

## 然後 M310.CEL 卡住

98 個檔解得乾乾淨淨，`M310.CEL` 第一個 sprite 的第二列就爆：`9f` 是 literal 32，可是列只有 24 寬。

先懷疑是自己的解碼器有 off-by-one，回去重讀 `0x56a0d` 三次，沒有。再懷疑檔頭的寬高不是 24×24，但欄位就是寫 24。再試前作另一種 `fd2_decode_dialog_pixel_byte` 的編碼，算出來的像素數是 1841，離 576 差太遠。試把 4-op 攤平成一維不管列邊界，508，也不對。

轉機是把整個串流按 24 byte 一列印出來看：開頭是 `d7 9f 00` 重複 16 次。`00` 太規律了，猜是列尾標記；那 `d7` 就得是「24 個 `9f`」——`(0xd7 & 0x3F) + 1 = 24`。往下驗 `cb 9f c6 ef c4 9f 00` 是 12 + 7 + 5 = 24，成立。`80`–`0xBF` 是 literal 串（`94` 後面真的跟著 21 個 byte），剩下 `0x01`–`0x7F` 一開始猜成「跳 N 個像素」，192 個 sprite 裡有 22 個過不了；改成「一個像素，值就是這個 byte」之後 192 個全過，每個剛好 24 個列尾、串流剛好用完。全部 4,608 個列尾 byte 一個不多一個不少。

算成圖是一組室內場景的圖磚（木地板、床、桌子），完全不是雜訊。所以這是一種真的編碼，而且 `0x0D` 那個欄位就是在標它。

麻煩的是**程式不讀 `0x0D`**。13 個 blit mode 全部逐一看過 assembly，差別只有調色盤重映與翻轉，讀的都是同一種串流；`0x575ed` 那個 mode 8 甚至只是算完垂直翻轉的起點就 `JMP` 回 `0x56a0d`。地圖圖磚的繪製路徑 `0x2c330` 也是 `cel + *(int *)(cel + tile * 4 + 0xf)` 再丟 `0x568db`，同一條路。找不到第二個解碼器。

`m%02d%d.cel` 的 sprintf 參數是 `DAT_00069cf4` 與 layer，所以 `M310.CEL` 是編號 31 的第 0 層，而且 `M31.DTL`、`M310.MPL`、`ATTR310.DAT` 都在，是一組完整的地圖資料。

寫到這裡被問了一句「遊戲只有三十章，怎麼會有地圖 31」，才發現自己一直沒確認 `DAT_00069cf4` 到底是什麼。回去查：同一個全域餵給 `map%02d.cod`、`map%02d.dat`、`M%02d.dtl`、`attr%02d%d.dat`、`fdetxt%02d.txt`，而 `FIELD.VFS` 裡實際有 `MAP00`–`MAP64`、`FDETXT00`–`FDETXT65`，值域根本不是 0–29。寫入點 `0x21c26` 是從腳本串流讀一個 byte 運算元直接存進去再呼叫換場常式，所以「跳到編號 N」是一條腳本指令。章節專屬的東西另有一張表：`0x60074` 恰好 30 筆函式指標（讀原始 byte 確認第 31 筆的位置已經是字串 `"IconAni.vfs"`），由同一個全域索引，只在章節場景那條路徑用到。

結論是它是**地圖編號**不是章號，0–29 與章節重合、31–64 是城鎮之類的額外場景。解出來的 `M310.CEL` 是室內圖磚也對得上。這個詞已經補進 `CONTEXT.md`，因為「30 以上的編號不代表有第 31 章」這件事很容易再踩一次。至於 `M310.CEL` 編碼不合的矛盾，票 05 的範圍內收不了，留給實機驗證。

## 調色盤

`.CEL` 裡沒有調色盤。第一輪全部用 `FDE.PAL` 算圖，`STBOARD.CEL` 出來是一團彩色雜訊，但「START NEW GAME / LOAD GAME / EXIT」那幾行字清清楚楚——形狀對、顏色錯。換成 `STBOARD.PAL` 立刻變成完整的標題畫面。所以調色盤是場景層級的選擇，工具就把它留成呼叫端的參數，不試圖自動配對。

## 沒做的事

沒有動 Ghidra。這輪讀了十幾個 function 的 assembly，但命名與 calling convention 的修正是票 10、11、15 的範圍，現在改進去只會跟那些票打架，位址直接寫進知識庫當證據。
