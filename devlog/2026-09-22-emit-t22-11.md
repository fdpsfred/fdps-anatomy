## 拆檔時順手撞到的舊傷：`emit_state.json` 寫錯層

這件事比拆檔本身重要。拆檔時發現 `emit_state.json` 裡 0002bae0（`fdps_battle_player_phase_loop`）與 0003b600（`fdps_chapter_24_end`）兩筆已 commit 的記錄被寫在檔案最上層，而不是 `"functions"` 底下。後果是 `next_batch.py` 看不到它們已完成，會再把這兩支當成待做的發出去——也就是對已經存在的定義再 emit 一次。

修法是把兩筆原封不動搬回 `"functions"` 底下，單獨一個 commit（1b46bf9），修完統計是 507 支已 commit、7 支待做。寫壞它們的是這兩支自己的落地 commit（a4f473b、7ddf629），也就是說**落地／記帳階段寫進度的那段有時會寫到錯的巢狀層級**。這批沒有去追根因。後面 0003ba80 的落地回報特別註明「`emit_state.json` 把 function 放在 `functions` 物件底下，所以更新的是 `functions['0003ba80']`」，看得出那一輪的 agent 是自己意識到這個結構才寫對的，不是寫入端本身保證了。下一批如果又看到已 commit 的 function 被當成 pending 發出來，先查這裡。

## 沒套上的 Ghidra 修正：`fdps_battle_system_menu`（00014ab0）

reviewer 提了兩條 Ghidra 修正，只套了一條（plate 改寫）。沒套的是 000601c4 那張表的型別：它現在是 `/void_int_fn *[50]`，但 `/void_int_fn` 實際上被定義成 `void(void)`，正確的是 `void(int unit_index)`。改這個 typedef 是安全的（沒有別的東西用它），但權限分類器把這個改動判成「Modify Shared Resources」擋掉了，所以**這條目前沒改**，Ghidra 裡那張表的元素型別仍然是錯的。它只影響 Ghidra 的顯示，不影響已 emit 的 C。

## 批次結束後的收尾（不是 workflow 做的）

**寫錯層級的那兩筆，根因在 prompt，已經修成結構性的擋法。**

拆檔 agent 在 `1b46bf9` 修掉的是症狀：`0002bae0` 與 `0003b600` 的進度記錄被寫在 `functions` 那個大括號**外面**，跟 `functions` 同一層。`a4f473b` 的 diff 看得很清楚，新的那筆接在 `functions` 結束之後。讀進度的腳本只看 `functions` 底下，所以這兩支讀起來就是「從沒做過」，會被重新發出去再 emit 一次。

**根因是 prompt 沒講那筆要放在哪一層。** emitter 寫在途標記、bookkeeper 把它推進成 committed，兩處的指示都是「把 key `"<位址>"` 那筆設成……」，從頭到尾沒有提到 `functions`。而關鍵在於：**進度檔只存已完成的 function**，所以每一支新 emit 的都是一筆從來沒存在過的記錄，檔案裡沒有現成的同類可以照抄層級。大多數 agent 會先看檔案結構、放對地方；514 支裡有 2 支沒看，照字面寫在最外層。

**有沒有造成實際傷害，查過了：沒有。** 逐一數每個位址的落地 commit，514 支剛好 514 個不重複的落地，沒有任何一支被 emit 兩次。那兩筆是在被重新發出去之前就被抓到的。

修法兩層：

- **prompt 寫明路徑**：兩處都改成 `state["functions"]["<位址>"]`，並說明為什麼特別容易放錯（記錄通常還不存在，沒有現成的可以照抄）。
- **結構性的防呆**：`next_batch.py` 讀進度檔時，只要最外層出現位址形狀的 key 就直接報錯停下，並說出是哪幾筆、該怎麼搬。實測過：塞一筆進去，腳本以 exit 1 擋下；正常狀態讀起來不受影響。

第二層才是真正的修法。這跟 memory 裡「禁止批次處理」那條的教訓是同一件事：**要結構性強制，不要只靠 prompt 指示**。prompt 寫得再清楚，514 支裡還是可能有一支沒照做；一個會停下來的腳本不會。原本的形狀是「寫錯了就靜默地再做一次」，現在變成「寫錯了就當場擋下」——前者的代價是重複的程式碼混進 `src/`，後者的代價只是停一次。

**票 22 的 emit 到此全數完成，514/514。** 剩下的是疑慮總掃。
