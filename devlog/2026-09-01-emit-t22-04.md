值得記的判讀是：這四支在第一輪的 build 都是乾淨的（0 errors、0 warnings、0 failed），WDISASM 對照也都過了。**build gate 這一批一次都沒有抓到東西**——四次修正輪全部是 reviewer 讀 assembly 讀出來的，而且三次是讀「文件說的」跟「assembly 說的」不合。這件事對之後的批次有兩個意涵：gate 對這類問題完全無感（它只證明自己會編會過測），以及註解裡那種「順手寫下的 caller 行為」是最容易寫錯的東西，因為它描述的是別支 function，emitter 手上正好沒有那支的完整 disassembly 也照樣寫得出來。

順帶一提，0002fe40 的 emit verdict 自己記了兩輪，第二輪是 `src/blit.h` 的註解修正；workflow 統計把它算成 rounds 1。這是計數口徑差異，不是漏記。

## 死路與雜訊

這些沒有一個造成失敗，但每一個都吃掉了時間，而且下一批不知道的話會再吃一次。

**PowerShell 的行數是錯的。** 至少四支的 bookkeeper 各自撞到同一件事：`Get-Content | Measure-Object -Line` 報的行數比真的少（`src/unitstat.c` 416 對 499、`src/blit.c` 582 對 680、`src/audio.c` 142 對 158 與 525 對 593）。它會跳過空行、也誤判編碼。要 `wc -l` 的語意就用 python 數 `\n`，不要用 Measure-Object。這條已經被獨立重新發現四次了。

**用 `git log -1` 確認 commit 有沒有成功是不可靠的。** 00030230 那支的 bookkeeper 送了一個壞掉的 PowerShell 參數（`--no-verify:$false`）而且把輸出丟給 `Out-Null`，git 直接拒絕；接著跑的 `git log -1` 回了一個 hash，那是**前一支** function 的 commit（1d235c4 / 00030120）。它是靠 `git status --porcelain` 還顯示五個檔在 staged、以及 `git log --grep "@ 00030230"` 是空的才發現。確認落地要用 `--grep` 打自己的位址，不要看 HEAD。重跑之後乾淨落地成 fc46e05，沒有 amend、沒有改寫歷史。同一支還記到 session 開頭 context 裡那份 git 快照列的近期 commit 跟 repo 實際的完全不同——那份快照是時間點的照片，不能拿來當判斷依據。

**`set_plate_comment` 的三條警告是雜訊。** 每次寫 plate 都會回「missing Algorithm / Parameters / Returns section」三條 advisory，至少六支各自停下來評估過一次。那是 MCP server 的通用樣板檢查，本專案的 plate 用的是 Pool/Evidence/Name/Boundary/Signature 格式，本來就沒有那三節。寫入是成功的，不要為了消警告去補節。

**「note」是資訊的死路。** 這批有好幾支的 reviewer 留了非阻擋的 note 而不是 `open_issues`，bookkeeper 依規則不能把 note 寫進 `emit_issues.json`，於是那些發現除了留在 verdict 檔裡以外沒有任何下游會看到。實際被擋在外面的至少有：`src/gamedata.h` 說幾個寫入者「各設一筆為 1」但 00021c8f 存的是 script data byte；`src/gauge.h` 說餘數區段「從 column 2 開始」而實際起點是 2 + fill_width；`src/statwin.c` 說 lower_right_x 的「最後兩步」需要 clamp 而實際是最後四步；`src/audio.c` 與 `tests/audio.c` 把 00047290 的指令引成 `TEST EAX,EAX / JZ RET`，實際是 `JNZ 0x00047299` 加落空到 RET（描述的行為對，助憶碼抄反）；`src/audio.c:174` 還在用位址稱呼 voice allocator；`src/gamedata.h` 兩個註解位址掛在序列的第一條指令而不是它指名的那條（00018e15 是 PUSH，MOV 在 00018e22；0001b8f4 是 PUSH，`CALL free` 在 0001b8fa）。這些現在只存在於這篇裡。要嘛 reviewer 該把這類東西升格成 `open_issues`，要嘛 workflow 該給 note 一個歸檔位置。

**`emit_state.json` 的結構跟指示不合。** 有兩支的 bookkeeper 各自報了同一件事：entry 不在頂層，是掛在 `functions` 物件底下（旁邊還有 `_doc`）。兩位都自己判斷去更新 `functions[addr]`，沒有出錯，但這是每支都要重新發現一次的摩擦。另外 00028ee0 那筆 in_flight 只帶 status 與 in_flight_since，沒有 name/target/body_size，是全檔唯一一筆缺這三個欄位的；bookkeeper 依「不要碰其他欄位」照做沒有補。如果收尾總掃或任何報表以 `name` 或 `target` 為鍵，這筆會讀成空白。

**Ghidra 修正的計數是「決定數」不是「編輯數」。** 好幾支的 emit 與 review 提出的是同一個修正，bookkeeper 一律只套一次；也有反過來的，一個 fix 描述「替換三處」而 plate 裡實際有五處（00030120 的 FUN_0001cb00）、描述「四處」而實際六處（00019250 的 DAT_00064000）。兩次都依 fix 的**理由**（把過時的佔位符從那一節清掉）全部替換，並在回報裡標明是 fix 文字數錯了而不是另一個決定。這個判斷往後應該一致：跟著理由走，不跟著數字走。

**autocrlf 警告每次都會出現。** `LF will be replaced by CRLF` 是這個 repo 既有的行為，不是這批引進的，不用追。

## 一條疑慮追下去，追出一個錯誤的假說和一個真的更正

`000192c0` 記的是：原版把每個記憶體運算元先 `MOV EAX` 再 `PUSH`，而定案旗標組直接 `PUSH` 記憶體，每個引數差一個 byte，這支 `0x4d` 對 `0x49`。它把 `needs` 寫成「跑一次旗標探針」——**那不是等不到的證據，工具鏈就在手上**，所以這條本來就該在 emit 當下解掉。既然它記下來了，就當場追。

追的過程走了一段死路，值得完整記著。

**第一步看起來是大發現。** 照 `tools/build_flags/` 既有的做法寫了探針 `pusharg.c` 與 `push_form.py`，把 `-o` 全家族、`-z` 家族、處理器與浮點旗標各掃一輪。`-d2` 命中了：它產出的正是 `PUSH EBX/ESI/EDI/EBP` + `MOV EBP,ESP` 的框架加上每個引數 `MOV EAX,槽位 / PUSH EAX`，與原版逐條一致。而 `build_flags.md` 當時寫著「`-d2` 接在 `-ot` 之後給出與 `-od` 相同的機械碼」——那句話被這個反例推翻了。把 `verify_flags.py` 的旗標換成 `-d2` 並加上第 16 項檢查，跑出 16/16；換回 `-od` 則正好只掛第 16 項。看起來就是「旗標組錯了一個字」。

**第二步整個推翻它。** 動旗標之前先去 image 裡驗那第 16 項的 reject 條件（「遊戲段沒有任何 `PUSH` 記憶體」）。`search_instructions` 掃 `PUSH` + `[EBP` 回來 **202 處直接形式**，第一筆就在 `fdps_map_actor_behavior_step` 的 `00010037`。更難堪的是 `00019442` 那四條連續的 `PUSH dword ptr [EBP-0x20/-0x2c/-0x28/-0x24]`：它在 `fdps_draw_unit_hp_mp_gauges` 裡，與 `000192c0` **同一個物件、呼叫同一個 callee `00019250`**，一個用直接形式一個用中轉形式。

所以原版兩種都用，而 `-od` 只產得出直接形式、`-d2` 只產得出中轉形式，**沒有任何單一旗標產得出混用**。emitter 那條疑慮的前提（「原版把*每個*記憶體運算元經 EAX 中轉」）本身就是錯的，而我差一點就照著它去改整個專案的旗標組。教訓很直接：**探針說「這組旗標產出原版的形狀」只證明了充分性，不證明必要性；動旗標之前要先回 image 驗那個形狀是不是真的到處都成立。** 我加的第 16 項檢查的 reject 條件正是沒驗就寫下去的，它才是這段路上真正的錯誤。

旗標組維持 `-od` 不動，`verify_flags.py` 回到 15/15。留下來的是三樣東西：`build_flags.md` 那句「兩者機械碼相同」的更正（它確實是錯的，只是更正的方向不是換旗標）、引數推送形式那一節的事實與量測工具、以及一個給重建者的實用結論——**重建 body 會比原版短掉「記憶體引數個數 × 1 byte」，拿長度差判斷有沒有漏轉錄時要先扣掉這一項**。成因還沒收斂，唯一還站得住的假說是原版逐檔用不同旗標建，下一步（把遊戲段每支 function 依形式分類看是否落成連續區塊）寫進了 `open_issues.md`。`000192c0` 那兩條疑慮標成 `resolved` 並附上這個答案，總掃不必再推導一次。
