# 票 28：角色屬性數值比較網頁

## 起點：前作能搬什麼

先讀前作 `fd2-anatomy/tools/growth_table/` 全部檔案與發佈檔。前作的資料來源是四張從 Ghidra MCP dump 出來的表（`raw_tables.json`），公式寫死在 `gen_growth.py` 的 docstring 裡：招募等級取 base[+2]、轉職「等級歸 1、立即擲一次新職業成長」、上限看 portrait `0x1E`／`0x1F`。票面已經說公式不能照搬，實際讀下來三處都不一樣：

- FDPS 的轉職（`src/church.c` `fdps_church_promote_loop`）不擲骰，是**直接加新型態成長表的原始上限 byte**，而且門檻是 LV20 不是 LV40。前作「承接 LV40、立即擲一次」若照抄，最大版本每項會少 1、最小版本會少（上限 − 下限）。
- 上限判定看肖像編號 9（蓋亞），`src/unitstat.c` 的兩個常數。
- 加入等級不能只看 `FRIAPRDA.DAT` 的等級欄：`assets/characters.md` 的「加入」表寫明法蓮娜、費塔加、瑪麗安實際以同章地圖上的單位留隊，蘭斯洛特與珊看到場前有沒有過關。

前作沒有處理「在哪一級轉職」，一律 LV40。FDPS 教會 LV20 就能轉，大多數玩家大概不會等到 40，所以加了一個全頁的轉職等級設定，產生器與比對因此要展開 20–40 每一級。

## 資料層

票面要求直接 import `tools/data_tables`。它的 `decode_appearance` 原本只解種族、職業、等級、法術遮罩，`decode_growth` 只留習得索引——都不夠。考慮過在本工具裡用 `appearance[...]["raw"]` 自己切 offset，但那就是「另寫解析」，而且 `raw` 只有 FRIAPRDA 有，FRILEVUP 沒有。最後是擴充擁有者：兩個 decoder 多吐出六個基礎值與五組成長 byte，先寫兩個手造記錄的測試（紅燈），再改。改完跑 `data_tables.py check`、`data_skill/build.py`，產物都沒有變。

## 期望值從哪來

測試需要不經本工具的數字。攻略站 `list.txt` 的「各人物職業滿級屬性」有 40(m)／99(m) 欄（「升到 40 級的最大值」），拿蘭迪斯試算：劍士 LV1 AP 18、每級最多 5 → LV40 213，攻略站 213；劍聖 534 = 213 + 原始上限 9 + 8 × 39，正好是「轉職加原始 byte、LV40 轉職」。反過來用前作「擲一次最大成長」算是 213 + 8 + 8 × 39 = 533，差 1——這組數字本身就是轉職公式的獨立證據。手抄了七人的出場列、六列 40(m)／99(m)、七條轉職後的 40(m) 與「轉職建議」的徽章進測試，一次全綠。攻略站 40 欄是平均值，所以下限 = 2 × 平均 − 上限，也順便驗了下限版。沒有寫解析器去讀 `list.txt`（專案規則：人寫的內容只做字串搜尋）。

## 獨立重算：照 src 逐級重播

票面要求與 `src/` 逐項獨立重算 0 誤差。前作的「獨立重算」是第二份閉式公式。這次改成 `src_replay.py`：逐行轉錄 `fdps_roster_add_character`、`fdps_level_up_apply_stat_gain`（`rand()` 換成回答 0 或 range − 1 的選擇器，零差時不問）、`fdps_unit_award_exp_and_level_up` 的上限判斷、教會的候選判斷與徽章優先順序、轉職加值，在 16 位元欄位上一級一級跑。上限、誰能轉、哪種徽章組合走到哪個型態都讓重播自己決定：每種加入等級 × 每個轉職等級 × 徽章的 8 種組合全跑，再與產生器的路線清單與每個值比。164,370 個值一致，1 秒內跑完。

為了確認它不是恆真，對產生器注入兩個常見錯誤：轉職加值改成 max − 1（抓到 141,120 處）、HP／MP 也乘 LV（抓到 65,618 處）。第一版的比對函式靠閉包讀外層迴圈的 `variant`，能跑但太隱晦，改成明傳參數。

## JS 與 Python 的比對：從貼 console 變成閘門

前作的 JS 驗證是「把 `verify_js_browser.js` 貼進 console」，而且那支腳本逐字複製了頁面的計算函式——頁面改了、複本沒改，比對照樣會過。這台機器沒有 Node，但有 Chrome：`chrome --headless=new --dump-dom` 會跑完頁面 script 再吐 DOM。做法是從**建好的頁面**原樣切出 `<script id="model">`（頁面唯一算數值的區塊）與內嵌資料，連同 `growth_data.json` 組成一個 harness 頁，比對結果寫進 `<pre id="result">`，Python 從 dump 出來的 DOM 讀回。注入「上限含 b」的錯誤能抓到 80,100 處。

同一招做了煙霧測試：三個分頁各載入一次，`--enable-logging=stderr` 會把 console 的 `Uncaught` 印到 stderr，注入一個 `window.__x.y` 確認抓得到。後來再加一段操作每個控制項的 script（轉職等級 20／30／40、每名角色、加入方式、路線、排序、比較的每個選項、在每張圖上移動滑鼠）。第一次跑回報 289 步、門檻寫 500——門檻是事先猜的，實際三輪就是這麼多步，錯的是門檻，改成 200。

## 視覺：幾輪截圖

先載入 `frontend-design` 與 `dataviz`。設計決定與和前作的差異寫在 `tools/growth_table/_index.md` 的「網頁設計」。過程中截圖發現的問題：

- 第一張「淺色」截圖其實是深色：headless Chrome 跟著系統的深色設定。改成另存一份在 `<html>` 上寫死 `data-theme` 的複本來截。
- `main` 的上下 padding 被 `.wrap` 的 `padding:0 28px` 蓋掉（類別選擇器比元素選擇器優先），內容貼著分頁列。改成 `main.wrap`。
- 屬性標籤「HP 上限」與本頁的「上限／下限」（最大／最小成長）撞詞，排名欄一片「上限」看不懂是哪個上限。屬性改用「生命、魔力、攻擊、防禦、敏捷」與「AP（不含裝備）」。
- 比較圖的線尾標籤被右邊界切掉；DX 的 y 軸刻度出現 63、188（250 四等分）。改成先挑 1／2／2.5／5 × 10ⁿ 的整數步長再決定頂端。
- LV40 轉職時「不轉職」那條灰線完全被轉職線蓋住，只在轉職等級低於 40 時才畫。
- 手機寬度的截圖看起來整頁往右溢出，但量了 `innerWidth` 是 500：headless 視窗有最小寬度，截圖只是切掉。改成把頁面放進 375px 寬的 iframe（media query 看 iframe 的寬），頁內用 `postMessage` 回報 `scrollWidth` 與超出右界的元素。真正溢出的只有角色明細：名冊的 grid 子項預設 `min-width:auto` 撐寬，以及職業成長表不換行。修掉之後三個分頁都沒有橫向捲動。

## 沒有新的踩雷點

照票面檢查了這次碰到的每條規則：出場公式的 LV／LV − 1 不對稱、上限不含、零差不抽亂數、轉職加原始 byte、轉職資格看肖像編號、名冊等級不等於加入等級、蓋亞的經驗餘數，`rebuild_info/pitfalls.md` 都已經有對應的列。這次沒有發現新的「照直覺寫就會與原版不同」的事，`pitfalls.md` 不動。

## 審查抓到的

收尾前分兩條線審查（規範、票面）。最實在的一條是測試本身的 bug：`Page` 類別裡跑 JS 比對的那個測試先呼叫 `build_page.main([])` 重建頁面，unittest 依名稱字母順序執行，它排在 `--check` 那個測試之前，所以發佈檔過期時會被測試悄悄重寫、`--check` 永遠通過，還讓工作樹變髒。改成測試只寫 workspace 預覽（`build_preview()`），發佈檔只准 `--check` 判斷。

其他照改的：`gen_growth.py` 的終端輸出有中文（「不需徽章」、頓號），違反腳本輸出一律英文的規範；加入方式的說明文字原本在 Python 裡組成中文字串塞進模型，改成模型只帶結構化欄位（`how`、到場回合），文字由頁面組；`decode_growth` 的 docstring 與 `data_tables/_index.md` 說「後一個 byte 是不含的上界」，漏了兩值相同時就是固定成長；路線徽章那段註解說「最前面的路線是教會最先測的」，對勇者徽章不成立（教會最先測的是勇者徽章），改寫；`verify_js.py` 的 docstring 沒寫到操作控制項那一段；頁面裡一支沒人呼叫的 `growthLine` 與只轉手 `BUILDS` 的 `rankBuilds` 刪掉。票面審查確認公式與 `src/` 一致，指出幾項未在票面宣告的附加功能（學會的法術、「不轉職」灰線、網址記分頁），補記進票面。

## 提早過關的版本

完成後開發者認為蘭斯洛特與珊「較高等級」的版本正常遊戲拿不到，像是填戰場用的 dummy 資料，要從頁面移除。動手前查了兩件事。其一，珊的情況相反：拿不到的是較低的 LV10（名冊記錄），她平常以戰場上的 LV15 加入；照「較高等級」移除會移掉她正常的版本。其二，攻略站遊戲攻略頁第 19、24 章的備註明寫「如果第五回合以前便結束，蘭斯洛特仍會加入，但屬性變成 LV15…」「如果第七回合以前便結束，珊仍會加入，但屬性變成 LV10…」，HP、MP、DX 與名冊記錄套出場公式完全相同，法術也是名冊記錄的遮罩，第 24 章還記了只有提早清場才會看到的「狂戰士自動認輸」，看起來是實際打出來的。

把這兩點交給開發者後，決定保留兩個版本，先試做「預設隱藏、開關才列出」，做到一半開發者改成全部照列、只在頁面上加文字說明。最後的做法：名冊版在排名標「提早過關」、比較頁與明細的選項標「LV15 加入（提早過關）」，說明文字由資料組出放在三個地方。知識庫原本就在 `assets/characters.md`、`chapters/ch19.md`、`chapters/ch24.md` 與 `pitfalls.md` 寫了兩筆記錄，只補一段攻略站的佐證到 `assets/characters.md` 的「加入」。

## 發佈

`docs/` 不是空的發佈目錄，以 `/docs` 為 Pages 來源會連攻略站鏡像一起公開。`docs/README.md` 寫了三種做法並建議另開只放網頁的 `gh-pages` 分支（`git subtree split`）；為了那個做法，`.nojekyll` 除了 `docs/` 也在網頁資料夾裡放一份。發佈檔取名 `index.html`，網址停在資料夾。repo 沒有遠端，Pages 的設定留給開發者。
