# 2026-09-02 emit t22-05：100 支，撞出「CD 模組不是用定案旗標組建的」

票 22 的第五批。開跑時待 emit 的清單還有 386 支，這批一口氣吃掉 100 支，全部落地、沒有跳過、沒有中途停、沒有拆檔、沒有一支沒走完。`recovered` 是空的，`cut_short` 也是空的：上一批沒有被砍掉、沒有留下半成品要丟，這批是從乾淨的樹開始跑到底的。

批次形狀跟前幾批一樣，不重述。要記住的只有一點：**這批的 100 支不是同一種東西**。前面約 50 支是章節事件與 post-action 處理器，形狀高度重複、幾乎都是十幾條指令的轉發；後面 40 幾支是 CD-ROM／MSCDEX 那一整個模組加上 DPMI 與鍵盤，全是跟真實硬體與 driver 打交道的東西。這批絕大部分的收穫都來自後半段，前半段的價值主要在於它便宜。

## 這批最大的一件事：CD 模組是用另一組旗標編出來的

`0003bade`（`fdps_cd_alloc_dos_buffers`）的 emitter 在對照 WDISASM 輸出時發現定案旗標組怎麼樣都對不上，於是回頭做了旗標探測，結果是**量出來的，不是推論的**：

- 用 `-bt=dos4g -mf -4s -fpi -os` 編出來的 `src/cd.c` body，與原版 `0003bade` **逐條指令、逐 byte 相同**，全部 0x9f 個 byte——`PUSH 0x14` / `CALL __CHK` 開頭、沒有暫存器框架、每個引數用 `PUSH imm32` 推位址、`0003bb5b` 是 `MOVZX EAX,word ptr`、bare `RET`。
- 用定案旗標組（`-s -ot -od`）編同一份原始碼得到 0xad 個 byte：四推框架、`MOV EAX,offset` / `PUSH EAX` 的引數推送、`XOR EAX,EAX` / `MOV AX` 取代 `MOVZX`、而且**沒有 stack probe**。

範圍是整個模組，不是這一支：`get_xrefs_to` 掃 `0004361a`（Watcom 的 `__CHK`）回來 34 個呼叫端，其中 **32 個是 `fdps_cd*`，位址從 `0003bade` 連續到 `0003c93f`**，另外兩個是 CRT 的 `spawnve` / `spawnvpe`。而且「用 `PUSH imm32` 推資料位址」這個形式在整個 image 裡也只出現在同一個區塊，`MOV EAX,<資料位址立即值>` 則一處都沒有。這一批後來每一支 CD function 各自用 WDISASM 對過自己的 object，`0003bc3f`（cdtoc.c）、`0003c51c`、`0003c636`（cd.c）都各記了一筆，把「模組性」而不是「單支」這件事釘死了。

### 為什麼 `build_flags.md` 沒有抓到

`rebuild_info/build_flags.md:127` 支持 `-s` 的理由寫的是「遊戲段 414 個標準框架的 function 沒有任何一個呼叫 `__CHK`；17 個呼叫端全部是程式庫 function」，`:246` 另外數到 18 個 `push imm` / `call` 序幕的模組。這句話在寫的當下沒有錯——它把「遊戲段」定義成 `0x3b000` 以下，而 CD 區塊起於 `0x3bade`，當時那 32 支還是沒有名字的 `FUN_`，理所當然被歸進「沒有 `-s` 的程式庫模組」那一類。**這一批把它們命名成 `fdps_cd_*` 之後，同一批機械碼的分類改變了，數字才對不上。** binary 沒變，變的是我們知道那是誰。

這是一個要記住的模式：**知識庫裡任何以「遊戲段 vs 程式庫段」為前提的量測，都會隨著命名進度而失效。** 那條線是我們畫的，不是檔案給的。

### 與票 22-04 那條死路的關係

上一批追引數推送形式時，「原版逐檔用不同旗標建」這個假說被 `open_issues.md:15` 明文判死：因為那 150 個直接 `PUSH` 的分佈在**同一支 function 內部**就混用，比例可以懸殊到 1 比 87，任何 per-file 的解釋都撐不住。

CD 的發現**沒有把那個假說救回來**，它是另一條軸上的獨立事實。`__CHK` 的有無是 `-s` 的直接後果，一支 function 的序幕不可能一半有一半沒有；32 支連續的位址全部有、其餘遊戲段全部沒有，這個形狀只有「那是一個獨立的 translation unit，用不同旗標編」能解釋。兩件事要分開記：引數推送形式的成因仍然未解，CD 模組的旗標差異則是已經量到的。

### 留給誰決定

這件事 emit 不能決定，也不該由 emit 決定。目前的狀態是：

- `build_emit.py` 對每個 unit 用同一組旗標，所以重建出來的 `cd.c` / `cdaudio.c` / `cdtoc.c` **全部失去 stack probe**。行為上的損失只有這一項：CD 程式碼裡發生堆疊溢位時，原版會印 `Stack Overflow!` 然後停，重建版會直接寫過去。按 `pitfalls.md:111`，這是可觀察的差異，而且方向跟 `pitfalls.md` 描述的相反。
- 其餘差異（四推框架、`XOR/MOV AX` 對 `MOVZX`、`MOV EAX,offset`+`PUSH` 對 `PUSH imm32`）都是 register allocation 與 instruction selection，ADR-0001 排除在外。

要收，只有兩條路：教 `build_emit.py` 吃 per-unit 旗標，或者在 `build_flags.md` 明文接受這個模組放棄 probe。兩條都是 `build_pipeline.md` / `build_flags.md` 的決定。**這件事在這批被記了六次**（`0003bade` 兩則、`0003bc3f`、`0003c51c`、`0003c636`、`0003c6e8`），每次都是不同的 agent 從自己的 WDISASM 輸出獨立走到，代表它已經不是「某一支的疑慮」而是模組層級的既成事實。

## 16 次修正輪：只有一次是真的程式錯了

14 支跑了修正輪（`00038020`、`00039670`、`000398f0`、`00039ab0`、`0003aa70`、`0003ad10`、`0003b150`、`0003b6b0` ×2、`0003b990` ×2、`0003ba50`、`0003c0c8`、`0002eab0`、`00029400`、`000227e0`），總共 16 輪。與上一批一致：**壓倒性多數不是 emit 出來的 C 錯了**，是註解寫錯或測試站不住腳。

### 唯一一次真的行為缺陷：`0002eab0`

`fdps_cycle_scene_palette` 的 round 1 把 `0002eccc` 的 `0f 86`（`JBE`）讀成了相等測試。實際上那條 `CMP [EBP-0x298],0x1c` / `JBE` 只在 `0002ecbf` 的 `CMP 0x1a` / `JBE` 已經確立 `v > 0x1a` 之後才到得了，所以它把 **0x1b 和 0x1c 兩個值**都送進 `0002f112` 那條臂。

會讀錯是因為隔壁 `0002ecf0` 的 `CMP 0x16` / `JBE` **真的**是相等測試——那裡既有的下界是 0x16，這裡是 0x1b，同樣的指令形狀在不同的既有下界之下意義不同。後果是章節索引 27 會被送去 default，**重建版第 28 章的調色盤動畫會整章不動**。修法是加 `case 27:` 讓兩個索引共用一條臂，跟已經存在的 `case 0: case 26:` 同形。

這是這批唯一一次修正輪動到 emit 出來的 C。教訓很具體：**`JBE`/`JZ` 這種二選一，不能只看指令本身，要看到達它時已經確立的界。**

### 其餘：註解與測試

值得單獨記的是三次「測試根本測不出東西」：

- **`0003c0c8`**：測試用來塗污堆疊的 `scribble_the_stack_below` 填的是均勻的 `0x5a`。`0x5a & 0xd0` 與 `0x5a & 0xf0` 都是 `0x50`，所以兩個 mask 的差異在斷言裡完全看不見；同樣地 `block+2` 與 `block+3` 變成同一個 dword、`block[5]` 與 `block[6]` 變成同一個 byte。改成 `0xa3, 0xb3, 0xe3, 0xf3` 這個四值循環（bit 5 全設、低位 `0x03` 全設、四個值在 `0xd0` mask 之內與之外都互異）之後，mask 與兩個位移才真的被分開。**均勻填充的塗污測試是假測試**，這條值得推廣到所有讀未初始化堆疊的測試上。
- **`0003aa70`**：章節 13 的「沒有別的 slot 會結束戰鬥」掃描跑在共用的八格 `stage_units` 上，所以只掃得到 slot 1..6——而複製而來的 handler 會攜帶的正是那之外的索引（章節 9 是 slot 6/7、章節 11 是 slot 8）。這條測試設計上就抓不到它要抓的東西。改成給章節 13 自己的十筆 stage。
- **`0003c1a1`**（這一輪不算 rounds，見下節）：斷言預期「track 查詢的起始磁區會與 lead-out 磁區不同」，實際上不會——`fdps_cdrom_read_disk_info` 會 memset 自己的七 byte 控制區塊，`fdps_cdrom_read_track_info` **不清** bytes 2..6，而第二個請求就疊在第一個剛用完的同一個 ESP 上，所以兩端都回報 00:00:00。錯的是對測試環境的預期，不是程式碼。

其餘的修正輪都是「沒去查就寫下去」：

- `00038020`：宣稱 `data_fdps_battle_turn_counter` 的正負號只在 `0003b163` 的 `JG` 可觀察。重掃 55 個 xref 之後找到**九個**帶號分支（reviewer 找到七個，emitter 自己掃出更多）。
- `000398f0`：把 Ghidra plate 裡一個**根本不存在的 sibling 名稱** `fdps_vfs_header_entry_count` 忠實抄進三個檔。`search_functions("fdps_vfs_")` 回來九個名字，那個拼法不在裡面；真正要指的是 `fdps_vfs_image_entry_count @ 00039960`。**plate 是三個來源之一，plate 本身會錯**，抄名字之前要查一次資料庫。
- `0003b150`：三個 `ADD` 立即值是 12/29/46（`0003b16c`/`0003b188`/`0003b1ad`），檔頭註解寫成 turn+13/+30/+47，而且三行之後自己又寫對了一次。
- `0003ba50`：宣稱章節 30 是唯一另一支不呼叫共用結束檢查的 handler；實際上 22、25、26、27 都不呼叫，章節 30 是第五支。第三輪再掃 `0x00069da0` 的 59 個參照，把「存入 2」的完整清單釘成十五條指令。
- `00029400`：out 槽在十三個呼叫點裡是全域的次數寫成 9/4，真的是 10/3——`000238a7` 那個 push 是 `MOV EAX,0x60140`（絕對位址）而不是 frame slot 的 `LEA`。
- `00039670`：宣稱兩個迴圈的範圍重疊且執行順序 load-bearing；實際上 `0x0c..0x59` 與 `0x5a..0x5b` 不相交，每筆各寫一次。
- `000227e0` / `0003ad10` / `00039ab0`：都是「該查沒查」的補掃，前者是六個 layer descriptor 的正負號，後者兩者是路徑推導與呼叫端掃描。

### `0003b6b0` 與 `0003b990`：兩支各跑了三輪內部輪次，都是資料判讀

這兩支值得完整記，因為錯的方式一模一樣：**用單一欄位或單一數字去認資料，沒有交叉驗證。**

`0003b6b0`（章節 25）第二輪：讀 MAP24.DAT 的 wave 欄位時讀成了 byte +0，那個欄位在兩個檔裡都是均勻的 0，於是「59 筆全是 wave 0」。真正的 wave 欄位是 **byte +0x15**（`fdps_deploy_wave` / `fdps_deploy_unit` 的 plate 已經記過），正確答案是 41 筆 wave 0 + 18 筆 wave 1；拿 MAP19.DAT 用同一個讀法得到 54+1，正好是章節 20 那節已經在用的數字，兩邊一致才算對上。

第三輪：把 wave 1 那組敵人認成「武藝武士」。攻略站章節 25 的清單是「弓兵×11 / 武藝武士×18 / 地獄劍士×8 / 天空劍士×18」——**兩組都是 18，光靠數量分不出來**。最後是拿章節 24（MAP23.DAT）破的局，那裡兩組的數量不同。記錄下來的欄位定義：character id 是 record byte **+1**，level 是 byte **+4**，wave 是 byte **+0x15**，record 長 0x1a。

`0003b990`（章節 28）第二輪：把攻略站的「第二、四、六、七、十、十二、十四、十六、十八回合結束時」讀成「2 到 18 的每個偶數回合」。那是九個列舉值，含奇數的 7、不含 8，兩項不符。**攻略站列舉的東西不要自己歸納成規則**——這一條跟 memory 裡「不要對人寫的內容做 parser」是同一件事的不同面向。

## build gate 抓到了東西，但不在 `rounds` 裡

上一批的結論是「gate 一次都沒抓到東西」。這批不一樣，而且抓到的方式很值得記——**它們全部發生在 emitter 自己的迴圈內，所以工作流看到的 `rounds` 是 0**。`rounds 0` 不等於一次就對。

**`0003cb01` 與 `0003cb93`：build PASS，但 emit 出來的定義根本沒被連進去。**

`fdps_dpmi_lock_region` 的第一次 build 回報 PASS，附帶 `Warning(1027): redefinition of fdps_dpmi_lock_region ignored`。原因是 `src/aildpmi.c` 還留著 AIL 連結驗證票（devlog 2026-08-28）當時手寫的 stand-in，linker 先載到它，**新 emit 的定義是死的**。`fdps_dpmi_lock_size` 撞到一模一樣的事。這批六支 DPMI function 有五支的 staged 檔案清單裡出現 `src/aildpmi.c` / `src/aildpmi.h`，都是在把那些 stand-in 一支一支退場。

這是整批最尖銳的一件事：**gate 的 PASS 不保證你剛寫的程式碼真的在執行檔裡。** `Warning(1027)` 是唯一的訊號，而它只是個 warning。任何 pool 有手寫 stand-in 的地方（`aildpmi.c` 是已知的一個）都要當心；build gate 目前不把 1027 當成失敗。

**`0003c1a1`：兩條斷言真的紅了**，見上一節。這是這批唯一一次測試在 gate 上失敗，而不是靠 reviewer 讀出來的。

## 50 條疑慮，36 條擠在 CD 區塊

`concerns_logged` 50，分佈在 22 支上，但 **36 條落在 `0003bade`..`0003c7aa` 這個 CD 區塊**。原因單一而且結構性：測試環境沒有 CD-ROM，harness 把 `data_fdps_cdrom_drive_letter_index` 設成 `0xff`，MSCDEX 一律拒絕每個請求。於是整個模組的疑慮反覆是同三種形狀：

1. **未初始化的請求標頭送進 driver。** `0003be36`、`0003c51c`、`0003c7aa`、`0003c0c8` 都是同一件事：staging memcpy 宣告的長度（0x18 / 0x1e）小於 `fdps_cd_request_header` 的 26 byte，而 body 從來不寫 `+0x14`（start sector）與 `+0x16`（volume-ID 指標），所以那幾個 byte 是純粹的 frame 殘留。**原版與重建版在種類上相同、在 byte 值上不同**——各送各的堆疊。這件事不能「修」，只能記下來。同一支檔案裡的兩個 IOCTL Input 建構器（`0003bdb4`、`0003bdbc`）反而有清這兩個欄位，所以這是 IOCTL Output 那個形狀特有的，不是模組屬性。
2. **回讀那一半測不到。** `0003bd99`、`0003c5a6`、`0003bb7d` 都是：memcpy 把 driver 的答案抄回來這件事，在沒有光碟機的機器上無法觀察。`0003bb7d` 更狠——DPMI 0300h 會把整個 50 byte 的 real-mode call block 用回傳狀態蓋掉，所以連「送出去的是什麼」都不能在呼叫後觀察，只能對 object 檔驗四個 store 的位移。
3. **打不到的分支。** `0003c636` 的 `return 2` 只在 `data_fdps_cd_last_request_status` 恰好等於 `0x810C` 時成立。reviewer 加上了一句讓它變得重要的話：**那個比較是單一相等測試，不是測 bit 15**，所以 driver 回報的任何其他錯誤字都會變成 1 送回 `main`，而 `main`（`000292e0` 的 `CMP [EBP-8],1` / `JZ`）把 1 當成成功、直接開始遊戲。

`0003c7aa`（`fdps_cd_set_door_lock`）是這批唯一一支被證明**在 shipped binary 裡完全打不到**的 function：`get_xrefs_to` 沒有、`get_function_callers` 沒有，reviewer 再用 `search_instructions` 掃全 image 的 89,420 條指令找 `3c7aa` 這個運算元，零命中。這關掉了「也許有間接呼叫表」這個可能。它的門鎖狀態該是什麼，binary 裡沒有東西能回答。

### CD 以外的四條，每一條都會回頭咬人

- **`000357a0`（`fdps_check_secret_code_key`）——最漂亮的一個。** 密碼表答的是章節 id 1..24，而遊戲有 30 章。`EBP-0xcc + id*8` 這個位址算術把其餘六個 id 直接打到 frame 上：id 25 落在 `EBP-4`（回傳值槽與存下的 EBP）、id 26 落在 `EBP+4`（EDI/ESI）、id 27 落在 `EBP+0xc`（EBX 與 return address）、id 28 落在 `EBP+0x14`、id 29 落在 `EBP+0x1c`。emit 忠實重現而不加保護，object 的 frame 與原版逐項相同，所以每次讀都落在同一個槽——**但槽裡的內容不可能相同**。唯一由 ABI 而非運氣決定的是 id 28：`EBP+0x14` 就是這支函式正在測的 scancode dword，第一個 byte 永遠等於被比較的值、第二個 byte 對 make code 永遠是 0，所以**任何一次按鍵都會讓密碼判定為「完成」**，這一項原版與重建版等價。id 0 與 25..27、29 則不等價。
- **`00031780`（`fdps_transition_zoom`）**：`last_tick` 在 `000318bd` 被讀取時還沒有任何東西寫過它，這是刻意保留的。原版把這個 local 放在 `[EBP-0x4]`，重建版放在 `[EBP-0x14]`；兩個 frame 都是 0x3c、ramp 都在 `-0x3c`、pass counter 都在 `-0x18`，其餘六個 local 的槽位分配不同。**兩邊讀的是不同的殘留 byte。** 最壞情況是一次 transition 的第一格多等一個 timer tick（約 55 ms）。六個呼叫端都還沒 emit，所以現在收不了。
- **`0003bade`：型別分歧。** `src/cd.h` 用 Watcom 的 `union REGS` / `struct SREGS` 宣告三個共用暫存器區塊（CRT 呼叫需要），而 `routing.json` 記的是 `byte[28]` / `byte[28]` / `byte[12]`。大小完全相符，contract B 需要的就是這個，現在也連得起來跑得過；但**票 23 emit 定義的時候如果照 routing 出 byte array，同一塊 28 或 12 byte 就會在兩個 translation unit 裡有兩個不同型別，Watcom 不會報任何診斷**。
- **`000567a0` / `00056799`（鍵盤）**：兩件事。第一，`0x70000`-`0x70053` 是手寫組語模組的資料段，scancode ring 是**完全緊貼、沒有 padding 也沒有對齊**的：queue[10] 在 `0x7000f`、read index 在 `0x70019`（緊接陣列最後一個元素的下一個 byte）、write index 在 `0x7001d`、prev scancode 在 `0x70021`，兩個 index 都不是 4 對齊。現在 emit 成四個獨立的 C 全域，linker 想怎麼排就怎麼排。沒有讀者跨越邊界（十四條指令全部直接指名自己的符號，唯一的折疊基底 `[EBX + 0x7000f]` 被 `000567db` 的 wrap 限制在 9 以內），所以今天沒事——但這塊儲存歸誰、要不要手排，是票 23 加上 `fdps_keyboard_isr`（`00056837`，真正的 IRETD handler，切 DS 且驅動 port 0x60/0x61/0x20）的 emit 決定的。第二，**`volatile` 只活在宣告側**：`keybd.h` 宣告 `extern volatile int`，而 `workspace/code_emit/stage/STB/STUBS.C:102` 產生的定義是純 `int`，因為 stub 產生器從 `routing.json` 的 `/int` 取型別、沒有欄位帶修飾詞。`gamedata.h:226` 的 `data_fdps_timer_tick_counter` 同樣如此。今天無害，票 23 一旦把 stub 換成真定義就變成活問題。

### 一條被 reviewer 直接關掉的

`00039ab0`（`fdps_vfs_open`）的疑慮是：entry count 用整個 dword 存進 handle（`00039b59` 的 `MOV [EDX],EAX`），而所有讀者都只取一個 byte。emitter 只掃到「所有直接呼叫端都不解參照 handle」就停住。reviewer 把剩下的讀完了——`fdps_load_data_tables`（83 條指令，對 `[EBP+0x14]` 只做 MOV/PUSH 送進九個呼叫）、`fdps_vfs_load_file_or_exit`、`fdps_vfs_load_file`（只碰 `+4` 與 `+0x11+i*0x1a`）、`fdps_vfs_load_entry`，以及七個呼叫端各自的 frame slot 使用（`fdps_load_global_resources` 24 次、`fdps_battle_show_win_fail_window` 5 次…全是 32-bit 指標載入與對 0 的 CMP），**整個消費者圖收斂了**，image 裡沒有任何地方讀 handle base 超過一個 byte。`needs` 寫成 `Nothing`。這是雙盲設計最好的一次表現：reviewer 不是附議，是把 emitter 少走的一步走完然後結案。

`concern_mismatches` 只有一筆：`000227e0` 的 verdict 文字宣稱 2 條疑慮但 `open_issues` 是空的。查過了，不是漏記——那兩條在修正輪裡被解掉了（「both blocking issues accepted；both were lookups I had not done…removal of both open_issues」），文字沒跟著改而已。

## 死路與雜訊

沒有一項造成失敗，但每一項都吃掉時間；有兩項是**上一批就寫過、這一批又被獨立重新發現**的。

**`emit_state.json` 的 in_flight entry 被寫到錯的層級——這次是真的危險。** `00037af0` 與 `0003c5a6` 兩支的 bookkeeper 各自發現 emitter 把 entry 寫在 JSON 的**頂層**，與 `_doc` 和 `functions` 並列，而不是 `functions` 物件裡面。`next_batch.py` 是用 `state.get("functions", {})` 讀進度的，**頂層的 entry 它看不到**——照原位置往下帶會產生一筆 status committed 但永遠讀不到的紀錄，那個位址會在之後某一輪被當成從沒 emit 過再發一次。兩位 bookkeeper 都自己判斷把它搬進 `functions` 並移除頂層 key，所以沒有出事。這**不是摩擦，是 emitter 寫入端的 bug**，下一批開跑前要修。上一批（t22-04）已經有兩支報過「entry 不在頂層」這件事，當時被當成慣例落差，現在知道方向是相反的：是 emitter 有時寫錯層。

順帶：`0003c85b` 的 in_flight entry 只帶 `status` 與 `in_flight_since`，沒有 `name` / `target` / `body_size`，是全檔唯一一筆缺這三欄的。bookkeeper 依「不要碰其他欄位」照做沒補。上一批的 `00028ee0` 一模一樣。

**PowerShell 的行數還是錯的，這批被獨立重新發現十二次。** `Get-Content | Measure-Object -Line` 少算空行：`src/roster.c` 459 對 531、`src/cd.c` 213 對 244 又 269 對 310 又 463 對 538、`src/cdtoc.c` 441 對 503 與 472 對 538、`src/cdaudio.c` 493 對 571、`src/chpost2.c` 96 對 108、310 對 353、645 對 735、`src/vfs.c` 69 對 78、145 對 163、589 對 658、`src/dpmi.c` 78 對 87。t22-04 已經寫過一次，這批十二支各自又停下來測一次。要 `wc -l` 的語意就用 python 數 `\n`。**這條該從 devlog 升格到某個 agent 一定會讀到的地方**——它已經被重新發現十六次了。

**用 `git log -1` 確認 commit 成功，又出事了一次。** `00036b60` 的 bookkeeper 送了個壞掉的旗標（`option 'no-verify' takes no value`），git 拒絕，接著跑的 `git log --format=%h -1` 回了 `c6eec73`——那是**前一支**（`00036af0`）的 commit。t22-04 的 `00030230` 是完全相同的失敗形狀。確認落地一律用 `git log --grep "@ <addr>"` 打自己的位址。真正的落地 commit 是 `be0c92d`。

**`set_plate_comment` 會把 `<<` HTML-escape 掉。** `0003be36` 第一次寫入之後，plate 的 Rebuild note 裡出現字面上的 `seg&lt;&lt;16`，原文是 `seg<<16`。bookkeeper 讀回發現、重設整個 comment 才救回來。**寫完 plate 要讀回比對**，尤其是含有 `<`、`>`、`&` 的文字。這是新的一條。

**Git Bash 下的 `>NUL` 會在 repo root 建出一個叫 `NUL` 的檔。** `0003aa10` 的 commit 指令做了這件事，發現後刪掉，沒有被 staged。要丟棄輸出就用 `/dev/null`。

**兩次 commit message 打錯中文字，兩次都 amend。** `0003b760` 打成「勝貥」（應為勝敗）、`0003c4ff` 打成簡體「暂」（應為暫）。兩次都在 hash 被記錄到任何地方之前就 amend 掉，`emit_state.json` 刻意不存 hash 所以沒有東西指向被丟棄的物件。值得注意的是這**不是編碼問題**——訊息一律寫成 UTF-8 檔案再用 `git commit -F` 送，那個機制運作正常；錯的是模型自己打的字。

**`set_plate_comment` 的「missing Algorithm / Parameters / Returns section」三條 advisory，這批又有八支各自停下來評估一次。** 跟 t22-04 的結論相同：那是 MCP server 的通用樣板檢查，本專案的 plate 格式沒有那三節，寫入是成功的，不要為了消警告補節。**這條需要的不是再記一次，是把它寫進 agent 會讀到的 Ghidra 操作規範裡。**

**fix 文字裡的出現次數又不可靠。** `0003a9a0` 的 fix 說 `FUN_0003a2e0` 出現三次，實際四次（Algorithm 段自己就寫了兩次）；`0003c3fa` 的 fix 說 `DAT_00069de8` 是「前者其中一處」，實際 plate 裡有兩處；`00056799` 反過來——兩份 verdict 都說 `FUN_00056818` 出現兩次，實際 plate 裡只有一處。三次 bookkeeper 都依 t22-04 定下的規則處理：**跟著 fix 的理由走，不跟著數字走**，並在回報裡標明是 fix 的文字數錯了。這個判準看來是對的，可以固定下來。

**`routing.json` 從來沒有被翻成 committed。** `00030c50` 的 reviewer 指出 routing.json 仍把該位址與兩個新全域記為 `pending`，並稱之為「bookkeeper 該做的翻轉」。bookkeeper 查了前例：已落地的 sibling `00030bf0` 在 `emit_state.json` 是 committed、在 `routing.json` 也還是 pending，**所以之前每一次落地都沒翻過**。這不是這一支漏了，是整條流程從來沒有這一步。要嘛 routing 的 status 欄位是死欄位該拿掉，要嘛落地階段要補這個動作——workflow 層級的決定。

**`00018930` 的 Ghidra 修正做不到，只好用 `run_script_inline`。** fix 標的是 `00061636`，但那不是 function，是一個定義好的字串（`"_^EnemyDat.dat"`，0xf byte），它的起點把 `5f 5e` 兩個 padding byte 吞了進去；決定是要讓它從 `00061638` 開始。`rename_function_by_address` 不對，`rename_data` 不能移動起點，`apply_data_type` 在 `00061638` 帶 `clear_existing=true` 被拒（`Conflicting data exists at address 00061636 to 00061644`）。最後用 `run_script_inline` 做 `clearCodeUnits(00061636..00061644)` + `createData(00061638, StringDataType)`。結果與決定完全相符（`00061638 | 0xd | /string | s_EnemyDat.dat_00061638`，與同池七個 sibling 同形），但機制在指定的三個工具之外。**「重新定義一個資料項目的起點」在現有工具集裡沒有直接做法**，這是下次會再撞到的。

**`0003c892` 的 "rename" fix 指的是變數不是 function。** fix 要求把 `uVar1`（`0003c8cf` 那個 `data_fdps_cd_play_range_end_sector` 的 EBX latch）改名為 `end_sector`。`rename_function_by_address` 會把 function 本身改名，所以 bookkeeper 改用 `rename_variable` 加 `function_address`。fix 的 `kind` 欄位不足以決定用哪個工具，要讀 `what`。

**`notes` 還是資訊的死路，但這批有一次僥倖。** `build_flags.md:127` 那個 `__CHK` 計數過時的發現，被 `0003bc78` 與 `0003c85b` 兩位 reviewer 各自填在 `notes` 裡——依規則 bookkeeper 不能把 note 寫進 `emit_issues.json`，那兩次都會消失。它之所以還在，是因為第三次（`0003c6e8`）的 reviewer 把它填成了 `open_issues`。**同一個發現在三個地方被找到，兩次會被制度丟掉。** t22-04 已經提過這件事，這批給了它一個具體的、後果很大的實例。其他被擋在外面的至少還有：`00033570` 的位址標註偏移（`00033618-0003361d` 是 entry 的 id byte，候選者的 type 在 `0003358b-00033590`）、`00039670` 提到 sibling 檔案裡 `fdps_deploy_spawn_unit` 拼錯與 `chevt6.h` 的斷行、`0003c85b` 的三則（其中一則就是上面那個）、`0003bc78` 的兩個註解措辭。

## 收尾

100 支全部落地，每支一個 commit，都能用 `git log --oneline --grep "@ <addr>"` 找到。Ghidra 這批動了 61 支的 plate、prototype 或資料定義，總共 80 筆修正；每次改動都跑了 baseline audit，**orphan code ranges 0、error bookmarks 0、`.object1` 的 undefined bytes 0，全批沒有例外**，程式已存檔、快照已重新匯出。沒有 function 被拆檔（`code_layout.md` 的行數預算這批一次都沒有踩到），沒有 function 沒落地。

一件流程上的例外值得記：`0003cb01` 的 emitter 發現 `rebuild_info/ail_link.md` 的擁有檔欄位在 `aildpmi.c` 的 stand-in 移除之後過時了。那是 pipeline 路徑之外的知識庫檔案，所以它**單獨 commit 了一次**（實際 hash `66faa3a`，emitter 自己在 verdict 裡引成 `26a4a71`，reviewer 抓到）再繼續。這是對的做法——落地階段的 staged 範圍必須乾淨，路徑外的修正要自己走一個 commit。

`ghidra_applied` 這個數字的口徑仍然不統一：有的 bookkeeper 數「決定數」（`00056799` 記 2 但只呼叫了一次 `set_plate_comment`），有的數「寫入數」（`00036b60` 記 1 但涵蓋三筆 fix）。80 這個總數要當成量級看，不是精確計數。

## 批次結束後的收尾（不是 workflow 做的）

**`Warning(1027)` 那件事當場修掉了，因為它會影響後面每一批。** 上面記的是「gate 的 PASS 不保證你剛寫的程式碼真的在執行檔裡」，追下去發現根因更難看：`build_emit.py` 與 `gate.py` 抓警告的條件都是字串 `"Warning!"`，而 **wlink 的警告是 `Warning(1027):` 這種括號寫法**，兩支腳本一條連結器警告都看不見。所以那次不是「1027 只是警告所以放行」，是**它根本沒有被讀到**。

修法兩層：偵測放寬成 `\bWarning[!(]`，同時把 `redefinition of ... ignored` 從警告升級成**錯誤**，而且刻意不走 baseline——沒有任何一種情況該讓 baseline 接受「你的定義被丟掉了」。

改完第一次跑 gate 直接紅了，138 條新警告，全部是 `Warning(1028): <symbol> is an undefined reference`——兩段式連結第一次連結必然吐出的票 23 資料全域。錯誤那條路徑本來就有 `expected_undef` 過濾，警告這條沒有，因為以前根本沒有警告會走到這裡。補上同樣的過濾之後 gate 回到 PASS。**這是放寬偵測的必然副作用：一個從來沒被讀過的通道一旦打開，第一件事是先看到所有本來就該在那裡的東西。**

**CD 模組的旗標差異寫進 `build_flags.md` 了**，連同更正 `-s` 那一列——它原本寫「遊戲段沒有任何一個呼叫 `__CHK`」，現在那句話有 32 個反例。要補 probe 還是明文放棄，是個決定不是證據問題，進了 `open_issues.md`。

**`open_issues.md` 裡引數推送形式那一條加了一段交叉引用**，講明 CD 的發現不救那個假說：CD 的邊界是整個 translation unit，而推送形式的混用在同一支 function 內部，兩者是不同的軸。這件事上面已經推導過，寫進 `open_issues.md` 是因為下一個讀那條的人不會先讀這篇。

**回報數字對不上的那一支查完了，沒有東西遺失。** `000227e0` 的報告說宣稱 2 條疑慮、實際寫入 0 條。查下來是好消息：emitter 第一輪記了 2 條，**reviewer 擋下來，理由正是「這兩條你當下就查得到」**——收斂門檻第一次由 reviewer 主動執行；emitter 第二輪自己重推、兩條都解掉並從判定檔移除。對不上的只是 emitter 第二輪的摘要還報著舊計數。順手把兩個摘要欄位的說明寫死：報的是**你離開時檔案裡的數目**，修正輪解掉了就要往下調，而且 reviewer 那個不是 `blocking_count`。

**那個失敗的 review agent 沒有造成任何後果。** `review:0003c3fa` 是連線中斷，`runAgent` 重試一次就過了，`fdps_cd_seek` 正常落地。這正是「一次沒回傳就重試、第二次才記未完成」那條規則要處理的情況。
