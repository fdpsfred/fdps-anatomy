# 票 25.6：全域文字與額外場景文字

## 出發點

25.1 已經把 66 個文字區塊全部解出來，`FDETXT00` 有 555 條。票上要的是「全頁轉錄 + 語意分區 + 每區的讀取端」與「`FDETXT31`–`65` 的轉錄 + 哪個場景用它」。先去翻前作 `fd2-anatomy/assets/text/global_text.md`：它把名稱表寫成「欄位值 + 常數」的表，下面接每一頁的 code block。形式可以借，但前作的分區是照 FD2 的 661 頁、FD2 的程式定錨的，一條也不能直接套。

票面列的分區裡有「章名、勝敗條件」，那是從前作範本抄來的。實際翻 `src/`：`btlend.c` 的勝敗條件視窗讀的是 `data_fdps_current_chapter_text_ptr` 的第 2、3 條，存檔格的章名讀的是另外載入的章節區塊第 1 條。FDPS 的全域文字裡根本沒有章名與勝敗條件，它們在各章自己的區塊開頭。頁面改成說明這件事並列出讀章節區塊前 9 條的地方，內容留給 25.8。

## 讀取端怎麼找

第一個念頭是手動讀每個呼叫點，把條目與 function 一條條抄進頁面。算了一下：`fdps_draw_text(data_fdps_all_game_text_ptr, …)` 有 93 個呼叫點，加上寫入兩個代入槽的 11 處。手抄一次不難，但 `src/` 還在被別的票改（本票進行中 25.15 正在動 `icon.c`、`chend2b.c`），手抄的表下一次改名就過期，而且沒有東西會發現。

所以改成掃描：去掉註解（`chpost1.c` 的註解裡就有一行看起來像呼叫的 `fdps_draw_text(data_fdps_current_chapter_text_ptr, 15, 0xa0000, …`），找呼叫、切出第二個引數、用同檔的 `#define` 解開。先寫了一支 scratch 腳本把全部呼叫點與巨集值印出來看形狀，發現只有三種：純巨集、`執行期值 + 巨集`、以及 `btlact.c` 的 `prompt_text_id` 這種只被賦予兩個巨集值的區域變數。把這三種寫成解析規則，其他一律報錯。

第一次跑 `build` 就撞到第四種：`vilbar.c` 抽獎的 `prize_class_by_reel_frame[reel_cursor[SAF_CURSOR_FRAME_INDEX]] + BONUS_PRIZE_FIRST_TEXT_ID`。它被當成名稱表讀取，而 `0x225` 不是任何名稱表的起點，閘門擋下來，同時 `0x225`–`0x228` 四條抽獎訊息變成「沒有讀取端」。第一個修法是加一張手寫的 `BOUNDED_INDEX = {0x225: 4}`——寫完覺得不對，「表裡的值是 0..3」又是一條手打、不會被驗的事實。改成讓掃描器自己讀同一個 function 裡那張區域表的大括號初值 `{0, 3, 1, 2, 3, 2, 1, 3, 2, 3}`，可到的條目就是基底加每個值，手寫表刪掉。

中間還有一個小坑：折疊巢狀下標時先把內層 `[SAF_CURSOR_FRAME_INDEX]` 換成 `[]`，外層 `[reel_cursor[]]` 因為裡面還有括號而對不上 `\[[^\[\]]+\]`，整個運算式就沒被認出來。改成先換成佔位字元、全部折完再換回 `[]`。

## 掃描之後才看出來的事

- 單位名的讀取端大多用 `char_id + 1`，只有 `fdps_church_promote_loop` 用 `portrait_id + 1`。去查這兩個欄位誰寫：`fdps_deploy_unit` 與 `fdps_roster_add_character` 都用同一個值同時寫兩者，所以票上說的「肖像編號 + 1」與程式裡多數的「角色編號 + 1」是同一條。
- 名稱表首尾相接、沒有上界檢查。物品編號 `0xFF` 照公式是第 `0x1c8` 條，剛好是法術 `0x0A`「裂地術」——攻略站的裝備列表寫「FF 裂地術／BUG物品，價格和作用隨時變化」（`guide_scrape search BUG` 找到的那一行），`assets/items.md` 原本只說 `FF` 超出 `ITEM.DAT`、沒解釋名字從哪來，現在知道是名稱表越界讀到的。這條進了 pitfalls：把名稱拆成各自的陣列或加上界，越界編號的名字就變了。
- `assets/enemies.md` 認出的三筆（列 0–2 平衡之神、列 45 幽魂、列 46 死靈）照「肖像編號 + 1」落在 `0x03d`–`0x03f`、`0x06a`、`0x06b`，名稱全對，公式得到獨立的旁證。
- 部署記錄用到的肖像編號 `0x97`–`0x9C` 照公式讀到種族名。只在過場地圖上，不會有人打開那些單位的狀態面板。

## 額外場景：哪些條目會顯示

一開始在頁面寫了「區塊的前 9 條（章名、勝敗條件、招牌的位置）在額外場景裡永遠不會顯示，有內容的是照章節區塊複製過來的殘留」。產生頁面後回頭看總表，`FDETXT36` 的 `0x04`–`0x06` 明明是 `ICON00` 在地圖 35 上顯示的台詞（「若干年後…」與父子對話）。前 9 條在額外場景只是普通條目，這句是錯的，刪掉改寫；「照章節區塊複製過來」那半句也是沒有根據的猜測，一起刪。

「會不會顯示只看腳本引用」這個結論要先確認沒有別的路徑會畫目前區塊的條目。查了所有寫入章節索引的地方：章節結束處理函式寫的下一章最大 `0x1d`，標題的新遊戲與示範戰鬥、讀檔都在 0–29；城鎮階段 `fdps_load_field_chapter_resources` 會照新章節重載文字，沒有城鎮的章節由 init 處理函式的 `fdps_chapter_state_reset` 重載；存讀檔畫面的章名是另外依存檔格記錄的章節載入。結束在過場地圖上的勝利腳本（例如 `WIN00` 停在地圖 43）之後，end 處理函式只寫章節索引，不畫字。確認完才把結論寫進頁面。

結果：地圖 30、31、33、49 沒有腳本切過去，對應的 `FDETXT31`、`32`、`34`、`50` 永遠不會載入；`FDETXT42`、`43`（`WIN00` 經過的地圖 41、42）與 `FDETXT63`（`WIN26` 經過的地圖 62）有載入但一條也沒顯示。這些只列編號，內容交給 25.14 的 `cut_content/`。

## 審查之後改的

兩個審查 agent（標準、規格）各跑一輪，採納的：

- 掃描器自己寫了一個去註解的 regex，而 `tools/_index.md` 早就把 `src/` 掃描指定給 `code_emit/build_emit.py` 的 `strip_c`，後者還會清掉字串字面值（`"/*"` 在字串裡時我的版本會吃掉後面的程式碼）。改成 import。
- 識別字 regex 會從 `0x1f0` 裡抓出 `x1f0`，後面「不是數字」的過濾從來沒作用：單寫十六進位條目會報錯、`BASE + 0x10` 甚至會被靜默當成名稱表讀取。加了 `(?<!\w)`，常數求和也從 `eval` 改成逐項加總，順便照 C 的規則處理前導 0 的八進位。
- 區域變數只看 `=` 賦值，遇到 `+=` 會少算；現在有任何累加或遞增就報錯不猜。章節區塊前 9 條的掃描原本沒傳函式本體，區域變數一律解不開，改成傳入，並在說明裡寫明它只收寫死條目。
- 額外場景頁的前提「章節索引只有 0–29」寫錯了：`SWITCH_MAP` 本身就把章節索引改成地圖編號，`WIN00` 等 11 支勝利腳本結束時它還停在 30 以上。結論不變（結束處理函式之後只寫下一章、不畫字），但論證改成「只有 `SWITCH_MAP` 會寫成 30 以上」。
- 頁面原本在總表與每個區塊列出「永遠不會顯示的條目」編號。總票的決定是 `assets/text/` 不另列這種清單，改成每處一句話連到 `cut_content/`，清單交給 25.14 以 `classify_scene_block` 取得。
- 單位名表多加的「數值表」欄（`FRIAPRDA`／`ENEMYDAT` 第幾列）是資料表的事實，擁有者是 `resource_info/data_tables.md`，拿掉。
- 頁面說明裡的物品數、空字串數、`0x1c8`「裂地術」、`FDETXT36` 的例子原本手寫在說明文字裡，改成由分區與資料算出來。

沒採納的：`cut_content/` 的連結目前指向不存在的資料夾——總票明定先連 `../cut_content/_index.md`，等 25.10 建立。`{speaker char=n}` 沒換成角色名——肖像編號與角色的對照由 25.7 的 `names.md` 擁有，這裡照原樣轉錄。
