接續 [`2026-09-26-chapter-docs-tooling.md`](2026-09-26-chapter-docs-tooling.md)。工具與閘門在前半寫好，這一段是 `tools/chapter_docs/chapters_ticket25_8.js` 從頭跑到尾的記錄。機器產出的原始回報在 [`runs/2026-09-26-chapters-t258-01.json`](runs/2026-09-26-chapters-t258-01.json)，本篇只寫它沒講清楚的事，以及跑完後我回頭查證的兩個拒絕原因。

## 起草與落地：五輪，每輪六章

準備階段重產了 30 份機械事實與 30 張戰場標註圖，接著每輪平行起草 6 章、閘門乾淨的草稿交給 `land.py` 落地，再對落地頁跑一次閘門。五輪的落地結果全是 `new`，落地閘門 0 錯誤。

**`land.py` 這次一章都沒有拒絕。** 回掃之後的重新落地也沒有：第 3、23、24、29、30 章是 `updated`，第 16 章是 `unchanged`。沒有任何一章需要重試起草。

各輪的「連到還沒落地的章」警告合計 10 條：第一輪 3 條（ch04→ch25、ch06→ch26、ch06→ch07），第二輪 2 條（ch12→ch16、ch12→ch13），第三輪 1 條（ch18→ch19），第四輪 4 條（ch20→ch25、ch23→ch27、ch24→ch27、ch24→ch25），第五輪 0 條。前半的審查曾指出這種連結如果當成錯誤會卡死整輪，改成逐輪只警告、最後一道嚴格閘門再檢查；這次這 10 條在最後的嚴格閘門下全部成立，證明那次修改是必要的——若沿用舊規則，第一輪的第 4、6 章就過不了閘門，而回掃只重開低信心的章，這些頁永遠回不來。

## 回掃：六章被送回，五章收掉，第 16 章收不掉

回掃的條件是首輪回報「信心低」或「有開放問題」。被送回的是第 3、16、23、24、29、30 章。回掃後五章回報 0 個開放問題、信心 high，落地時頁面都有改動（`updated`）；第 16 章仍有 1 題，頁面沒改（`unchanged`），符合回掃 prompt「解不了就不改頁面，誠實的開放問題也是正確結果」的要求。

**這裡有一個資訊缺口：第 3、23、24、29、30 章首輪到底問了什麼，已經無法重建。** 回掃 prompt 要求 agent 在成功時直接改寫 meta（把解掉的問題從 `open_questions` 移除），結束時刪掉 `.bak` 備份；workflow 的 `drafted` 陣列也在回掃後被新的摘要覆蓋。run record 只剩回掃後的狀態，`workspace/chapter_docs/drafts/` 裡也沒有留下備份。所以只能確定「首輪有低信心或開放問題、回掃後收掉並改了頁」，收掉的是什麼問題、怎麼收的，沒有記錄。以後寫類似的回掃段，應該在回掃前把首輪的 `open_questions` 抄進 run record。

第 16 章收不掉的那一題，問題不在第 16 章，在工具：

- `chapter_facts.py` 的讀取端掃描把條目 `0x00`（「第十六章」）的讀取端記成 `fdps_chapter_16_event_wandering_smith_forge`（`0x37cd0`）。實際上那支函式的回應編號初值是 0，只有找到劍、改成 `0x0d` 或 `0x0e` 之後才拿去畫，`0x00` 從來不會被畫出來。掃描器把「初值 0 的變數被傳進繪字呼叫」當成一次對 `0x00` 的繪製。
- 前半 devlog 的「產生器先看到的東西」裡記了一條線索「各章區塊的 `0x00` 只有第 16 章的流浪工匠事件會讀」——那條線索就是這個誤判，是錯的。
- 判定規則不允許把「掃描已找到讀取端」的條目列進 `never_shown`，所以章節 agent 沒有合法的方式把它標成不顯示；產生的對話區塊仍然列著錯的讀取端。第 16 章的 agent 在頁面上加了一句更正（`chapters/ch16.md` 對話一節，條目 `0x00` 之前），並把它列進刪減內容候選。
- 章節 agent 不准改工具，回掃同樣改不了掃描器，所以這一題第二次也不可能收掉。

這題不在 run record 的 `unfinished` 清單裡——workflow 的 `unfinished` 只記停機、失敗與拒絕，不記「回掃後仍開著的問題」，只在 `rescanned` 裡以 `open: 1` 出現。它需要改 `chapter_facts.py` 的讀取端判定（初值常數不算繪製）後重產第 16 章的區塊，頁面上那句更正才能拿掉。

## 套用踩雷點：兩筆被拒，原因各不相同

`apply_pitfalls.py` 插入 34 列、補了 4 列連結（`ch02-julian-joins-at-init-not-at-victory`、`ch07-post-action-no-farlena-test`、`ch20-farena-defeat-string-not-enforced`、`ch21-advance-range-past-unit-count`），其餘不變；連結檢查 0 錯誤。兩筆 `linked` 被拒，訊息都是「the row changed since it was read」，沒有人手動修。跑完之後我回頭對了現在的 `pitfalls.md`，兩筆的原因其實不一樣：

- **`ch23-time-limit-is-a-walk`：真的是同一輪裡被改過。** 它要補連結的是「攻略站列出的失敗條件不一定有程式實作」那一列（第 14 章那列）。`ch07-post-action-no-farlena-test` 要補的也是同一列。`apply_pitfalls.py` 依檔名排序套用，`ch07-…` 排在 `ch23-…` 前面，先把 `chapters/ch07.md` 加進那列的正典欄；輪到 `ch23-…` 時它的 `old_line` 已經對不上。兩位判定者各自讀到的都是套用前的原列，這是設計上的洞：判定階段「讀現在的 `pitfalls.md`」而套用集中在最後，兩筆 `linked` 指到同一列時，第二筆必定被拒。現在那一列有 `ch07.md`，沒有 `ch23.md`。
- **`ch28-reinforcement-wave-halving`：那一列這輪根本沒被動過，是判定檔抄錯了。** 判定檔的 `old_line` 在正典欄只有 `program_info/chapter.md`、`cut_content/story.md`，但 `HEAD` 的那一列本來就還連著 `program_info/known_bugs.md`。判定者沒有逐字照抄現在的列，套用時自然對不上。拒絕訊息說「列被改過」在這裡是誤導。現在那一列仍沒有 `chapters/ch28.md`。

兩筆要補的都只是正典欄的一個連結，內容判定本身（已有列涵蓋、只缺連結）不受影響。
