## Pitfalls found

### From struct layouts (42)

**`__stream_link`** — A dynamically allocated stream is ONE allocation, not two: __allocfp calls malloc(0x22) and hands out (char *)node + 8 as the FILE (0004be6c, 0004be81), so the node and its FILE are a single 34-byte block with the node first. __purgefp then calls free() on the node address alone (0004beff) and that one call releases the FILE with it -- it never frees node->stream separately, and must not, or the rebuild double-frees. Writing this the intuitive way (two mallocs, or the FILE first with the node embedded) produces a runtime that runs and corrupts the heap at exit. The corollary is that the struct must stay exactly 8 bytes: the FILE's position is computed as node+8 by pointer arithmetic (puVar1 + 2 on an undefined4 *), so any added field or alignment padding silently moves every dynamic stream's control block.

**`AIL_DRIVER`** — Two things in this record read the opposite of the obvious. First, the teardown hook is called with the OTHER field: 000458eb CALL dword ptr [ESI+0x20] is preceded by 000458e7 MOV EBX,dword ptr [ESI+0x24] / PUSH EBX, so it receives descriptor -- the DIG_DRIVER or MDI state block -- and never the AIL_DRIVER. Writing the natural drvr->destructor(drvr) hands AIL_internal_dig_driver_teardown a pointer to the wrong record and it will free the wrong blocks. Second, the shutdown escape 0x306 is NOT unconditional in uninstall: it is gated on initialized (00045902), because the DIG and MDI setup routines already send their own 0x306 and clear the flag on each of their failure paths (00046de9, 00046e7d, 00046f41, 00049b67, 00049bcb, 00049cc2). Making uninstall always shut the device down double-shuts a driver whose setup failed. A third trap is layout-level: linear_addr (+8) and vdi_hdr (+0xc) are set to the same address at install (0004571b-00045722) and never diverge, so collapsing them into one member looks free -- but the record's size is fixed at 0x28 by three allocation and free sites, and dropping a member shifts every field after it by four bytes.

**`ail_xmidi_timb_chunk`** — Two things about this record break if written the obvious way. (1) The header mixes endianness: length_be at +4 is big-endian IFF (00 00 00 04) while entry_count at +8 is little-endian (01 00). Declaring the length as a C int and assigning 4 produces a different image and a chunk the driver reads as astronomically long -- it must stay byte[4]. The static instance also cannot be const even though it sits in the CONST/_DATA image, because AIL_internal_install_timbre_inner writes bytes +10 and +11 on every call. (2) When the driver rejects a timbre, AIL_internal_init_sequence_inner adjusts the length by 2 at bytes +4 and +5 (0004a36d-0004a391) -- the TOP half of the big-endian length, not the bottom -- so a real chunk whose length is at most 0x200 ends up with 0xFF 0xFE in those bytes rather than a length two smaller. Only entry_count is consulted afterwards, so the game is unaffected; reproducing Miles' behaviour means keeping the odd byte pair, not 'fixing' the arithmetic to touch +6/+7.

**`DIG_DRIVER`** — build_size is channels_per_buffer * 4, not samples_per_buffer * 4. The two are equal for a mono output format, which is what this game gets by default, so the obvious rewrite build_size = samples_per_buffer * 4 tests clean and then under-allocates the build buffer by half the moment a stereo .DIG driver is selected - and the finalize pass writes past the end of it from inside a hardware interrupt. Second trap in the same record: last_served_buffer_half is initialised to -1 and the ISR skips its pass when the hardware's current half equals it, so zero-initialising the whole record instead of writing that -1 makes the first buffer fill get skipped whenever the driver happens to report half 0.

**`fdps_cd_q_channel_block`** — The block must stay a single file-scope object in _BSS. fdps_cd_read_q_channel writes only byte 0 and then hands all eleven bytes down to the driver, so bytes 1..10 go out holding whatever the previous reply left there -- zero on the very first call only because the CRT clears _BSS. Rewriting it as a stack local, or adding the memset a modern author would reach for, changes the bytes the driver receives. The struct must also stay eleven bytes of uchar: widening any field to a short or an int would make the compiler pad the record and break the memcpy(...,0xb) that moves it whole.

**`fdps_cd_request_header`** — Two values in this header look like mistakes and must be copied as they are. (1) fdps_cd_read_q_channel sets transfer_byte_count to 6 (0003c5de) but copies 0x0b bytes of Q-channel block back out of data_fdps_cd_ioctl_buffer (0003c62f/0003be27) and fdps_cd_read_audio_position then reads +6 of it. Writing the obvious 0x0b makes the driver fill bytes the original left stale, so the reconstructed build can report a different audio position from the original at the same point in the disc. (2) fdps_cd_read_head_sector sets header_length to 0x1e (0003bcef) although the record is 0x1a and it fills nothing past +0x19; the memcpy at 0003bd38 therefore sends four uninitialised stack bytes, and the copy-back at 0003bd6a is sized by that same 0x1e. Tidying it to 0x1a changes what the driver is told the header length is. Also structural rather than a typo: everything from +0x0d on is a union keyed by command. The fields declared here are the IOCTL Input/Output tail, which is what twelve of the fifteen wrappers build. Play Audio (0x84) reads +0x0e as a dword start sector and +0x12 as a dword sector count, and Seek (0x83) reads +0x14 as a dword target sector -- both straddle the fields named above, so this type must NOT be applied to the frames of fdps_cd_play_audio_range or fdps_cd_seek.

**`fdps_cel_cache_slot`** — The twelve entries are offsets from the cache base, not pointers, and that is load-bearing: fdps_cache_cel_sprite_group realloc()s the block on every miss (0002320c), which moves it, and the already-filled slots stay valid only because their entries are relative. Storing real pointers -- the obvious C once the record has a type -- leaves every previously cached sprite dangling after the first realloc. The reader side must match: base + slot->sprite_offset[i], with the base reloaded from data_fdps_cel_sprite_cache_ptr, never a cached copy of it.

**`fdps_chapter_entry`** — The four per-chapter dispatch tables are four independent arrays, not one array of records, and the post-action table at 0006028c is immediately followed by the end table at 00060304 (0006028c + 30*4 = 00060304) with no gap. Anyone who sees two adjacent 30-entry pointer arrays and declares one array of a two-pointer chapter record produces code that indexes at stride 8 and calls the wrong handler for every chapter but the first. The code settles it: each call site loads chapter_id, scales it by exactly 4, and adds its own base.

**`fdps_char_spawn_record`** — Carrying FD2's char_spawn_record over field for field builds a table that loads and plays wrong in two silent ways. FD2 sources the byte that reaches unit record +0x3d from spawn offset +0x02 and calls it ai_target_id; FDPS sources it from +0x14 and it is the cell event code, so a reader written to FD2's layout takes 0 (the value +0x02 always holds in FDPS) and the four ai_class 5 units stop finding their scripted cell. And FD2 documents +0x19 as always-zero padding; in FDPS it is the fifth byte of the 40-bit learned-spell mask, so dropping it quietly removes every spell numbered 0x20-0x27 from the units that have one -- 珊 loses 審判之雷, and the level-20 bosses of chapters 20-30 lose theirs. The record's spell mask is split across +0x0d..+0x10 and +0x19 with nine unrelated bytes between the two pieces, which is the shape that invites treating it as four bytes plus padding.

**`fdps_character_base_record`** — The record is 0x18 bytes with 16-bit fields at the odd offsets +0x03 and +0x05 (and the +0x12/+0x14/+0x16 trio starting on an even offset only by accident of what precedes it). Declaring the obvious C struct lets Watcom align those shorts, the stride stops being 0x18, and fdps_get_character_base_record's char_id * 0x18 then lands inside the wrong record for every character past the first -- a build that runs and hands out wrong stats. The struct must be byte-packed (#pragma pack(1)) or the fields read through explicit byte offsets. Also load-bearing: the four bytes at +0x08 are a spell bitmap, not four spell ids, and the six item bytes are two unconditionally-equipped slots followed by four 0xff-tested carried slots, not one flat six-slot list.

**`fdps_character_growth`** — Each *_max byte is one greater than the largest gain the player can actually get, because the roll is min + rand() % (max - min); normalising the byte down by one on parse costs a point on every church promotion bonus, which adds the raw byte. Already recorded in rebuild_info/pitfalls.md.

**`fdps_class_equip_record`** — The empty slot value is 0xFF, not 0. The anchor comment on 00063fe4 says unused slots hold 0; the file says otherwise -- no byte of PROEQU.DAT is zero, and 0xFF is the fill in every record that has one. This matters because ITEM.DAT's 25 blank records (ids 0xE2-0xFA) have a type byte of 0, so a rebuild that fills the table or a hand-written row with 0 makes every class able to equip every blank item, while 0xFF matches nothing. Second, the loop bound in fdps_unit_can_equip_item is the literal 6 at 00026032, not sizeof: the array length and the record stride are the same number written twice in different places, so enlarging this struct silently leaves the consumer reading only the first six bytes of a longer row.

**`fdps_class_record`** — magic_resist_complement is 100 minus the resistance, not the resistance. Writing the obvious damage = power * magic_resist / 100 inverts every flat-power spell in the game: 活屍, whose 90% resistance is stored as 0x0a, would take 90% of the power instead of 10%. The record is also indexed by class code PLUS ONE (row 0 being the all-costs-1 default row), with the map-AI handler at 000126b0 the one original site that omits the +1 -- both already recorded in rebuild_info/pitfalls.md and assets/tables/classes.md.

**`fdps_dpmi_real_mode_call`** — Two, both of which produce a build that runs and reaches MSCDEX wrongly. (1) The whole-structure clear at the top of fdps_cd_device_request is load-bearing, not hygiene. DPMI 0300h takes the real-mode stack from ss/sp (+0x30/+0x2e) and allocates one itself only when both are zero, loads flags (+0x20) into the simulated interrupt, and writes the returned register values back into this same structure. Filling in only the four fields the call needs -- the obvious economy once the object is a named struct in already-zeroed _BSS -- leaves the previous call's returned SS:SP and FLAGS behind from the second call onwards. (2) The record must be exactly 50 bytes, which it is only because wcc386's default is -zp1 (rebuild_info/build_flags.md). Under -zp4 or -zp8 the field offsets stay put but the struct is padded out to 52, and then the sample's own idiom memset(&rmi,0,sizeof(rmi)) clears two bytes past the end -- in this image that is data_fdps_cd_request_header_real_mode_seg at 00069e54, read three instructions later to fill es, so ES goes to zero and MSCDEX is handed a request header at 0000:0000. Keep the packing, or write the literal 50. The corollary is the usual one for ABI blocks: the fifty bytes are one object, and splitting the four written fields into separate globals lets the linker pad them apart, after which DPMI reads the other thirteen registers out of whatever sits between them.

**`fdps_enemy_data`** — HP, MP, AP, DP and DX in this record are per-level coefficients, not the enemy's stats: fdps_deploy_unit multiplies each by the deployment record's level byte (unit HP = level * hp, and both current and maximum take it, so the enemy arrives at full health). Reading the table as an ordinary stat block gives every enemy its level-1 numbers. Two of the ten fields are deliberately not scaled -- mv (+8) and race/class (+0, +1) are copied verbatim -- so a rebuild that scales the whole record uniformly is also wrong. Note as well that the roster-side path in the same function uses a different formula (base + growth * level for the combat stats but base + growth * (level - 1) for HP and MP); the enemy path has no base term at all and no level - 1 anywhere.

**`fdps_item_effect`** — FD2's item_effect and FDPS's are both 23 bytes and share almost every field, but FDPS has no leading prefix byte: type is at +0 here and at +1 in FD2, so the whole record is shifted by one. Copying FD2's struct into the FDPS rebuild compiles, links and produces a game whose every weapon stat, price and use effect is read one byte high. The size matching is exactly what makes this one silent.

**`fdps_map_cell_code_layer`** — Two traps, both of the form 'the obvious rewrite reads the wrong bytes'. (1) The .dtl and .mpl headers open identically -- magic, version, offset word at +5, width at +7, height at +9 -- so it is natural to give them one shared header type or to cache one map width and index both planes with it. That is wrong: their planes start at different offsets (0x10 vs 0x0b), their cells are different sizes (1 byte vs 2), and their dimensions differ for the same map (M00.DTL is 64x64 while the same chapter's M000.MPL is 30x24). fdps_map_load_tile_info and fdps_map_apply_triggered_cell_changes must each keep the two separate width loads the original has. (2) The header self-describes its data offset at +5 as 14, but FDPS.LE ignores that field and hard-codes the cell plane at +0x10; a rebuilt loader that 'correctly' honours the header field reads two bytes early on every map. Same shape as the .cel loader, which hard-codes 0x0f and ignores its own +5.

**`fdps_map_spawn_pos_record`** — The executable's cursor into this table is base + 0xb + i * 6, and 0xb is NOT the header size. The header is 9 bytes; the extra 2 are this record's own char_id field, which the code skips because it takes the character id from map%02d.dat instead. Casting the table pointer as ((fdps_map_spawn_pos_record *)(ptr + 0xb)) -- the obvious move, since 0xb is the constant in the assembly -- shifts every field name by one field and makes record i's coordinates read as record i's char_id and desired_x. The correct base for the rebuilt C is ptr + 9, and the coordinates the old code fetched at +0xb + i*6 and +0xd + i*6 are table[i].desired_x and table[i].desired_y.

**`fdps_move_grid_cell`** — The marker byte must be declared unsigned. Watcom 10.0a's plain char is signed, so writing `char marker;` and keeping the image's `!= 0xff` test makes the comparison always true after integer promotion (-1 != 255) and every tile then reads as marked -- fdps_map_grid_collect_marked_tiles would return the whole map and fdps_draw_scene_layer would pulse every tile. The anchor verdict for 00060144 records the opposite pitfall (that the byte is a signed char tested against -1); the assembly does not support it: every test site zero-extends first (00011e0a MOV AL,byte ptr [EAX] / AND EAX,0xff / CMP EAX,0xff, and the same at 00012031), and there is no MOVSX of this byte anywhere. Second trap, from FD2: the marker counts UP from 0 as accumulated movement cost, it is not FD2's remaining-budget counter, so a path tracer written to walk toward the larger value -- FD2's direction -- would walk away from the unit instead of back to it.

**`fdps_promotion_record`** — The 勇者徽章 entry (offsets 9..11) is all zeros in eight of the nine records, and zero is not a sentinel there: portrait id 0 and class id 0 are 蘭迪斯 and 劍士, real values. A rebuild that offers entry 3 to anyone but character id 0, or that treats a zeroed entry as "no route", turns the unit into character 0's base form with no movement bonus. The original guards this outside the table, in fdps_church_promote_loop, by probing item 0xdb only when unit record byte 0x7 is 0. A second trap of the same shape sits on the eligibility test and is already recorded in rebuild_info/pitfalls.md: the church tests byte 0x7 (portrait id) below 9, not the class code, because the table has only nine rows.

**`fdps_save_slot`** — The five-dword stamp at +0x9ec..+0x9ff lands INSIDE the 0xa00 bytes just memmoved from the roster, not after them. Declaring the obvious struct -- fdps_unit_record roster[32]; uint bonus_flag; uint minute; ... -- puts the stamp at +0xa00 and shifts chapter_index, party size, gold and all four option bytes 20 bytes down the record, which silently breaks every existing FDE.SAV and every other routine that reads a slot. **`fdps_spell_effect`** — Two ways to get this record wrong that both compile and link. (1) ALIGNMENT: it is 7 bytes beginning with a 16-bit field. Declaring the natural C struct gives sizeof 8, so table[id] strides by 8 and every spell from id 1 upward reads the wrong record -- the original computes base + id * 7 by hand in fdps_get_spell_record. The declaration needs Watcom's _Packed / #pragma pack(1), and the accessor must keep its explicit * 7. (2) SIGNEDNESS: power is signed, and a negative value is an attack multiplier in percent, not damage. FD2's solved record declares the same offset as uint16 damage, so copying FD2's struct across is the natural move and it silently breaks the eight ultimate spells: 聖龍烈霸斬's -250 becomes 65286, fdps_spell_damage_unit's JL branch at 0002837d is never taken, and instead of AP x 2.50 the spell deals 65286 * class_modifier / 100. Every field offset matches between the two games, which is exactly what makes this one invisible.

**`fdps_spell_learning_record`** — There is no terminator and no count. 22 of the 60 records carry content and record 0x11 fills all six pairs, so a reader that walks pairs until it meets 0xff and assumes such a pair exists runs off the end of that record into the next one; the original always loops exactly six times and tests each level byte. The second trap is narrower than the anchor verdict for 00063fe8 states, and the difference matters: the original grants EVERY pair whose level equals the new level rather than the first, so the obvious search-and-break rewrite would drop a second spell learned at the same level -- but no record in the shipped GetMgTab.dat has two pairs at one level (checked across all 60), so that rewrite is behaviourally identical on the shipped file and diverges only on modified data. Nothing here needs packing: twelve byte fields give sizeof 12 on their own, unlike the 7-byte fdps_spell_effect.

**`fdps_tile_attr_entry`** — Two ways of writing this record from what looks like prior knowledge produce a build that runs and plays wrong. First, DO NOT carry FD2's layout over: FD2's 4-byte tile attribute is {flags, terrain_class, background_index, reserved} and FDPS's is {flags, blend_level, terrain_class, combat_backdrop_id}. Copying FD2 puts the terrain class at +1 and the backdrop at +2, which reads the always-zero blend byte as the terrain class -- every terrain AP/DP modifier and every terrain movement cost silently becomes the index-0 entry, and every fight opens the same backdrop, with no crash and no wrong-looking map to give it away. Second, the record array does not start at the resource base: FDPS's attribute blob carries a 0x11-byte container header and the array is at base + 0x11 + tile_id * 4, whereas FD2's equivalent blob has no header at all. Indexing base + tile_id * 4, the FD2 form, reads 17 bytes of header as records 0..4 and shears every later record by one byte.

**`fdps_unit_record`** — portrait_id (+7) and char_id (+8) hold the same value on every unit the game creates, and they stop being the same the moment a character is promoted at the church: fdps_church_promote_unit rewrites +7 with the new form id and leaves +8 alone. They index different tables -- +7 selects the FACE.CEL portrait, the ICON.CEL walk sprites and the FRIAPRDA.DAT / FRILEVUP.DAT row (and, at 0x3c and above, ENEMYDAT.DAT), while +8 is the RANKUP.DAT index and the key every chapter event and fdps_battle_find_unit_by_character_id matches on. A rebuild that treats them as one field, or that picks whichever is in hand at the call site, tests clean for the first seventeen chapters and then quietly draws the wrong portrait, grows the wrong stats, or fires the wrong character's event.

**`fdps_vfs_image_header`** — The VFS header must be byte-packed and so must the directory entry it points at. Declared the obvious way -- struct { char magic[3]; unsigned short version; unsigned short entry_table_offset; unsigned long entry_count; } -- Watcom aligns the shorts and the long, the record becomes 12 bytes with version at +4, entry_table_offset at +6 and entry_count at +8, and the memmove that copies sizeof(header) then copies 12 bytes and reads all three values out of the wrong places. The original is 11 bytes with a u16 at +5 and a u32 at +7, both unaligned; the 26-byte entry is worse, with u32 fields at +0x0d, +0x11 and +0x16. rebuild_info/pitfalls.md already carries this for MAGICDAT.DAT's 7-byte spell record, but that row is about data tables and points at assets/tables/spells.md; the container format needs its own row pointing at resource_info/vfs.md, because the field that gives the trap away -- entry_table_offset reading 35 rather than 36 -- is only visible from the file side.

**`FILE`** — sizeof(FILE) is 26, not 28. Watcom 10.0a's <stdio.h> opens with '#pragma pack(1)' (line 10), so the six 4-byte members plus two chars get none of the tail padding a modern compiler would add. Two constants in the image are built on that 26: __allocfp's end-of-table bound CMP EBX,0x61358 (= __iob + 20*26) and L$N_ioexit_docloseall's CMP EAX,0x611d2 (= &__iob[5], the window of statically initialised streams). If a rebuilt module ever sees a padded FILE -- because someone hand-declares struct __iobuf in src/, or because a module is compiled against a different Watcom version's headers -- __iob's stride changes, those two windows stop covering the records they are meant to cover, and the standard streams get released or spared at the wrong time. So never declare this record in src/: include <stdio.h> and link the same Watcom 10.0a CLIB3S. FD2 hit the same class of hazard and records the rule in rebuild_info/link/wlink_settings.md as linking with the same-version toolchain to avoid _iobuf layout ABI differences. Second trap, in Ghidra rather than in C: Ghidra ships a built-in FILE in generic_clib whose layout is neither 26 bytes nor this field order. Binding that one instead of this record leaves every access past +0x0c reading the wrong member while still looking typed, so the transcription step has to create this FILE explicitly and make sure the built-in is not what gets applied.

**`IO_PARMS`** — The 'field not specified' value is -1 and the fields are read SIGNED. Declaring them unsigned (some Miles headers publish U16/U32) or letting the block start zeroed makes every field look specified: AIL_internal_dig_apply_io_parms then stops substituting the driver's default table and the card is configured for IO port 0 on IRQ 0 with DMA channel 0. That is why both driver setup routines open with memset(...,-1,0x18) even though 0006a038 is in _BSS and the CRT has already zeroed it, and why the .INI parser fills its own block with 0xFF before parsing -- neither memset is redundant and neither may be dropped. A second, sharper trap: the two merge routines do not use the same test. The DIG side treats a field as unspecified when it is < 0 (00046881 JGE after TEST), the MDI side when it is < 1 (00049700 CMP EAX,0x1 / JGE), so a legitimately zero DMA channel survives on a .DIG driver and is silently replaced by the driver's default on a .MDI driver. Writing one shared helper for both, or 'fixing' the MDI comparison to match the DIG one, changes which configuration the MIDI driver is handed. Finally, 0006a054 must stay a file-scope static whose address AIL_get_IO_environment returns and whose failure paths leave untouched, and it must start all-zero from _BSS rather than pre-filled with the 0xFF markers this record uses elsewhere.

**`L$1_emu387_tag_mask_set`** — The table is indexed by a register-file BYTE OFFSET (0, 10, 20, ... 70) taken from the ring at 0004e83a, not by the stack-slot number 0..7, the same trap already recorded for the ring itself. Writing the C as tag_masks[top] instead of indexing by the slot's byte offset silently reads the wrong row for every slot but 0. No apply_to variable entries: every reference is an absolute CS:[EDI + 0x4e88a] displacement in hand-written assembly, so no local or parameter in the database holds a pointer to the table and there is nothing to type at a call site.

**`L$N_dosinite_extender_sysreg_block`** — The struct must keep its full 64 bytes even though only 4 are named, and the store must always be preceded by its matching fetch. The other 60 bytes are the extender's, filled by the AX=2535h fetch and handed straight back by the store; declaring only the known field, or filling a fresh local block and issuing the store alone, hands the extender 60 bytes of garbage system state. Separately, the teardown path assigns the whole dword (cr0 = saved MSW & 6) rather than masking and OR-ing the way the ring-0 path at 000446ca does; the natural read-modify-write does not reproduce the original.

**`L$N_emu387_stack_ring_entry`** — next_slot_offset and prev_slot_offset are BYTE OFFSETS (0, 10, 20 ... 70), not slot indices. Writing ring[e->next_slot_offset] indexes eight rows past the table; the code uses the value unscaled as a displacement, both into this table and into the 10-byte temp-real register file at state+0x1c, which is the whole reason the row is 10 bytes rather than the 8 its four live fields would need. If the table is ever regenerated, the obvious next = (i+1)*10 is wrong at the ends: slot 7's next_slot_offset is 0x0000, not 0x50, and slot 0's prev_slot_offset is 0x0046. And the record must not be padded to 12 by natural alignment -- five ushorts give exactly 10, but any added field or alignment would break the stride identity above.

**`L$N_emu387_state`** — These 122 bytes must be emitted as one contiguous object in this order. FLDENV and FSTENV copy 28 bytes straight off the base (0004f0e7, 0004f145), FRSTOR and FSAVE copy 28 + 8*10 (0004f4d2, 0004f519), and the SIGFPE shim copies 0x6c bytes to the stack and back around the user handler (0004ee5b, 0004ee8f) - so rebuilding the six pieces as six separate C objects compiles and runs but reads and writes whatever the linker happened to place between them. Two further traps inside the record: the register slots are 10 bytes apart, not the 12 a struct of two dwords and a word would be padded to, because the index is computed as TOP*10 (LEA EDI,[EDI+EDI*0x4] / ADD EDI,EDI); and the two reserved bytes after each of control_word, status_word and tag_word are part of the 32-bit environment image and must stay reserved - 0004eca8 reads the status word as a dword and relies on the upper half being masked away, so packing the three words together would break both the environment copies and that read.

**`L$N_scale_pow10_entry`** — Two ways to write this record that look right and are not. (1) The double at +2 is unaligned by design. Declaring the obvious struct { short decimal_exponent; double power_of_ten; } lets the compiler pad the record to 16 bytes, and the walk's ADD EAX,0xa then lands mid-record on every step; the record must be packed to exactly 10. (2) The array has no element count and no terminator except the value 1 in the last record's decimal_exponent: 00055bf2 CMP word ptr [EAX],0x1 / JZ keeps the pointer on the final rung and applies 1e1 repeatedly until the remainder reaches zero, instead of advancing. Iterating the eight records with a for loop, or continuing the ladder as though it halved (216, 108, 54, 27, 13, 6, 3, 1 -- it does not; the real rungs are 216, 108, 54, 27, 14, 8, 4, 1), changes which rungs are visited and therefore the order of the multiplications and the last-bit rounding of every floating-point conversion. A last record whose decimal_exponent is not exactly 1 sends the pointer off the end of the table.

**`L$N_spawn386_exec_params`** — The block is byte-packed: each 16-bit selector sits immediately after a 32-bit offset with no padding (+0x00/+0x04, +0x06/+0x0a, +0x0c/+0x10, +0x12/+0x16). Written as the obvious C struct of dword/word pairs, the compiler aligns each pair to 4 bytes and the record grows from 32 to 40, moving every field DOS reads -- the child is handed a garbage environment pointer and command tail. It must be declared with #pragma pack(1) (or _Packed), or kept as a raw byte array written at explicit offsets.

**`long_double_80`** — Two ways to get this wrong in the rebuild, both of which produce a binary that links and runs. First, do not spell it long double: Watcom 10.0a's long double is the 8-byte double (H/FLOAT.H gives LDBL_MANT_DIG 53 and LDBL_MAX == DBL_MAX), so an array of long double constants is a 32-byte table at 8-byte stride with silently truncated values while every walker steps LEA reg,[reg + 0xa] and reads a word at +8 -- it walks off the end of the table and every transcendental computed without a coprocessor comes back wrong. Second, the struct must be byte-packed: natural alignment of two dwords and a word makes the record 12 bytes, and a 12-byte stride breaks the same walkers and moves the register file's scratch operand off state+0x6c. Emit the raw byte images, or better, resolve the emulator out of EMU387.LIB with wlink and do not re-emit the module at all.

**`miniheapblkp`** — The mini heap does not start at the address the operating system returned. Eight bytes of allocation bookkeeping sit immediately BELOW this header and are not part of it: [base-8] is the DPMI memory handle (read as two words at 00043fc9/00043fcc and fed to INT 31h AX=0503h, or to AX=0502h in SI:DI at 00043f18) and [base-4] is the DOS paragraph segment, non-zero only when the block came from INT 21h AH=48h and is released with AH=49h at 00043f2c. __FreeDPMIBlocks reaches them with LEA ESI,[EBX-0x8] at 00043efc and __ReAllocDPMIBlock with LEA EAX,[EBX-0x8] at 00043f80. Treating the pointer in __nheapbeg as the start of the allocation, or growing the struct downwards to cover those two dwords, shifts every field by 8 and breaks the whole chain. The second trap is len: it is the allocation size minus 4, not the allocation size, because the last dword of the block holds the 0xFFFFFFFF end-of-heap marker that every block walk stops on (planted at 000440d9, tested at 00043e24 and 0004d055).

**`REGS`** — Two traps, both of which FD2 hit. (1) These 28 bytes are ONE object, not seven scalars. Ghidra shows several anchors inside each block (00069dac/00069db0/00069db4/00069dc4 and 00069dc8/00069dc9/00069dcc/00069dcd/00069dd0/00069ddc) because the code touches individual register slots, and declaring those as separate globals is the obvious thing to write and is wrong: the linker may reorder or pad them apart, after which int386x loads and returns the wrong registers. FD2 shipped exactly this bug on its own 28-byte REGS scratch and it produced a dead keyboard (playtest bug B / B2, FD2 rebuild_info/build_test/playtest_bugs.md). (2) The type is a UNION, and the original reaches it through the .w and .h views: 16-bit and 8-bit stores that leave the upper halves of the dwords holding whatever the previous interrupt left there, and 16-bit and 8-bit loads that ignore them. Emitting the fields as x.eax/x.ebx dwords changes behaviour in both directions -- a dword store clears halves the original left stale, and fdps_cdrom_detect reading regs.x.ebx instead of regs.w.bx can see a non-zero drive count with no CD-ROM redirector loaded and take the wrong branch. The rebuilt .c must get 'union REGS' from <i86.h> and use .w / .h at the call sites; the flat seven-dword layout recorded here is the Ghidra view of the same bytes, chosen because the transcription step cannot express overlapping members.

**`rt_init`** — Two ways to write this record that compile and then behave differently from the original. First, packing: the natural declaration struct rt_init { unsigned char rtn_type; unsigned char priority; void (*rtn)(void); } compiles to 8 bytes under Watcom's default structure alignment, because the pointer is aligned to 4 and the tail is padded. The original is 6 bytes with the pointer at +2, and both walkers step it with a literal ADD ESI,0x6, so an 8-byte record makes every step after the first land inside the previous entry. The record must be declared packed to 1. Second, constness: a table of function pointers invites a const declaration, and that is wrong here -- __InitRtns and __FiniRtns write 2 into byte 0 of each record as they go, so the XI and YI contributions have to land in writable data. Declaring the entries const puts them in a read-only section and the first store faults or is silently dropped, which lets the whole chain run twice. Third, and it is the reason the tables have no bounds of their own: the extents 0x638f0..0x63920 and 0x63920..0x6392c are wlink's XI and YI segment boundaries baked into inirt386 as immediates, not data in the image, so the record count is a link-time fact -- adding or removing an initialiser changes it and nothing in the C source states it.

**`SEQUENCE`** — Two things bite anyone who writes this record the obvious way. (1) chan_map is addressed as [seq + 0x8c + chn*4], not [seq + 0x90 + chn*4], because AIL_map_sequence_channel and AIL_true_sequence_channel take 1-based MIDI channel numbers 1..16 while the interpreter uses 0-based ones -- and AIL_map_sequence_channel additionally stores new_chn - 1. Declaring the field at 0x90 and indexing it 0-based from the public API shifts every channel by one; declaring it at 0x8c to make the public API's arithmetic look natural overruns the array by one dword at chn = 16. (2) beat_period and beat_increment are in SIXTEENTHS of a microsecond, not microseconds: the meta 0x51 tempo value is multiplied by 16 on the way in and the per-interval increment is 16000000 / service_rate. Writing the natural 1000000 / rate and storing the raw tempo makes the beat/bar counters that AIL_sequence_position reports run sixteen times fast, while playback itself, which is driven by interval_count and tempo_error, keeps perfect time -- so the bug is silent everywhere except in the beat callback.

**`SREGS`** — Three traps, all of which make a build that runs and behaves differently. (1) The type comes from <i86.h>; do not declare a local copy. i86.h wraps its declarations in #pragma pack(1), so a hand-written 'struct SREGS { unsigned short es, cs, ss, ds, fs, gs; }' compiled under the project's own packing is the right size only by luck, and the two members int386x actually uses sit at +0 and +6. (2) fdps_cd_device_request must keep its memset-then-set-es sequence. The textbook idiom, and the one Watcom's manual pairs with int386x, is segread(&sregs) -- which is what int386 itself does at 0004326f -- and it fills all six members from the current registers; ES then carries whatever selector happened to be live instead of the game's data segment, and DPMI 0300h reads the real-mode call structure from the wrong base. The two allocate calls in fdps_cd_alloc_dos_buffers are likewise handed an all-zero SREGS on purpose. (3) The 12 bytes at 00069df0 are one object. Splitting them into separate word globals lets the linker pad them apart, after which int386x's MOV ES,[EBX] and MOV BP,[EBX+6] read the wrong storage -- the same shape of bug FD2 shipped on its 28-byte REGS scratch (playtest bug B).

**`tm`** — The two TZ transition-rule records at 0006145c (__start_dst) and 00061480 (__end_dst) are struct tm objects whose slots do not hold what their names say, so writing them as ordinary struct tm values and using them as dates is wrong in three separate ways. tm_mday holds the week ordinal of an "Mm.w.d" rule, 1..5 with 5 meaning "the last such weekday in the month" -- the built-in end rule's initialiser IS that 5, so the default depends on the special case. tm_isdst holds the rule form (1 = Jn, 0 = Mm.w.d, -1 = bare n), not a DST flag. tm_yday holds n as written in the TZ string: one-based and counted as if February 29 did not exist for the J form, which __isindst corrects with a +1 in leap years past day 59 and then a -1, and not at all for the bare form; comparing rule.tm_yday straight against tm->tm_yday puts every J-rule transition a day early. Separately, both records live in initialised data and carry the M4.1.0/M10.5.0 02:00 defaults, and the parser overwrites only the fields the TZ string actually supplies -- declaring them as plain zero-initialised file statics compiles, links and silently moves the default transition to week 0 of January.

**`VDI_CALL`** — Three traps, all cases where the obvious rewrite runs and misbehaves. (1) The in block's AX and BX slots are dead on input and live on output. AIL_call_driver never reads in->AX or in->BX -- it loads the real-mode AX from its own fn argument (00044e6b) and the real-mode BX from the driver's slot number in the loaded image's VDI header at vdi_hdr+0x32 (00044e9d-00044ea4) -- but it writes both back into the out block afterwards. Two consequences: tidying the API so the function number travels inside the block sends the driver the wrong AX, and passing the same pointer as both in and out (which looks free, since the record is symmetric) clobbers the caller's own CX/DX before it is finished with them. Miles' own code never does either; every site in this image passes either an in block with a NULL out or a NULL in with a separate out block. (2) The far pointers the 0x301 driver-description call returns are NOT paired in register order. Both driver setups build them as DX:AX and CX:BX -- 00046a79/00046a7e computes DDT = (DX << 4) + AX and 00046a8f/00046a9b computes DST = (CX << 4) + BX, and 00049879/00049885 and 00049895/0004989a do the same in the MDI twin -- so the segment always sits in the HIGHER-offset slot of the pair. Writing the natural AX:BX and CX:DX pairing produces two pointers into nowhere and the driver description is read out of unmapped memory. (3) The static instance at 0006a0ac must stay a file-scope static and must stay only half written. AIL_internal_audio_mix_isr sets CX and DX and relies on the CRT's _BSS clear for AX, BX, SI and DI, and the block is DPMI-locked with a hard-coded 0xc because the only code that touches it runs at interrupt time; declaring the record as a local inside the ISR and filling just those two fields -- exactly what the single call site invites -- hands the driver whatever the stack held in the other four register slots and puts the block on a page that can be swapped out under the handler.

**`00069c08` data_fdps_scene_layer_scroll_offset_y** — The pixel origin is computed with an arithmetic shift, `(view_origin_y * factor + offset) >> 3`, on signed ints. A rewrite that spells it `/ 8` gets round-toward-zero instead of round-down and displaces the layer by one pixel for every negative accumulator value, which a negative scroll step in the dsc record produces routinely.

**`00069c20` data_fdps_scene_layer_tile_sheet_ptrs** — The three per-layer resource arrays (this one, the .mpl pointers at 00069cb0 and the attribute pointers at 00069c98) are freed only over the current layer count at 00069cdc, and the freed slots are never set to NULL. A slot filled by a chapter with many layers and not refilled by the next chapter keeps a dangling pointer, which is harmless only because every loop is bounded by the count. Writing the obvious teardown -- free all six slots, or free over a saved maximum -- double-frees those stale slots.

**`00069c38` data_fdps_scene_layer_scroll_step_y** — The value is a signed 1/8-pixel-per-tick step, and fdps_draw_scene_layers applies it only when the tick counter at 00069d64 differs from the latched copy at 00069d14, not on every call. Writing the obvious C -- adding the dsc dword to the layer position each time the scene is drawn, and treating it as whole pixels -- makes every auto-scrolling layer move many times faster than the original, and typing the column unsigned turns an upward-scrolling layer's negative step into a huge positive one.

**`00069c50` data_fdps_scene_layer_scroll_x_step** — The step is a signed 1/8-pixel-per-tick value taken verbatim from dsc%02d.dat, and it is added on a tick edge rather than every frame. Writing the column as an unsigned type makes a left-drifting layer (negative step) add about four million instead of subtracting, and hoisting the add out of the 00069d14 / 00069d64 tick guard makes every layer scroll at frame rate.

**`00069c68` data_fdps_scene_layer_parallax_factor_y** — The factor is in eighths of the viewport origin, and the original combines it with the layer's scroll accumulator before reducing the sum with a single arithmetic shift right by 3: (DAT_00069ce0 * factor + accumulator) >> 3. Writing the obvious camera_y * factor + accumulator as a pixel value, or shifting the two terms separately, scrolls every parallax layer eight times too far; typing the column unsigned turns a layer that drifts against the camera (negative factor) into a huge positive offset.

**`00069c80` data_fdps_scene_layer_parallax_factor_x** — The column is a signed multiplier and the sum it feeds is reduced with SAR by 3. Writing it as an unsigned int makes `DAT_00069ce4 * factor + accumulator` an unsigned expression in C, turning the shift logical, so any layer whose combined scroll origin goes negative -- the case fdps_draw_scene_layer floors by hand -- lands at a huge positive source offset and the layer wraps to the wrong part of the tile map.

**`00069c98` data_fdps_scene_layer_tile_attr_ptr** — The free loop at the top of fdps_field_load_chapter_resources runs over the OUTGOING chapter's layer count, before the count is replaced from the new "dsc<chapter>.dat". Freeing all six slots instead, or moving the free loop after the descriptor load, double-frees or leaks whenever two chapters differ in layer count. The slots are also never NULLed after free, so nothing may read them between the free loop and the reload loop.

**`00069cb0` data_fdps_scene_layer_tile_map_ptrs** — Nine of the thirteen functions that reach this address use only slot 0, and use it as a scalar pointer they dereference (MOV EAX,[0x00069cb0] then MOVSX word ptr [EAX + 0x7]); only fdps_draw_scene_layers, fdps_field_load_chapter_resources, fdps_load_field_chapter_resources and fdps_shutdown_free_resources index it. Declaring it as a single byte * -- the shape almost every use suggests -- makes those four index past it into the next column at 00069cc8. It must be declared as the 6-element array, with every scalar-looking use written as element 0.

**`00069cc8` data_fdps_map_unit_walk_anim_counter** — The walk phase is a single global shared by every unit on the map, not a field of the 0x50-byte unit record, and nothing resets it between chapters. Storing a per-unit phase -- the obvious layout, and the one the FD2 record used -- makes units animate out of step with each other, which the original never does.

**`00069ccc` data_fdps_map_cursor_world_y** — fdps_collect_targets_in_line hands its scan position to fdps_battle_find_unit_at_cursor through this global (and 00069cd4) rather than as arguments, saving and restoring the real cursor around the loop; rewriting the scan with local coordinates, or omitting the restore, changes which units a line attack finds and leaves the on-screen cursor displaced. The variable must also be a signed int -- that same scan relies on the value going negative and being caught by a signed (-1 < value) test, and every tile conversion is a signed IDIV by 0x18.

**`00069cd0` data_fdps_map_cursor_draw_mode** — The exit paths store the literal 1, they do not restore what the variable held on entry, and fdps_map_cursor_select_loop reads the targeting radius back out of it as mode-1. Writing the obvious save/restore around the hidden-cursor sequences, or giving the drawing its own variable, changes which tiles an ability can select.

**`00069cd4` data_fdps_map_cursor_world_x** — fdps_collect_targets_in_line does not pass the scanned position to its helper: it saves this global and 0x69ccc, walks them along the line by +/-0x18 per step, calls the argument-less fdps_battle_find_unit_at_cursor which reads them back, and restores both at 000137c1. Rewriting that loop with local x/y and a find_unit(x, y) call would find nothing. The same loop lets the value fall below zero and stops on a signed CMP ... ,0x0 / JGE, so typing it unsigned (or dividing by 24 unsigned) makes lines that run off the left edge wrap instead of terminating.

**`00069cd8` data_fdps_map_unit_array_ptr** — This pointer does not always own its block, and the block moves. fdps_load_field_chapter_resources assigns it DAT_00064108 and guards the preceding free with 'pointer != DAT_00064108'; writing the obvious 'free(units); units = field_units;' double-frees a block the other global still points at. Separately, fdps_relocate_unit_array reallocates the array on every unit iteration, so hoisting 'unit = &units[i]' out of a loop that calls it -- the natural C rewrite -- leaves a pointer into memory that has been zeroed and freed.

**`00069ce0` data_fdps_battle_view_window_origin_y** — This is a signed int and the code depends on it. The screen shake in fdps_apply_item_effect_to_targets and fdps_cast_spell_on_targets adds rand()%4 - 2, so the value reaches -2 when the view is at the top of the map, and every /0x18 conversion is a signed truncating IDIV. Writing it as unsigned (a natural choice for a pixel coordinate) turns fdps_map_cursor_move_to's "if (origin < 0) origin = 0" clamp into dead code and makes origin / 0x18 a huge number during the shake; using >> 4 or >> 3 instead of / 0x18 is wrong for the same reason.

**`00069ce4` data_fdps_battle_view_window_origin_x** — The view-shake and view-pan loops (fdps_icon_script_animate_view_offset, fdps_apply_item_effect_to_targets, fdps_cast_spell_on_targets) latch the origin into a local first and write origin = saved_origin + step_offset every frame, restoring the saved value when the loop ends. Rewriting it as the obvious origin += step_offset accumulates each step on top of the last: ICON06.DAT's ramp of -6,-12,-18,-24 becomes -6,-18,-36,-60, and the camera does not return to where it started.

**`00069ce8` data_fdps_battle_turn_counter** — The counter is 1-based and is read for a turn before it is advanced for that turn: fdps_chapter_state_reset writes 1 before the first player phase, and fdps_battle_advance_turn increments it only after fdps_battle_run_turn_events has fired the turn's scripted events. **`00069cec` data_fdps_battle_pending_xp_credit** — fdps_unit_award_exp_and_level_up returns without clearing this accumulator on its three early exits (total is 0, fdps_unit_is_retired reports the unit gone, unrecognised id); only the full path zeroes it. Writing the obvious C -- clearing it once in the epilogue, or on entry -- makes a skipped award vanish instead of persisting, which differs from the original because callers, not the award routine, own the clear at the start of each action.

**`00069cf0` data_fdps_cel_sprite_cache_count** — This count, not the pointer, is the cache-empty predicate: the six teardown sites free data_fdps_cel_sprite_cache_ptr and zero this variable but leave the pointer dangling on purpose. Rewriting the guard as the obvious cache_ptr != NULL would treat a freed buffer as a populated cache and index it, and clearing the pointer alongside the count would suppress the free in fdps_shutdown_free_resources, which guards on the pointer instead.

**`00069cf4` data_fdps_chapter_current_chapter_id** — The chapter id is 0-based but the per-chapter filenames built from it are mixed: fdetxt%02d.txt is formatted with the value plus one, while map%02d.dat, M%02d.dtl, dsc%02d.dat, m%02d%d.mpl, m%02d%d.cel, attr%02d%d.dat, Shop%02d.dat and map%02d.cod take it raw. Storing a 1-based chapter number, or adding the +1 uniformly at the sprintf sites, makes the game open the wrong chapter's resources.

**`00069cf8` data_fdps_scene_layer_tile_attr_mode** — The value is not a boolean even though the code tests it against 0 and then against 1: 0, 1 and "any other non-zero" are three distinct rendering paths in fdps_draw_scene_layer (no attribute table; attributes with mode 0xa tint on marked tiles; attributes with mode 9 translucency on marked tiles). Declaring it as a flag, or collapsing the 1-versus-other test into an if/else on truth, silently loses the mode 9 blend.

**`00069cfe` data_fdps_scene_layer_draw_depth** — fdps_draw_scene_layers blits the slots with depth < 10 before the units and the slots with depth > 10 after them, and draws nothing at depth == 10; writing the obvious complementary split (< 10 / >= 10) makes a layer of depth exactly 10 visible where the original hides it. The byte is also compared unsigned in both the two passes and the bubble sort in fdps_build_scene_layer_draw_order, so declaring it char reverses the draw order of any depth >= 0x80.

**`00069d06` data_fdps_map_current_cell_event_code** — As a searchable-cell code this value is a 0-based index into data_fdps_map_cell_event_triggered_flags, but as an event code it is 1-based: fdps_map_set_pending_tile_event addresses the tile-event record as base + code * 2 + 0x31 while the table starts at image offset 0x33. A rebuild that keeps a pointer to the table proper and writes table[code] is off by one record and fires the wrong chapter event.

**`00069d08` data_fdps_map_current_tile_attr_flags** — The 0x60 field of this byte is a four-valued special-cell class, not a boolean flag, and the four readers each test a different subset of it (0; 0x20; 0x20 or 0x40; 0x20 or 0x60). Writing the obvious single predicate -- (attr & 0x20) or attr & 0x60 -- diverges from the original: class 0x40 cells are searchable but must never be turned over, and class 0x60 cells are turned over but must never be searchable.

**`00069d0a` data_fdps_map_current_tile_attr_reserved** — The four bytes of a tile attribute entry are not copied into the four tile-info globals in order: the original stores entry+2 to data_fdps_map_tile_terrain_type (00069d09) and entry+1 to this reserved byte (00069d0a). Writing the obvious in-order assignments swaps them, which puts the always-zero reserved byte into the terrain class and silently kills every terrain AP/DP modifier and movement cost.

**`00069d0b` data_fdps_map_tile_combat_backdrop_id** — The tile stores the backdrop id 1-based and the file name is 0-based, but the conversion is a guarded decrement: the byte is decremented only when it is non-zero, so 0 and 1 both select Back00.saf. Writing the obvious backdrop - 1 wraps a zero byte to 255 and asks BackGrnd.vfs for Back255.saf.

**`00069d0c` data_fdps_map_current_move_grid_marker** — The sentinel is unsigned. The emitted reads are XOR EAX,EAX / MOV AL,[0x00069d0c] / CMP EAX,0xff, so the variable is an unsigned char tested against 0xff, but Ghidra renders both sites as DAT_00069d0c != -1. Declaring it unsigned char -- which the code requires -- and copying the decompiler's -1 makes the test always true after integer promotion, so every tile reads as reachable: cursor confirmation stops rejecting out-of-range tiles and the blocked-route retarget walks to the end of the path.

**`00069d10` data_fdps_view_frame_last_tick** — This latch is one half of a spin loop (0002bf35-0002bf40) whose other half, the tick counter 00069d64, is advanced by an interrupt handler, and the loop re-reads both globals every iteration. Writing them as plain uint -- the obvious C -- lets the compiler hoist both loads out of the loop, and fdps_render_view_frame hangs forever on the first frame; both must be volatile.

**`00069d20` data_fdps_scene_palette_last_cycle_tick** — fdps_cycle_scene_palette calls fdps_cd_music_repeat_poll BEFORE it tests this latch and returns early. Writing the guard as the first statement of the function, which is the natural way to express "this tick is already done", silently drops that poll on every call within an already-serviced tick and CD background music stops repeating when a track ends.

**`00069d24` data_fdps_scene_palette_cycle_phase** — One single phase global is shared by all ten scene branches and is never reset on a scene change. Rewriting the switch with a per-scene static counter -- the natural thing to do when each case is written as its own block -- makes each scene start its colour cycle where it last left off instead of where the previous scene left the shared phase, so the DAC entries a scene shows on entry differ from the original.

**`00069d30` data_fdps_audio_sample_handle_table** — fdps_audio_init stores AIL_allocate_sample_handle's return without checking it, so a driver that runs out of voices leaves a null handle in the middle of the table and the voice scan still passes it to AIL_sample_status. Writing the obvious guard -- breaking out of the allocation loop, or skipping null slots in the scan -- changes which voices exist and which slot a sound lands on.

**`00069d50` data_fdps_audio_timer_handle** — The -1 failure branch in fdps_audio_timer_install only prints " Timer fail !!! " and falls through: the invalid handle is still passed to AIL_set_timer_frequency and AIL_start_timer. Writing the obvious guarded form (`if (handle == -1) { printf(...); return; }`) diverges from the original. The variable must also stay signed so the compare against -1 keeps its meaning.

**`00069d54` data_fdps_audio_cd_current_music_index** — The variable sits in _BSS and the CRT zeroes it, but 0 means "music index 0" (CD track 1), not "no music" -- the no-music sentinel is -1. Writing the obvious C, a file-scope int relying on zero initialisation with main's explicit store to -1 treated as redundant, would leave fdps_cd_music_repeat_poll seeing a selected track from the first tick and restarting CD track 1 whenever the drive is idle, before any music has been asked for.

**`00069d5c` data_fdps_audio_sample_playback_rate** — The game reads this rate before anything writes it: its only writer, fdps_audio_set_sample_playback_rate, has no caller, so at run time fdps_audio_start_sample always passes the _BSS zero to AIL_set_sample_playback_rate. Writing the obvious C -- an initialiser such as 11025, or any startup default -- would send AIL a different rate than the original ever does.

**`00069d60` data_fdps_audio_bgm_sequence_handle** — Nothing reads this global, so the obvious cleanup -- deleting a write-only variable -- would also delete the AIL_allocate_sequence_handle call that produces it. That call has side effects inside the MDI driver (it claims one of the driver's sequence slots and initialises it), so the store and the call must both survive into the rebuild.

**`00069d64` data_fdps_timer_tick_counter** — The tick counter is incremented from the AIL timer callback while roughly fifty game routines busy-wait on it (snapshot into a local, then CMP local,[counter] / JZ back). Nothing in the original declares it volatile; the loops work only because the settled flag set compiles with -od, which reloads the global on every iteration. Writing the obvious 'unsigned int data_fdps_timer_tick_counter;' is right for the production build, but the same source compiled with optimisation on -- a unit-test harness, or any module built without -od -- lets the compiler hoist the load and the wait loops never terminate.

**`00069d71` data_fdps_audio_sfx_driver_available_flag** — The audio gate is two separate bytes, not one: this flag is the driver-present fact and 00069d70 is the player's sound-effects option. A rewrite that collapses them into a single 'sound on' variable changes behaviour, because fdps_load_savegame writes the saved option byte straight into 00069d70 -- loading a save made on a machine with sound on would then re-enable playback on a machine where AIL_install_DIG_INI failed, and calls would go to NULL sample handles.

**`00069d80` data_fdps_shop_stock_table_ptr** — 0xff in a shop stock row is an empty-slot marker, not an end-of-row sentinel: it appears between two stocked entries (SHOP05.DAT row 1 is 03 04 ff 1f 20 30 31 65 ff 74 75 83). Writing the obvious loop that breaks at the first 0xff instead of scanning all twelve bytes of the row makes most of a shop's stock invisible.

**`00069d90` data_fdps_chapter_pending_event_idx** — The slot sits in _BSS, so it powers on as 0, which is a valid handler ordinal (slot 0, chapter 3's wave-deploy handler) rather than "no event" -- 0xff only ever gets there because each dispatcher writes it before the unit acts, so any rewrite that adds a dispatch path without seeding it first, or that treats the zero-initialised state as empty, fires the wrong chapter event. Separately, the sentinel is the positive constant 0xff and every test is CMP dword ptr [...],0xff, so declaring this int and using C's idiomatic -1 for "no index" makes the != 0xff test pass and dispatches through table[-1].

**`00069da0` data_fdps_chapter_event_or_battle_end_code** — Whether a store into this code is guarded by "only while it is still 0" belongs to each writing site, not to the variable. fdps_battle_check_default_end_conditions guards its stores, but most fdps_chapter_NN_post_action handlers (22, 25, 26, 27 among them) store 1 or 2 unconditionally, so on a turn where a victory and a defeat both fire the last writer wins. Factoring the guard into one shared setter -- the obvious cleanup once the pattern is noticed -- changes which ending those chapters produce.

**`00069da4` data_fdps_cd_ioctl_buffer** — The value must be a pointer into DOS conventional memory obtained from DPMI INT 31h function 0100h, and specifically the same block whose seg:0000 far pointer is stored at 00069da8 and handed to MSCDEX in the request header. Rewriting it as a plain C buffer (a static array or malloc) compiles and runs, but the driver then reads and writes a real-mode block the game never touches, so every CD-ROM IOCTL quietly returns stale or zero data instead of failing.

**`00069da8` data_fdps_cd_ioctl_buffer_real_mode_ptr** — 00069da8 (real-mode seg:0000, packed as segment<<16) and 00069da4 (flat linear, segment<<4) are two encodings of the same 512-byte DOS block, and the code feeds each to a different consumer: the seg:off form to the device request header's transfer-address field at offset 0x0e, the flat form to the memcpy that fills and drains the buffer. Writing the obvious single pointer variable and passing it to both makes MSCDEX decode the flat value as a segment:offset pair and transfer at an unrelated physical address, so every CD IOCTL silently returns whatever stale bytes were already in the buffer.

**`00069dac` data_fdps_cdrom_int_out_regs** — These 28 bytes are one union REGS, not seven scalars. int386/int386x write the whole block, so the CD-ROM drive count at +0x04 and the first-drive index at +0x08 only land where the game reads them while they stay fields of a single object; emitting them as separate globals lets the linker separate them and the interrupt result clobbers whatever neighbour ends up at those offsets (this is FD2 playtest bug B2). Separately, the carry flag at +0x18 is never tested, so adding the obvious DPMI allocation-failure check changes behaviour relative to the original.

**`00069db0`** — fdps_cdrom_detect reads only the 16-bit BX member of the int386 output REGS (CMP word ptr [0x00069db0],0x0 / MOV AX,[0x00069db0]); MSCDEX leaves the top half of EBX undefined and the block is reused by the module's other INT calls, so a rewrite that reads regs.x.ebx instead of regs.w.bx can see a non-zero value with no CD-ROM driver present and take the wrong branch.

**`00069dc8` data_fdps_cd_int_regs_in** — These 28 bytes are one `union REGS`, but the code touches individual register fields, so Ghidra shows several anchors inside them (0x69dc8, 0x69dc9, 0x69dcc, 0x69dcd, 0x69dd0, 0x69ddc). Declaring those as separate globals is the obvious thing to write and it is wrong: the linker is free to reorder or pad them apart, and int386x then loads the wrong registers -- FD2 shipped exactly this bug on its own 28-byte REGS scratch and it produced a dead keyboard (playtest bug B). Second trap in the same object: the writes are word and byte stores to the .w / .h members, which leave the upper halves of the registers stale from the previous call; writing `regs.x.eax = 0x100` instead of `regs.w.ax = 0x100` zeroes bits 16-31 the original preserves.

**`00069dc9`** — The register block this byte belongs to is a file-scope _BSS object that the CRT zeroes once, and no caller ever clears it whole: fdps_cdrom_detect writes only al and ah (0003c640, 0003c647) plus the low word of ebx, leaving the upper 16 bits of eax and all of ecx/esi/edi at whatever the previous DPMI or MSCDEX call left there. Rewriting these functions with a local 'union REGS regs;' -- the obvious C -- feeds uninitialised stack bytes to INT 2Fh/31h and the CD-ROM detection can fail or the DPMI call can be handed a junk pointer. The block must stay a static (or be memset to zero) for the partial writes to mean what the original meant.

**`00069de4` data_fdps_cd_play_range_end_sector** — fdps_cd_resolve_track_range overwrites both this range-end global and the range-start global at 00069dec on every call, so the two halves of a multi-track range have to be latched between the two resolve calls. Writing the obvious sequence -- resolve first_track, resolve last_track, then read both globals -- gives last_track's start sector as the range start and plays the wrong range.

**`00069de8` data_fdps_cd_request_header_buffer** — This must stay the flat (segment<<4) pointer to a DPMI-allocated DOS conventional-memory block, and specifically the same block whose real-mode segment is stored as a word at 00069e54 and handed to MSCDEX as ES with BX=0. Writing the obvious C -- a static array or a malloc'd buffer, or passing this flat value to the driver instead of the segment -- compiles and runs, but the driver then reads the request header from an unrelated physical address and writes its status somewhere the game never reads, so every CD-ROM request silently returns stale bytes instead of failing.

**`00069dec` data_fdps_cd_play_range_start_sector** — fdps_cd_resolve_track_range rewrites this range-start global (and the range-end global at 00069de4) on every call, and fdps_cd_play_track_range depends on latching this value into a register between its two resolve calls. A faithful-looking rewrite that calls resolve for the first track, calls resolve for the last track, and only then reads data_fdps_cd_play_range_start_sector gets the LAST track's start sector and plays a range that begins in the wrong place.

**`00069df0` data_fdps_cd_int_sregs** — int386x is handed an SREGS that is zero apart from es = ds, set by hand at 0003bbfe. The obvious rewrite is segread(&sregs) -- the idiom Watcom's manual pairs with int386x -- which fills all six members from the current registers; ES then carries whatever selector the caller happened to leave there instead of the data segment, and the DPMI 0300h call in fdps_cd_device_request reads its real-mode call structure through the wrong base. The two allocate calls in fdps_cd_alloc_dos_buffers are likewise passed an all-zero SREGS on purpose.

**`00069e01` data_fdps_cd_track_start_sector** — fdps_cdrom_read_track_info rewrites this global on every call, and both readers query a second track in the middle of their own computation. A faithful-looking rewrite that queries the track, queries track + 1, and only then reads data_fdps_cd_track_start_sector for the start point gets the second track's start sector and returns a zero-length track or an empty play range; the original latches the first value into a register (0003c1cc, 0003c80e) before the second query.

**`00069e05` data_fdps_cd_track_info_control_flags** — fdps_cd_track_is_audio decides audio versus data by comparing this byte for equality with 0x40, after the writer has masked the drive's control byte with 0xd0. A faithful-looking rewrite that tests the data bit (`control & 0x40`) or that masks the full control nibble (0xf0) classifies tracks with pre-emphasis, four-channel or copy-permit bits differently from the original.

**`00069e07` data_fdps_cd_highest_track_number** — This byte is latched disc state, not a per-call result. fdps_cd_resolve_track_range (and its callers fdps_cd_play_track / fdps_cd_play_track_range) read it without issuing a Read Disk Info request of their own, depending on the one fdps_cdrom_detect made at startup. A rewrite that returns the disc summary from fdps_cdrom_read_disk_info rather than publishing it into this global, or that skips the startup detect, leaves it zero; every track then tests as the last on the disc and the play range ends at the lead-out sector in DAT_00069e0b, which is zero as well, so audio playback silently stops working.

**`00069e08` data_fdps_cd_leadout_msf_minute** — These three bytes hold the drive's raw lead-out address, which includes the 150-frame Red Book lead-in, while fdps_cd_get_disk_info_msf derives the disc's playing time independently from the lead-out sector count with 0x96 subtracted. Because the bytes are otherwise unread, a rewrite is tempted to make fdps_cd_get_disk_info_msf return them directly; doing so reports every disc as two seconds longer than the original does.

**`00069e0b` data_fdps_cd_leadout_sector** — The value here has already had the 150-frame CD lead-in subtracted by fdps_cd_msf_to_sector, but fdps_cd_get_disk_info_msf subtracts 0x96 from it again before converting to minutes/seconds/frames, so the total playing time it reports is two seconds short. A faithful rewrite must keep both subtractions; writing the single lead-in adjustment that the Red Book convention suggests changes the reported time.

**`00069e0f` data_fdps_cd_media_catalog_number** — The 7 bytes are packed BCD with no NUL terminator; declaring them as char[7] and printing or copying them with str* routines overruns into the adjacent CD-state globals. All-zero is the meaningful "disc has no catalog number" value, not merely uninitialised _BSS.

**`00069e20` data_fdps_cd_last_request_status** — The status word must be unsigned. Written as short, the comparison fdps_cdrom_detect makes has to be spelled == -0x7ef4 instead of == 0x810c, and the BUSY extraction turns into an arithmetic shift, so a faithful-looking rewrite that types this as a signed 16-bit int silently stops detecting the failed-request case.

**`00069e22` data_fdps_cd_real_mode_call** — The memset of all fifty bytes at the top of fdps_cd_device_request is load-bearing. DPMI function 0300h takes the real-mode stack from SS:SP at +0x30/+0x2e and allocates one itself only if both are zero, and it loads the flags word at +0x20 into the simulated interrupt; DPMI also writes the returned register values back into this same structure.
