## `apply_kb.py` 的順序與冪等

record 說踩雷點套用有 4 個錯，其中 3 個是「連結指向同一批才新增的列」：判定檔依檔名排序套用，`link-*` 排在它要連的列之前，套的時候那列還不存在。更糟的是重跑：連結把新增的列 X 改寫成帶連結的 N 之後，「新增」的檢查找不到 X，又插一份，每跑一次多一份。套用 agent 在想拿回被截斷的輸出時多跑了兩次，檔案裡真的長出兩份多餘的列，它用機械式腳本還原了。

修法照 TDD 先寫兩條會紅的測試：一批裡「連結在前、新增在後」的檔案順序也要先新增後連結；同一批重套一次什麼都不變。實作是把新增排在所有連結之前，並且在判斷「這列已存在」時，同批有哪條連結會把它改寫成什麼，改寫後的樣子也算存在。

修好之後我自己也踩了一次同一個坑：用 PowerShell pipe 把 `apply_kb.py pitfalls` 的輸出交給 `python -c` 解析，JSON 卡在 BOM 上失敗，但套用已經寫檔了，而且因為沒看到輸出又跑了一次。這次腳本已經冪等，兩次的結果相同，檢查過沒有重複列。之後改成寫成腳本檔、用 `utf-8-sig` 解碼。

第 4 個錯 `item-aim-select-mode-vs-use-target` 是真的不符：判定 agent 抄的 `old_line` 結尾多一段「；`src/item.c` 的註解」，但另一張票在這一輪開跑之後把那段拿掉了。要做的修改（正典欄補 `program_info/spell.md`）沒變，所以把 `old_line` 照現在的列重抄、`new_line` 由同一個替換重算，判定檔裡留下 `_superseded_old_line` 與 `_retranscribed` 兩欄說明。這不是改判定，是重抄一次轉錄的來源。

## 重複列不只一組

上一篇發現暗號表有兩列（第 41、54 行）。我把這一輪新增的 68 列逐一拿去跟 HEAD 裡既有的列比對提到的 function 名稱，又找到第二組：第 28 章援軍（第 40、47 行）。兩組的成因相同——判定 agent 讀 `pitfalls.md` 的時候，那兩列還沒被別的子票寫進去（25.9／25.14 在同一段時間平行跑），判定「沒有既有列」是當下正確的，只是等套用時已經有了。所以不是 agent 讀漏，是併行寫同一個共用檔的競態。

處理：刪掉本輪加的兩列（第 47、54 行），保留原本的兩列；兩份判定檔改成 `already_covered` 並記下原判定，免得之後有人重跑套用又把它們插回去。原本那列的內容都比本輪加的完整，沒有要合併的東西。

比對用的是「提到同一個 function」這種粗篩，會漏掉用不同寫法描述同一件事的列；粗篩出來的其他十幾組逐一看過，講的都是不同的事。
