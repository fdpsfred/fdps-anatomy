# 票 25.1：字模對照表與文字解碼器

## 先看前作

照 CLAUDE.md 先翻 `fd2-anatomy`。`tools/glyph/` 有兩支腳本（`render_glyph_atlas.py`、`et3_pixel_match.py`）與 `ET3_fonts/`，`resource_info/chinese_glyph_encoding.md` 講了倚天 `STDFONT.15` 的字序為什麼不是 Big5 線性公式，`tools/decoders/fdtxt_parser.py`／`fdtxt_dialog_decoder.py` 是前作的文字解碼器。倚天字序的建表函式與兩個字型檔照抄；解碼器沒有照抄，因為 FDPS 的文字格式跟前作不同（前作是 u16、`0xFFxx` 系列的操作碼、四種肖像代碼；FDPS 是 signed 16-bit、-2 到 -6 與 -0x11／-0x12 兩種說話者代碼），格式本身在 `src/text.c` 的 `fdps_draw_text` 已經 emit 得很清楚，照那支寫比改前作的快。

前作的 `render_glyph_atlas.py` 沒有沿用：它只是把字模畫成 PNG 圖集給人翻，這次的人工步驟改成網頁，圖在網頁裡直接畫。

## 逐像素比對

先用一支丟棄式的腳本摸資料：`FDETXT.FON` 57,344 byte = 1792 × 32，沒有檔頭。第 16 列在 1792 個字模裡一個像素都沒有，第 1 列有 1711 個在用——字形全部畫在上方 15 列。所以倚天的 15 列字模應該放在第 0 列起比。

前作的腳本是「丟掉頂列或底列再比」，取最小距離。這個做法有個漏洞：被丟掉的那一列若有像素，距離仍可能是 0，會被當成完全吻合。這次改成把倚天字模放進 16 列的格子（第 0 列起或第 1 列起）、整格比，空出來的那一列有像素就算差異。實際結果兩種對齊裡只有「第 0 列起」吻合過，這個漏洞在本作沒有造成差別，但規則照嚴格的寫。

整格比用把 16 列打包成一個 256 bit 整數、XOR 後 `bit_count()`，1792 × 13,094 × 2 在純 Python 裡幾秒就跑完，不需要 numpy。

結果：

- 完全吻合 1723 個，每一個都只對到倚天裡唯一一個字模（`STDFONT.15` 本身沒有重複的字模，另外檢查過）
- 全空白 2 個（`0x020B`、`0x04A9`，兩格內容相同）
- 其餘 67 個對不上

67 個的最近距離（取倚天中文與倚天 ASCII 兩者較小者）分佈：1–9 有 3 個、10–19 有 8 個、20–29 有 9 個、30–39 有 3 個、40–49 有 8 個、50–59 有 19 個、60–69 有 13 個、70 以上 4 個。沒有「差一兩個像素」的情形，最近的是 6——也就是沒有哪個字是倚天的字稍微改了一筆；對不上的就是真的對不上。

對不上的是哪些字，看出現的文字片段就清楚：

- `0x0000`–`0x0023` 這 36 格是數字與大寫英文字母（「職業只能升到 `04` `00` 級」「這 `05` `00` `00` `00` 元」「移動力（`16` `1F`）增加」讀起來是 40、5000、MV）。字形與倚天的 ASCII 半形字模、也與前作的英數字模都不同，距離全在 30 以上。這跟數字代碼 -6 把字元減 `'0'` 當索引一致
- 其餘多半是全形標點：倚天 `STDFONT.15` 從 `0xA440` 的「一」開始，根本沒有 `0xA1xx`–`0xA3xx` 符號區，標點不可能在它裡面吻合
- 少數是字形不同的字，例如 `0x052B` 出現在「那個潑辣的小□頭」

我在這裡停手，沒有自己判讀這 69 個。總票的決定是「不完全吻合的字由開發者逐字填入，不由 agent 猜」，而且上面那幾個例子裡看起來很明顯的字（MV、HIT 之類）也正好是最容易自以為是的地方。

## 前作的交叉驗證

前作有一份人工校正過的 1824 字對照表。拿來做兩件事：

1. **驗證**：FDPS 有 1354 個字模與前作 `FDOTHER.DAT[4]` 的某個字模逐 byte 相同。其中 1345 個在 FDPS 這邊與倚天完全吻合，這 1345 個與前作對照表給的字全部一致，0 個不一致。倚天字序的建表與比對規則因此有一個獨立來源背書。
2. **提示**：對不上的 69 個，每個都附上前作最接近的字模與前作給它的字，放在校對網頁上當候選。其中 9 個與前作字模逐 byte 相同（例如 `0x01FC` 是前作的「）」、`0x022A` 是「～」）。它只是候選，開發者要自己點下去才算數。

途中順便推翻了知識庫原本的一句話。`resource_info/text.md` 寫「1354 個與前作逐 byte 相同，可直接沿用前作的字對照表」。逐 byte 相同是對的，但一查索引：1354 個裡只有 6 個索引也相同。前作的表按索引套到 FDPS 會幾乎全錯。已改成結論。

## 解碼器

`tools/text_decode/text_decode.py`。先寫測試再寫實作，測試縫定在兩個公開介面：`parse_block(bytes)` 與 `render_entry(entry, table)`。測試資料是依 `fdps_draw_text` 的行為手工組出來的區塊，不是從解碼器自己算出來的，包括兩個容易寫錯的點：字模 0 不是結尾、說話者代碼的運算元是 -1 時不會結束該筆（原版的迴圈條件只檢查 token 位置，運算元被 `+= 4` 跳過）。

66 個區塊先掃了一遍結構：offset 表全部遞增、沒有重複、沒有夾在筆與筆之間沒被任何一筆涵蓋的 word、最後一筆恰好結束在檔尾、沒有 -2..-6、-0x11、-0x12 以外的負數、最大字模索引 1791。共 1746 筆。控制碼的出現次數：換行 4337、以角色 id 換說話者 1467、換頁 1115、以單位索引換說話者 17、代入 16（-4 有 11、-5 有 5）、數字 11。

目前用只有 1723 個字的表跑 `all`，對照表外的索引恰好就是那 69 個，每一個都至少在某個區塊出現過（兩格空白也是，它們夾在「蘭迪斯死亡」與「索爾死亡」這種並列之間）。

## 為什麼不用 workflow

CLAUDE.md 與 ADR-0002／0007 規定逐一判定 function 或 data 的工作要由 workflow 一次派一個 agent。這張票裡沒有任何 agent 做逐項判斷：完全吻合是對整張表的一個確定性測試（整格逐像素相等，沒有門檻可調），不吻合的由開發者本人判讀。所以沒有需要派 agent 的清單，也就沒有寫 workflow。

## 校對網頁

要求是「輸入要能被程式讀回，不靠開發者手動轉貼」。考慮過三個做法：

- 本機 HTML 加「下載 JSON」按鈕——等於要開發者自己把檔案搬回來，就是手動轉貼的變形，放棄。
- Artifact 的 `artifact` 能力，每次輸入就把整頁連同答案重新發佈——69 格、每格一次發佈，發佈又會讓頁面重新載入，打字中途被打斷，放棄。
- Artifact 的 `db` 能力——每格一份文件，打字停頓 0.6 秒後寫入；我這邊用 ArtifactData 的 `list` 帶 `out_dir` 把整個集合傾印成檔案，再由 `glyph_table.py import` 轉成 `developer_answers.json`。採用。

網頁上每格有：放大的字模、前作最接近的字與倚天最接近的五個中文字與兩個 ASCII 字（都畫出字模並標差異像素數，點一下就填入）、這個字模出現的最多三段文字（其他還沒填的字模直接畫成小圖、已填的換成字、本格以框標出）、輸入框。上方有常用全形標點列（含全形空白），會填進最後點過的輸入框。資料庫連不上時退回瀏覽器本機儲存並明講 Claude 讀不到。

發佈後以 ArtifactData 讀了一次 `answers` 集合，空的，符合預期。為了確認傾印出來的檔案長什麼樣（`glyph_table.py import` 原本猜它可能包一層 `data`），在另一個集合 `selftest` 寫了一份測試文件、帶 `out_dir` 傾印、讀檔、再刪掉：檔案是平的 `{"char": …, "index": …}`，路徑是 `<out_dir>/<集合名>/g0001.json`。`import` 改成只認平的格式。

## 審查後的修正

實作完請兩個 subagent 分別從「專案規範」與「票的要求」兩個角度審。有用的發現與處理：

- 網頁的同步邏輯會掉資料：寫入失敗時答案還留在頁面上，但下一次資料庫快照會把「資料庫裡沒有的」全刪掉，再覆寫本機草稿，答案就無聲消失；離線時改過、資料庫裡已有舊值的答案，連線後會被舊值蓋掉。改成記住「本機改過、資料庫還沒確認寫入」的索引集合（連同草稿存在瀏覽器），快照只覆蓋不在集合裡的格子，集合裡的在連線後重寫，失敗五秒後自動重試。
- 用注音等輸入法時，組字中途的半個音節會在 0.6 秒後被當成答案存進去。改成組字期間不存，組完才存。
- 對照表與 `import` 原本接受多於一個字的答案，網頁也只是提醒。改成網頁不存、`import` 與 `build` 直接中止：一個字模就是一個字。
- 讀回的 `list` 沒有指定每頁筆數，萬一分頁，`import` 會只拿到一部分答案。現在讀回時指定 `limit: 1000`，`import` 也會跟待填清單比對、列出沒答的字並以非零結束。
- `resource_info/text.md` 的「索引 0–9 是數字 0–9 的字模」與對照表（這 10 格還在待填）互相矛盾，而且寫的是對照表擁有的事實。改寫成程式端的事實：數字代碼不經對照表、直接拿字元減 `'0'` 當索引，所以字模表必須把數字放在 0–9。開發者填完後要回頭核對這 10 格。
- `developer_answers.json` 放在 `tools/glyph/` 而不是 `workspace/`，這是對儲存慣例的例外，原本沒寫出來。已在 `tools/_index.md` 的儲存慣例補上。
- 幾處重複與錯誤處理：字模切片抽成一個函式、兩支產生 bitmap 的函式合併、`review_page.py` 找區塊改用解碼器的檔名規則而不是寫死 66、兩支腳本加上找不到檔案時的單行錯誤訊息、解碼器不再攔 `KeyError`（會蓋掉程式錯誤），改成讀表時驗證格式。

沒有採納的：審查者認為網頁上的中文字串違反「程式輸出用英文」。這頁是給開發者本人用的介面，屬於對使用者的回覆，維持中文。

## 讀回開發者的答案

開發者填完 69 格後，用 ArtifactData `list`（`limit: 1000`、帶 `out_dir`）一次倒出 69 份文件，`import` 沒有報任何缺漏。幾格的版本號是 2 或 3，表示開發者改過答案；倒出來的是最後的值。

答案裡值得記的：

- `0x0000`–`0x0009` 是 0–9，`0x000A`–`0x0023` 是 A–Z，和數字代碼「字元減 `'0'`」的推論一致。
- `0x0041` 是「？」、`0x01A9` 是「！」、`0x019A` 是「，」、`0x01E0` 是「。」——這四個加上 `0x0264`（﹒）是全遊戲用得最多的標點，每個出現數百到兩千多次，倚天字型裡沒有符號區，所以一個也對不上。
- `0x0203`–`0x0208` 與 `0x05AB`／`0x05AC` 是「·＃％＊＆＠＄︿」這些符號，組成強化套件安裝時那兩行亂碼似的畫面。
- `0x021C`–`0x021E` 是小寫的 i、s、k，只出現在「請放入Disk 1／2」。

開發者另外交代：`0x00C4` 和 `0x0196` 在一個字模裡並排畫了兩個相同的符號（印出點陣確認過：兩個問號、兩個驚嘆號），網頁一格只能填一個字，所以他各只填了一個。這和「一個字模一個字」的規則衝突。處理方式是不整體放寬：`glyph_table.py` 寫死一張只有這兩個索引的例外表，例外必須是同一個字元重複兩次，其他索引照舊必須恰好一個字元；網頁填的單一字元在 `import` 時自動重複。對照表在說明與備註欄註明這兩格。解碼器本來就只是把表裡的字串接起來，不假設一格一字，不用改。

`build` 順手印出「一個字對到多個索引」的清單，多了一個沒預期的：「丫」同時是 `0x052B`（開發者填的）和 `0x05CE`（倚天吻合）。印出點陣看，兩個字形確實不同，`0x052B` 是另一種寫法，只用在「小丫頭」那幾句。這不是填錯，是字模表本身就有兩個「丫」。把這件事連同全形空白的兩格一起寫進對照表的說明，並在 `rebuild_info/pitfalls.md` 記一條：字與字模索引不是一對一，拿解出來的文字反向編碼回文字檔會得到不同的 byte。

## 全解

`text_decode.py all` 66 個區塊、1746 筆，對照表外的字模 0 個，以零結束。抽看幾個區塊（道具店說明、第 1 章對話、抽獎、強化套件）讀起來都通順。
