# SAF 動畫格式

`.SAF` 是 FDPS 的動畫容器，也是數量最大宗的資源類型：硬碟安裝後 525 個，其中 522 個在最外層的 `.VFS` 內，另外 3 個包在 `MISC.VFS!BASEANI.VFS`（[`vfs.md`](vfs.md)）。戰鬥背景、角色待機與攻擊、法術、圖示動畫、開頭與結尾演出全部是這個格式。

一個 `.SAF` 是一整段動畫的全部素材：畫格腳本、每格的拼圖佈局、拼圖用的小圖，以及這段動畫自己的音效，四者裝在同一個檔裡。

## 四層結構

檔案分成四個 section，彼此是逐層引用的關係：

| section | 內容 | 引用誰 |
| --- | --- | --- |
| 0 | frame：一格的停留時間、要放的圖層、要發的音效 | section 1、section 3 |
| 1 | tilemap：一張圖的格子佈局，`columns × rows` 個格子 | section 2 |
| 2 | tile：一個 cell 大小的 sprite，RLE 壓縮 | — |
| 3 | sound：8-bit PCM 音效 | — |

所以「畫一格」＝走它的每個 layer，每個 layer 取一張 tilemap，把 tilemap 的每個格子取出對應的 tile 貼上去。

## 佈局

header 52 byte，之後四個 section 依序首尾相接排到檔案結束。

| 偏移 | 型別 | 內容 |
| ---: | --- | --- |
| `0x00` | `char[3]` | magic `"SAF"` |
| `0x03` | `u16` | 版本，恆為 6 |
| `0x05` | `u16` | header 大小，恆為 52 |
| `0x07` | `u16` | cell 寬，525 個檔一律 24 |
| `0x09` | `u16` | cell 高，一律 24 |
| `0x0B` | `u8` | 恆為 0 |
| `0x0C` | — | 四個 section 描述子，每個 10 byte |

每個 section 描述子：

| 偏移 | 型別 | 內容 |
| ---: | --- | --- |
| `0x00` | `u16` | 項目數 |
| `0x02` | `u32` | section 起點，自檔案開頭起算 |
| `0x06` | `u32` | section 大小 |

section 內部一律是同一種形狀：開頭 `count` 個 `u32` 偏移（自檔案開頭起算），緊接各項目的內容，項目之間沒有間隙。所以第 `i` 項的長度是 `offset[i+1] - offset[i]`，最後一項到 section 結束為止——**沒有哨兵項**，收尾靠的是描述子裡的 section 大小。空的 section 大小為 0，起點等於前一個 section 的終點。

## frame

| 偏移 | 型別 | 內容 |
| ---: | --- | --- |
| `0x00` | `i16` | 這格要發的音效編號，`-1` 表示不發 |
| `0x02` | `i16` | 這格停留幾個 tick，實測 1–45 |
| `0x04` | `u8` | 給呼叫端的計數，見下 |
| `0x05` | `u8` | 命中標記，見下 |
| `0x06` | `u16` | 恆為 0 |
| `0x08` | `i16` | layer 數 |
| `0x0A` | — | `layer 數` 個 layer，每個 13 byte |

`0x04` 與 `0x05` 這兩個 byte 播放器本身不看，是留給呼叫端的提示欄位，讀它們的只有戰鬥流程與法術演出：

- `0x05` 非 0 的畫格，攻擊演出（`0x196d0`）會先數出全部有幾格，再把目標的血條分攤在這些格上扣掉，同時播命中音。全部 8,335 個 frame 裡有 324 格帶這個標記。把它叫「命中標記」是從這個用法推得的。
- `0x04` 非 0 時，同一個演出會先跑一段以這個值為次數的前置迴圈才進主迴圈。戰鬥開場（`0x18d60`）也讀它，用來決定要不要再載一張背景。這個欄位的意義因呼叫端而異，名字同樣是推論。
- 法術演出（`0x1a4c0`）另有一種用法：`M`／`E` 前綴的 `?L??.SAF`（法術本體的循環段）播完一輪時，播放游標的畫格編號被設成該檔第 0 格的 `0x04`，也就是循環重播的起始格，不做範圍檢查。出貨的 38 個 `ML??`／`EL??` 檔中此值非 0 的只有 ML28（12/35）、ML29（7/16）、ML34（24/48）、ML36（12/19）、ML38（18/37），括號內是起始格／畫格數，全部小於畫格數；其餘為 0。

## layer

| 偏移 | 型別 | 內容 |
| ---: | --- | --- |
| `0x00` | `u16` | 要畫的 tilemap 編號 |
| `0x02` | `i16` | x，相對於動畫原點 |
| `0x04` | `i16` | y，同上 |
| `0x06` | `u8` | 0 是不透明貼、1 是半透明貼 |
| `0x07` | `u8` | 半透明程度 0–16 |
| `0x08` | `u8[5]` | 恆為 0 |

播放器把 `0x07` 以 `16 -` 反轉後送進繪製器的 mode 9，查的是當下裝在兩張全域混色表裡的內容：啟動時裝的是 `MER1.TMP`／`MER2.TMP`（地圖用的調色盤算出的那組），攻擊演出、法術演出、教會轉職與片尾名單四個畫面進場時換成 `FMER1.TMP`／`FMER2.TMP`（戰鬥調色盤那組），離場時換回來。9,886 個 layer 裡有 617 個開了半透明，散在 64 個檔；`0x06` 為 0 的那 9,269 個 layer 的 `0x07` 一律是 0，反過來開了半透明卻寫 0 的有 4 個。

程式讀 `0x07` 的指令是 16-bit 的 `MOVSX`，也就是連 `0x08` 那個保留 byte 一起讀進來。保留 byte 恆為 0，所以實際效果與只讀一個 byte 相同。

座標的原點就是螢幕左上角：播放器（`0x196d0`）配一張 368 寬的背景緩衝，把動畫原點設在 `(24, 24)`，最後從這個原點取 320×200 送上螢幕，兩者相消。實測 x 落在 −28–316、y 落在 −61–210，超出螢幕的部分由繪製器裁掉。

## tilemap

| 偏移 | 型別 | 內容 |
| ---: | --- | --- |
| `0x00` | `i16` | 欄數 |
| `0x02` | `i16` | 列數 |
| `0x04` | `i16[欄數 × 列數]` | 每個格子的 tile 編號，逐列排 |

格子的編號是**帶號**的：`0x13fd0` 以 `short *` 取值，`0x13ed0` 用 `-1 < index` 當下界擋。layer 的 tilemap 編號（`layer + 0x00`）則是無號的，兩者型別不同，重建時不能混用。實際檔案裡 tile 數最多 3,487，遠不到 `i16` 的上界，所以兩種讀法目前不會有差別。

格子逐列走，每走一格 x 加 cell 寬，每換一列 y 加 cell 高。最常見的佈局是 14×9（1,022 張），展開是 336×216，比 320×200 的螢幕大一圈，超出的部分裁掉；其次是 1×1（607 張）這種單格特效。

## tile

tile 的像素串與 `.CEL` 的 4-op RLE 完全相同，格式細節見 [`cel.md`](cel.md) 的「像素編碼」。這不是形似而是同一段程式：`0x13ed0` 把 tile 的串流位址直接交給 `0x568db`，也就是 `.CEL` 用的那個繪製器。

像素同樣是 8-bit 調色盤索引，調色盤不在檔內，戰鬥相關的用 `MISC.VFS` 的 `FIGHT.PAL`。

## sound

| 偏移 | 型別 | 內容 |
| ---: | --- | --- |
| `0x00` | `u8` | 聲道數，608 段一律 1 |
| `0x01` | `u8` | 取樣位元數，一律 8 |
| `0x02` | `u16` | 取樣率，490 段 11025 Hz、118 段 22050 Hz |
| `0x04` | `u32` | 後面的取樣 byte 數 |
| `0x08` | — | 無號 PCM 取樣 |

播放（`0x142d0`）把前兩個欄位配成 AIL 的取樣型別（1/8 → 0、1/16 → 1、2/8 → 2、其餘 → 3），音量固定 0x28，不循環，同時最多 8 個 channel，掃到第一個已播完的就用。

## 程式端只讀其中一部分

四張 section 表只能靠 `saf + *(u32 *)(saf + 0x0E / 0x18 / 0x22 / 0x2C)` 這個動作走到，而全程式只有七個地方做這個動作：

| 位址 | 做的事 | 讀的 header 欄位 |
| --- | --- | --- |
| `0x144e0` | 回傳畫格數 | magic、`0x0C` |
| `0x140e0` | 取第 `i` 格的位址 | `0x0C`、`0x0E` |
| `0x14550` | 依停留時間推進一個 tick | magic、`0x0C`、`0x0E` |
| `0x14140` | 畫一格：走完 layer 再發音效 | `0x0C`、`0x0E` |
| `0x13fd0` | 畫一個 layer：走完 tilemap 的格子 | `0x07`、`0x09`、`0x16`、`0x18` |
| `0x13ed0` | 畫一個格子：把 tile 交給繪製器 | `0x07`、`0x09`、`0x20`、`0x22` |
| `0x142d0` | 透過 AIL 播一段音效 | `0x2A`、`0x2C` |

除了這七個以外，還有三個呼叫端會直接讀 frame 記錄裡的兩個提示 byte（見上面的 frame 一節）：攻擊演出 `0x196d0` 讀 `0x05` 與 `0x04`，戰鬥開場 `0x18d60` 與法術演出 `0x1a4c0` 讀 `0x04`。它們拿到 frame 位址的方式是呼叫 `0x140e0`，自己不碰 section 表。

這七個函式一律不讀版本（`0x03`）、header 大小（`0x05`）、`0x0B` 的填充，以及四個 section 大小（`0x12`、`0x1C`、`0x26`、`0x30`）。四個大小是外部工具走檔案時唯一能不解碼就知道 section 到哪裡結束的依據，程式不需要它們是因為它只從 `count` 與偏移表取用項目，從不走到最後一項的尾巴。

magic 的檢查（`0x144e0` 與 `0x14550` 各一份）是 `p[0] == 'S' || p[1] == 'A' || p[2] == 'F'`——**三個條件是 OR**，任一個對上就當成合法。實際上等於沒有檢查，餵一個非 SAF 檔進去只有在三個 byte 全部不符時才會被擋下，而擋下的後果只是畫格數回 0。

範圍檢查倒是每一層都有，而且都是同一個寫法：索引小於 0 或不小於該 section 的項目數就當場放棄這一層的繪製，不會越界。

## 自洽性

容器的每個欄位都能互相驗證，不需要外部資訊：

- 版本恆為 6、header 大小欄位恆為 52、`0x0B` 恆為 0
- 第一個 section 從 52 開始，每個 section 的起點等於前一個的終點，第四個的終點恰好等於檔案大小
- 每個 section 的第一個項目緊接在自己的偏移表之後，偏移嚴格遞增，最後一個項目在 section 結束處收尾——沒有間隙也沒有殘料
- frame 的長度恰好是 `10 + 13 × layer 數`，`0x06` 恆為 0，停留時間至少 1
- frame 的音效編號是 `-1` 或落在 section 3 的範圍內；layer 的 tilemap 編號落在 section 1 的範圍內；tilemap 每個格子的 tile 編號落在 section 2 的範圍內
- layer 的 `0x08`–`0x0C` 五個 byte 恆為 0，半透明開關只有 0 與 1，半透明程度不超過 16
- tilemap 的長度恰好是 `4 + 2 × 欄數 × 列數`
- 每個 tile 解碼時每一列剛好蓋滿 cell 寬、剛好走完 cell 高、串流剛好在下一個 tile 的偏移處用盡
- sound 的長度恰好是 `8 + 取樣 byte 數`

525 個檔、8,335 個 frame、9,886 個 layer、7,967 個 tilemap、418,601 個格子、229,238 個 tile、132,041,088 個像素、608 段音效（7,313,279 byte 取樣）全部通過。

## 哪些是實測、哪些是推論

這個格式在前作沒有對應，全部從零逆向，所以三種確信程度要分清楚：

- **由 `FDPS.LE` 的讀取碼直接讀出**：cell 寬高、四個 section 的項目數與起點、frame 的音效編號與停留時間與 layer 數、layer 的 tilemap 編號與 x、y 與半透明開關與程度、tilemap 的欄列數與格子內容、tile 的像素編碼、sound 的四個 header 欄位。這些欄位的語意是程式怎麼用就怎麼寫的，沒有猜測成分。
- **上述七個函式不讀，由 525 個檔的自洽性確立**：版本恆為 6、header 大小欄位恆為 52、`0x0B` 恆為 0、四個 section 大小、frame 的 `0x06` 恆為 0、layer 的 `0x08`–`0x0C` 恆為 0。值是實測的，「應該恆為這個值」則是從全量一致推得。要注意「七個函式不讀」不等於「全程式沒人讀」——後者沒有掃乾淨過，`0x30` 這種偏移在 `EBP` 相對定址裡雜訊太大。
- **推論**：frame 的 `0x04` 與 `0x05` 這兩個 byte。程式只有戰鬥流程的兩處與法術演出的一處讀它們，其他呼叫端一概不看，所以它們的名字（「前置計數」與「命中標記」）描述的是戰鬥流程的用法，不是格式本身保證的語意。別的呼叫端要拿它們當別的東西用，格式也擋不住。

## 空殼檔

17 個檔只有 66 byte：一個沒有任何 layer 的 frame，三個空 section。它們是編號有缺口的特效表裡補位用的空殼，播起來是一格什麼都不畫的動畫。全部在 `MISC.VFS`：`EE05`、`EE06`、`EE07`、`EE23`、`ME03`–`ME07`、`ME26`–`ME28`、`ME30`、`ME31`、`ME34`、`ME35`、`ME39`。

它們各是哪個法術的第三段、哪些會被載入，以及其他永遠不會被載入或播放的 SAF 與內嵌音效，見 [`cut_content/battle_assets.md`](../cut_content/battle_assets.md)。

## 與前作的對應關係

前作 FD2 沒有對應的格式。唯一相通的是最底層的像素編碼——tile 的 4-op RLE 就是前作 `fd2_rle_blit_sprite` 的那一種，經由 `.CEL` 一路傳下來。上面三層（frame 腳本、tilemap 拼圖、內嵌音效）在前作沒有對應物。
