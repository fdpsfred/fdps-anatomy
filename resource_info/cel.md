# CEL 圖檔格式

`.CEL` 是 FDPS 的 sprite 圖表容器：一個檔裝固定尺寸的一批 sprite，全部共用檔頭宣告的寬高，各自以 RLE 壓縮的像素串排在偏移表後面。

硬碟安裝後有 99 個：`FACE.CEL`（人物頭像）與 `ICON.CEL`（棋子圖示）在根目錄，另外 97 個在 `.VFS` 容器內（`FIELD1.VFS` 69 個、`MISC.VFS` 28 個介面圖）。光碟上的 `FACE.CEL` 與 `ICON.CEL` 包在 `PACK.VFS` 裡，見 [`disc_images.md`](disc_images.md)。

`FIELD1.VFS` 那 69 個裡只有 68 個是取得到的地圖圖磚表：程式的檔名是 `m%02d%d.cel`（地圖編號兩位加圖層一位），對到 64 個地圖的第 0 層與其中 4 個的第 1 層。剩下的 `M09.CEL` 只有兩位數字，這個格式產不出來，`FDPS.LE` 裡也沒有別的字串指向它，是一個開不到的殘留檔——數 `FIELD1.VFS` 的圖磚表時不能把它算進去。它與 `M090.CEL` 的逐格比對見 [`cut_content/story.md`](../cut_content/story.md)。

像素是 8-bit 調色盤索引，調色盤不在 `.CEL` 內，由場景另外指定 `MISC.VFS` 的 5 個 `.PAL`（各 768 byte，256 × RGB 的 6-bit VGA DAC 值，還原成 8-bit 是 `c8 = c6 << 2 | c6 >> 4`）。同一個 `.CEL` 套錯調色盤會得到形狀正確但顏色全錯的圖。

## 佈局

header 15 byte，緊接 `count + 1` 個 u32 偏移，再緊接各 sprite 的像素串。

| 偏移 | 型別 | 內容 |
| ---: | --- | --- |
| `0x00` | `char[3]` | magic `"CEL"` |
| `0x03` | `u16` | 版本，恆為 1 |
| `0x05` | `u16` | 偏移表的位置，恆為 15 |
| `0x07` | `i16` | sprite 寬，全檔共用 |
| `0x09` | `i16` | sprite 高，全檔共用 |
| `0x0B` | `i16` | sprite 筆數 |
| `0x0D` | `u16` | 像素串的編碼，見下 |

偏移表的第 `i` 項是 sprite `i` 的像素串起點，自檔案開頭起算；第 `count` 項是哨兵，等於檔案大小。所以 sprite `i` 的像素串長度是 `offset[i+1] - offset[i]`。

## 程式端只讀其中一部分

取用 sprite 時（`0x2dba0`）程式讀 `0x07` 的寬、`0x09` 的高，並以 `sheet + *(i32 *)(sheet + index * 4 + 0x0F)` 取像素串——**偏移表的位置是寫死的 `0x0F`，`0x05` 那個欄位程式從不讀**。把整批 24×24 sprite 展開成連續緩衝時（`0x2e640`）另外讀 `0x0B` 的筆數。magic、版本、`0x05` 的表位置與 `0x0D` 的編碼四者程式一律不讀，也就沒有任何格式檢查。

## 像素編碼

`0x0D` 為 2 的編碼是繪製器（`0x568db` 分派、mode 0 的本體在 `0x56a0d`）唯一看得懂的那種，與前作 `fd2_rle_blit_sprite` 的 4-op RLE 完全相同。指令 byte 的高 2 bit 選 op，低 6 bit 是長度減 1：

| op | 名稱 | 行為 |
| --- | --- | --- |
| `0b00` | fill | 把**下一個** byte 寫進 `len` 個像素 |
| `0b01` | stretch | 把**下一個** byte 每隔一個像素寫一次，蓋掉 `2 × len` 個 column，跳過的那些維持原樣 |
| `0b10` | literal | 從串流原樣複製 `len` 個 byte |
| `0b11` | skip | 前進 `len` 個像素，不寫（透明） |

stretch 寫的是每一對的**後面**那個像素：繪製器是 `INC EDI` 再 `STOSB`，所以先跳一格再寫。

繪製器逐列處理：每列開始把剩餘 column 數設成檔頭的寬，每個 op 減掉自己蓋到的 column 數，減到剛好 0 才換列。**一個 op 若超出列尾，剩餘 column 數會繞回成極大值，繪製器就會寫穿記憶體**——所以編碼端必須讓每一列的指令剛好填滿寬度，這也讓「每列剛好用完、每個串流剛好用完」成為解碼時可以驗證的硬條件。

繪製器共有 13 種 mode，差別只在調色盤重映與翻轉，讀的都是同一種串流；沒有第二種像素格式的解碼路徑。

## `0x0D` 為 1 的第二種編碼

`M310.CEL` 是唯一一個 `0x0D` 為 1 的檔，它的像素串用完全不同的編碼——沒有 column 計數，改用明確的列尾 byte：

| byte | 行為 |
| --- | --- |
| `0x00` | 列結束，該列剩下的 column 保持透明 |
| `0x01`–`0x7F` | 一個像素，值就是這個 byte |
| `0x80`–`0xBF` | 原樣複製 `(b & 0x3F) + 1` 個 byte |
| `0xC0`–`0xFF` | 把**下一個** byte 寫進 `(b & 0x3F) + 1` 個像素 |

192 個 sprite 全部在剛好 24 個列尾 byte 後串流用盡，解出來是一組室內場景的圖磚，所以這是一種真的格式而不是壞檔。

`FDPS.LE` 裡沒有讀這種編碼的程式碼：`0x0D` 從來不被讀取，13 個 blit mode 讀的都是同一種串流。這不構成矛盾，因為原版從不載入 `M310.CEL`：它是地圖編號 31 的第 0 層，而地圖 31 沒有 `DSC31.DAT`，載入常式在讀圖磚表之前就先讀 `DSC`、讀不到就結束程式（見 [`terrain.md`](terrain.md)）；也沒有任何過場腳本切到地圖 31（見 [`cutscene_script.md`](cutscene_script.md)）。`M%02d%d.cel` 只有這一個載入點，所以這個檔在出貨的遊戲裡構不到。地圖 31 本身見 [`cut_content/story.md`](../cut_content/story.md)。

## 自洽性

容器的欄位互相驗證，不需要外部資訊：

- 偏移表的哨兵等於檔案大小
- 偏移單調不減
- 第一個 sprite 的起點不會落在偏移表內
- 每個 sprite 解碼時剛好走完 `height` 列、串流剛好在下一個 sprite 的偏移處用完
- 編碼為 2 的每一列剛好蓋滿 `width` 個 column；編碼為 1 的每一列以列尾 byte 收尾、不超過 `width`

99 個檔、28,467 個 sprite、19,112,119 個像素全部通過。

8 個地圖圖磚表在偏移表與第一個 sprite 之間留了沒有任何偏移指到的 byte，內容是解不完整的圖磚，屬編碼工具留下的殘料：`M080.CEL` 212、`M190.CEL` 16、`M290.CEL` 764、`M540.CEL` 2,488、`M570.CEL` 2,488、`M580.CEL` 188、`M610.CEL` 252、`M620.CEL` 32。

## 與前作的對應關係

前作 FD2 的 `FDICON.B24` 是 `[寬 u16][高 u16][筆數 u16][偏移 u32 × (筆數+1)]` 加像素串。`.CEL` 就是它前面補上 7 byte 的 magic、版本與表位置，並在筆數之後插入 2 byte 的編碼欄位——欄位順序、偏移表語意、哨兵慣例、像素的 4-op RLE 全部沿用。前作的 sprite 另有一種在串流開頭自帶 `[寬][高]` 的框法，`.CEL` 不用，尺寸一律取自檔頭。
